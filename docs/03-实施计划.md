## 1. 这份文档怎么用

本项目被切成 **23 个 Git tag**：1 个文档 tag + 22 个实现 tag。每个 tag 是一个**完整、可运行、可对比**的状态。

推荐学习流程：

```bash
git checkout v0.5.0                    # 切到某个 tag
# 读本文档中 v0.5.0 的「学习要点」，先自己想想会怎么做
python manage.py runserver             # 跑起来看看当前能做什么

git diff v0.5.0 v0.6.0 --stat          # 先看改了哪些文件
git diff v0.5.0 v0.6.0                 # 再看具体改了什么
# 读本文档中 v0.6.0 的「diff 重点看什么」

git checkout main                      # 回到最新
```

排除 Tailwind 构建产物的干扰（ADR-015）：
```bash
git diff v0.7.0 v0.8.0 -- ':!static/css/tailwind.css'
```

## 2. Tag 规范

### 命名

`v<主版本>.<阶段>.<修订>`，语义如下：

| 段位 | 含义 |
| --- | --- |
| `v0.x.0` | 阶段一：Django 模板 + Tailwind（前后端不分离） |
| `v1.0.0` | 阶段一完整版 |
| `v1.x.0` | 阶段二：DRF API（前后端分离） |

### 每个 tag 的硬性要求

| # | 要求 |
| --- | --- |
| 1 | **必须能跑**：`migrate` + `runserver` 无错，声明的功能可用（NFR-11） |
| 2 | **变更受控**：单 tag 代码变更 ≤ 400 行（不含迁移文件和 CSS 产物），超出必须拆分 |
| 3 | **测试同步**：本 tag 新增的核心逻辑必须带测试，`pytest` 全绿 |
| 4 | **CSS 已构建**：提交前跑 `npm run build:css` |
| 5 | **消息规范**：`feat(v0.6.0): 用户-角色绑定与有效权限解析` |
| 6 | **附注说明**：`git tag -a v0.6.0 -m "..."`，注释里写清本 tag 做了什么、对应哪些需求 |

### 打 tag 的标准流程

```bash
npm run build:css
pytest
git add -A
git commit -m "feat(v0.6.0): 用户-角色绑定与有效权限解析"
git tag -a v0.6.0 -m "实现 UserRole 模型与 get_user_perm_codes()。对应 FR-4.1/4.3。"
```

### 🏷 `v0.3.0` — 部门树

| 项 | 内容 |
| --- | --- |
| **需求** | FR-1.1、FR-1.2、FR-1.4、ADR-003 |
| **交付** | `Department` 模型、path/depth 自动维护、树形 CRUD 页面、`rebuild_dept_path` 命令 |

**关键实现点**
```python
class Department(TimestampedModel):
    code = models.CharField(max_length=64, unique=True)
    name = models.CharField(max_length=64)
    parent = models.ForeignKey("self", null=True, blank=True,
                               on_delete=models.PROTECT, related_name="children")
    path  = models.CharField(max_length=255, db_index=True, editable=False)
    depth = models.SmallIntegerField(default=0, editable=False)

    def save(self, *args, **kwargs):
        super().save(*args, **kwargs)          # 先存拿到 pk
        new_path = f"{self.parent.path if self.parent else '/'}{self.pk}/"
        new_depth = (self.parent.depth + 1) if self.parent else 0
        if (new_path, new_depth) != (self.path, self.depth):
            old_path = self.path
            Department.objects.filter(pk=self.pk).update(path=new_path, depth=new_depth)
            self.path, self.depth = new_path, new_depth
            if old_path:
                self._cascade_children(old_path, new_path)   # 移动节点时更新子树

    def get_descendants(self, include_self=True):
        qs = Department.objects.filter(path__startswith=self.path)
        return qs if include_self else qs.exclude(pk=self.pk)
```

同时给 `User` 加上 `department` 外键。

**验收**
- 建三层部门树，检查 `path` 形如 `/1/3/7/`。
- 把一个中层部门挂到别的父节点下，检查整棵子树的 `path` 和 `depth` 都正确更新。
- 删除有子部门的部门 → `ProtectedError`，界面给出友好提示。
- `get_descendants()` 只产生 1 次查询。

**学习要点**
`save()` 里为什么要 `super().save()` 之后才算 path？因为新建时 `self.pk` 还是 None，path 里需要它。这导致新建时有两次写库（insert + update）——**接受它**，因为部门写操作极低频。

如果这里追求「一次写入」，就得先取序列的下一个值，那是数据库特有的操作，会破坏可移植性（ADR-014）。**这是一个具体的、可感知的取舍：为了可移植性，接受一次多余的 UPDATE。**

### 🏷 `v0.4.0` — 权限点模型与代码化声明

| 项 | 内容 |
| --- | --- |
| **需求** | FR-2.1 ~ FR-2.5、ADR-004、ADR-005 |
| **交付** | `Permission` 模型、各 app 的 `permissions.py`、`sync_permissions` 命令、权限树查看页 |

**关键实现点**
- `Permission` 模型三种 `perm_type`：`catalog` / `menu` / `button`（ADR-005 合一方案）。
- 每个 app 一个 `permissions.py` 声明权限清单（结构见 ADR-004）。
- `sync_permissions` 命令**幂等**：
  - 新增 → 插入
  - 已存在 → 更新名称/排序/图标
  - 代码里没了但库里有 → 标记 `is_deprecated=True`，**不物理删除**（保留历史授权的可解释性）
- 权限码常量类，供视图 import。

**验收**
- 连续跑两次 `sync_permissions`，第二次输出「0 新增 / 0 更新」。
- 从 `permissions.py` 里删掉一个权限点再同步 → 该权限点被标记为已废弃，数据仍在。
- 权限树页面正确显示三层结构。

**学习要点**
「权限点在代码里声明」是本项目最重要的工程决策之一。它把权限点的定义权交给代码，带来三个收益：可 grep、无 typo、进 code review。

反过来想：如果允许管理员在界面上自由新增权限点，他可以创建一个 `ticket:ticket:approve`，勾给某个角色，然后以为审批被管控了——但代码里根本没有任何地方检查这个权限码。**这是一个「配了但不生效」的静默失败，比报错危险得多。**

### 🏷 `v0.7.0` — 认证：登录、登出、会话

| 项 | 内容 |
| --- | --- |
| **需求** | FR-5.1 ~ FR-5.6 |
| **交付** | 登录页、登出、会话配置、登录失败锁定、`last_login_ip` 记录 |

**关键实现点**
- 直接用 Django 的 `authenticate()` / `login()` / `logout()`（ADR-001：认证不重写）。
- 登录失败统一提示，不区分用户不存在与密码错误（FR-5.2）。
- 失败计数放 cache，key = `login_fail:{username}`，5 次锁 15 分钟。
- `SESSION_COOKIE_AGE = 7200`，`SESSION_SAVE_EVERY_REQUEST = True`（滑动过期）。

**验收**
- 密码错误 5 次后第 6 次提示已锁定，即使密码正确也拒绝。
- 未登录访问受保护 URL → 跳登录页，登录后回到原地址（`?next=`）。
- 登录前后 session key 不同（Django `login()` 自动 `cycle_key()`，防会话固定）。

**学习要点**
`SESSION_SAVE_EVERY_REQUEST = True` 让会话变成「滑动过期」（有操作就续期），代价是每个请求都写一次 session 存储。用数据库存 session 时这是个真实的写压力——生产环境通常改用 Redis。**又一处「便利 vs 成本」的具体取舍。**

### 🏷 `v0.9.0` — 视图层权限校验与启动自检

| 项 | 内容 |
| --- | --- |
| **需求** | FR-6.1、FR-6.2、FR-6.6、FR-6.7、ADR-008 |
| **交付** | `@require_perm` 装饰器、`PermRequiredMixin`、`@public_view` 标记、Django system check |

**关键实现点**
```python
# apps/rbac/decorators.py
def require_perm(code): ...            # 打 wrapper._required_perm = code
def public_view(reason): ...           # 打 view._is_public = True，reason 必填

# apps/rbac/checks.py
@register()
def check_view_permissions(app_configs, **kwargs):
    """遍历 URLConf，报告未声明权限要求的视图 → rbac.W001"""
```

自检的难点是**穿透 Django 的包装层**：`View.as_view()` 返回闭包，`csrf_exempt` 等装饰器还会再包一层，要沿 `__wrapped__` / `view_class` 追溯到真正的视图。

**验收**
- 无权限访问 → 403 页面（不是 500，不是静默通过）。
- 故意给一个视图不加装饰器 → `python manage.py check` 报 `rbac.W001`。
- 超管访问任意视图畅通。

**学习要点**
`@public_view(reason="...")` 为什么要强制填写理由？

因为「这个接口不需要权限」是一个**安全决策**，安全决策必须留下依据。三个月后有人看到这行，能立刻知道当初为什么这么定，而不是猜「是有意的还是忘了加」。

> **沉默不能被解释为同意。** 没有装饰器 = 配置错误（告警），而不是 = 公开访问。这是「默认拒绝」在工程实践中的具体形态。

### 🏷 `v0.10.0` — 模板层权限渲染

| 项 | 内容 |
| --- | --- |
| **需求** | FR-6.3、FR-6.5、ADR-012 |
| **交付** | context processor、`LazyPermSet`、页面按钮按权限渲染 |

**关键实现点**
```python
class LazyPermSet:
    """惰性权限集合：模板不用到就不查库。"""
    def __init__(self, request): self._request, self._codes = request, None
    def __contains__(self, code):
        if self._codes is None:
            self._codes = get_user_perm_codes(self._request.user)
        return code in self._codes
```

```django
{% if 'ticket:ticket:delete' in perms %}
  <button class="rounded bg-red-600 px-3 py-1.5 text-sm text-white">删除</button>
{% endif %}
```

**验收**
- 不同权限的用户看到不同的按钮组合。
- 未登录页面渲染时不产生权限相关查询（惰性生效）。
- **关键测试**：直接 POST 一个被隐藏按钮对应的 URL → 仍然 403。

**学习要点**
上面那条「关键测试」是本 tag 存在的真正理由。

> 隐藏按钮是**体验**，视图校验是**安全**。
> 攻击者不点你的按钮，他直接发请求。
>
> 每一个受控按钮，都必须有一个对应的 `@require_perm`。**成对出现，缺一不可。**

这是权限系统里最高频的真实漏洞成因，所以我们用一个专门的测试用例把它钉死。

**验收**

- `assertNumQueries` 断言菜单构建**只产生 1 次查询**，且与层级深度无关。

**diff 重点看什么**
对比 v0.8.0 的写死菜单和本 tag 的动态菜单——因为 v0.8.0 已经把布局做完了，这次 diff 里只有菜单逻辑，非常干净。

「空目录不渲染」这个细节容易漏，但它直接影响体验：一个点开是空的目录，用户会以为系统坏了。算法上它对应「先标记有权限的叶子，再向上传播保留祖先」——**自底向上**，而不是自顶向下遍历。

### 🏷 `v0.14.0` — 数据权限：范围模型与 QuerySet 过滤

| 项 | 内容 |
| --- | --- |
| **需求** | FR-7.1 ~ FR-7.3、FR-7.5、FR-7.6、ADR-007、ADR-009 |
| **交付** | `DataScope` 枚举、`build_scope_q()`、`DataScopedQuerySet.for_user()`、`ScopedListMixin` |

**关键实现点**
```python
# apps/rbac/services.py
def build_scope_q(user, cfg) -> Q | None:     # 完整实现见设计文档 4.3
    ...

# apps/common/models.py
class DataScopedQuerySet(models.QuerySet):
    def for_user(self, user):
        q = build_scope_q(user, self.model.ScopeConfig)
        return self if q is None else self.filter(q)

# apps/tickets/models.py
class Ticket(models.Model):
    class ScopeConfig:
        owner_field = "creator"
        dept_field  = "department"
    objects = DataScopedQuerySet.as_manager()
```

**⚠️ 本 tag 是全项目最容易写出安全漏洞的地方。** 四处「默认拒绝」必须逐一实现并测试（见设计文档 4.3 的表格）：

| 情形 | 必须返回 |
| --- | --- |
| 未登录 / 已禁用 | 空集 |
| 无任何角色 | 空集 |
| 所有角色 scope 都不可识别 | 空集 |
| 用户无所属部门 | 空集 |

**验收**（用 `seed_demo` 造的数据）
- `ALL` 角色 → 看到全部 80 张工单。
- `DEPT_AND_BELOW`（客服部，含 3 个子部门）→ 看到 50 张。
- `DEPT_ONLY` → 只看到客服部本级的 20 张。
- `SELF_ONLY` → 只看到自己创建的 5 张。
- 无角色用户 → 看到 0 张（**不是 80 张**）。
- 检查生成的 SQL：过滤发生在 `WHERE` 子句里，不是 Python 里（NFR-2）。

**diff 重点看什么**
对比 v0.13.0，业务代码只多了 `ScopeConfig` 三行和 `.for_user()` 一处调用——**接入成本极低**是这个设计的目标（FR-7.6），diff 是最好的证明。

**学习要点**
两个必须理解透的点：

1. **多角色的数据范围是「真并集」，不是「取最宽枚举」。**
   角色 A = `SELF_ONLY`、角色 B = `CUSTOM[市场部]` 时，取最宽枚举会得到 `SELF_ONLY`，丢掉市场部的数据——违反 RBAC「多角色取并集」的基本语义。正确做法是 `Q(creator=user) | Q(department__in=市场部子树)`。

2. **`Q(pk__in=[])` 和 `Q()` 只差两个字符，安全后果天差地别。**
   `Q()` 是空条件（不过滤，返回全集），`Q(pk__in=[])` 是不可满足条件（返回空集）。写错就是「新用户默认看到全公司数据」。这是本项目最该被测试守住的一行。

### 🏷 `v0.15.0` — 自定义部门范围与单条记录校验

| 项 | 内容 |
| --- | --- |
| **需求** | FR-3.7、FR-3.8、FR-7.4 |
| **交付** | `RoleDepartment` 模型、自定义部门勾选界面、详情/编辑/删除的范围校验、导出受控 |

**关键实现点**
```python
# ✅ 唯一正确的写法
ticket = get_object_or_404(Ticket.objects.for_user(request.user), pk=pk)

# ❌ IDOR 漏洞的标准写法
ticket = get_object_or_404(Ticket, pk=pk)
if ticket.department != request.user.department:
    raise PermissionDenied
```

- `CUSTOM` 范围下，勾选的部门**含其子树**（勾「客服部」= 客服部及所有下级）。
- CSV 导出走同一个 `.for_user()`（FR-8.5）。

**验收**
- 用他部门的工单 ID 访问详情 → **404**（不是 403）。
- 同样的 ID 发编辑/删除 POST → 404。
- 导出的 CSV 行数 = 列表页总数。

**学习要点**
**为什么范围外返回 404 而不是 403？**

403 的含义是「这东西存在，但你没权限」——它泄露了记录的存在性。攻击者可以遍历 ID，用 403/404 的差异画出整个数据库的 ID 分布。

统一返回 404 的含义是「对你而言，这东西不存在」。这是**信息最小泄露**原则。

顺带一提：错误写法的第二个问题是重复实现了范围判断逻辑（`ticket.department != user.department`），它和 `build_scope_q` 的规则迟早会不一致——而不一致的那一刻，就是漏洞诞生的时刻。**同一个规则只能有一处实现。**

### 🏷 `v0.16.0` — 权限缓存

| 项 | 内容 |
| --- | --- |
| **需求** | NFR-1、NFR-4、FR-4.5、ADR-010 |
| **交付** | L1 请求级缓存、L2 Django cache、版本号失效、signal 挂载、角色全量内存缓存 |

**关键实现点**
```python
RBAC_VERSION_KEY = "rbac:version"

def bump_version():
    try:
        cache.incr(RBAC_VERSION_KEY)
    except ValueError:
        cache.set(RBAC_VERSION_KEY, 1, None)

# apps/rbac/signals.py —— 用信号保证不遗漏
@receiver([post_save, post_delete], sender=RolePermission)
@receiver([post_save, post_delete], sender=UserRole)
@receiver(post_save, sender=Role)
@receiver([post_save, post_delete], sender=RoleDepartment)
def _invalidate(sender, **kwargs):
    bump_version()
```

**验收**
- 同一请求内判断 50 次权限 → `assertNumQueries` 显示权限相关查询只有 1 次。
- 跨请求命中 L2 缓存 → 0 次查询。
- **关键测试**：撤销用户的角色后**立即**发请求 → 403（不等 TTL 过期）。
- 角色继承展开不产生 DB 查询（角色全量已在内存缓存中）。

**diff 重点看什么**
`services.py` 里缓存是**包在原有逻辑外面**的，原有的解析函数几乎没动。这说明 v0.6.0 的接口设计是对的——**好的抽象让优化可以后加**。

**学习要点**
版本号失效法的本质是一次交换：

> 用**可量化的性能损失**（一次变更导致全体缓存失效，几分钟内命中率下降）
> 换**不可量化的正确性保证**（绝不会漏失效，即绝不会出现「权限已撤销但仍生效」）。

在安全相关的设计里，这个方向的交换几乎总是对的。反方向（为性能牺牲正确性）几乎总是错的。

**进阶思考题**：如果用户量到十万级，全局版本号的抖动不可接受了，怎么办？（提示：按角色分级版本号，key 由该用户涉及的所有角色版本组合而成。想想这个方案的复杂度成本在哪里。）

### 🏷 `v1.2.0` — API 层权限复用

| 项 | 内容 |
| --- | --- |
| **需求** | FR-10.3、FR-10.4、ADR-013 |
| **交付** | `HasPerm` 权限类、`ScopedQuerysetMixin`、`/api/v1/auth/profile` 接口 |

**关键实现点**
```python
class HasPerm(BasePermission):
    def has_permission(self, request, view):
        code = getattr(view, "required_perm", None)
        return code is None or user_has_perm(request.user, code)

class ScopedQuerysetMixin:
    def get_queryset(self):
        return super().get_queryset().for_user(self.request.user)
```

`/api/v1/auth/profile` 返回用户信息 + 权限码列表 + 菜单树，供前端渲染路由和菜单。

**🎯 本 tag 的核心验收条件（也是整个架构设计的检验）**

```bash
# 期望输出：空
```

> **`services.py` 一行都不用改。**
>
> 如果需要改，说明 ADR-013 的解耦没做到位——内核里漏进了表现层的关注点。
> 这是一个**可检验的架构承诺**，而不是一句「我们的架构是解耦的」的空话。

**验收**
- 无权限的 token 调受保护接口 → 403 JSON（不是 HTML 403 页面）。

**学习要点**
这个 tag 是对前面所有设计的**总检验**。ADR-013 在 v0.6.0 就定下了「内核不认识 HTTP」的约束，中间 13 个 tag 一直遵守，收益在此刻一次性兑现：接入一套全新的表现层，只写了两个类、约 30 行代码。

## 7. 三个刻意留下的「不安全中间态」

本项目有三处故意让系统处于不完整状态的安排，它们不是疏漏：

| Tag | 缺什么 | 为什么这么安排 |
| --- | --- | --- |
| `v0.8.0` | 菜单是写死的 | 让 v0.11.0 的「动态菜单」diff 干净单一 |
| `v0.13.0` | 有功能权限，无数据权限 | 让你亲眼看到「只有功能权限的系统」长什么样——很多真实项目就停在这里 |
| `v1.1.0` | 有认证，无授权 | 让 v1.2.0 的「内核复用」价值可见 |

> **先看见问题，再看解法。** 直接给最终答案，你会记住结论；先经历问题，你会记住原因。

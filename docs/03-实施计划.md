## 1. 本项目的推荐学习方式：先自己实现，再对比

这是最有效但也最费力的方式。流程：

```
1. 读该 tag 的指南（不看「渐进提示」部分）
2. 独立完成第一节的思考题 —— 不要跳过，这是最有价值的部分
3. 按「接口契约」和「实现步骤」自己写代码
4. 卡住了才展开「渐进提示」
5. 跑「自测清单」
6. git diff 对照我的实现，逐条走「对比检查点」
7. 读「延伸思考」
```

### ⚠️ 关于「接口契约」这一节

每份指南都有一节叫「**接口契约（必须与我的实现对齐）**」，里面规定了模型字段名、函数签名、URL name、常量值等。

**请照抄这些。** 原因很实际：

> 你的目标是实现完之后 `git diff` 我的版本，看差异学东西。
> 如果连字段名和函数签名都不一样，diff 会全是噪音，看不出真正的**设计**差异。

**契约部分照抄，实现部分自由发挥。** 这正是真实工作中「接口先行」的意义——团队协作时，你也是拿到接口定义各自实现。

### 每份 tag 指南的结构

| 节 | 内容 | 什么时候看 |
| --- | --- | --- |
| 一、动手之前先想清楚 | 3~6 个思考题 | **动手前**，必看 |
| 二、交付物清单 | 要建/改哪些文件 | 动手前 |
| 三、接口契约 | 必须对齐的名字和签名 | 动手前，**照抄** |
| 四、实现步骤 | 有序的 Step | 动手时 |
| 五、⚠️ 容易写错的地方 | 陷阱预警（不剧透答案） | 动手前扫一遍，卡住时细看 |
| 六、卡住了看这里 | 折叠的渐进式提示，含代码骨架 | **实在想不出来才展开** |
| 七、自测清单 | 可执行的验证命令和用例表 | 写完后 |
| 八、和我的实现对比什么 | 具体的 diff 检查点 | 写完后 |
| 九、延伸思考 | 开放问题，含部分答案折叠 | 最后 |

### 如果你只想读代码不想自己写

也可以。跳过第一、三、四、六节，直接：

```bash
git checkout v0.5.0
git diff v0.5.0 v0.6.0 -- ':!static/css/tailwind.css'
```

然后读该 tag 指南的「五、陷阱」「八、对比点」「九、延伸思考」三节。

## 2. Tag 规范

### 命名

`v<主版本>.<阶段>.<修订>`：

| 段位 | 含义 |
| --- | --- |
| `v0.x.0` | 阶段一：Django 模板 + Tailwind（前后端不分离） |
| `v1.0.0` | 阶段一完整版 |
| `v1.x.0` | 阶段二：DRF API（前后端分离） |

### 每个 tag 的硬性要求

| # | 要求 |
| --- | --- |
| 1 | **必须能跑**：`migrate` + `runserver` 无错，声明的功能可用（NFR-11） |
| 2 | **变更受控**：单 tag 代码变更 ≤ 400 行（不含迁移文件和 CSS 产物） |
| 3 | **测试同步**：本 tag 新增的核心逻辑必须带测试，`pytest` 全绿 |
| 4 | **CSS 已构建**：提交前跑 `npm run build:css` |
| 5 | **没有越界**：不提前实现后续 tag 的功能，不做与本 tag 无关的重构 |
| 6 | **消息规范**：`feat(v0.6.0): 用户-角色绑定与有效权限解析` |

完整的完成定义（DoD）见 [`CLAUDE.md`](../CLAUDE.md) 第 8 节。

### 打 tag 的标准流程

```bash
npm run build:css
pytest
python manage.py check
git add -A
git commit -m "feat(v0.6.0): 用户-角色绑定与有效权限解析"
git tag -a v0.6.0 -m "实现 UserRole 模型与 get_user_perm_codes()。对应 FR-4.1/4.3。"
```

### 对比 diff 时排除 CSS 产物

```bash
git diff v0.7.0 v0.8.0 -- ':!static/css/tailwind.css'
```

## 5. 三个刻意留下的「不安全中间态」

本项目有三处故意让系统处于不完整状态的安排。**它们不是疏漏，是教学设计。**

| Tag | 缺什么 | 在哪补上 | 为什么这么安排 |
| --- | --- | --- | --- |
| `v0.8.0` | 菜单是写死的 | `v0.11.0` | 让「动态菜单」的 diff 干净单一——布局改动不会淹没菜单算法 |
| `v0.13.0` | 有功能权限，无数据权限 | `v0.14.0` | 让你亲眼看到「只有功能权限的系统」长什么样。**很多真实项目就停在这里** |
| `v1.1.0` | 有认证，无授权 | `v1.2.0` | 让「权限内核复用」的价值可见——13 个 tag 前定下的约束在此兑现 |

> **先看见问题，再看解法。**
> 直接给最终答案，你会记住结论；先经历问题，你会记住原因。

配套的方法论：**tag 的切分要让 diff 讲故事。** 每个 diff 应该只回答一个问题。

## 6. 贯穿全项目的几条原则

这些原则在多个 tag 里反复出现。读到第二次时，留意一下它们的共性。

### 让默认状态是安全的

| 出现位置 | 形态 |
| --- | --- |
| `v0.5.0` | `data_scope` 默认 `SELF_ONLY`（最窄）而非 `ALL` |
| `v0.9.0` | 没有权限装饰器 = 配置错误（告警），不是公开访问 |
| `v0.14.0` | 无角色 → 返回空集 `Q(pk__in=[])`，不是全集 `Q()` |
| `v0.18.0` | 表单用白名单 `fields`，不用黑名单 `exclude` |
| `v1.2.0` | `perm_map` 漏配 → 403，不是静默放行 |

**共同点**：不是「小心不要出错」，而是「让出错需要额外的动作」。

### 用机制保证，不靠自觉

| 出现位置 | 机制 |
| --- | --- |
| `v0.4.0` | 权限点从代码声明 + 同步命令，杜绝手工录入的 typo |
| `v0.9.0` | 启动自检 `rbac.W001` 发现漏加装饰器的视图 |
| `v0.15.0` | `ScopedObjectMixin` 让 GET/POST 走同一个 queryset |
| `v0.16.0` | signal 挂载缓存失效，不在视图里手写调用 |
| `v0.19.0` | 越权矩阵 = 可执行的权限规格说明书 |

### 显式优于隐式（安全代码里尤其）

| 出现位置 | 决定 |
| --- | --- |
| `v0.14.0` | 拒绝 thread-local 隐式数据过滤，坚持显式 `.for_user()` |
| `v0.9.0` | `@public_view(reason=...)` 的 reason 必填 |

**判断标准**：你应该能通过 `grep` 找出所有绕过安全机制的地方。

### 有历史意义的信息要快照，不能只存引用

| 出现位置 | 快照什么 |
| --- | --- |
| `v0.13.0` | 工单的 `department`（创建人转岗后历史工单不该跟着变） |
| `v0.17.0` | 审计日志的 `actor_name`、`target_repr`（对象删了还得知道是谁/是什么） |

## 7. 学习自检清单

走完全部 tag 后，用这份清单检验掌握程度（对应 PRD 的教学目标 G-1 ~ G-9）：

### 理论

- [ ] 能说出 RBAC0/1/2/3 的区别，以及本项目停在 RBAC1 的理由
- [ ] 能解释 ACL 的根本缺陷，以及 RBAC 的「角色」这一间接层真正买到了什么
- [ ] 能说清为什么「只能看本部门数据」在 NIST RBAC 标准里找不到位置
- [ ] 能说出判断「该用对象级权限还是数据范围」的那一条判据

### 设计

- [ ] 能解释为什么不用 `django.contrib.auth.Permission`，以及它的能力边界在哪
- [ ] 能说出 `AUTH_USER_MODEL` 必须在首次 migrate 前设定的原因
- [ ] 能画出部门树四种存储方案的对比，并说明本项目选路径枚举的负载依据
- [ ] 能设计一套权限码规范，并论证粒度选择
- [ ] 能说清功能权限和数据权限在**实现机制**上的根本差异
- [ ] 能设计权限缓存的失效策略，并论证版本号法的取舍

### 实现

- [ ] 能手写 `build_scope_q()`，并指出其中四处「默认拒绝」
- [ ] 能解释为什么多角色的数据范围要做真并集，而不是取最宽枚举
- [ ] 能说出 `Q()` 和 `Q(pk__in=[])` 的差异及其安全后果
- [ ] 能说出部门 `path` 尾斜杠的必要性（`/1/` vs `/11/`）
- [ ] 能解释为什么角色继承结果不该物化到数据库

### 安全

- [ ] 能列出至少 6 种越权场景及其防御手段
- [ ] 能解释为什么范围外的记录返回 404 而不是 403
- [ ] 能说出「隐藏按钮不是安全边界」的完整理由
- [ ] 能说出表单为什么要用白名单 `fields` 而不是黑名单 `exclude`

### 架构

- [ ] 能说明权限内核为什么不能 import `django.http`，以及这个约束在 `v1.2.0` 兑现了什么
- [ ] 能说出「让默认状态是安全的」在本项目出现的至少 3 处
- [ ] 能判断什么时候该提前抽象、什么时候该等（YAGNI 的边界）

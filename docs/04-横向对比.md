## 1. 为什么这份文档排在最后

README 里从一开始就预留了这份文档，但刻意推迟到实现完成之后才写。理由很实在：

> 不写它，学完只会我们这一套，遇到别的实现会懵。
> 但**没亲手实现过就去读别人的方案，只能记住结论，记不住原因**——
> 你不知道他们在躲哪个坑，因为你还没踩过。

现在你（和我）都踩过了：`Q()` vs `Q(pk__in=[])`、`queryset.update()` 不触发信号、
`ORDER BY path` 不等于树序、`disabled` 的 checkbox 不会被提交。带着这些再看别人的代码，
读到的东西完全不一样。

**这份文档还有一个功能：纠正我自己的一处错误。** 见第 4.4 节。

## 3. Django 原生 `auth.Permission`

### 3.1 它长什么样

```python
# 自动为每个模型生成 add / change / delete / view 四个权限
user.has_perm("tickets.delete_ticket")

# Group 当角色用
group.permissions.add(Permission.objects.get(codename="delete_ticket"))
user.groups.add(group)

# 自定义权限必须挂在某个模型下
class Ticket(models.Model):
    class Meta:
        permissions = [("export_ticket", "可以导出工单")]
```

### 3.2 我们保留了它的一半

这是 [ADR-001](02-设计文档.md) 最容易被误读的地方——**我们没有「弃用 Django 的权限系统」，
我们弃用的是它的授权部分，认证部分照单全收**：

| Django 提供的 | 我们的做法 |
| --- | --- |
| `AbstractUser`、`UserManager`、密码哈希 | ✅ 全用（`v0.2.0`） |
| `authenticate()` / `login()` / session | ✅ 全用（`v0.7.0`） |
| `login_required`、`AuthenticationMiddleware` | ✅ 全用 |
| `user.has_perm()` 这个 **API 形状** | ✅ 保留，用自定义 backend 接管（`v0.9.0`） |
| `auth.Permission` 表、`Group` | ❌ 不用 |

`apps/rbac/backends.py` 只有十几行：

```python
class RBACBackend(ModelBackend):
    def has_perm(self, user_obj, perm, obj=None):
        return user_has_perm(user_obj, perm)
```

继承 `ModelBackend` 而不是 `BaseBackend`，是为了保住 `authenticate()` 和
`get_user()`（后者含 `is_active` 检查，构成 `v0.18.0` 三道防线之一）。

### 3.3 为什么它撑不住

实现完之后回看，最致命的不是「功能少」，而是**权限点必须挂在模型上**：

```python
# 我们的 26 个权限点里，有几个不对应任何模型？
system:perm:view       权限点查看     —— 对应 Permission 模型，勉强
system:audit:view      审计日志查看   —— 对应 AuditLog，勉强
system:role:assign_perm 分配权限      —— 这不是对 Role 的 CRUD，是一个动作
system:user:assign_role 分配角色      —— 同上
ticket:ticket:assign   派单          —— 也不是 CRUD
ticket:ticket:export   导出          —— 也不是
```

6 个里有 4 个是**动作而非 CRUD**。用 `Meta.permissions` 硬挂当然能做，
但语义是别扭的——`assign_perm` 挂在 `Role` 下，读起来像是「对 Role 对象的某种操作」，
实际上它是「对角色-权限关系的操作」。

其余四条能力缺口（无层级、无继承、无数据权限、无菜单信息）在 ADR-001 有表，不重复。

### 3.4 一个副作用：两套权限表并存

我们的库里现在有 `auth_permission` 表（Django 自动填充，约 40 条）和
`rbac_permission` 表（我们的 26 条）。前者始终为空转——没有任何代码读它。

`AUTHENTICATION_BACKENDS` 里我们**移除了 `ModelBackend`** 就是为了避免混淆：

```python
AUTHENTICATION_BACKENDS = ["apps.rbac.backends.RBACBackend"]
```

代价：`auth_permission` 表白占空间。收益：不存在「两套权限体系谁说了算」的疑问。

## 4. django-guardian：对象级权限

### 4.1 它长什么样

```python
from guardian.shortcuts import assign_perm, get_objects_for_user

assign_perm("change_ticket", alice, ticket_123)    # 逐对象授权
get_objects_for_user(alice, "tickets.change_ticket")
```

存储上是两张带 `GenericForeignKey` 的表（`UserObjectPermission` /
`GroupObjectPermission`）：`content_type` + `object_pk` + 权限。

### 4.2 它和数据权限是两种东西

这是[理论基础 6.4](00-RBAC理论基础.md) 那条判据的具体化：

> **问自己「授权关系是被人指定的，还是被规则推导的？」**

| | django-guardian | 本项目的数据范围 |
| --- | --- | --- |
| 授权关系怎么来 | **人工指定**：alice 把文档分享给 bob | **规则推导**：主管能看本部门树 |
| 存储量 | 每个「用户×对象」一行 | 角色上一个枚举字段 |
| 新建对象时 | 要为所有相关用户批量写授权 | **自动适用**，什么都不用做 |
| 部门调整时 | 全量重算 | 什么都不用做 |

用我们的演示数据算一下：80 张工单 × 6 个用户 × 6 种操作 = **2880 条授权记录**，
而且每建一张工单就要再写 36 条。我们的实现是 `Role.data_scope` 上的**一个整数**。

反过来，如果需求是「alice 主动把这张工单分享给 bob 看」，我们的枚举表达不了，
guardian 正好合适。**两者不是替代关系，是适用场景不同。**

### 4.3 性能上的已知问题

guardian 官方文档专门有一章 [Performance tuning](https://django-guardian.readthedocs.io/en/3.0.1/userguide/performance/)，
说的就是 `GenericForeignKey` 的代价：它不是真正的外键，数据库无法用它做 join 优化，
数据量大时要改用「直接外键」模式——为每个业务模型单独建一张权限表
（继承 `UserObjectPermissionBase`）。

官方原话大意：如果你在做一个工单系统、要支持成千上万的用户和工单，
通用方案的对象级权限检查会很慢。

**这正好印证了 6.1 节的结论**：对象级权限的成本随「授权关系条数」增长，
而规则推导的成本不随数据量增长。选错路线的代价是结构性的。

## 5. Casbin：策略引擎

### 5.1 它长什么样

Casbin 把授权拆成 `model.conf`（模型）+ `policy.csv`（策略）两部分：

```ini
# model.conf —— PERM 元模型：Policy, Effect, Request, Matchers
[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[role_definition]
g = _, _                      # 角色继承

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub, p.sub) && r.obj == p.obj && r.act == p.act
```

```csv
# policy.csv
p, cs_manager, ticket, delete
g, wang, cs_manager           # wang 属于 cs_manager
g, cs_manager, cs_specialist  # 角色继承
```

```python
e.enforce("wang", "ticket", "delete")   # -> True
```

### 5.2 它做得比我们好的地方

诚实地列：

- **模型可换**。改 `model.conf` 就能从 RBAC 切到 ABAC，甚至加多租户维度（`domains`）。
  我们的模型是硬编码在 Django models 里的。
- **跨语言**。同一套 policy 可以给 Go/Java/Python 服务共用。做微服务时这是实打实的优势。
- **策略即数据**。policy 可以放数据库、Redis、甚至配置中心，热更新。
- **matcher 表达力强**。`keyMatch2`、正则、自定义函数，能表达 `/api/tickets/*` 这类模式。

### 5.3 我们为什么没用它

**核心矛盾在于「列出我能看的所有工单」这件事。**

`enforce(sub, obj, act)` 回答的是「**这一个**请求能不能过」。要拿到列表，你有两条路：

```python
# 路 A：全表扫描后逐行判断 —— 违反 NFR-2，80 张工单还行，8 万张就废了
[t for t in Ticket.objects.all() if e.enforce(user.name, f"ticket:{t.id}", "view")]

# 路 B：把策略翻译成 SQL —— 但只有部分 matcher 翻译得出来
```

Casbin 有 `BatchEnforce` 和一些过滤适配器，但**「策略 → SQL WHERE」这件事本质上
只对受限的 matcher 子集成立**。而我们的五个枚举值，每一个都能确定性地翻译成 Q 对象——
这正是[ADR-007](02-设计文档.md) 说的「刻意退化的 ABAC」换来的东西。

第二个矛盾是**可配置性**：

```
我们的界面：   下拉选「本部门及以下」，勾几个部门        ← 行政人员能操作
Casbin 的界面：写 model.conf 的 matcher 表达式          ← 这是编程
```

第三个是**可审计性**（[理论基础 2.5](00-RBAC理论基础.md)）：Casbin 能回答
「这个请求能不能过」，回答不了「谁能删工单」——后者要对所有主体×所有对象求解策略。
而合规审计问的恰恰是后者。

### 5.4 什么时候该选 Casbin

- 多语言微服务，需要共享一套策略
- 权限规则本身经常变，且变的是**规则形状**而不只是数据
- 不需要「列出我能看的全部数据」这类集合查询，或者数据量小到可以内存过滤
- 有人愿意长期维护 model.conf

**如果你的系统是单体 Django + 大列表页 + 行政人员配权限，Casbin 是杀鸡用牛刀，
而且刀还不好使。**

## 6. 若依 RuoYi：同路人

### 6.1 一处更正

> ⚠️ **我在 [ADR-007](02-设计文档.md) 里写过「若依等主流国产后台用的是取最宽枚举，
> 这是我们刻意偏离之处」。写这份对比时去核对源码，发现这个说法是错的。**

若依 `DataScopeAspect.dataScopeFilter()` 的实际行为：

| 行为 | 若依 | 本项目 |
| --- | --- | --- |
| 多角色合并 | **OR 并集**（`sqlString.append(" OR ...")`） | **OR 并集**（`q \|= sub`） |
| 遇到「全部数据」 | 清空条件并 `break` | `return None` 短路 |
| 无匹配角色 | 拼 `dept_id = 0`（查不到任何数据） | `Q(pk__in=[])` |

**三条全都一致。** 不存在我说的那个偏离。

「取最宽枚举」是一个真实存在的错误写法——我自己第一版就差点这么写，
`DataScope` 编号从大范围到小范围递增，`min()` 看起来太顺手了。但把它按到某个具体项目
头上，是我在没核实的情况下为了让论证更有张力而写的。

那段论证不需要这个对照也成立：`SELF_ONLY(4)` + `CUSTOM(5)[市场部]` 取最宽会得到
`SELF_ONLY`，丢掉市场部的数据——这个反例本身就够了。
`tests/security/test_horizontal_escalation.py::test_union_with_custom_does_not_lose_data`
就是它的可执行版本。

> **教训**：拿别的项目当反面教材时，必须先读源码。
> 论证的说服力不该建立在对手的稻草人版本上。

### 6.2 枚举取值的对照

| 语义 | 若依 | 本项目 |
| --- | --- | --- |
| 全部数据 | 1 | 1 |
| 自定义部门 | **2** | **5** |
| 本部门 | 3 | 3 |
| 本部门及以下 | **4** | **2** |
| 仅本人 | 5 | 4 |

语义集合完全相同，只是编号顺序不同。我们的编号刻意按「范围从宽到窄」排，
这样 `min(scopes)` 就是最宽的——但**只用于 `ALL` 的短路优化，不用于合并**
（`apps/rbac/constants.py` 的注释专门写了这一点）。

> 不同的人独立解同一个问题，收敛到了几乎同一个形状——这本身说明
> **这个形状是被真实需求逼出来的，不是谁的偏好**。

### 6.3 真正的差异：SQL 字符串拼接 vs Q 对象

这才是两者的实质区别。

**若依**：`@DataScope` 注解 + AOP 切面，把生成的 SQL 片段塞进 MyBatis 的
`${params.dataScope}` 占位符：

```xml
<!-- Mapper XML -->
SELECT * FROM sys_user u WHERE 1=1 ${params.dataScope}
```

```java
// 切面生成
" OR u.dept_id IN ( SELECT dept_id FROM sys_dept WHERE dept_id = " + deptId
+ " OR find_in_set(" + deptId + " , ancestors) )"
```

**本项目**：构造 `Q` 对象交给 ORM。

| | 字符串拼接 | Q 对象 |
| --- | --- | --- |
| SQL 注入风险 | 拼接的是内部 ID，但**这条防线靠的是自觉** | ORM 参数化，结构上不可能 |
| 可组合性 | 拼好的字符串没法再和别的条件安全组合 | `q1 \| q2`、`q & extra`，天然可组合 |
| 数据库可移植 | `find_in_set` 是 MySQL 特有 | ORM 抽象掉；我们用 `path__startswith` |
| 可测试性 | 要跑到数据库才知道对不对 | `build_scope_q()` 是纯函数，可单测 |
| 可读性 | XML 里一个 `${}` 占位符，看不出会被塞什么 | `Ticket.objects.for_user(user)` 显式可见 |

最后一条对应我们的 [ADR-009](02-设计文档.md)：**你应该能通过 grep 找出所有
绕过数据权限的查询**。若依的 `${params.dataScope}` 藏在 XML 里，
而且是否生效取决于 Service 方法上有没有 `@DataScope` 注解——这和我们否决的
thread-local 隐式方案有同样的问题：**看不见**。

### 6.4 若依做得比我们完整的地方

- **岗位（sys_post）**：我们只有部门，没有岗位。真实 HR 系统里两者是分开的
  （[理论基础第 4 章](00-RBAC理论基础.md)提过）。
- **字典管理（sys_dict）**：枚举值可配置化。
- **代码生成器**：建表 → 一键生成 CRUD + 权限点。这对交付效率是实打实的。
- **多数据源、定时任务、在线用户监控**：完整后台该有的都有。

若依是一个**交付型框架**，目标是让你快速做出能上线的系统。
本项目是**教学项目**，目标是让每个决策的理由和代价都可见。定位不同，不该直接比。

## 8. 选型决策树

```
需要「列出我能看的所有数据」这类集合查询吗？
├── 不需要（只做单点鉴权，如网关）
│   └── 多语言 / 策略常变？ → Casbin
│       否则 → Django 原生够用
│
└── 需要
    └── 授权关系是「人工指定」还是「规则推导」？
        │
        ├── 人工指定（alice 分享给 bob）
        │   └── django-guardian
        │       ⚠️ 数据量大时改直接外键模式
        │
        └── 规则推导（主管看本部门树）
            └── 需要角色继承 / 权限溯源 / 树形权限点吗？
                ├── 需要 → 自建（本项目的形态）
                └── 不需要 + Java 生态 + 要快 → 若依
```

**再补一条**：三种路线不互斥。真实系统常见组合是
「RBAC 打底（功能权限）+ 数据范围（列表过滤）+ 少量对象级授权（分享/委托）」。
本项目的 `ScopeConfig.extra_q` 钩子就是给第三种留的缝。

## 9. 回看本项目的 16 条 ADR

实现完 22 个 tag、读完这四个方案之后，重新评估几条关键决策：

| ADR | 决策 | 现在的评价 |
| --- | --- | --- |
| 001 弃用 `auth.Permission` | ✅ 站得住 | 26 个权限点里 4 个不对应 CRUD，原生方案确实别扭 |
| 003 邻接表 + 冗余 path | ✅ 站得住，但有教训 | 「读多写少」的判断是对的；「`ORDER BY path` 就是树序」是错的 |
| 005 菜单权限合表 | ✅ 站得住 | 四个方案里只有若依和我们做了树形权限点，也只有这两个管理员配得动 |
| 006 单继承 | ⚠️ 可再议 | Casbin 的 `g` 规则支持 DAG 且实现不复杂。我们选单继承换的是**溯源可解释性**——`v0.12.0` 的溯源页确实只有单继承才写得出来 |
| 007 枚举 data_scope | ✅ 强烈站得住 | 和若依独立收敛到同一形状；Casbin 的通用性在这里反而是负担 |
| 009 显式 `.for_user()` | ✅ 站得住 | 若依的 `@DataScope` + `${params.dataScope}` 是隐式方案的另一种形态，同样有「看不见」的问题 |
| 010 全局版本号失效 | ⚠️ 够用但粗糙 | 实现时才发现 `queryset.update()` 不触发信号，补了 `RbacQuerySet`。用户量上十万要换方案 |
| 013 内核纯函数化 | ✅ **最超值的一条** | `v1.2.0` 接入 DRF，`services.py` 一行未改，新增 147 行里 0 行权限逻辑 |

### 最该带走的一条

不是某个具体决策，而是这个：

> **选型的第一个问题不是「哪个库好」，而是「我的授权关系是被指定的还是被推导的」。**
>
> 这一个问题就把 django-guardian 和数据范围分开了，把 Casbin 和自建分开了。
> 答错了，后面所有努力都在错误的路线上优化。

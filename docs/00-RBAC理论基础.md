## 1. 访问控制要回答的三个问题

任何访问控制系统，本质上都在回答同一个问题的三个部分：

```
   谁          能对什么         做什么
（Subject）   （Object）      （Operation）
   用户张三     工单 #123        删除
```

不同的访问控制模型，区别只在于**这个三元组是怎么被存储和推导出来的**。

- 存成一张大表，逐条列举 → **ACL**
- 按对象的所有者来决定 → **DAC**
- 按安全等级标签来决定 → **MAC**
- 引入「角色」作为中间层 → **RBAC**
- 用属性和规则动态计算 → **ABAC**
- 沿对象间的关系图推导 → **ReBAC**

理解这一点，后面所有模型的差异都会变得清晰：**它们是同一个问题的不同存储/推导策略。**

## 2. 访问控制模型的演进

### 2.1 DAC：自主访问控制（Discretionary Access Control）

**规则**：资源的所有者自己决定谁能访问它。

你最熟悉的例子是 Unix 文件权限：

```
-rw-r--r--  1 alice  staff  1024  ticket.txt
   ↑  ↑  ↑
 owner group other
```

alice 是所有者，她可以自由地 `chmod` 把权限给任何人。

**解决了什么**：极其简单直观，权限决策分散到每个所有者手里，无需中央管理。

**暴露了什么**：
- **权限会失控扩散**。alice 可以把文件设成 `777`，管理员事前无法阻止、事后难以发现。
- **无法回答组织级问题**。「公司里谁能读财务数据」——你得遍历所有文件的权限位。
- **所有者离职了怎么办**？

DAC 适合个人计算环境，不适合组织。

### 2.2 MAC：强制访问控制（Mandatory Access Control）

**规则**：系统给每个主体和客体打上**安全标签**，访问由中央策略强制决定，所有者无权更改。

经典模型是 Bell-LaPadula（1973，为美军设计）：

```
标签等级：绝密 > 机密 > 秘密 > 公开

规则一（no read up）  ：不能读比自己等级高的
规则二（no write down）：不能写到比自己等级低的  ← 防止高密级信息向下泄漏
```

第二条规则很反直觉——一个「绝密」级用户**不能**往「公开」文件里写东西。因为那等于把绝密信息搬运了出去。

**解决了什么**：信息流被严格管控，所有者无法绕过。

**暴露了什么**：僵硬到无法用于商业环境。企业里的权限不是线性等级——市场部经理和研发部经理谁的「等级」更高？这个问题本身就问错了。

SELinux、AppArmor 是 MAC 在现代系统里的遗产。

### 2.3 ACL：访问控制列表

**规则**：为每个资源维护一张「谁能做什么」的列表。

```
工单 #123:
  张三 → 读、写、删
  李四 → 读
  王五 → 读、写
```

这是最直白的实现，也是绝大多数项目的起点。

**它的问题在规模上暴露**。假设有 N 个用户、M 个资源：

| 痛点 | 说明 |
| --- | --- |
| **条目爆炸** | 最坏情况 N × M 条授权记录 |
| **人员变动是灾难** | 张三转岗，要找出他在**所有**资源上的授权逐一修改。漏一个就是安全隐患 |
| **新人入职要手工重建** | 「给新来的小李配得和张三一样」——只能靠人肉比对 |
| **无法审计** | 「谁能删工单」这个问题，要扫描全部工单的 ACL 才能回答 |
| **权限无法解释** | 张三为什么能删这个工单？因为列表里有他。为什么列表里有他？没人记得了 |

> **ACL 的根本缺陷**：它把权限直接绑在「人」和「具体资源」上。而组织里，权限真正对应的是**职责**——人和资源都在流动，职责相对稳定。

### 2.4 RBAC：基于角色的访问控制

**核心洞察**（Ferraiolo & Kuhn, 1992）：

> 权限不应该跟着人走，应该跟着**职责**走。
> 人通过**担任某个职责**来获得权限。

引入一个间接层「角色」：

```
   ACL：      用户 ──────────────► 权限        （N × M 条关系）

   RBAC：     用户 ────► 角色 ────► 权限        （N + M 条关系）
```

这个间接层带来了质变：

| 场景 | ACL | RBAC |
| --- | --- | --- |
| 新人入职 | 逐个资源配权限 | 分配一个角色 |
| 员工转岗 | 找出所有授权逐一改 | 换一个角色 |
| 「谁能删工单」 | 扫描全部资源 | 查「拥有该权限的角色」的成员 |
| 「为什么他能删」 | 无法回答 | 因为他是客服主管，客服主管有此权限 |
| 新增一项权限给全体主管 | 改 N 条记录 | 改 1 条记录 |

**关键收益是「可解释性」和「可审计性」**，而不只是省了几条记录。权限系统的运维成本，80% 花在回答「他为什么能/不能做这件事」上——RBAC 让这个问题有确定答案。

**代价**（必须清楚）：
- 多了一层抽象，需要有人设计和维护角色体系。角色设计得烂，RBAC 会比 ACL 更难用。
- 经典失败模式是**角色爆炸**：为了表达每种权限组合，角色数量逼近用户数量。这时 RBAC 退化成了改名版的 ACL。角色继承（RBAC1）就是缓解这个问题的手段之一。

### 2.5 ABAC：基于属性的访问控制

**规则**：不预先分配权限，而是在**请求发生时**根据属性动态计算。

```
IF   subject.department == resource.department
AND  subject.level >= 3
AND  time.hour BETWEEN 9 AND 18
AND  request.ip IN corporate_network
THEN allow
```

四类属性：主体属性、资源属性、动作属性、环境属性（时间、IP、设备）。

**解决了什么**：表达力极强，能表达 RBAC 表达不了的动态条件（时间、地点、资源状态）。

**暴露了什么**（这几点决定了本项目为什么不用它）：

| 问题 | 说明 |
| --- | --- |
| **不可审计** | ABAC 能回答「这个请求能不能通过」，但**无法回答「谁能做什么」**——那需要对所有用户×所有资源求解策略。而后者恰恰是审计和合规要问的问题 |
| **策略爆炸** | 策略之间会冲突、重叠、相互覆盖，需要冲突消解规则，最终没人说得清系统实际行为 |
| **难以下推数据库** | 策略通常在应用层求值。要做「列出我能看的所有工单」，要么把策略翻译成 SQL（只有部分策略能翻译），要么全表扫描后逐行判断 |
| **管理员配不了** | 写策略是编程。而权限配置的实际操作者是行政/IT 人员 |

### 2.6 演进总览

| 模型 | 权限的载体 | 决策时机 | 强项 | 死穴 |
| --- | --- | --- | --- | --- |
| DAC | 资源所有者 | 事前 | 简单 | 权限失控扩散 |
| MAC | 安全标签 | 事前 | 信息流严控 | 僵硬，不适合商业 |
| ACL | 用户-资源直连 | 事前 | 直白 | N×M 爆炸，不可审计 |
| **RBAC** | **角色（职责）** | **事前** | **可审计、可解释、随组织变动** | 角色爆炸；表达不了动态条件 |
| ABAC | 属性 + 规则 | 事中 | 细粒度、动态 | 不可审计、难下推 SQL |
| ReBAC | 对象间关系图 | 事中 | 天然表达层级共享 | 需要专门的图存储与一致性机制 |

> **RBAC 为什么赢了企业市场**：它在「表达力」和「可管理性」之间找到了那个甜点。ABAC 表达力更强但管不了，ACL 好管但表达不了组织结构。
>
> 而现代的主流实践是**混合**：RBAC 打底解决 80% 的场景，在需要动态条件的地方补一点 ABAC。**本项目就是这个形态**（见第 6 章）。

## 3. NIST RBAC 标准

RBAC 在 1992 年提出后，各家实现互不兼容。2004 年美国 NIST 主导制定了 ANSI INCITS 359-2004 标准，定义了四个层级。

**这四层是递进关系，后面的包含前面的。**

### 3.1 RBAC0：核心 RBAC

标准定义了五个基本元素：

```
   USERS ────UA────► ROLES ────PA────► PRMS = OPS × OBS
     │                 ▲
     │                 │
     └──► SESSIONS ────┘
          （角色激活）
```

| 元素 | 含义 |
| --- | --- |
| `USERS` | 用户集合 |
| `ROLES` | 角色集合 |
| `OPS` | 操作集合（读、写、删……） |
| `OBS` | 客体集合（受保护的资源） |
| `PRMS` | 权限 = 操作 × 客体 的组合 |
| `UA` | User Assignment，用户-角色多对多 |
| `PA` | Permission Assignment，角色-权限多对多 |
| `SESSIONS` | 会话：用户在一次会话中**激活**其部分角色 |

**`SESSIONS` 是最常被忽略的元素**，值得单独说。

标准的原意是：用户拥有多个角色，但在一次会话中可以只**激活**其中一部分。这直接服务于**最小权限原则**——一个同时是「普通员工」和「系统管理员」的人，日常办公时只激活前者，需要维护时才切换到后者。

类比：Linux 下你平时用普通用户，需要时才 `sudo`。

**本项目不实现角色激活**（见第 5 章的取舍说明）：用户登录后，其全部角色自动生效。这是绝大多数企业后台的做法，但你应该知道标准里有这个东西，以及它为什么存在。

### 3.2 RBAC1：角色层级（Hierarchical RBAC）

在 RBAC0 上增加**角色继承**——角色之间构成偏序关系（partial order）。

```
        客服主管
           │  继承
           ▼
        客服专员
           │
           ▼
        普通员工
```

「客服主管」自动拥有「客服专员」的全部权限，再加上自己独有的。

**解决什么问题**：直接缓解 2.4 节提到的**角色爆炸**。没有继承时，「客服主管」要把客服专员的 10 个权限重新勾一遍；客服专员加权限时，主管还得记得同步——这是必然出错的流程。

标准区分两种继承：

| 类型 | 说明 |
| --- | --- |
| **一般层级**（General Hierarchy） | 允许多继承，角色关系是 DAG（有向无环图） |
| **受限层级**（Limited Hierarchy） | 限制为树结构（单继承），或限制继承深度 |

本项目采用**受限层级：单继承 + 深度上限 5**，理由见设计文档 ADR-006（核心是可解释性——单继承下「权限从哪来」的答案永远是一条链，不是一张图）。

⚠️ **术语陷阱**：「父角色」这个词在不同系统里含义相反。本项目在字段名上直接消除歧义，用 `inherits_from` 而不是 `parent`。

### 3.3 RBAC2：约束 RBAC（Constrained RBAC）

在 RBAC0 上增加**约束**，核心是**职责分离**（Separation of Duty, SoD）。

SoD 的思想来自会计和内控：**一项关键业务不能由同一个人独立完成。**

| 约束类型 | 说明 | 例子 |
| --- | --- | --- |
| **SSD** 静态职责分离 | 互斥角色不能同时**分配**给一个用户 | 一个人不能同时拥有「付款申请」和「付款审批」角色。分配时就拒绝 |
| **DSD** 动态职责分离 | 互斥角色可以同时拥有，但不能在同一会话中同时**激活** | 一个人可以既是申请人又是审批人，但一次只能扮演一个（且不能审批自己提的单） |
| **基数约束** | 角色的成员数上限 | 「财务总监」角色最多 1 人 |
| **先决角色** | 分配角色 B 的前提是已拥有角色 A | 必须先是「员工」才能是「部门主管」 |

注意 **DSD 依赖 RBAC0 的 `SESSIONS`**——没有角色激活机制，就无法实现动态职责分离。

### 3.4 RBAC3：合一

RBAC3 = RBAC1 + RBAC2。同时具备角色继承和约束。

**继承和约束合在一起会产生冲突**，这是 RBAC3 的难点：如果「财务经理」继承了「付款申请」，又继承了「付款审批」，那 SSD 约束该怎么判定？标准要求约束检查必须在**继承展开之后**进行，这让实现复杂度显著上升。

### 3.5 四层对比

| 层级 | 新增能力 | 解决的问题 | 实现复杂度 | 企业实际采用率 |
| --- | --- | --- | --- | --- |
| RBAC0 | 用户-角色-权限 + 会话 | 权限与人解耦 | 低 | 100% |
| **RBAC1** | 角色继承 | 角色爆炸 | 中 | 高 |
| RBAC2 | SoD 等约束 | 内控合规 | 中高 | 低（金融/ERP 除外） |
| RBAC3 | 两者合一 | — | 高 | 很低 |

## 4. 与 RBAC 容易混淆的概念

| 概念 | 与 RBAC 的关系 |
| --- | --- |
| **认证 vs 授权** | 认证（Authentication）= 你是谁；授权（Authorization）= 你能做什么。RBAC 只管后者。SSO、OAuth2、JWT 都属于前者。本项目 PRD 的 `NG-2` 明确把 SSO 排除在外，就是这个道理 |
| **组（Group）** | 组是**用户的集合**，角色是**权限的集合**。两者方向相反。Django 的 `Group` 被当角色用，是因为它同时挂了权限——概念上是混用 |
| **岗位（Position）** | 国内 HR 系统常见的概念，属于**组织事实**（一个人的职务），不是授权概念。常见做法是「岗位 → 默认角色」的映射，但两者不应合并 |
| **ReBAC** | 基于关系的访问控制，Google Zanzibar / SpiceDB 是代表。用对象间的关系图推导权限（「文档的父文件夹的编辑者，也是该文档的编辑者」）。擅长表达嵌套共享，适合协作类产品（Google Docs、GitHub），不适合科层制组织 |
| **PBAC / 策略引擎** | OPA、Casbin 等。是 ABAC 的工程化形态，通常作为独立服务或库存在 |

## 5. 本项目的定位与取舍

### 5.1 我们停在 RBAC1

| 层级 | 本项目 | 理由 |
| --- | --- | --- |
| RBAC0 核心 | ✅ 完整实现 | 基础 |
| RBAC0 的 `SESSIONS`（角色激活） | ❌ 不实现 | 见下 |
| RBAC1 角色继承 | ✅ 实现（受限层级：单继承 + 深度 5） | 教学价值高，是缓解角色爆炸的关键机制 |
| RBAC2 约束 | ❌ 不实现 | 见下 |
| RBAC3 | ❌ | — |

**为什么不做角色激活（SESSIONS）**

理论上它服务于最小权限原则，实践中企业后台几乎都不做，原因是**用户体验成本远大于安全收益**：每次登录要选角色，做事做到一半发现权限不够要重新切换。而企业内网的威胁模型里，「员工误操作」的风险远低于「配置太复杂导致所有人都被授予超管」的风险。

> 这是一个反复出现的模式：**理论上更安全的机制，如果难用，实际部署后会更不安全**——因为人会绕过它。

如果你要在高风险场景实现它，建议不做「登录时选角色」，而做「敏感操作时临时提权」（类似 `sudo`），把摩擦成本只加在真正危险的操作上。

**为什么不做 RBAC2 的 SoD 约束**

- SoD 主要服务于**财务内控和合规审计**（SOX 法案等），典型场景是金融、ERP。普通企业后台里罕见。
- DSD 依赖角色激活机制，而我们已经不做那个了。
- 实现 SSD 需要在角色分配、角色继承变更、权限同步等每个入口都做约束检查，且约束本身要可配置——这是一个独立的子系统，边际教学收益低于它的实施成本。

如果你的场景需要 SoD，本项目的模型可以扩展：加一张 `RoleExclusion` 互斥表，在 `UserRole` 保存时和 `expand_roles()` 之后各校验一次。**关键点是必须在继承展开之后校验**——否则通过继承链间接获得互斥角色的路径会被漏掉。

### 5.2 一句话定位

> 本项目 = **NIST RBAC1**（受限层级）**+ 数据行级权限**（一个 NIST 标准之外的、退化形态的 ABAC）。

下一章解释这个加号后面的东西是怎么回事。

## 6. 数据权限：NIST 标准里没有的那一半

**这是本文最重要的一章。** 它解释了一个现象：为什么国外成熟的权限库（django-guardian、Casbin）拿到中国的企业后台里，普遍解决不了「只能看本部门数据」这个最常见的需求。

### 6.1 标准里为什么找不到它

回到 RBAC0 的定义：`PRMS = OPS × OBS`。

`OBS`（客体）在标准里是抽象的，理论上**可以是单个数据行**——「删除工单 #123」完全可以是一个合法的权限。

那为什么现实中没人这么做？因为规模：

```
1 万张工单 × 5 种操作 × 50 个角色 = 250 万条授权记录
而且每新建一张工单，就要为它生成 250 条授权
```

**RBAC 的权限模型是为「操作类型」设计的，不是为「数据实例」设计的。** 这不是标准的疏漏，是刻意的边界——RBAC 解决的是「谁能做什么类型的事」，从来就不打算解决「能对哪些具体数据做」。

### 6.2 于是出现了两条路

**路线 A：对象级权限（Object-level Permission）**

代表是 `django-guardian`：为每个「用户/组 + 对象实例」组合存一条授权记录。

```python
assign_perm('change_ticket', alice, ticket_123)
```

**适用场景**：授权关系是**离散、显式、人工指定**的。比如 Google Docs 的分享——alice 主动把文档分享给 bob，这是一个明确的动作，值得记一条。

**不适用场景**：授权关系是**由规则推导**的。「客服部主管能看客服部的所有工单」——这条规则下的授权关系有几万条，而且随着新工单创建持续增长。用 guardian 意味着每建一张工单就要为所有相关用户批量写授权，且部门调整时要全量重算。这条路走不通。

**路线 B：数据范围（Data Scope）**

不存储「谁能看哪条数据」，而是存储**一条推导规则**，在查询时把它翻译成 SQL 的 `WHERE` 条件。

```
角色「客服主管」的数据范围 = 本部门及以下
              ↓ 查询时翻译
WHERE department_id IN (SELECT id FROM department WHERE path LIKE '/1/3/%')
```

存储量从「几万条授权记录」降到「角色上的一个枚举字段」，且**自动适用于未来新建的数据**。

**中国的企业后台系统（若依 RuoYi、Jeecg、各家自研）几乎全部走的是路线 B**，通常叫「数据权限」或「数据范围」。本项目也走这条路（设计文档 ADR-007）。

有意思的是，若依的枚举取值和本项目几乎一样（全部 / 自定义 / 本部门 / 本部门及以下 / 仅本人），
连「多角色求并集」「无匹配则拒绝」这些细节都一致——**不同的人独立解同一个问题，
收敛到了同一个形状**。这本身就说明这个形状是被真实需求逼出来的，而不是谁的偏好。
逐项对比见 [04-横向对比.md](04-横向对比.md)。

### 6.3 数据权限在理论上是什么

严格地说，**数据权限属于 ABAC**：

```
allow IF subject.department.path IS PREFIX OF resource.department.path
        ↑ 主体属性                        ↑ 资源属性
```

它是一条基于主体属性和资源属性的匹配规则——这正是 ABAC 的定义。

但它是一个**被刻意退化的 ABAC**：

| ABAC 通用形态 | 本项目的数据权限 |
| --- | --- |
| 任意属性、任意谓词 | 只有「归属人」和「归属部门」两个属性 |
| 用策略语言书写 | 五个预定义枚举值 |
| 应用层求值 | 编译成 Q 对象，SQL 层求值 |
| 管理员写不了 | 管理员点几下就能配 |

**这个退化是有意为之的，它换来三样东西**：

1. **可配置**——管理员在界面上勾选，不需要写表达式。
2. **可下推 SQL**——五个枚举值都能确定性地翻译成 `WHERE` 条件，不会退化成全表扫描（这是 PRD `NFR-2` 的硬要求）。
3. **可审计**——能回答「这个角色能看哪些数据」，因为规则是有限且已知的。而通用 ABAC 回答不了这个问题（见 2.5 节）。

> **本项目的完整定位**：
> **RBAC1 处理功能权限**（能不能做这个操作）**+ 退化 ABAC 处理数据权限**（能对哪些行做）。
>
> 这两者在实现上必须**彻底分离**——功能权限在视图层做布尔判断，数据权限在 ORM 层做集合过滤。试图用一套机制表达两者，是权限系统腐化的头号原因（设计文档 ADR-007 详述）。

### 6.4 三条路线的选择依据

| 路线 | 授权关系的性质 | 适合的产品 | 代表实现 |
| --- | --- | --- | --- |
| 对象级权限 | 离散、显式、人工指定 | 协作类（文档共享、项目管理） | django-guardian |
| **数据范围** | **由组织结构规则推导** | **科层制企业后台** | **若依、本项目** |
| ReBAC | 沿对象关系图传播 | 嵌套共享（Drive、GitHub） | Zanzibar、SpiceDB |

选错路线的代价是结构性的、后期无法挽回的。判断依据只有一条：

> **问自己「授权关系是被人指定的，还是被规则推导的？」**
> 前者用对象级权限，后者用数据范围。

## 五、⚠️ 容易写错的地方

### 1. 失败提示必须统一（FR-5.2）

```python
# ❌ 泄露了用户是否存在
if not User.objects.filter(username=username).exists():
    return "该用户不存在"
if not user.check_password(password):
    return "密码错误"

# ✅
return LOGIN_FAILED_MESSAGE
```

第一节第 1 问的答案：分开提示等于给攻击者一个**用户名枚举**接口。他可以批量试用户名，把「该用户不存在」和「密码错误」区分开，先拿到有效账号清单，再针对性撞库。

**同类问题还有一个更隐蔽的版本**：即使提示文案统一了，如果「用户不存在」时直接返回、「密码错误」时走了一遍 PBKDF2 哈希计算（耗时约 100ms），攻击者可以通过**响应时间**区分两者。

Django 的 `authenticate()` 已经处理了这个——用户不存在时它会跑一次 `UserModel().set_password(password)` 来消耗等量时间。**你自己写认证逻辑时要记得这一点。**

### 2. `last_login_ip` 从哪取

```python
def get_client_ip(request):
    xff = request.META.get("HTTP_X_FORWARDED_FOR")
    if xff:
        return xff.split(",")[0].strip()
    return request.META.get("REMOTE_ADDR")
```

⚠️ **`X-Forwarded-For` 是客户端可伪造的**。只有在你确信请求经过了可信反向代理（且代理会覆写这个头）时才能信任它。直接暴露在公网的应用不能信。

在代码里写注释说明这个前提。这是一个「实现正确但依赖部署假设」的典型例子。

### 3. 登录失败计数放 cache，不放数据库

- **数据库字段**：每次失败都要写库，且要处理并发；用户不存在时无处可写（总不能为不存在的用户建记录）。
- **session**：攻击者换个 session 就绕过了，形同虚设。
- **cache**：✅ 有天然的 TTL（正好对应锁定时长），无需清理任务。

注意：cache key 用 `username` 而不是 IP。用 IP 会误伤同一出口 IP 下的整个办公室。生产环境通常两者都限（用户名维度防撞库，IP 维度防暴力扫描）。

### 4. 登出必须是 POST

Django 5.x 起，`LogoutView` **只接受 POST**（4.1 开始废弃 GET，5.0 正式移除）。

为什么？`GET /logout/` 意味着攻击者可以在论坛发一张 `<img src="https://yoursite/logout/">`，任何浏览到该页面的用户都会被强制登出。这是 CSRF 的一种（虽然危害较小）。

**如果你按老教程写了 `<a href="{% url 'accounts:logout' %}">退出</a>`，在 Django 5.2 上会得到 405。** 要用一个带 CSRF token 的 form + button。

### 5. 用户被禁用后，session 会自动失效吗？

第一节第 5 问。**取决于配置。**

Django 的 `AuthenticationMiddleware` 从 session 还原 user 时，`ModelBackend.get_user()` 里有一句 `user if self.user_can_authenticate(user) else None`，而 `user_can_authenticate` 会检查 `is_active`。所以**用 `ModelBackend` 时会自动失效**。

但我们在 `v0.9.0` 会加自定义 backend。**到时候如果忘了实现 `get_user()` 或忘了检查 `is_active`，这个保护就没了。**

所以我们在 `v0.6.0` 的 `get_user_perm_codes()` 里也检查了一次 `is_active`——**纵深防御**：同一个安全属性由两处独立保证，一处失效不至于全面失守。

### 6. `login()` 会 cycle session key

第一节第 2 问的答案：Django 的 `login()` 内部调用 `request.session.cycle_key()`，生成新的 session ID。

防的是**会话固定攻击（Session Fixation）**：攻击者先拿到一个 session ID，诱导受害者用这个 ID 登录，登录后攻击者手里的 ID 就变成了已认证会话。

这个你不用做任何事，但**要知道它存在**——如果哪天你自己写认证流程绕过了 `login()`，就得记得手动 cycle。

<summary><b>提示 1：登录视图骨架</b></summary>

```python
def login_view(request):
    if request.user.is_authenticated:
        return redirect(settings.LOGIN_REDIRECT_URL)

    form = LoginForm(request.POST or None)
    if request.method == "POST" and form.is_valid():
        username = form.cleaned_data["username"]
        locked_for = get_lockout_remaining(username)
        if locked_for:
            form.add_error(None, LOGIN_LOCKED_MESSAGE.format(minutes=locked_for // 60 + 1))
        else:
            user = authenticate(request, username=username,
                                password=form.cleaned_data["password"])
            if user is None:
                record_login_failure(username)
                form.add_error(None, LOGIN_FAILED_MESSAGE)   # 统一文案
            else:
                clear_login_failure(username)
                login(request, user)                          # 内部会 cycle_key
                User.objects.filter(pk=user.pk).update(last_login_ip=get_client_ip(request))
                return redirect(get_safe_redirect(request))

    return render(request, "accounts/login.html", {"form": form})
```

<details>
<summary><b>提示 2：失败计数</b></summary>

```python
def _key(username): return f"login_fail:{username}"

def record_login_failure(username):
    key = _key(username)
    try:
        count = cache.incr(key)
    except ValueError:
        cache.set(key, 1, settings.LOGIN_FAIL_LOCKOUT_SECONDS)
        count = 1
    return count

def get_lockout_remaining(username) -> int:
    """返回剩余锁定秒数，0 表示未锁定。"""
    count = cache.get(_key(username), 0)
    if count < settings.LOGIN_FAIL_MAX_ATTEMPTS:
        return 0
    return cache.ttl(_key(username)) if hasattr(cache, "ttl") else settings.LOGIN_FAIL_LOCKOUT_SECONDS
```

⚠️ LocMemCache 没有 `ttl()` 方法，Redis 后端才有。想想怎么写才能两种后端都工作。
</details>

<details>
<summary><b>提示 3：next 参数的安全处理</b></summary>

```python
from django.utils.http import url_has_allowed_host_and_scheme

def get_safe_redirect(request):
    nxt = request.POST.get("next") or request.GET.get("next")
    if nxt and url_has_allowed_host_and_scheme(nxt, allowed_hosts={request.get_host()},
                                               require_https=request.is_secure()):
        return nxt
    return settings.LOGIN_REDIRECT_URL
```

**不校验 `next` 就是开放重定向漏洞**：攻击者构造 `/login/?next=https://evil.com`，用户登录后被跳到钓鱼站，而且是从你的域名跳过去的，很有迷惑性。
</details>

## 九、延伸思考

1. **锁定策略的副作用**：攻击者知道你的规则后，可以**故意**用错误密码去锁定别人的账号——这叫「账号锁定 DoS」。

   怎么缓解？（提示：按 IP + 用户名的组合计数、指数退避而非硬锁定、引入验证码、只锁定「异常 IP」的尝试）

   想想：本项目作为教学项目做了最简单的实现，生产环境你会怎么改？

2. **`SESSION_SAVE_EVERY_REQUEST = True` 的代价**（第一节第 4 问）：每个请求都写一次 session 存储。用数据库存 session 时，这意味着**每个请求一次 UPDATE**——在高并发下是真实的写压力。

   生产环境通常改用 Redis 存 session。查一下 `SESSION_ENGINE` 的几种选项，比较它们的取舍。

3. 本项目**不做** SSO / OAuth2（PRD 的 `NG-2`）。想想：如果要接企业微信扫码登录，本 tag 的哪些代码要改？哪些不用改？

   （提示：`authenticate()` 是一个可插拔的 backend 机制。理解这一点，你就知道为什么 [ADR-001](../02-设计文档.md#adr-001不使用-djangocontribauthpermission自建权限模型) 说「Django 的认证做得很好，没有理由重写」。）

4. **纵深防御的例子**：`is_active` 检查在 `ModelBackend.get_user()` 和我们的 `get_user_perm_codes()` 里各有一次，是冗余的。

   冗余的代码通常是坏味道。**为什么安全检查是例外？** 想清楚这个问题，你就理解了「纵深防御」和「重复代码」的边界在哪。

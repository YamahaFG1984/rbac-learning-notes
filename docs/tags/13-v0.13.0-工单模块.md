## 五、⚠️ 容易写错的地方

### 1. `department` 要在创建时**快照**，不能实时取

第一节第 3 问的答案。

```python
# 创建工单时
ticket.department = request.user.department      # 存下来
```

如果不存这个字段，而是在查询时用 `creator.department`——那么创建人**转岗**之后，他以前创建的所有工单会**跟着他一起换部门**。

后果：原部门的主管突然看不到历史工单了，新部门的主管莫名其妙看到一堆不相干的工单。而且这个变化是**静默**的，没人会立刻发现。

> **快照 vs 引用**：业务上有历史意义的归属关系，要快照；实时反映当前状态的，用引用。
> 判断依据：这个值变化时，历史记录该不该跟着变？

同类例子：订单里的商品价格必须快照，不能引用商品表的当前价格。

### 2. 列表页的 N+1

```python
# ❌ 模板里每行访问 ticket.creator.real_name → 每行一次查询
Ticket.objects.all()

# ✅
Ticket.objects.select_related("creator", "assignee", "department")
```

**用 `assertNumQueries` 锁死**。100 条工单的列表页，查询次数应该是个位数常量，不是 100+。

### 3. `creator` 用 `PROTECT`，`assignee` 用 `SET_NULL`

为什么不一样？

- `creator`：工单的创建人是历史事实，删了用户就丢了这个事实。用 `PROTECT` 强制先处理工单（或者干脆不允许删用户，只允许禁用）。
- `assignee`：处理人是当前状态，人走了工单变成"无人认领"是合理的。

**`on_delete` 的选择本质上是在回答「这个关系断了之后，剩下的数据还有意义吗」。**

### 4. 派单（assign）要单独的权限点

派单不是普通的编辑——它是把工作分配给别人。很多组织里，能改工单内容的人不一定能派单。

**这是 [ADR-004](../02-设计文档.md#adr-004权限码采用-appresourceaction-三段式以界面上可点的东西为粒度) 粒度原则的实例**：界面上有一个独立的「派单」按钮 → 它就该有独立的权限点。

### 5. 别提前写数据权限

看到 `creator` 和 `department` 两个字段，手会痒——「顺手过滤一下不就完了」。

**忍住。** 数据权限是 `v0.14.0` 的内容。理由见第九节。

```python
class TicketListView(PermRequiredMixin, ListView):
    model = Ticket
    template_name = "tickets/list.html"
    paginate_by = 20
    required_perm = TicketPerm.VIEW

    def get_queryset(self):
        # ⚠️ v0.13.0：此处尚无数据权限过滤，任何有 view 权限的用户
        #    都能看到全部工单。这是刻意留下的中间态，v0.14.0 补上。
        qs = Ticket.objects.select_related("creator", "assignee", "department")
        if status := self.request.GET.get("status"):
            qs = qs.filter(status=status)
        if kw := self.request.GET.get("kw"):
            qs = qs.filter(title__icontains=kw)
        return qs
```

那条注释很重要——**它在标记「这里是故意不完整的」**，防止将来有人（包括你自己）以为这是遗漏。

<details>
<summary><b>提示 2：创建时快照部门</b></summary>

```python
class TicketCreateView(PermRequiredMixin, CreateView):
    required_perm = TicketPerm.CREATE

    def form_valid(self, form):
        form.instance.creator = self.request.user
        form.instance.department = self.request.user.department   # 快照，见陷阱 1
        return super().form_valid(form)
```

⚠️ `creator` 和 `department` 绝不能出现在 `form.Meta.fields` 里——否则用户可以构造 POST 伪造创建人。这是 `CLAUDE.md` 安全红线第 3 条（表单白名单）的一个实例。

## 九、⚠️ 关于本 tag 刻意留下的漏洞

现在做个实验：

1. 用 `seed` 数据或手工造：客服部 20 张工单，技术部 30 张工单。
2. 建一个「客服专员」角色，只给 `ticket:ticket:view` 权限。
3. 用客服专员账号登录，打开工单列表。

**你会看到 50 张工单——包括技术部的全部 30 张。**

### 这是有意的

**功能权限（能不能看列表）有了，数据权限（能看哪些行）没有。**

这个状态非常有价值，因为它让你**亲眼看到「只有功能权限的系统」长什么样**。

而且——**很多真实项目就停在这一步**。它们做了完善的角色管理、精细的按钮权限、漂亮的动态菜单，然后在某天发现「普通员工能看到全公司的数据」。

### 为什么不一次做完？

> **先看见问题，再看解法。**
> 直接给最终答案，你会记住结论；先经历问题，你会记住原因。

`v0.14.0` 的 diff 会清晰地展示「数据权限是怎么被加进去的」——如果本 tag 就把它做了，那个 diff 就消失了。

这是本项目三个刻意中间态之一（另两个是 `v0.8.0` 的写死菜单和 `v1.1.0` 的无授权 API）。

### 延伸思考

1. **在只有功能权限的系统里，怎么临时挡住这个洞？** 很多项目的做法是在视图里手写：

   ```python
   qs = Ticket.objects.filter(department=request.user.department)
   ```

   这样能跑。但想想：
   - 列表页写了，详情页记得写吗？导出呢？统计呢？
   - 主管要看「本部门及以下」，这个 `filter` 怎么改？
   - 20 个业务模块，每个都这么写，规则改了要改几处？

   **这就是 `v0.14.0` 要用统一机制解决的问题。**

2. 数一数：如果不做统一的数据权限机制，本项目的工单模块有几处需要过滤？（列表、详情、编辑、删除、派单、导出、统计……）

   每多一处，就多一个「忘了写」的机会。**而忘了写的后果是静默的越权。**

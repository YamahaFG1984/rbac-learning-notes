### `DataScope` 枚举（**编号顺序有讲究，必须一致**）

```python
class DataScope(models.IntegerChoices):
    ALL            = 1, "全部数据"
    DEPT_AND_BELOW = 2, "本部门及以下"
    DEPT_ONLY      = 3, "仅本部门"
    SELF_ONLY      = 4, "仅本人"
```

## 五、⚠️ 容易写错的地方

### 1. `data_scope` 默认值必须是 `SELF_ONLY`，不是 `ALL`

第一节第 4 问的答案。

`CLAUDE.md` 的编码约定里有一条：**默认值必须指向「出错时后果最轻」的方向。**

新建角色时忘了配数据范围：
- 默认 `SELF_ONLY` → 用户看得太少 → 有人来报障 → 修好 ✅
- 默认 `ALL` → 用户看到全公司数据 → **没有任何人会来报障** ❌

**安全问题的特征就是「出错时没有反馈信号」。** 所以默认值要选那个「出错会被发现」的方向。

### 2. 保存权限时：先删后插 vs 差集更新

```python
# 方案 A：先删后插（简单）
RolePermission.objects.filter(role=role).delete()
RolePermission.objects.bulk_create([RolePermission(role=role, permission_id=p) for p in ids])

# 方案 B：算差集（精确）
current = set(RolePermission.objects.filter(role=role).values_list("permission_id", flat=True))
to_add, to_del = set(ids) - current, current - set(ids)
```

方案 A 在本 tag 完全够用，且更简单。但**到了 `v0.17.0` 做审计日志时，你会需要知道「这次改动加了哪些、减了哪些」**——那时方案 A 就不够了。

现在选 A 没问题（YAGNI）。但心里有数：这是一处**已知会被改的地方**。到 `v0.17.0` 时回来看看，重构的成本大不大？这是练习「什么时候该提前设计、什么时候该等」的好素材。

### 3. 必须包在事务里

```python
with transaction.atomic():
    RolePermission.objects.filter(role=role).delete()
    RolePermission.objects.bulk_create(...)
```

不加事务的话，删完之后 `bulk_create` 抛异常，这个角色的权限就**全没了**。而且没人会立刻发现。

### 4. 目录（catalog）节点要不要存进 `RolePermission`？

管理员勾选了「工单管理」这个目录，要不要往 `RolePermission` 里写一条？

**两种做法都可以，但必须想清楚并保持一致：**

- **存**：菜单树构建时可以直接用（`v0.11.0`）；但目录没有 `code`，鉴权时必须记得排除它们（`v0.6.0` 的查询要加 `.exclude(code__isnull=True)`）。
- **不存**：数据更干净；但菜单树构建时要靠「有权限的子菜单」反推目录可见性。

**本项目选「存」**，因为勾选状态的回显更直接。相应地，`v0.6.0` 解析权限码时必须记得 `.exclude(code__isnull=True)`——**忘了这一步，`None` 会混进权限码集合里**。

### 5. 内置角色的删除保护

`is_builtin=True` 的角色不能删。但要注意：**这个检查写在视图里是不够的**，因为 Django admin、shell、管理命令都能绕过。

更稳的做法是在模型的 `delete()` 里也加一道，或者用 `pre_delete` 信号。想想哪种更好。

### 6. 权限树勾选的前端联动别写复杂了

不需要引入任何前端框架。原生 JS，监听 checkbox 的 change 事件，往下遍历子节点、往上更新父节点的 `indeterminate` 属性。40 行以内能搞定。

**注意 `indeterminate` 只是视觉状态，提交时不会被计入。** 半选的父节点要不要提交，取决于你在陷阱 4 里的决定。

## 六、卡住了看这里（渐进提示）

<details>
<summary><b>提示 1：权限树渲染成扁平列表</b></summary>

沿用 `v0.3.0` 部门树的思路：按 `path` 排序，用 `depth` 算缩进，模板平铺渲染。

```python
def role_perm_assign(request, pk):
    role = get_object_or_404(Role, pk=pk)
    perms = Permission.objects.filter(is_active=True, is_deprecated=False).order_by("path")
    checked = set(RolePermission.objects.filter(role=role).values_list("permission_id", flat=True))
    rows = [{"p": p, "indent": p.depth, "checked": p.id in checked} for p in perms]
    return render(request, "rbac/role_perm_assign.html", {"role": role, "rows": rows})
```

一次查询取全部权限点，一次查询取已勾选 ID。共 2 次查询，与树深度无关。
</details>

<details>
<summary><b>提示 2：保存逻辑</b></summary>

```python
@transaction.atomic
def save_role_permissions(role, permission_ids):
    """全量覆盖式保存。

    注意事务：删除和插入必须原子，否则中途失败会导致角色权限被清空。
    """
    valid_ids = set(
        Permission.objects.filter(id__in=permission_ids, is_active=True, is_deprecated=False)
        .values_list("id", flat=True)
    )                                     # ⚠️ 必须校验，不能信任前端提交的 ID
    RolePermission.objects.filter(role=role).delete()
    RolePermission.objects.bulk_create(
        [RolePermission(role=role, permission_id=pid) for pid in valid_ids]
    )
```

⚠️ 那行「必须校验」很重要：直接用前端传来的 ID 建关联，等于允许构造请求把任意 ID（包括已废弃的权限点）塞进来。**永远不要信任客户端提交的主键。**
</details>

<details>
<summary><b>提示 3：checkbox 父子联动</b></summary>

```javascript
// 给每个 checkbox 加 data-id 和 data-parent
document.querySelectorAll('input[type=checkbox][data-id]').forEach(cb => {
  cb.addEventListener('change', e => {
    setDescendants(e.target, e.target.checked);   // 向下：全选/全不选
    refreshAncestors(e.target);                   // 向上：更新 checked / indeterminate
  });
});
```

`indeterminate` 属性只能用 JS 设置，没有对应的 HTML 属性。
</details>

## 九、延伸思考

1. **`DataScope` 的编号为什么从大范围到小范围递增？**

   <details>
   <summary>答案</summary>

   这样「哪个范围更宽」就变成一次整数比较：`min(scopes)` 就是最宽的那个。

   `v0.14.0` 里会用到这个性质做短路优化（只要有任一角色是 `ALL`，直接返回不过滤）。

   **但要小心**：`v0.14.0` 里我们**不会**简单地「取最宽枚举」——那样在 `CUSTOM` 参与时会丢数据。编号顺序只用于短路优化，不用于合并逻辑。这个区别在 [ADR-007](../02-设计文档.md#adr-007数据权限用枚举-data_scope多角色范围做真并集) 里详述，到了 `v0.14.0` 你会亲自实现它。
   </details>

2. **本 tag 刻意没加 `inherits_from`。** 如果你觉得「反正后面要加，不如现在一起写了」——想想 `CLAUDE.md` 第 0 条。提前写了会发生什么？

   （提示：`v0.12.0` 的 diff 本该清晰地展示「RBAC0 → RBAC1 需要改哪些地方」。提前写了，这个 diff 就消失了，而它是本项目最有教学价值的 diff 之一。）

3. 现在角色权限的保存是「全量覆盖」。**如果两个管理员同时编辑同一个角色**，会发生什么？后提交的会完全覆盖先提交的，且没有任何提示。

   这是经典的「丢失更新」问题。查一下乐观锁（版本号字段）怎么解决它。想想：企业后台里这个问题值得解决吗？判断依据是什么？

4. **角色数量会失控吗？** 回想 [理论基础 2.4 节](../00-RBAC理论基础.md) 提到的「角色爆炸」——为了表达每种权限组合，角色数逼近用户数，RBAC 退化成改名版的 ACL。

   现在没有角色继承，如果要配「客服专员」和「客服主管」两个角色，后者比前者多 2 个权限，你要怎么配？重复勾 10 个权限吗？**这个痛点就是 `v0.12.0` 要解决的**——先亲身体验一下它有多烦。

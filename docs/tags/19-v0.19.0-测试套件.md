## 五、⚠️ 要点

### 🔴 1. 越权矩阵是「可执行的权限规格说明书」

第一节第 4、5 问的答案。

设计文档 6.2 的矩阵：

```
        │ 超管 │ 系统管理员 │ 客服主管 │ 客服专员 │ 无角色 │ 匿名
────────┼──────┼───────────┼─────────┼─────────┼───────┼──────
用户列表 │  ✅  │    ✅     │   ❌    │   ❌    │  ❌   │ ↪登录
角色配置 │  ✅  │    ✅     │   ❌    │   ❌    │  ❌   │ ↪登录
工单列表 │ 全部 │   全部    │ 本部门树 │  仅本人  │  空   │ ↪登录
工单删除 │  ✅  │    ❌     │   ✅    │   ❌    │  ❌   │ ↪登录
他部门单 │  ✅  │   可见    │   404   │   404   │  404  │ ↪登录
```

**不要写 30 个测试函数。用参数化把这张表直接搬进代码：**

```python
MATRIX = [
    # (user_fixture, url_name, method, expected_status)
    ("superadmin",  "accounts:user_list", "get", 200),
    ("sysadmin",    "accounts:user_list", "get", 200),
    ("cs_manager",  "accounts:user_list", "get", 403),
    ("cs_staff",    "accounts:user_list", "get", 403),
    ("no_role",     "accounts:user_list", "get", 403),
    ("anonymous",   "accounts:user_list", "get", 302),
    ...
]

@pytest.mark.parametrize("user_key,url_name,method,expected", MATRIX)
def test_permission_matrix(request, demo_data, client, user_key, url_name, method, expected):
    ...
```

**这张表同时是三样东西**：
1. **验收清单**——PRD 的 AC-6
2. **回归基线**——任何一格从 ❌ 变 ✅ 都是安全事故，CI 会立刻变红
3. **权限规格说明书**——产品问「客服主管能不能删工单」，答案在这里

> 第一节第 5 问的答案：**文档会过期，测试不会——因为过期的测试会变红。**

### 🔴 2. 「永远不会触发」的分支，只有测试能保证

第一节第 2 问。

`build_scope_q()` 的四处默认拒绝、`expand_roles()` 的环保护、`ScopeConfig` 缺失时的异常——这些分支在正常使用中永远走不到。

**这意味着**：
- 手工测试测不出来
- 用户不会报障
- code review 时容易被认为「多余」而删掉

**只有测试能保证它们是对的，也只有测试能阻止它们被误删。**

给这类测试加个显眼的标记：

```python
@pytest.mark.security
class TestDenyByDefault:
    """默认拒绝分支。这些分支在正常使用中永不触发，
    删掉任何一个都不会有人报障——所以只有测试能守住它们。
    """
```

### 🔴 3. `assertNumQueries` 是权限系统的必备测试

第一节第 3 问。

权限相关代码是 N+1 的**高发区**：
- 菜单树（每层一次查询）
- 每个按钮判断一次权限
- 列表页每行访问关联对象
- 角色继承展开（每层一次）

**把查询次数写死在测试里**，任何回退都会立刻暴露：

```python
def test_ticket_list_query_count(client, demo_data, django_assert_num_queries):
    client.force_login(demo_data["cs_manager"])
    with django_assert_num_queries(8):        # 具体数字以实测为准
        client.get(reverse("tickets:list"))
```

⚠️ 这类测试会「假阳性」——加个功能查询数变了，测试就红。**这是特性不是缺陷**：它强迫你每次改动都意识到查询数的变化。

但要写好注释说明这个数字的构成，否则后人只会无脑改数字：

```python
# 8 = 1 session + 1 user + 1 权限码 + 1 角色映射 + 1 菜单 + 1 count + 1 list + 1 部门子树
```

### 4. 覆盖率不是目标，是**发现盲区的工具**

跑 `--cov-report=term-missing`，看没覆盖的行。逐个问「为什么没覆盖」：

| 原因 | 该怎么办 |
| --- | --- |
| 忘了测 | 补测试 ✅ |
| 是防御性分支（永不触发） | **必须补测试**（见要点 2） |
| 是死代码 | 删掉 ✅ |
| 难以构造的边界 | 想想是不是设计太复杂了 |

**追求 100% 覆盖率是浪费**（getter、`__str__`、迁移文件），但 `apps/rbac` 低于 90% 一定有真问题。

### 5. 测试之间不能互相污染

权限系统的测试特别容易踩这个坑：

```python
@pytest.fixture(autouse=True)
def clear_rbac_cache():
    cache.clear()            # v0.16.0 加了缓存后必须清
    yield
    cache.clear()
```

不清缓存的话，测试 A 的权限结果会被测试 B 读到，出现「单独跑绿、一起跑红」的诡异现象。

同理，请求级缓存挂在 user 对象上（`v0.16.0`），复用 user 实例的测试也会串。

```python
# 功能权限矩阵
PERM_MATRIX = [
    ("superadmin", "accounts:user_list", "get", None, 200),
    ("sysadmin",   "accounts:user_list", "get", None, 200),
    ("cs_manager", "accounts:user_list", "get", None, 403),
    ("cs_staff",   "accounts:user_list", "get", None, 403),
    ("no_role",    "accounts:user_list", "get", None, 403),
    ("anonymous",  "accounts:user_list", "get", None, 302),
    # ... 其余格子
]

@pytest.mark.parametrize("user_key,url_name,method,args,expected", PERM_MATRIX,
                         ids=lambda v: str(v))
def test_permission_matrix(as_user, user_key, url_name, method, args, expected):
    client = as_user(user_key)
    url = reverse(url_name, args=args or [])
    resp = getattr(client, method)(url)
    assert resp.status_code == expected, (
        f"{user_key} {method.upper()} {url} → {resp.status_code}，期望 {expected}"
    )


# 数据权限矩阵
SCOPE_MATRIX = [
    ("superadmin", 80),
    ("sysadmin",   80),   # data_scope=ALL
    ("cs_manager", 50),   # 客服部树
    ("cs_staff",    5),   # 仅本人
    ("no_role",     0),   # ⚠️ 默认拒绝
]

@pytest.mark.parametrize("user_key,expected_count", SCOPE_MATRIX)
def test_data_scope_matrix(demo_data, user_key, expected_count):
    user = demo_data[user_key]
    assert Ticket.objects.for_user(user).count() == expected_count
```

那句 `assert` 的错误消息很重要——参数化测试失败时，默认消息只告诉你「200 != 403」，加上上下文才能一眼看出是哪一格。

## 九、延伸思考

1. **测试金字塔在权限系统里的形状**

   通常建议「大量单元测试 + 少量集成测试 + 极少 E2E」。但权限系统有点特殊：

   **单元测试能验证 `build_scope_q` 返回的 Q 对象是对的，但验证不了「视图真的调用了它」。** 后者只能靠集成测试。

   而「视图忘了调用」恰恰是最常见的漏洞成因。所以权限系统的集成测试比例应该**高于**常规项目。

   想想：本项目的测试比例是什么样的？合理吗？

2. **变异测试（Mutation Testing）**

   覆盖率只说明「这行代码被执行了」，不说明「这行代码错了会被发现」。

   试试 `mutmut` 或 `cosmic-ray`：它会自动把你的代码改坏（比如把 `Q(pk__in=[])` 改成 `Q()`），看测试会不会红。**红了说明测试有效，绿了说明测试是摆设。**

   对权限系统来说，这是个非常合适的工具——正好能验证「四处默认拒绝」的测试是不是真的守得住。

3. **性能测试的数字会随环境变化吗？**

   `assertNumQueries` 断言的是查询**次数**，不是耗时——所以它在任何机器上都稳定。这是它比「断言响应时间 < 100ms」优越的地方。

   想想：还有哪些性能属性可以用「确定性断言」而不是「阈值断言」来测？

4. **CI 里该跑什么？**

   - `pytest`（必须）
   - 覆盖率门槛（`--cov-fail-under=85`）
   - `python manage.py check`（会跑 `rbac.W001` 自检！）
   - 依赖方向检查（`v0.1.0` 延伸思考 1 提到的）

   **`manage.py check` 进 CI 这一条特别值得做**——它把 `v0.9.0` 的「启动自检」变成了「合并前自检」，漏加权限装饰器的代码根本进不了主干。

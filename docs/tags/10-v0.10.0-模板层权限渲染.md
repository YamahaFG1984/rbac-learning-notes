## 三、接口契约（必须与我的实现对齐）

```python

TEMPLATES[0]["OPTIONS"]["context_processors"] += [
    "apps.rbac.context_processors.rbac",
```

```django
{% if 'ticket:ticket:delete' in perms %}
```

```python
'code' in perms          # __contains__     ← 主要用法
```

## 五、⚠️ 容易写错的地方

### 1. 惰性必须真的惰性

```python
# ❌ 每次渲染都查库，哪怕模板压根没用到 perms
def rbac(request):
    return {"perms": get_user_perm_codes(request.user)}

# ✅ 只有模板里真的写了 `in perms` 才触发
def rbac(request):
    return {"perms": LazyPermSet(request.user)}
```

第一节第 2 问的答案。登录页、错误页、静态页面都不需要权限，惰性让它们零成本。

**验证方法**：渲染登录页，用 `assertNumQueries(0)` 断言没有权限相关查询。

### 2. context processor 里不要访问 `request.user` 的属性

```python
# ❌ 这一行就会触发 SimpleLazyObject 的求值，把 user 从 session 里加载出来
def rbac(request):
    if request.user.is_authenticated:      # ← 提前求值了
        return {"perms": LazyPermSet(request.user)}
    return {"perms": frozenset()}
```

`request.user` 本身是 Django 的 `SimpleLazyObject`。碰它的任何属性都会触发数据库查询加载用户。

把判断推迟到 `LazyPermSet.__contains__` 里面去。

### 3. 模板里的权限码 typo 不会报错

第一节第 4 问的答案：**不会报错，只会静默地不渲染那个按钮。**

这是本方案最大的缺点。管理员配好了权限，用户却看不到按钮，排查时你会怀疑缓存、怀疑角色配置、怀疑数据库——就是想不到是模板里少打了一个字母。

**缓解**：`v1.0.0` 会给 `sync_permissions` 加一个 `--check-templates` 选项，扫描模板里的权限码字面量，报告数据库里不存在的。

现在先记住这个坑存在。

### 4. 超管的 `len(perms)`

`ALL_PERMS` 哨兵对象（`v0.6.0` 定义的）的 `__iter__` 返回空。所以 `len(perms)` 对超管是 0，但 `'anything' in perms` 是 True。

这是个**故意的不一致**。如果模板里有 `{% if perms %}` 这种判断，超管会走进 else 分支——想想怎么处理（提示：实现 `__bool__` 恒为 True）。

**这类哨兵对象的坑值得体会**：它伪装成集合，但只在 `in` 这一个语义上成立。用它的地方越多，越容易踩到不成立的那些语义。

### 5. 别忘了视图层也要有对应的检查

见第九节第 1 条。**这是本 tag 最重要的一条。**

<details>
<summary><b>提示 1：LazyPermSet</b></summary>

```python
class LazyPermSet:
    """惰性权限集合：模板真的用到才解析，不用则零成本。

    ⚠️ 本对象只用于模板渲染，是「体验优化」不是「安全边界」。
       服务端的权限检查在 apps/rbac/decorators.py（ADR-012）。
    """

    __slots__ = ("_user", "_codes")

    def __init__(self, user):
        self._user = user
        self._codes = None

    def _resolve(self):
        if self._codes is None:
            self._codes = get_user_perm_codes(self._user)
        return self._codes

    def __contains__(self, code):
        return code in self._resolve()

    def __iter__(self):
        return iter(self._resolve())

    def __len__(self):
        return len(self._resolve())

    def __bool__(self):
        return True          # 见陷阱 4：超管的 __len__ 是 0，但不该被当成假值

    def __repr__(self):
        return f"<LazyPermSet unresolved>" if self._codes is None else f"<LazyPermSet {len(self._codes)}>"


def rbac(request):
    return {"perms": LazyPermSet(getattr(request, "user", None))}
```
</details>

## 九、延伸思考

### 1. ⚠️ 本 tag 最重要的观念（第一节第 3 问的答案）

> **隐藏按钮的用户，照样能删除。**
>
> 模板里隐藏按钮是**体验优化**——让用户不去点一个必然失败的东西。
> 真正的安全边界只有一个：**服务端视图层的权限校验**（`v0.9.0` 做的那个）。
>
> **攻击者不点你的按钮，他直接发请求。**

这是权限系统里**最高频的真实漏洞成因**：开发者在模板里 `{% if %}` 了一下，就以为管住了，忘了在视图上加装饰器。

所以本 tag 的验收里有一条专门的测试（用例 4）：**用无权限账号直接 POST 删除 URL，断言 403。**

**每一个受权限控制的按钮，都必须有一个对应的服务端检查。成对出现，缺一不可。**

自查一遍：你模板里写了几个 `in perms`？视图层有几个 `@require_perm`？数字对得上吗？

### 2. 为什么不用 `{% if_perm %}` 自定义标签？

`in perms` 是 Django 模板原生支持的运算符，不需要 `{% load %}`，模板作者零学习成本；而且和 Django 自带的 `{{ perms.app.codename }}` 心智一致。

但自定义 tag 有一个优势：**可以在标签内部校验权限码是否存在**，typo 时直接报错而不是静默失败（陷阱 3）。

想想：这个优势值不值得放弃 `in` 的自然语法？如果你选了 tag 方案，`--check-templates` 就不需要了——两条路解决同一个问题，成本各在哪？

### 3. 前端隐藏 vs 后端不返回

现在的做法是「后端返回了完整数据，前端决定显不显示」。另一种做法是「后端根据权限决定返回什么」。

对模板渲染来说两者差别不大（都在服务端）。但到了 `v1.2.0` 做 API 时，这个区别就大了：API 返回的 JSON 里包含用户无权查看的字段吗？

（提示：这就是**字段级权限**，PRD 明确列为非目标。但你应该知道它在哪一层实现——序列化层，而不是 RBAC 层。）

### 4. 到这里，功能权限的三层已经齐了

| 层 | 做了什么 | tag |
| --- | --- | --- |
| 服务端视图层 | 拦截请求 —— **安全边界** | `v0.9.0` |
| 模板层 | 隐藏按钮 —— 体验优化 | `v0.10.0` |
| 菜单层 | 隐藏入口 —— 体验优化 | `v0.11.0` |

**只有第一层是安全的，后两层都只是体验。** 记住这张表。

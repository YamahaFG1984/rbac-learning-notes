## 五、⚠️ 容易写错的地方

### 🔴 1. JWT 的「无状态」是把双刃剑

第一节第 3 问的答案：**能。**

JWT 是自包含的——服务端不查库就能验证它。这带来了性能优势，但也意味着：

> **签发出去的 token，在过期前无法撤销。**

用户被禁用、角色被改、密码被重置——手里的 access token 照样能用，直到过期。

**缓解手段**：

| 手段 | 说明 |
| --- | --- |
| 缩短 access 有效期 | 30 分钟（我们的配置）。风险窗口 = 有效期 |
| refresh token 黑名单 | `BLACKLIST_AFTER_ROTATION`，撤销 refresh 能阻止续期 |
| 每次请求查一次用户状态 | **牺牲了无状态**，但安全 |

⚠️ **`simplejwt` 的 `JWTAuthentication` 默认会查库取 user**（因为 `request.user` 需要一个真实对象），并且会检查 `is_active`。所以禁用用户**其实会被挡住**——但这依赖于 `USER_AUTHENTICATION_RULE` 的默认实现。

**亲自验证一下**：拿到 token → 禁用用户 → 用 token 调接口 → 看是 401 还是 200。

这是 JWT 最重要的认知点：**它的「无状态」在实际实现里往往是打折的**，而打折的地方正是安全和性能的取舍点。

### 2. 不要在 JWT payload 里塞权限列表

看起来很诱人：把用户的权限码放进 token，前端和后端都不用查库了。

**千万别。**

| 问题 | 说明 |
| --- | --- |
| 权限变更完全失效 | token 里的权限是签发时的快照，改了角色也没用，直到 token 过期 |
| token 体积膨胀 | 200 个权限码 = 几 KB，每个请求都要带 |
| 暴露内部结构 | JWT 的 payload 是 base64，**不是加密**，任何人都能解开看 |

**权限必须在服务端实时判断**（走我们的 `services.py` + 缓存）。这正是 `v1.2.0` 要做的。

### 3. API 和 Web 并存，不要互相污染

第一节第 1 问。

**并存的教学价值**：同一套业务逻辑、同一套权限内核，服务两种完全不同的表现层。这是验证 [ADR-013](../02-设计文档.md#adr-013权限内核与表现层解耦让模板和-api-共用同一套判断) 解耦是否成功的唯一方法。

技术上要注意：
- API 路由不能触发 Web 的 CSRF（JWT 认证的请求 DRF 会跳过 CSRF）
- Web 的 `LOGIN_URL` 重定向不该影响 API（API 应该返回 401 JSON，不是 302）
- 两者共用 Model、共用 `services.py`，**不共用 View 和 Form**

### 4. Serializer 的字段也要用白名单

```python
class UserSerializer(serializers.ModelSerializer):
    class Meta:
        model = User
        fields = ["id", "username", "real_name", "phone", "email",
                  "department", "is_active"]        # ✅ 白名单
        # exclude = ["password"]                    # ❌ 黑名单
```

**和 `v0.18.0` 洞 1 是同一个道理**——黑名单会随时间劣化。而且 API 的风险更大：Web 表单至少还有个界面，API 是直接暴露的。

⚠️ 特别注意：`ModelSerializer` 的 `fields = "__all__"` 是最危险的写法。它会把 `is_superuser`、`password` 全都暴露出去。**永远不要用。**

### 5. 分页、过滤、排序要和 Web 层行为一致

如果 Web 列表页默认按 `-created_at` 排序、每页 20 条，API 也应该一样。不一致会让前端和后端对不上账。

### 6. 本 tag 不要做授权

`DEFAULT_PERMISSION_CLASSES` 先用 `IsAuthenticated`。

看到 ViewSet 就想加 `permission_classes` 是很自然的冲动，**忍住**——理由和 `v0.13.0` 一样：让 `v1.2.0` 的 diff 只包含「权限内核复用」这一件事。

## 九、⚠️ 关于本 tag 刻意留下的漏洞

用 `no_role` 账号（什么权限都没有）换一个 token，然后：

```bash
curl -X DELETE http://127.0.0.1:8000/api/v1/tickets/1/ -H "Authorization: Bearer $TOKEN"
# → 204 No Content   工单被删了
```

**一个没有任何权限的用户，删掉了一张不属于他的工单。**

### 这是有意的

Web 层花了 11 个 tag 建立的权限体系（`v0.9.0` 视图鉴权、`v0.14.0` 数据权限），在 API 层**一个都没生效**。

这个状态展示了一个真实的、常见的失败模式：

> **团队做了完善的后台权限系统，然后为了对接前端/小程序/开放平台加了一套 API——而 API 走的是另一条代码路径。**

如果这时候有人在 API 层「重新实现一遍」权限逻辑，两套逻辑必然漂移，漏洞就在漂移处诞生。

### `v1.2.0` 的解法

不重新实现。**直接复用 `services.py`**——那个从 `v0.6.0` 开始就不许 import `django.http` 的模块。

现在你该明白那条约束的价值了。

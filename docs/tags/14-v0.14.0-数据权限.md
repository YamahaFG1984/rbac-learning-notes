## 五、⚠️ 容易写错的地方

### 🔴 1. 四处「默认拒绝」

这是本 tag 的重中之重。`build_scope_q()` 里有四个分支，**每一处写反都是严重越权**：

| # | 情形 | 必须返回 | 写成 `Q()` 的后果 |
| --- | --- | --- | --- |
| 1 | 未登录 / 已禁用 | `Q(pk__in=[])` | **匿名用户看到全部数据** |
| 2 | **无任何角色** | `Q(pk__in=[])` | **新建用户默认看到全公司数据** |
| 3 | 所有角色的 scope 都无法识别（脏数据） | `Q(pk__in=[])` | 脏数据导致权限完全失效 |
| 4 | 用户无所属部门 | `Q(pk__in=[])` | 无部门用户绕过所有部门限制 |

```python
Q()             # 空条件 → 不过滤 → 返回全集   ❌
Q(pk__in=[])    # 不可满足条件 → 返回空集     ✅
```

**差两个字符，安全后果天差地别。**

情形 2 尤其危险：它是**最常见的状态**（新建用户还没配角色），而且后果最严重。

> **默认拒绝（deny by default）是权限系统的第一原则。**
> 这四个分支在正常使用中**永远不会被触发**——所以**只有测试能保证它们是对的**。
> 每一处都必须有对应的测试用例。

### 🔴 2. 多角色的数据范围要做**真并集**，不是「取最宽枚举」

第一节第 3 问的答案。

```python
# ❌ 取最宽枚举：CUSTOM 参与时会丢数据
widest = min(role.data_scope for role in roles)
# 角色A=SELF_ONLY(4), 角色B=CUSTOM(5) → min=4 → 只看到自己的，丢了市场部

# ✅ 真并集
q = Q()
for role in roles:
    q |= translate(role)           # Q(creator=user) | Q(department__in=[市场部子树])
```

**为什么必须是并集？** 因为 RBAC 的基本语义就是「多角色权限取并集」（FR-4.1）。数据范围是权限的一部分，没有理由用不同的合并规则。

> 若依（RuoYi）等主流国产后台用的是「取最宽枚举」。这是一个**已知的、我们刻意偏离的**实现差异。差异的原因就在上面。

**短路优化是可以的**：只要有任一角色是 `ALL`，直接 `return None`，跳过其余计算。这不影响正确性（`ALL` 本来就是最大集合）。

### 3. 过滤必须下推到 SQL（NFR-2）

```python
# ❌ 先查全量再在 Python 里筛 —— 10 万条数据会直接把内存打爆
[t for t in Ticket.objects.all() if can_see(user, t)]

# ✅ 生成 Q 对象交给 ORM
Ticket.objects.filter(q)
```

**验证方法**：打印 `str(queryset.query)`，确认过滤条件出现在 `WHERE` 子句里。

### 4. 坚决不用隐式过滤（thread-local）

第一节第 6 问的答案。看起来很美：

```python
# ❌ 重写默认 Manager，从 thread-local 拿 request.user 自动过滤
class TicketManager(models.Manager):
    def get_queryset(self):
        return super().get_queryset().for_user(get_current_user())
```

业务代码零改动，写 `Ticket.objects.all()` 就自动安全了。**但这是生产事故的常见来源**：

| 问题 | 说明 |
| --- | --- |
| Celery / 管理命令 / 定时脚本 | 没有 request，thread-local 是空的。返回全集（危险）还是空集（任务全挂）？两个答案都不对 |
| 测试 | 没有 request，要么每个测试 mock thread-local，要么测的根本不是生产路径 |
| 异步（ASGI） | Django 5.2 的 async view 里，同一线程可能服务多个并发请求，thread-local 会串。改用 `contextvars` 也不保证第三方库配合 |
| **最根本的** | **它让「这个查询有没有被过滤」变得不可见。** 读到 `Ticket.objects.all()` 时，你无法判断它返回什么 |

> **显式优于隐式**——这条 Python 之禅在安全代码里不是风格偏好，是硬要求。
> **你应该能通过 `grep` 找出所有绕过数据权限的查询。** 隐式方案让这件事变得不可能。

代价是「可能忘记调用 `.for_user()`」。我们不假装这个代价不存在——我们用测试和 Mixin 缓解它。

> **在安全工程里，可观测的风险优于隐形的保证。**

### 5. `get_user_dept_ids` 返回集合，不是单值

```python
def get_user_dept_ids(user, include_children=True) -> set[int]:
```

现在用户只有一个部门（FR-1.4 的简化），返回单元素集合看起来很傻。

**但这是刻意的**：将来支持兼岗时，只需改这一个函数，调用方全都不用动。

注意分寸——我们**预留了形状，但没有预先实现**。这和过度设计的区别在于：预留形状的成本是 0（就是个返回类型的选择），而预先实现兼岗的成本是一整套模型改造。

### 6. 超管短路要在最前面

```python
if user.is_superuser:
    return None          # 不过滤
```

放在函数开头，在任何查询之前。否则超管也会白白走一遍角色展开。

<details>
<summary><b>提示 1：build_scope_q 完整骨架</b></summary>

```python
def build_scope_q(user, cfg) -> Q | None:
    """构造数据范围过滤 Q。返回 None 表示不过滤。

    ⚠️ 本函数有四处「默认拒绝」，每一处都必须返回空集而非空条件。
       Q() 是不过滤（全集），Q(pk__in=[]) 才是空集。详见 ADR-007。
    """
    # 默认拒绝 1：未登录 / 已禁用
    if not user or not user.is_authenticated or not user.is_active:
        return Q(pk__in=[])

    if user.is_superuser:
        return None

    roles = expand_roles(Role.objects.filter(user_roles__user=user, is_active=True))

    # 默认拒绝 2：无任何角色（最常见也最危险的情形）
    if not roles:
        return Q(pk__in=[])

    owner_f, dept_f = cfg.owner_field, cfg.dept_field
    q, matched = Q(), False

    for role in roles:
        scope = role.data_scope
        if scope == DataScope.ALL:
            return None                                   # 短路：最宽范围

        if scope == DataScope.DEPT_AND_BELOW:
            ids = get_user_dept_ids(user, include_children=True)
            sub = Q(**{f"{dept_f}_id__in": ids})
        elif scope == DataScope.DEPT_ONLY:
            ids = get_user_dept_ids(user, include_children=False)
            sub = Q(**{f"{dept_f}_id__in": ids})
        elif scope == DataScope.SELF_ONLY:
            sub = Q(**{f"{owner_f}_id": user.pk})
        elif scope == DataScope.CUSTOM:
            sub = Q(**{f"{dept_f}_id__in": get_role_custom_dept_ids(role)})   # v0.15.0
        else:
            continue                                      # 脏数据，跳过

        q |= sub                                          # ⚠️ 真并集，不是取最宽
        matched = True

    # 默认拒绝 3：所有角色的 scope 都不可识别
    if not matched:
        return Q(pk__in=[])

    extra = getattr(cfg, "extra_q", None)                 # ABAC 扩展点
    if extra:
        q &= extra(user)
    return q


def get_user_dept_ids(user, include_children: bool = True) -> set[int]:
    """返回集合而非单值——为将来的兼岗（一人多部门）预留形状。"""
    dept = getattr(user, "department", None)
    # 默认拒绝 4：用户无部门
    if dept is None:
        return set()
    if not include_children:
        return {dept.id}
    return set(
        Department.objects.filter(path__startswith=dept.path, is_active=True)
        .values_list("id", flat=True)
    )
```

⚠️ 注意 `DEPT_AND_BELOW` 和 `DEPT_ONLY` 都用了 `__in` 和集合——统一形式，为兼岗预留。
</details>

```python
# apps/common/managers.py
class DataScopedQuerySet(models.QuerySet):
    def for_user(self, user):
        """按用户的数据范围过滤。

        ⚠️ 必须显式调用。本项目坚决不做隐式/thread-local 自动过滤，
           理由见 ADR-009。
        """
        cfg = getattr(self.model, "ScopeConfig", None)
        if cfg is None:
            raise ImproperlyConfigured(
                f"{self.model.__name__} 使用了 DataScopedQuerySet 但未定义 ScopeConfig"
            )
        q = build_scope_q(user, cfg)
        return self if q is None else self.filter(q)
```

那个 `ImproperlyConfigured` 很重要——**配置错误要在第一次调用时立刻炸掉**，而不是静默地返回全集。

## 九、延伸思考

1. **功能权限和数据权限必须彻底分离**（第一节第 1 问）

   | | 功能权限 | 数据权限 |
   | --- | --- | --- |
   | 结果 | 布尔值 | 集合（SQL 的 WHERE） |
   | 位置 | 视图层装饰器 | Manager 层 |
   | 时机 | 进入视图前 | 构造 QuerySet 时 |
   | 绕过的后果 | 垂直越权 | 水平越权 |

   > **试图用一套机制表达两者，是权限系统腐化的头号原因。**

   自查：你的 `build_scope_q` 里有没有混进「这个人能不能删」这类判断？

2. **我们的 `data_scope` 在理论上属于 ABAC**（[理论基础 6.3](../00-RBAC理论基础.md)）——它是基于主体属性（用户部门）和资源属性（工单部门）的匹配规则。

   但它是一个**被刻意退化的 ABAC**：只有两个属性、五个预定义值。这个退化换来三样东西：可配置（管理员点几下就行）、可下推 SQL、可审计（能回答「这个角色能看哪些数据」）。

   想想：如果换成通用的 ABAC 策略引擎（Casbin / OPA），这三样各自会怎样？

3. **`extra_q` 扩展点是通往 ABAC 的门，但我们只开了一条缝。**

   什么样的需求该用它？（比如「只能看未归档的工单」）什么样的需求不该用？（比如「周末不能看」——那是环境属性，塞进 `extra_q` 会让它不可审计）

   想想这条缝开多大合适。开太大，你就重新发明了一个策略引擎；不开，遇到稍微特殊的需求就没辙。

4. **`Q(pk__in=[])` 生成的 SQL 长什么样？** 打印出来看看。Django 会不会聪明到直接返回空而不查库？（提示：试试 `EmptyQuerySet` 和 `qs.none()`，比较三者）

5. **现在只有 `Ticket` 接入了数据权限。** 如果有 20 个业务模型都要接入，你会怎么降低重复？（提示：抽一个 `DataScopedModel` 抽象基类？还是保持现在的「显式声明 ScopeConfig」？想想哪种更难被误用。）

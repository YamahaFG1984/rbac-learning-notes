## 五、⚠️ 容易写错的地方

### 1. 步骤顺序：先设 `AUTH_USER_MODEL`，再 `makemigrations`

如果你先 `makemigrations` 再改 settings，Django 会以 `auth.User` 为准生成一堆错误的外键。

**判断你有没有踩坑的方法**：打开 `apps/accounts/migrations/0001_initial.py`，看它有没有把 `AbstractUser` 的全部字段（`username`、`password`、`is_superuser`……）都列出来。列出来了才对——说明 Django 知道这是一个**具体的**用户模型，而不是继承关系。

### 2. `related_name` 冲突

`AbstractUser` 继承自 `PermissionsMixin`，后者带了 `groups` 和 `user_permissions` 两个 M2M 字段。绝大多数情况下不用管，但如果你在同一个项目里有第二个继承 `PermissionsMixin` 的模型，就会报 `related_name` 冲突。

本项目只有一个用户模型，不会遇到。但你应该知道这个报错长什么样、为什么。

### 3. 不要新增 `is_superadmin` 字段

复用 Django 自带的 `is_superuser`（第一节第 4 问）。

理由：多一个语义重叠的字段，就多一处「两个字段不一致时听谁的」的 bug 温床。而且 Django 生态（admin、`ModelBackend`、`createsuperuser`）都认 `is_superuser`——你新建一个字段，等于要在所有地方同步维护两套。

### 4. `is_staff` 的语义要在代码里写清楚

`is_staff` **只**控制「能不能登录 Django admin」，和我们的 RBAC 体系毫无关系。

这个字段名太容易被误读成「是不是员工」。**在模型里加一行注释说明**，否则三个月后一定有人拿它当业务字段用。

### 5. 别删 `first_name` / `last_name`

它们确实用不上（我们用 `real_name`），但删除继承来的字段需要重写整个字段定义，得不偿失。留着，空着，加注释说明不用。

**这是一个「接受小冗余，换取不折腾」的取舍**——和 ADR-002 里说的是同一个道理。

## 六、卡住了看这里（渐进提示）

<details>
<summary><b>提示 1：User 模型骨架</b></summary>

```python
from django.contrib.auth.models import AbstractUser
from django.db import models


class User(AbstractUser):
    """系统用户。

    继承 AbstractUser 而非 AbstractBaseUser：保留 Django 全套认证机制
    （UserManager、密码哈希、REQUIRED_FIELDS），只增量添加业务字段。
    详见 ADR-002。

    注意：继承来的 is_staff 仅控制能否登录 Django admin，
    与本系统的 RBAC 权限体系无关，业务代码不要使用它。
    继承来的 first_name / last_name 不符合中文姓名习惯，一律留空，用 real_name。
    """

    real_name = models.CharField("姓名", max_length=32, blank=True)
    phone = models.CharField("手机号", max_length=20, blank=True)
    last_login_ip = models.GenericIPAddressField("最后登录IP", null=True, blank=True)

    class Meta:
        verbose_name = "用户"
        verbose_name_plural = verbose_name
        ordering = ["id"]

    def __str__(self):
        return self.real_name or self.username
```
</details>

<details>
<summary><b>提示 2：admin 注册</b></summary>

```python
from django.contrib import admin
from django.contrib.auth.admin import UserAdmin as BaseUserAdmin
from .models import User


@admin.register(User)
class UserAdmin(BaseUserAdmin):
    # 继承 BaseUserAdmin 才能得到密码修改表单等特殊处理
    fieldsets = BaseUserAdmin.fieldsets + (
        ("业务信息", {"fields": ("real_name", "phone", "last_login_ip")}),
    )
    list_display = ("username", "real_name", "phone", "is_active", "is_superuser")
```

注意必须继承 `BaseUserAdmin`。直接 `admin.site.register(User)` 的话，密码字段会变成明文输入框——admin 会把哈希串原样存进去，账号就废了。
</details>

## 九、延伸思考

1. **如果需求变成「用手机号登录」，本 tag 要怎么改？** 这时 `AbstractUser` 还够用吗？（提示：`USERNAME_FIELD`、`REQUIRED_FIELDS`、以及 `username` 字段的 unique 约束怎么处理）

2. `AbstractUser` 里的 `PermissionsMixin` 带来了 `groups` 和 `user_permissions` 两个 M2M——**这正是 Django 自带的权限体系**（[ADR-001](../02-设计文档.md#adr-001不使用-djangocontribauthpermission自建权限模型) 决定弃用的那套）。

   问题来了：既然要弃用，为什么不干脆不继承 `PermissionsMixin`？

   <details>
   <summary>我的答案</summary>

   因为 `is_superuser` 字段就在 `PermissionsMixin` 里，`has_perm()` / `has_module_perms()` 这些方法也在。我们要在 `v0.9.0` 通过自定义 authentication backend 接管 `has_perm()`，让 Django admin 和第三方代码继续可用——这需要这些方法存在。

   代价是数据库里会多出 `auth_permission`、`auth_group` 等表且始终为空。**这是「兼容性」和「洁净度」之间的取舍**，我们选了兼容性。
   </details>

3. 查一下 Django 5.x 新增的 `django.contrib.auth.hashers` 默认哈希器是什么，迭代次数多少。想想为什么密码哈希要「故意慢」。

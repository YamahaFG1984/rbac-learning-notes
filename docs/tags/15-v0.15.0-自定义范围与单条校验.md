## 五、⚠️ 容易写错的地方

### 🔴 1. 单条获取必须走 `.for_user()`，不能「先取出再判断」

第一节第 3 问的答案。写法 B 有**两个**问题：

**问题一：重复实现了范围判断逻辑。**

```python
if ticket.department != request.user.department:      # 这是 DEPT_ONLY 的规则
```

但用户的角色可能是 `DEPT_AND_BELOW`、`SELF_ONLY` 或 `CUSTOM`。这行判断和 `build_scope_q` 的规则**迟早会不一致**——而不一致的那一刻，就是漏洞诞生的时刻。

> **`CLAUDE.md` 安全红线第 5 条：权限规则只能有一处实现。**

**问题二：返回 403 泄露了记录的存在性。** 见下一条。

正确写法只有一种：

```python
ticket = get_object_or_404(Ticket.objects.for_user(request.user), pk=pk)
```

范围内找得到 → 正常；找不到 → 404。**一行代码同时解决了「存在性」和「权限」两件事。**

### 🔴 2. 范围外返回 404，不是 403

第一节第 2 问的答案。

- **403 的含义**：「这东西存在，但你没权限」→ 泄露了记录存在性。
- **404 的含义**：「对你而言，这东西不存在」→ 信息最小泄露。

**攻击场景**：攻击者遍历 ID `1..10000`，根据 403/404 的差异，就能画出整个数据库的 ID 分布——哪些 ID 存在、哪些是空洞。结合业务语义（比如订单号连续），还能推算出业务规模。

这是 OWASP 明确建议的做法：**对未授权资源，不要泄露它是否存在。**

⚠️ 注意区分两种 403：
- 「你没有 `ticket:ticket:view` 权限」→ **403**（功能权限，不涉及具体记录）
- 「这条记录不在你的数据范围内」→ **404**（数据权限）

两者的信息泄露风险完全不同。

### 3. 自定义部门要含子树

第一节第 4 问。

管理员勾选「客服部」时，他的意图几乎肯定是「客服部及其下属」——如果只含本级，那勾选 3 个子部门就要点 4 次，而且新增子部门后还要记得回来补勾。

```python
def get_role_custom_dept_ids(role) -> set[int]:
    depts = Department.objects.filter(role_departments__role=role, is_active=True)
    ids = set()
    for d in depts:
        ids.update(
            Department.objects.filter(path__startswith=d.path, is_active=True)
                              .values_list("id", flat=True)
        )
    return ids
```

⚠️ 这个实现是 N+1（每个勾选的部门一次查询）。勾选数量少时可忍，但想想能不能一次查完。（提示：把所有 path 组合成一个 `Q` 用 `|` 连起来。）

**如果你希望「只含本级」的语义，那必须在界面上写清楚**，否则管理员会配错——而配错的后果是静默的越权或漏权。

### 4. **每一处**都要接入，不能只改列表

FR-7.2 要求覆盖：列表、详情、更新、删除、统计、导出。

数一数工单模块有几个入口：
- 列表 ✅（`v0.14.0` 做了）
- 详情
- 编辑（GET 表单 + POST 提交，**两次**都要）
- 删除
- 派单
- 导出

**漏一个就是一个越权入口。** 这正是 `v0.13.0` 第九节延伸思考 2 说的问题。

⚠️ **编辑视图特别容易漏 POST**：GET 时用 `.for_user()` 拿到对象渲染表单，POST 时却直接 `get_object_or_404(Ticket, pk=pk)`。攻击者直接构造 POST 就绕过了。

用 `ScopedObjectMixin` 重写 `get_queryset()` 可以让 GET/POST 都走同一条路——**这就是用机制而非自觉来保证正确性**。

### 5. 导出要走同一条路

第一节第 5 问：**需要**。

导出是最容易被忽略的越权入口——因为它通常是后加的功能，而且代码路径和列表页不同（不走 ListView）。

```python
qs = Ticket.objects.for_user(request.user)       # 和列表页完全一致
```

**验收标准**：导出的 CSV 行数 == 列表页显示的总数。

### 6. `data_scope` 表单的联动

选 `CUSTOM` 时才显示部门勾选。但要注意：**后端不能信任前端的显隐**。

如果用户选了 `SELF_ONLY` 却提交了一堆部门 ID，你要么忽略它们，要么报错——但不能存进去（存了之后一旦有人改成 `CUSTOM`，就会有意外的范围）。

<details>
<summary><b>提示 2：一次查询取自定义部门子树</b></summary>

```python
from functools import reduce
import operator

def get_role_custom_dept_ids(role) -> set[int]:
    paths = list(
        Department.objects.filter(role_departments__role=role, is_active=True)
                          .values_list("path", flat=True)
    )
    if not paths:
        return set()
    q = reduce(operator.or_, (Q(path__startswith=p) for p in paths))
    return set(
        Department.objects.filter(q, is_active=True).values_list("id", flat=True)
    )
```

2 次查询，与勾选的部门数量无关。
</details>

<summary><b>提示 3：CSV 导出</b></summary>

```python
@require_perm(TicketPerm.EXPORT)
def ticket_export(request):
    qs = Ticket.objects.for_user(request.user).select_related(
        "creator", "assignee", "department"
    )
    response = HttpResponse(content_type="text/csv; charset=utf-8-sig")
    response["Content-Disposition"] = 'attachment; filename="tickets.csv"'
    writer = csv.writer(response)
    writer.writerow(["ID", "标题", "状态", "创建人", "所属部门", "创建时间"])
    for t in qs.iterator():
        writer.writerow([t.id, t.title, t.get_status_display(),
                         t.creator.real_name, t.department.name, t.created_at])
    return response
```

`utf-8-sig`（带 BOM）是为了让 Excel 正确识别中文编码。没有 BOM 的话，用 Excel 打开会是乱码。

## 九、延伸思考

1. **`ScopedObjectMixin` 让 GET/POST 走同一条路**——这是「用机制保证正确性」的又一个例子。

   回顾一下这个模式在本项目出现了几次：
   - `v0.9.0`：启动自检发现漏加装饰器的视图
   - `v0.14.0`：`ScopeConfig` 缺失时抛 `ImproperlyConfigured`
   - 本 tag：Mixin 统一 GET/POST 的 queryset

   **共同点**：都不是「更小心」，而是「让疏漏变得不可能或立即可见」。

2. **404 会不会误伤正常用户？** 一个用户点了收藏夹里的旧链接，工单被转到别的部门了，他看到 404 会困惑。

   想想有没有折中方案？（提示：404 页面上给一句「如果你认为这是权限问题，请联系管理员」。既不泄露信息，又给了用户下一步动作。）

3. **`get_role_custom_dept_ids` 每次都要查两次库。** 一个角色的自定义部门几乎不变，这个结果能缓存吗？

   `v0.16.0` 会加缓存。想想它的失效条件是什么——比权限码的失效条件多了什么？

4. **现在数据权限只在「读」的路径上生效。** 那「写」呢？

   比如：用户能不能创建一张归属于**别的部门**的工单？现在的实现里，`department` 是从 `request.user.department` 快照的（`v0.13.0`），所以不能。

   但如果表单里允许选部门呢？**你需要校验「所选部门必须在用户的数据范围内」。** 这个校验该写在哪一层？（提示：表单的 `clean_department()`，或者收窄字段的 queryset。）

   想想：这算数据权限还是功能权限？（它是数据权限在写路径上的体现——本项目没有实现，是一个已知的简化。）

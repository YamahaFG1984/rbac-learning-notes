## 五、⚠️ 容易写错的地方

### 🔴 1. 只写不改不删

第一节第 3 问。

```python
class AuditLog(models.Model):
    def save(self, *args, **kwargs):
        if self.pk is not None:
            raise RuntimeError("审计日志不可修改")
        super().save(*args, **kwargs)

    def delete(self, *args, **kwargs):
        raise RuntimeError("审计日志不可删除")
```

⚠️ **这只挡得住单对象操作。** `AuditLog.objects.filter(...).delete()` 不走模型的 `delete()`——它是 QuerySet 的方法。

要挡住批量删除，需要自定义 Manager：

```python
class AuditLogQuerySet(models.QuerySet):
    def delete(self):
        raise RuntimeError("审计日志不可删除")
    def update(self, **kwargs):
        raise RuntimeError("审计日志不可修改")
```

**但这仍然挡不住有数据库权限的人。** 所以第一节第 3 问的完整答案是：

> **在应用层做的不可变保护，只能防止「误操作」和「代码里的错误」，防不住「有权限的恶意者」。**
>
> 真正的审计需要**独立存储**：写到日志系统（ELK / Loki）、只追加的表、或 WORM（一次写入多次读取）存储。审计数据和被审计的系统必须由不同的人控制。

这是本项目的一处**已知简化**（设计文档第 9 节第 5 条）。在代码注释里写清楚。

### 🔴 2. 权限变更必须记「变更前后」，不只是「改了什么」

第一节第 2 问。

```python
# ❌ 三个月后这条日志毫无价值
log(AuditAction.ROLE_PERM_SET, actor=request.user, target=role)
# → "张三 在 3月5日 修改了 客服主管 的权限"  ...改成什么了？

# ✅
log(AuditAction.ROLE_PERM_SET, actor=request.user, target=role, detail={
    "before": sorted(old_codes),
    "after": sorted(new_codes),
    "added": sorted(new_codes - old_codes),
    "removed": sorted(old_codes - new_codes),
})
```

**审计日志要能回答的是「当时到底发生了什么」，不是「有人动过」。**

⚠️ 这意味着 `v0.5.0` 的「先删后插」保存逻辑现在不够用了——你需要在删除前把旧集合读出来。

**回想一下 `v0.5.0` 陷阱 2**：我当时说「现在选先删后插没问题，但心里有数这是一处已知会被改的地方」。现在就是那个时候。

**对比一下**：如果你当时用了「差集更新」方案，现在改动量是多少？如果用了「先删后插」，现在改动量是多少？**这就是「什么时候该提前设计、什么时候该等」的实际答案**——在这个例子里，等到现在再改，成本很小（多读一次旧集合），所以当初等是对的。

### 3. 冗余存 `actor_name`

`actor` 是 `SET_NULL` 外键。用户被删除后，日志里的 actor 变成 null——**你就不知道当初是谁操作的了**。

所以要冗余存一份用户名快照。

> 这和 `v0.13.0` 陷阱 1（工单部门快照）是同一个道理：**有历史意义的信息要快照，不能只存引用。**
>
> 审计日志几乎所有字段都该是快照——它记录的是「当时的事实」，不该随着当前状态变化。

同理，`target_repr` 也是快照（角色被删了，你还得知道当初改的是哪个角色）。

### 4. 拒绝访问的日志量

第一节第 4 问。

正常用户很少触发 403（因为菜单和按钮已经隐藏了）。触发 403 通常意味着：
- 有人在探测（**这正是最需要记录的**）
- 权限配置有问题（**这也需要知道**）

所以量不大，且价值高。**记。**

但要防日志刷屏：同一用户短时间内大量 403，可以做聚合或限流。本项目不做，但要知道这个问题存在。

### 5. 记日志不能影响主流程

```python
def log(action, **kwargs):
    try:
        return AuditLog.objects.create(...)
    except Exception:
        logger.exception("审计日志写入失败")
        return None                    # 不要往上抛
```

审计日志写失败，不应该导致用户的正常操作失败。

**但这是有争议的**：在高合规要求的场景（金融），「审计写不进去就不许操作」才是对的。想想你的场景属于哪种。

### 6. `JSONField` 里不要放不可序列化的东西

```python
detail={"before": old_codes}          # ❌ frozenset 不能 JSON 序列化
detail={"before": sorted(old_codes)}  # ✅ list
```

Model 实例、`datetime`、`Decimal`、`set` 都会炸。转成基础类型再存。

<summary><b>提示 2：在装饰器里记拒绝访问</b></summary>

```python
def require_perm(code):
    def decorator(view_func):
        @wraps(view_func)
        def wrapper(request, *args, **kwargs):
            if not user_has_perm(request.user, code):
                audit_log(
                    AuditAction.PERM_DENIED, actor=request.user, result="failure",
                    detail={"path": request.path, "method": request.method,
                            "required_perm": code},
                    ip=get_client_ip(request),
                    user_agent=request.META.get("HTTP_USER_AGENT", ""),
                )
                raise PermissionDenied
            return view_func(request, *args, **kwargs)
        wrapper._required_perm = code
        return wrapper
    return decorator
```

⚠️ 这让 `decorators.py` 依赖了 `apps.audit`。检查依赖方向：`rbac → audit` 是允许的吗？

回看 `CLAUDE.md` 的依赖图：`tickets/audit → rbac → accounts → common`。**`audit` 依赖 `rbac`，不是反过来！**

所以这里有个循环依赖问题。想想怎么解？（提示：signal？还是把 audit 移到更底层？还是用 Django 的 `dispatch` 解耦？）

<details>
<summary>我的做法</summary>

用信号解耦：`rbac` 定义一个 `permission_denied` 信号并发送，`audit` 订阅它。这样 `rbac` 不需要 import `audit`。

```python
# apps/rbac/signals.py
permission_denied = django.dispatch.Signal()

# apps/audit/receivers.py
@receiver(permission_denied)
def _on_denied(sender, user, path, required_perm, **kw): log(...)
```

**信号在这里的作用是「反转依赖方向」**——这是它的另一个恰当用法。

## 九、延伸思考

1. **审计日志的三个经典问题**，想想本项目各自处于什么状态：

   | 问题 | 本项目 | 生产该怎么做 |
   | --- | --- | --- |
   | 日志能被篡改吗 | 应用层保护，DB 权限者可改 | 独立存储 / WORM / 区块链式链式哈希 |
   | 日志会不会撑爆库 | 无归档策略 | 分区表 + 定期归档冷存储 |
   | 日志能查得动吗 | 只有 action 和时间的索引 | 按查询模式建复合索引 / 上 ES |

2. **「谁审计审计者」**：日志查询页本身需要 `system:audit:view` 权限。那么——**谁能给自己分配这个权限？**

   如果一个管理员既能改角色权限、又能看审计日志，他可以：给自己加权限 → 做坏事 → ~~删日志~~（删不掉）→ 但他能看到自己被记录了什么。

   真正的隔离需要**职责分离**（SoD，RBAC2 的内容，见[理论基础 3.3](../00-RBAC理论基础.md)）：审计员角色和管理员角色互斥。

   本项目不做 RBAC2。想想：用现有的机制能部分模拟吗？

3. **`perm_denied` 日志能用来做什么？**

   - 安全监控：同一用户短时间大量 403 → 可能在探测
   - 权限配置诊断：某个权限码频繁被拒 → 可能是角色配少了
   - 界面问题定位：某个按钮频繁 403 → 可能是模板忘了加 `{% if %}`

   **第三条很有意思**：它能帮你发现「模板隐藏和视图校验不成对」的地方（`v0.10.0` 强调的那个问题）。想想怎么把它做成一个自动化的检查。

4. **本 tag 的日志是同步写的。** 高并发下每个请求多一次 INSERT，值得吗？

   异步化的选项：Celery 任务、写本地文件后异步收集、批量缓冲后定时刷。各自的取舍是什么？（提示：异步意味着可能丢日志——对审计来说这可以接受吗？）

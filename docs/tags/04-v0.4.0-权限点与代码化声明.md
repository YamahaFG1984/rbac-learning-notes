## 三、接口契约（必须与我的实现对齐）

### 权限码格式

```
{app}:{resource}:{action}
```

全小写，词内下划线。`action` 取自受控词表：
`view` / `create` / `update` / `delete` / `export` / `import` / `assign` / `assign_perm` / `audit`

### `PermType` 枚举

```python
class PermType(models.TextChoices):
    CATALOG = "catalog", "目录"
    MENU    = "menu",    "菜单"
    BUTTON  = "button",  "按钮"
```

### `Permission` 字段

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `code` | `CharField(128)` | `unique=True, null=True, blank=True`（catalog 为 null） |
| `name` | `CharField(64)` | |
| `perm_type` | `CharField(16)` | `choices=PermType.choices` |
| `parent` | `FK("self")` | `null=True, on_delete=PROTECT, related_name="children"` |
| `path` | `CharField(255)` | `db_index=True, editable=False`，格式同部门树 |
| `order_num` | `SmallIntegerField` | `default=0` |
| `url_name` | `CharField(128)` | `blank=True`，Django URL name，如 `tickets:list` |
| `icon` | `CharField(64)` | `blank=True` |
| `is_visible` | `BooleanField` | `default=True` |
| `is_active` | `BooleanField` | `default=True` |
| `is_deprecated` | `BooleanField` | `default=False` |

`Meta.ordering = ["path"]`。

## 五、⚠️ 容易写错的地方

### 1. `code` 允许 null，但 unique 约束怎么办？

`catalog` 类型没有权限码。多行 `code=NULL` 会不会违反 unique？

**不会** —— SQL 标准规定 `NULL` 不等于任何值（包括另一个 `NULL`），所以 unique 索引允许多行 NULL。SQLite、PostgreSQL、MySQL 行为一致。

但要注意：**不要用空字符串 `""` 代替 NULL**。空串是一个确定的值，第二个 catalog 就会撞唯一约束。

模型里要写 `null=True, blank=True` 两个都有。

### 2. 同步命令必须幂等

「幂等」的操作定义：跑第二次时，输出必须是 `新增 0 个，更新 0 个`。

容易破坏幂等的写法：
- 每次都 `Permission.objects.all().delete()` 再重建 → 主键全变，已有的角色-权限授权全部失效。**这是灾难性的**。
- 用 `get_or_create` 但把 `order_num` 之类的可变字段放进查询条件 → 改了排序就变成新增。

正确做法：以 `code` 为幂等键做 `update_or_create`；`catalog` 没有 code，用 `(parent, name)` 组合作为幂等键。

### 3. 「代码里删了」不要物理删除

```python
# ❌
Permission.objects.exclude(code__in=code_in_code).delete()

# ✅
Permission.objects.exclude(code__in=codes_in_code).update(is_deprecated=True)
```

为什么？如果物理删除，`RolePermission` 里的关联记录也会被级联删掉（或者因 PROTECT 而报错）。而历史授权记录是有价值的——三个月后有人问「这个角色以前有没有导出权限」，你要能答得出来。

废弃的权限点在鉴权时被排除（`v0.6.0` 的查询里会加 `is_deprecated=False`），但数据还在。

### 4. 建树时的父子顺序

同步是递归的，必须**先建父节点拿到实例，再建子节点**。如果你先批量建所有节点再补 parent，会多一轮更新且 path 算不出来。

### 5. 权限码里不要出现大写和连字符

统一小写 + 下划线。混用 `assignPerm` / `assign-perm` / `assign_perm` 的后果是：某天鉴权失败，你 grep 半天找不到，因为大小写差一个字母。

**建议在同步命令里加一条格式校验**，不符合 `^[a-z][a-z0-9_]*:[a-z][a-z0-9_]*:[a-z][a-z0-9_]*$` 的直接报错。让机器帮你守规范。

<details>
<summary><b>提示 2：同步命令的核心循环</b></summary>

```python
def sync_node(node: dict, parent: Permission | None, stats: dict):
    code = node.get("code")
    defaults = {
        "name": node["name"],
        "perm_type": node["type"],
        "parent": parent,
        "order_num": node.get("order", 0),
        "url_name": node.get("url_name", ""),
        "icon": node.get("icon", ""),
        "is_visible": node.get("visible", True),
        "is_deprecated": False,          # 代码里又出现了 → 取消废弃标记
    }
    if code:
        obj, created = Permission.objects.update_or_create(code=code, defaults=defaults)
    else:
        # catalog 无 code，用 (parent, name) 作幂等键
        obj, created = Permission.objects.update_or_create(
            parent=parent, name=node["name"], perm_type=PermType.CATALOG,
            defaults=defaults,
        )
    stats["created" if created else "updated"] += 1

    for child in node.get("children", []):
        sync_node(child, obj, stats)
```

⚠️ `update_or_create` 在「值没变」时也会计入 `updated`。要做到真正的「0 更新」，得先比对再决定是否写。想想怎么实现。

<details>
<summary><b>提示 3：怎么发现所有 app 的 permissions.py</b></summary>

```python
from django.apps import apps
from importlib import import_module

def collect_permissions():
    result = []
    for config in apps.get_app_configs():
        if not config.name.startswith("apps."):
            continue
        try:
            mod = import_module(f"{config.name}.permissions")
        except ModuleNotFoundError:
            continue
        result.extend(getattr(mod, "PERMISSIONS", []))
    return result
```

## 九、延伸思考

1. **「代码声明权限点」这个决定，最大的代价是什么？**

   管理员不能自助添加权限点，加一个要走「改代码 → 提 PR → 部署 → 跑命令」的流程。这在快节奏的团队里会被抱怨。

   但反过来想：如果允许自助添加，管理员可以创建一个 `ticket:ticket:approve`，勾给某个角色，然后以为审批被管控了——**而代码里根本没有任何地方检查这个权限码**。这是「配了但不生效」的**静默失败**，比报错危险一百倍。

   你会怎么向一个抱怨流程慢的产品经理解释这个取舍？

2. **字段级权限**（第一节第 3 问的第三小问）我们明确不做（PRD 的 `NG` 清单）。想想如果真要做，权限点数量会是多少？管理界面会变成什么样？实现上要侵入哪一层？

3. `sync_permissions` 现在只处理新增/更新/废弃。**如果一个权限码要改名怎么办？**（比如 `ticket:ticket:assign` 改成 `ticket:ticket:dispatch`）现在的实现会：把旧的标记废弃 + 新建一个 → **所有角色对这个权限的授权都丢了**。

   想想怎么支持「重命名」而不丢授权。（提示：声明里加一个 `renamed_from` 字段？还是走数据迁移？两者的可靠性差别在哪？）

4. 现在权限点的 `url_name` 是给服务端渲染用的。到了 `v1.2.0` 做 API 时，前端需要的是路由 `path` 和组件名。**同一张表要同时服务两种前端形态**，你打算怎么设计？

## 五、⚠️ 要点

### 🔴 1. 不要重新实现任何判断逻辑

```python
# ❌ 在 API 层重新写一遍
class HasPerm(BasePermission):
    def has_permission(self, request, view):
        roles = Role.objects.filter(user_roles__user=request.user)
        codes = Permission.objects.filter(role_permissions__role__in=roles)...
        return required in codes

# ✅ 调统一内核
class HasPerm(BasePermission):
    def has_permission(self, request, view):
        code = view.perm_map.get(view.action)
        return code is None or user_has_perm(request.user, code)
```

**两套逻辑必然漂移。** 今天你在 Web 层加了「已废弃的权限点不生效」，忘了在 API 层加——漏洞就在那里。

> **`CLAUDE.md` 安全红线第 5 条：权限规则只能有一处实现。**

### 2. `perm_map` 里没有的 action 怎么办？

```python
code = view.perm_map.get(view.action)
return code is None or user_has_perm(request.user, code)
```

上面这个写法：没配就**放行**。这是「默认允许」——**违反了本项目的第一原则**。

正确的做法应该是「没配就拒绝」，或者至少**在启动时检查每个 ViewSet 的 `perm_map` 是否覆盖了它的全部 action**。

**这是 `v0.9.0` 的 `rbac.W001` 自检在 API 层的对应物。** 想想怎么实现：

<details>
<summary>思路</summary>

扩展 `apps/rbac/checks.py`：遍历 router 注册的 ViewSet，对比 `get_extra_actions()` + 标准 action 集合与 `perm_map` 的键集合，差集报 `rbac.W002`。

或者更严格：`HasPerm` 里没配就返回 `False`，让漏配立刻表现为 403（而不是静默放行）。

**我推荐后者 + 自检双保险。** 静默放行是最糟的失败模式。
</details>

### 3. 自定义 action 容易漏

```python
@action(detail=True, methods=["post"])
def assign(self, request, pk=None): ...
```

`perm_map` 里忘了加 `"assign"` → 按要点 2 的默认放行逻辑，**这个接口就裸奔了**。

自定义 action 是漏配的重灾区，因为它们不在标准的 CRUD 列表里。

### 4. 数据权限：`get_queryset()` 一处解决

```python
class ScopedQuerysetMixin:
    def get_queryset(self):
        return super().get_queryset().for_user(self.request.user)
```

**DRF 的所有单对象操作（retrieve / update / destroy）都走 `get_object()`，而 `get_object()` 内部调用 `get_queryset()`。**

所以重写 `get_queryset()` 一处，就同时保护了列表和所有单对象操作——`v0.15.0` 在 Web 层要挨个改视图的活，在 DRF 里一次搞定。

⚠️ 但要验证 `get_object()` 找不到时返回的是 **404**（DRF 默认行为），不是 403。

### 5. `/auth/profile` 直接调内核

```python
@api_view(["GET"])
def profile(request):
    user = request.user
    codes = get_user_perm_codes(user)
    return Response({
        "user": UserProfileSerializer(user).data,
        "perms": sorted(codes) if not user.is_superuser else ["*"],
        "menus": get_user_menu_tree(user),
    })
```

**注意 `get_user_menu_tree()` 是模板层用的同一个函数**（`v0.11.0` 写的）。它返回 `list[dict]`，正好能直接 JSON 序列化——`v0.11.0` 契约里让你返回 dict 而不是 model 实例，伏笔在这里。

⚠️ 超管的处理：`ALL_PERMS` 哨兵不能 JSON 序列化。返回 `["*"]` 让前端知道「全部放行」，或者返回数据库里的全部权限码。**两种做法前端的处理逻辑不同，要和前端约定好。**

### 6. `menus` 里的 url 是 Django 路径，前端要的是前端路由

`get_user_menu_tree()` 返回的 `url` 是 `reverse()` 出来的 Django URL（`/tickets/`）。前端路由可能是 `/system/ticket`。

**本项目不解决这个问题**（PRD 的 `NG-6`：不做前端工程）。但要知道它存在，并想想有哪些解法：
- `Permission` 加一个 `route_path` 字段
- 约定 Django URL 和前端路由同构
- 前端自己维护映射表

## 六、卡住了看这里（渐进提示）

<details>
<summary><b>提示 1：HasPerm（完整实现，就这么短）</b></summary>

```python
from rest_framework.permissions import BasePermission
from apps.rbac.services import user_has_perm


class HasPerm(BasePermission):
    """基于 view.perm_map 的功能权限校验。

    ⚠️ 本类不包含任何权限判断逻辑——它只是把 DRF 的调用约定
       翻译成对统一内核 user_has_perm() 的调用。
       Web 层的 @require_perm 装饰器做的是同一件事（ADR-013）。
    """

    message = "权限不足"

    def has_permission(self, request, view):
        perm_map = getattr(view, "perm_map", None)
        if perm_map is None:
            return True                      # 该 view 不受权限管控（需显式声明）

        action = getattr(view, "action", None)
        if action is None:
            return True                      # 非 ViewSet

        if action not in perm_map:
            # 默认拒绝：漏配 perm_map 表现为 403，而不是静默放行
            return False

        code = perm_map[action]
        return code is None or user_has_perm(request.user, code)
```

**17 行。** 其中 0 行是权限判断逻辑。
</details>

<details>
<summary><b>提示 2：ScopedQuerysetMixin（4 行）</b></summary>

```python
class ScopedQuerysetMixin:
    """数据范围过滤。

    DRF 的 get_object() 内部走 get_queryset()，所以重写一处
    即可同时保护 list / retrieve / update / destroy。
    """
    def get_queryset(self):
        return super().get_queryset().for_user(self.request.user)
```
</details>

## 九、终章：回看这条约束的完整生命周期

`v0.6.0` 创建 `services.py` 时，我们定了一条约束：

> **不得 import 任何 `django.http` / DRF 的东西，函数不接收 `request` 参数。**

当时它看起来是纯粹的负担——为什么不能直接传 `request` 呢？多方便啊。

之后 13 个 tag，每一次写内核函数时都要多想一步：这个信息该从哪来？能不能不依赖 request？

**现在收益兑现了**：接入一整套全新的表现层，只写了两个类、约 60 行代码，其中 0 行是权限逻辑。

> **好的架构约束，收益总是延迟兑现的。**
> 这也正是它们容易在中途被放弃的原因——**每次违反约束，当下都能省几行代码，代价要到很久以后才付。**
>
> 而当代价真正到来时，通常已经没人记得是哪次「省事」造成的了。

### 三个刻意中间态的完整闭环

| tag | 缺什么 | 在哪补上 | 学到了什么 |
| --- | --- | --- | --- |
| `v0.8.0` | 菜单写死 | `v0.11.0` | tag 切分要让 diff 讲故事 |

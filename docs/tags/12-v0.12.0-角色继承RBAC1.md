## 五、⚠️ 容易写错的地方

### 1. 环检测必须在 `clean()` 里，而且视图要调 `full_clean()`

```python
def clean(self):
    super().clean()
    if not self.inherits_from_id:
        return
    if self.pk and self.inherits_from_id == self.pk:
        raise ValidationError({"inherits_from": "角色不能继承自己"})

    seen, cur, depth = {self.pk}, self.inherits_from, 0
    while cur is not None:
        if cur.pk in seen:
            raise ValidationError({"inherits_from": "检测到角色继承环"})
        depth += 1
        if depth >= settings.RBAC_MAX_ROLE_DEPTH:
            raise ValidationError({"inherits_from": f"继承深度不得超过 {settings.RBAC_MAX_ROLE_DEPTH} 层"})
        seen.add(cur.pk)
        cur = cur.inherits_from
```

⚠️ **`ModelForm.is_valid()` 会自动调 `full_clean()`，但 `Model.save()` 不会。** 如果你在 shell 或管理命令里直接 `role.save()`，环检测不会触发。

想想：要不要在 `save()` 里也调一次 `full_clean()`？（代价是每次保存多一轮校验；收益是任何路径都挡得住。这是 `v0.3.0` 陷阱 5「用约束而非检查」的同一类问题。）

### 2. `expand_roles()` 里必须有 visited 集合

```python
result, stack = set(), list(roles)
while stack:
    role = stack.pop()
    if role in result:        # ← 这个判断同时做了两件事
        continue
    ...
```

`visited` 集合同时起两个作用：
- **防环**：即使数据库里因为某种原因存在了环（比如绕过 `clean()` 直接改库），展开也不会死循环。
- **去重剪枝**：两个角色共享同一个祖先时，祖先只展开一次。

**纵深防御**：`clean()` 防止环被存进去，`expand_roles()` 防止已存在的环导致死循环。两道独立的防线。

### 3. 深度限制不只是防死循环

第一节第 5 问的答案：

> **5 层以上的角色继承链，人已经无法在脑内推演了。**
>
> 深度限制是在保护**可运维性**，不只是保护程序。

当有人问「张三为什么能删工单」，答案是「张三 → 客服主管 → 客服专员 → 普通员工 → [该权限]」。这条链有 4 环还能讲清楚，有 10 环就没人听得懂了。

### 4. 表单的父角色下拉要排除后代

```python
# ❌ 只排除自己，选了自己的后代就成环
qs = Role.objects.exclude(pk=self.instance.pk)

# ✅ 排除自己 + 所有后代
```

怎么找后代？`Role` 没有 `path` 字段（不像 `Department`）。你需要沿 `inheritors` 反向遍历。角色数量少，递归可以接受。

**或者**：不排除，靠 `clean()` 挡住，报错给用户看。哪种体验更好？（提示：能不给用户选择错误选项的机会，就不要让他选完再报错。）

### 5. 不要物化继承结果

第一节第 6 问。

```python
# ❌ 保存角色时，把继承来的权限也写进 RolePermission
```

**为什么不？** 物化让查询快一次，但代价是：父角色权限变更时，要重算所有后代角色的物化数据。这个重算一旦漏了或失败，就出现「数据库里的权限和规则不一致」——而且这种不一致是**静默的**，没有任何人会发现。

运行时计算 + 缓存（`v0.16.0`），用缓存版本号保证一致性，是更安全的组合。

> **一般原则**：可以从规则推导出来的数据，不要物化存储，除非性能上真的扛不住。
> 物化的代价不是空间，是**一致性维护**——而一致性 bug 是最难发现的一类 bug。

### 6. 权限分配页要区分「直接」和「继承」

管理员看到一堆勾选，必须能分清哪些是这个角色自己的、哪些是继承来的。

继承来的应该是**只读**（灰色 + `disabled`）——不能在子角色里取消一个继承来的权限（那需要「负权限」，本项目不做，见 `v0.6.0` 延伸思考 2）。

⚠️ `disabled` 的 checkbox **不会被提交**。所以保存时要注意：不要因为它没提交就把它当成「取消勾选」。

<details>
<summary><b>提示 1：expand_roles</b></summary>

```python
def expand_roles(roles: Iterable[Role]) -> set[Role]:
    """展开为「直接角色 + 全部祖先角色」。

    单继承使得这是一次简单的向上遍历。
    visited 集合同时防环（即使库里有脏数据）和去重剪枝。
    """
    result: set[Role] = set()
    for role in roles:
        if role in result or not role.is_active:
            continue
        result.add(role)
        cur, depth = role.inherits_from, 0
        while cur is not None and depth < settings.RBAC_MAX_ROLE_DEPTH:
            if cur in result:
                break                       # 剪枝：这条链上面都展开过了
            if cur.is_active:
                result.add(cur)
            cur = cur.inherits_from
            depth += 1
    return result
```

⚠️ 这个实现每走一步 `cur.inherits_from` 都是一次数据库查询。角色数少时可以忍，`v0.16.0` 会改成「全量角色加载进内存」的零查询版本。**现在别优化。**

<details>
<summary><b>提示 3：权限来源溯源</b></summary>

```python
def get_role_perm_sources(role) -> dict[str, Role]:
    """权限码 → 授予它的角色。

    从最远的祖先开始往回填，这样直接授予的会覆盖继承来的，
    显示时优先展示「最近的来源」。
    """
    chain = []
    cur, depth = role, 0
    while cur is not None and depth < settings.RBAC_MAX_ROLE_DEPTH + 1:
        chain.append(cur)
        cur, depth = cur.inherits_from, depth + 1

    sources = {}
    for r in reversed(chain):                 # 祖先 → 自身
        codes = Permission.objects.filter(
            role_permissions__role=r, is_active=True, is_deprecated=False
        ).exclude(code__isnull=True).values_list("code", flat=True)
        for c in codes:
            sources[c] = r
    return sources
```
</details>

## 九、延伸思考

1. **单继承 vs 多继承的真正理由**（第一节第 3 问）

   多继承（DAG）表达力更强，接近 NIST 的完整定义。但：

   > 单继承下，「为什么张三有这个权限」的答案永远是**一条链**：`张三 → 客服主管 → 客服专员 → [权限]`。
   > 多继承下，答案是**一张图**里的一条路径——而且可能有多条路径。

   **可解释性是权限系统的刚需**：排查权限问题时，不可解释 = 不可运维。

   而且「同时拥有 A 和 B 的权限」这个需求，**已经被「用户可以有多个角色」满足了**。多继承是在角色层再做一次同样的事，收益重复。

2. **权限溯源页看起来是锦上添花，实际是运维刚需。**

   当有人问「为什么张三能删工单」，你必须能在 10 秒内回答。没有这个页面，你要查：`UserRole` → `Role` → 递归 `inherits_from` → `RolePermission` → `Permission`，五张表。

   想想：这个页面还能怎么增强？（提示：反过来查——「哪些用户拥有这个权限」）

3. **现在的 `expand_roles()` 每层一次查询。** 一个继承深度为 4 的角色，展开要 4 次查询；用户有 3 个角色就是 12 次。

   算一下：一个页面渲染 30 个按钮 × 每次判断都要展开一遍 = 多少次查询？

   **先感受这个痛，`v0.16.0` 会解决它。** 顺便想想：为什么解法不是「把 `expand_roles` 写得更聪明」，而是「加缓存」？

4. **`is_active=False` 的祖先角色，其权限该不该生效？**

   我的实现里不生效（`if cur.is_active` 判断）。但另一种设计是：停用一个角色只影响「直接分配给用户」，不影响「被继承」。

   哪种更符合直觉？想想管理员停用「客服专员」时，他的意图是什么。**这类语义歧义在权限系统里很多，关键不是选对，而是选定后写进文档并保持一致。**

5. 我们做的是 **RBAC1（受限层级：单继承 + 深度 5）**。回看 [理论基础 3.2 节](../00-RBAC理论基础.md)，NIST 标准里的「一般层级」和「受限层级」区别是什么？我们的选择属于哪一类？

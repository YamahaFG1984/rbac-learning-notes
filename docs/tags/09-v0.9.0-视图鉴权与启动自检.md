## 五、⚠️ 容易写错的地方

### 1. `public_view` 的 `reason` 必须是必填参数

```python
# ❌
def public_view(reason=""): ...

# ✅
def public_view(reason: str): ...
```

为什么？「这个接口不需要权限」是一个**安全决策**，安全决策必须留下依据。

三个月后有人看到 `@public_view` 这行，能立刻知道当初为什么这么定，而不是猜「是有意的还是忘了加」。给默认值等于允许省略理由，那这个标记就退化成了一个纯粹的「消警告」开关。

```python
@public_view(reason="登录页，未认证用户必须能访问")
def login_view(request): ...
```

### 2. system check 要穿透 Django 的层层包装

这是本 tag 的技术难点。一个类视图经过 `as_view()` 后变成闭包，再经过 `csrf_exempt`、`login_required` 等装饰器又包了几层。你的自检要沿着包装链找到真正的视图函数。

关键属性：
- `functools.wraps` 会设置 `__wrapped__` → 沿它向内追溯
- `View.as_view()` 返回的函数带 `view_class` 属性 → 类视图从这里取类
- `URLPattern.callback` 是入口

### 3. 检查 Mixin 时要看类属性，不是函数属性

类视图的权限声明写在类属性 `required_perm` 上，不是包装函数上。自检要分两种情况处理。

### 4. 移除 `ModelBackend` 的后果

契约里让你把 `ModelBackend` 从 `AUTHENTICATION_BACKENDS` 里去掉，只留 `RBACBackend`。

**但 `RBACBackend` 必须实现 `authenticate()` 和 `get_user()`**，否则登录会直接失败——`authenticate()` 是遍历所有 backend 找一个能认证的。

最省事的做法是让 `RBACBackend` 继承 `ModelBackend` 然后只重写 `has_perm()`：

```python
class RBACBackend(ModelBackend):
    def has_perm(self, user_obj, perm, obj=None):
        return user_has_perm(user_obj, perm)
    def get_all_permissions(self, user_obj, obj=None):
        return set(get_user_perm_codes(user_obj)) if not user_obj.is_superuser else set()
```

继承来的 `authenticate()` 和 `get_user()`（含 `is_active` 检查，见 `v0.7.0` 陷阱 5）就都保留了。

### 5. `PermissionDenied` vs 返回 `HttpResponseForbidden`

用 `raise PermissionDenied`。Django 会捕获它并调用 `handler403`，渲染你在 `v0.8.0` 写的 `403.html`。

直接 `return HttpResponseForbidden("...")` 会返回一个裸的纯文本页面，绕过了错误页机制。

### 6. 装饰器顺序

```python
@login_required                   # 外层
@require_perm(DeptPerm.CREATE)    # 内层
def dept_create(request): ...
```

`login_required` 要在外层。否则匿名用户会先撞上权限检查得到 403，而不是被引导去登录页（FR-5.6 要求跳登录页并带 `next`）。

**装饰器从下往上执行包装，从上往下执行调用。** 写反了不会报错，只会得到糟糕的用户体验。

## 六、卡住了看这里（渐进提示）

<details>
<summary><b>提示 1：装饰器</b></summary>

```python
from functools import wraps
from django.core.exceptions import PermissionDenied
from apps.rbac.services import user_has_perm, user_has_any_perm


def require_perm(code: str):
    """要求当前用户拥有指定权限码，否则 403。

    权限声明写在视图旁边——代码即文档。配合 rbac.W001 自检，
    保证没有视图被遗漏（ADR-008）。
    """
    def decorator(view_func):
        @wraps(view_func)
        def wrapper(request, *args, **kwargs):
            if not user_has_perm(request.user, code):
                raise PermissionDenied
            return view_func(request, *args, **kwargs)
        wrapper._required_perm = code
        return wrapper
    return decorator


def public_view(reason: str):
    """显式声明本视图无需权限。reason 必填——安全决策必须留下依据。"""
    def decorator(view_func):
        view_func._is_public = True
        view_func._public_reason = reason
        return view_func
    return decorator
```
</details>

<details>
<summary><b>提示 2：Mixin</b></summary>

```python
class PermRequiredMixin:
    required_perm: str | None = None
    required_any_perms: tuple[str, ...] = ()

    def dispatch(self, request, *args, **kwargs):
        if self.required_perm and not user_has_perm(request.user, self.required_perm):
            raise PermissionDenied
        if self.required_any_perms and not user_has_any_perm(request.user, self.required_any_perms):
            raise PermissionDenied
        return super().dispatch(request, *args, **kwargs)
```

⚠️ MRO 顺序：`class MyView(PermRequiredMixin, ListView)`，Mixin 必须在前面，否则 `super().dispatch()` 链走不到它。
</details>

<details>
<summary><b>提示 3：system check（本 tag 最难的部分）</b></summary>

```python
from django.core.checks import Warning, register
from django.urls import get_resolver, URLPattern, URLResolver


def _iter_views(resolver=None, prefix=""):
    resolver = resolver or get_resolver()
    for p in resolver.url_patterns:
        if isinstance(p, URLResolver):
            yield from _iter_views(p, prefix + str(p.pattern))
        elif isinstance(p, URLPattern):
            yield prefix + str(p.pattern), p.callback


def _unwrap(view):
    """穿透装饰器包装链和 as_view() 闭包，拿到权限声明的载体。"""
    # 类视图：as_view() 的返回值带 view_class
    cls = getattr(view, "view_class", None)
    if cls is not None:
        return cls
    # 函数视图：沿 __wrapped__ 向内找，但我们的标记打在最外层 wrapper 上，
    # 所以先看当前对象，找不到再往里
    seen = set()
    cur = view
    while cur is not None and id(cur) not in seen:
        seen.add(id(cur))
        if hasattr(cur, "_required_perm") or hasattr(cur, "_is_public"):
            return cur
        cur = getattr(cur, "__wrapped__", None)
    return view


@register()
def check_view_permissions(app_configs, **kwargs):
    IGNORE_PREFIXES = ("admin/", "static/", "__debug__/")
    errors = []
    for route, view in _iter_views():
        if route.startswith(IGNORE_PREFIXES):
            continue
        target = _unwrap(view)
        has_perm_decl = (
            getattr(target, "_required_perm", None)
            or getattr(target, "_required_any_perms", None)
            or getattr(target, "required_perm", None)
            or getattr(target, "required_any_perms", None)
        )
        if not has_perm_decl and not getattr(target, "_is_public", False):
            errors.append(Warning(
                f"视图 {getattr(target, '__name__', target)} (路由 /{route}) 未声明权限要求。",
                hint="用 @require_perm('...') 声明所需权限，"
                     "或用 @public_view(reason='...') 显式声明公开。",
                id="rbac.W001",
            ))
    return errors
```

⚠️ 记得在 `apps/rbac/apps.py` 的 `ready()` 里 `from . import checks`，否则 `@register()` 不会执行。
</details>

## 九、延伸思考

1. **第一节第 3 问的完整答案**：装饰器的风险是「忘了加」，而我们的解法不是「更小心」，是**用机制把风险变成启动期可见的错误**。

   > **默认拒绝需要机制来保证，不能靠开发者的自觉。**
   > **沉默不能被解释为同意。** 没有装饰器 ≠ 公开访问，而 = 配置错误。

   回想一下，这个思路你在哪里见过？（提示：`v0.1.0` 延伸思考 1 的依赖方向检查、`v0.18.0` 的表单白名单。这是同一条原则的三次应用。）

2. **`rbac.W001` 是 Warning 还是 Error？**

   我用了 Warning——它不会阻止 `runserver`。想想：设成 Error（启动即失败）会更安全，但会不会太粗暴？

   一个折中方案：dev 环境是 Warning，prod 环境是 Error。怎么实现？（提示：check 函数里读 `settings.DEBUG`）

3. **现在权限检查生效了，但侧边栏还是写死的**——用户能看到点进去会 403 的菜单。

   这个体验有多糟？亲自用一个低权限账号点几下。**这就是 `v0.11.0` 要解决的问题。**

   顺带想想：如果只做动态菜单而不做视图鉴权，会怎样？（这是很多真实项目的做法，也是 `v0.10.0` 会重点强调的陷阱。）

4. **中间件方案真的一无是处吗？** 想想这个场景：你要给所有 API 加一个「必须实名认证才能访问」的全局规则。这种**横切的、与具体视图无关**的规则，装饰器和中间件哪个合适？

   结论不是「装饰器永远更好」，而是「**与视图强相关的用装饰器，与视图无关的用中间件**」。

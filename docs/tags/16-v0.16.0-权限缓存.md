## 三、接口契约（必须与我的实现对齐）

### settings

```python
RBAC_CACHE_TTL = 1800          # 30 分钟
RBAC_VERSION_KEY = "rbac:version"
```

### 缓存 key 格式（**固定**）

```python
f"rbac:perms:{user_id}:{version}"
f"rbac:roles:all:{version}"          # 全量角色映射
f"rbac:role_depts:{role_id}:{version}"
```

### `cache.py` 接口

```python
def get_version() -> int: ...
def bump_version() -> None: ...
def perms_key(user_id: int) -> str: ...
```

### 请求级缓存的存放位置

挂在 **user 对象**上（不是 request）：

```python
user._rbac_perm_codes_cache
```

> 为什么挂 user 不挂 request？因为 `services.py` 不认识 request（[ADR-013](../02-设计文档.md#adr-013权限内核与表现层解耦让模板和-api-共用同一套判断)）。挂在 user 上，Web 层和 API 层都能用。

## 五、⚠️ 容易写错的地方

### 🔴 1. 用版本号失效，不要逐 key 删除

第一节第 3、4 问的答案。

**逐 key 删除**需要反查受影响的用户：

```python
# ❌ 反查昂贵，而且极容易写漏继承链那部分
affected_roles = get_all_inheritors(role)          # 递归找所有继承者
user_ids = UserRole.objects.filter(role__in=affected_roles).values_list("user_id")
for uid in user_ids:
    cache.delete(perms_key(uid))
```

**版本号失效**：

```python
# ✅ 绝不会漏
def bump_version():
    try:
        cache.incr(RBAC_VERSION_KEY)
    except ValueError:                 # key 不存在
        cache.set(RBAC_VERSION_KEY, 1, None)
```

版本号一变，所有旧 key 立刻不可达，靠 TTL 自然淘汰。

**第一节第 4 问的答案**：

| | 后果 |
| --- | --- |
| **失效漏了** | 「权限已撤销但仍然生效」→ **安全问题** |
| 失效多了 | 缓存命中率短暂下降 → **性能问题** |

> **用可量化的性能损失，换不可量化的正确性保证。**
> 在安全相关的设计里，这个方向的交换几乎总是对的。反过来（为性能牺牲正确性）几乎总是错的。

代价可量化：企业后台的权限变更是**低频**操作（一天几次到几十次），用户数千级。一次全量失效造成的后果是接下来几分钟缓存命中率下降——完全在承受范围内。

### 🔴 2. 用 signal 挂载，不要在视图里手写调用

```python
# ❌ 每个改权限的视图都要记得调一次，必然有人忘
def role_perm_assign(request, pk):
    save_role_permissions(role, ids)
    bump_version()                     # 忘一处 = 一处权限不生效
```

```python
# ✅ 挂在模型上，任何路径的变更都触发
@receiver([post_save, post_delete], sender=RolePermission)
@receiver([post_save, post_delete], sender=UserRole)
def _invalidate(sender, **kwargs):
    bump_version()
```

**信号在这里是恰当的用法**：它天然是横切关注点，且不能被遗漏——shell、管理命令、admin、测试，任何路径改了数据都会触发。

（对比一下：`v0.14.0` 我们**反对**用 thread-local 做隐式过滤。同样是「隐式机制」，为什么这里可以那里不行？

想想差别：signal 的作用是**让某件事一定发生**（失效缓存），thread-local 的作用是**改变查询的语义**。前者失败会导致性能问题，后者失败会导致安全问题；前者的行为在任何上下文都一致，后者依赖上下文。**隐式机制用于「保证副作用发生」是好的，用于「决定业务语义」是危险的。**）

### 3. `bulk_create` / `bulk_update` / `queryset.delete()` 不触发 signal

⚠️ 这是个大坑。`v0.5.0` 保存角色权限用的是：

```python
RolePermission.objects.filter(role=role).delete()      # ← queryset.delete() 触发 post_delete？
RolePermission.objects.bulk_create([...])              # ← bulk_create 不触发 post_save！
```

- `queryset.delete()`：**会**触发 `post_delete`（Django 会逐个发信号，除非用了 `_raw_delete`）
- `bulk_create()`：**不会**触发 `post_save`
- `bulk_update()`：**不会**触发 `post_save`

所以光挂 signal 是不够的。**必须在批量操作后手动调一次 `bump_version()`**，或者改用逐个 `save()`（角色权限数量少，可以接受）。

**这个坑一定要亲自验一遍**：改完角色权限，看缓存有没有真的失效。

### 4. 请求级缓存挂在 user 上，注意 `SimpleLazyObject`

```python
user._rbac_perm_codes_cache = codes
```

`request.user` 是 `SimpleLazyObject`，给它设属性会转发到被包装的真实对象上——所以这样是可以的。但要注意：

- 匿名用户（`AnonymousUser`）是单例吗？不是，每个请求新建，所以安全。
- 在测试里手工构造的 user 对象，缓存会跨测试残留吗？**会**——如果你复用同一个 user 实例。测试里记得 `refresh_from_db()` 或重新取。

### 5. 超管不进缓存

```python
if user.is_superuser:
    return ALL_PERMS        # 短路，在任何缓存逻辑之前
```

超管的短路本来就是零成本，走缓存反而多余。

### 6. LocMemCache 的 `incr` 是进程内的

开发环境用 `LocMemCache`：**每个进程有独立的缓存**。`runserver` 的自动重载会开两个进程，你可能看到诡异的失效行为。

生产用 Redis。测试里用 `LocMemCache` 但记得每个测试清一次缓存（`cache.clear()`），否则测试之间会互相污染。

<details>
<summary><b>提示 1：cache.py</b></summary>

```python
from django.conf import settings
from django.core.cache import cache

VERSION_KEY = getattr(settings, "RBAC_VERSION_KEY", "rbac:version")
TTL = getattr(settings, "RBAC_CACHE_TTL", 1800)


def get_version() -> int:
    v = cache.get(VERSION_KEY)
    if v is None:
        cache.set(VERSION_KEY, 1, None)      # None = 永不过期
        return 1
    return v


def bump_version() -> None:
    """任何权限相关变更后调用。

    版本号一变，所有旧 key 立即不可达，靠 TTL 自然淘汰。
    不精确但绝不会漏失效——用性能换正确性（ADR-010）。
    """
    try:
        cache.incr(VERSION_KEY)
    except ValueError:
        cache.set(VERSION_KEY, 1, None)


def perms_key(user_id: int) -> str:
    return f"rbac:perms:{user_id}:{get_version()}"
```

<details>
<summary><b>提示 2：两级缓存包在原逻辑外面</b></summary>

```python
def get_user_perm_codes(user) -> frozenset[str]:
    if not user or not user.is_authenticated or not user.is_active:
        return frozenset()
    if user.is_superuser:
        return ALL_PERMS

    # L1：请求级
    cached = getattr(user, "_rbac_perm_codes_cache", None)
    if cached is not None:
        return cached

    # L2：进程外
    key = perms_key(user.pk)
    codes = cache.get(key)
    if codes is None:
        codes = _resolve_perm_codes(user)       # ← v0.12.0 的原逻辑，原封不动搬进来
        cache.set(key, codes, TTL)

    user._rbac_perm_codes_cache = codes
    return codes
```

**注意 `_resolve_perm_codes` 就是之前的函数体，一行没改。**

这说明 `v0.6.0` 的接口设计是对的——**好的抽象让优化可以后加**。对比你自己的实现：你为了加缓存，改动了多少原有逻辑？
</details>

<details>
<summary><b>提示 3：角色全量内存缓存</b></summary>

```python
def _get_role_map() -> dict[int, Role]:
    """全部激活角色的 {id: Role} 映射。

    角色数量很少（几十个），一次性加载后 expand_roles 变成纯内存操作，
    零 DB 查询。
    """
    key = f"rbac:roles:all:{get_version()}"
    data = cache.get(key)
    if data is None:
        data = {r.id: r for r in Role.objects.filter(is_active=True)}
        cache.set(key, data, TTL)
    return data


def expand_roles(roles):
    role_map = _get_role_map()
    result = set()
    for role in roles:
        cur, depth = role, 0
        while cur is not None and depth <= settings.RBAC_MAX_ROLE_DEPTH:
            if cur.id in {r.id for r in result}:
                break
            result.add(cur)
            cur = role_map.get(cur.inherits_from_id)     # ← 内存查找，不查库
            depth += 1
    return result
```

⚠️ 缓存 Model 实例有个坑：它们会被 pickle。如果模型定义变了（加了字段），旧缓存反序列化可能出问题。版本号失效正好也解决了这个——但要确保部署时 bump 一次。
</details>

## 九、延伸思考

1. **版本号方案的代价**：任何一个用户的授权变更，会导致**全体**缓存失效。

   算一算：1000 个在线用户，一天 20 次权限变更，每次失效后大家重新解析一遍——多出多少查询？在什么规模下这会成为问题？

2. **进阶方案：按角色分级版本号**

   思路：每个角色一个版本号，用户的缓存 key 由**他涉及的所有角色的版本号**组合而成。

   ```
   key = f"rbac:perms:{uid}:{hash(tuple(sorted(role_versions)))}"
   ```

   改角色 A 只会失效「涉及角色 A（含继承）」的用户。

   **想想它的复杂度成本在哪**：
   - 构造 key 前要先知道用户有哪些角色 → 这本身就要查库，缓存的意义打了折扣
   - 角色继承变更时，要失效哪些角色的版本号？（继承链上下都要）
   - key 的组合可能爆炸

   **这就是为什么我们选了简单方案。** 复杂方案的正确性更难保证，而正确性是这里的第一优先级。

3. **缓存击穿**：如果 1000 个用户同时刷新，缓存刚好失效，会同时有 1000 次权限解析打到数据库。

   查一下「缓存击穿 / 惊群效应」的常见解法（互斥锁、逻辑过期、预热）。想想本项目需要处理吗？判断依据是什么？

4. **`ALL_PERMS` 哨兵不进缓存，那它 pickle 得了吗？**

   试试 `cache.set("x", ALL_PERMS)`。如果你的哨兵类定义在模块顶层，可以 pickle；如果是闭包或局部类，不行。

   这类「能不能序列化」的问题在加缓存时经常撞上。养成习惯：**放进缓存的东西，先确认它可 pickle。**

5. **两级缓存的第三级**：还有一种更快的——进程级全局字典（不带 TTL，靠版本号判断新旧）。

   它比 Redis 快一个数量级，但每个进程一份。想想什么场景下值得加？（提示：权限数据小、变更少、进程多）

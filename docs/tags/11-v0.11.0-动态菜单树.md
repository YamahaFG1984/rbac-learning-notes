## 五、⚠️ 容易写错的地方

### 1. 算法方向：自底向上，不是自顶向下

第一节第 2、3 问的答案。

```
❌ 自顶向下：遍历目录 → 判断目录有没有权限 → 目录没有 code，判断不了
✅ 自底向上：先找出所有「有权限的菜单」→ 沿 parent 向上，把祖先目录全部保留
```

**目录的可见性 = 它是否有任何一个有权限的后代菜单。**

这样「空目录」自然就不会出现——因为没有任何后代菜单被保留，它自己也不会被保留。

第一节第 3 问：空目录必须不显示。**一个点开是空的目录，用户会以为系统坏了。**

### 2. 必须是 1 次查询（NFR-3）

```python
# ❌ N+1，每层一次查询
def build(parent):
    for node in Permission.objects.filter(parent=parent):
        node.children = build(node)

# ✅ 一次查全部，内存里组树
nodes = list(Permission.objects.filter(perm_type__in=["catalog", "menu"], ...))
```

菜单节点总数很少（几十个），一次全部取出来在内存里处理，比递归查库快几个数量级。

**用 `assertNumQueries(1)` 把这个锁死**——加上权限解析的查询，总数应该是固定的小数字，且**与菜单层级无关**。

### 3. `button` 类型不能出现在菜单里

```python
.filter(perm_type__in=[PermType.CATALOG, PermType.MENU])
```

漏了这个过滤，侧边栏会冒出「新建部门」「删除部门」这种按钮。

### 4. 过滤条件要齐

```python
.filter(
    perm_type__in=[PermType.CATALOG, PermType.MENU],
    is_active=True,
    is_visible=True,          # ← 容易漏：有些菜单是隐藏的（比如详情页）
    is_deprecated=False,      # ← 容易漏
)
```

`is_visible=False` 的典型场景：详情页/编辑页有独立的权限码，但不该出现在侧边栏里。

### 5. `reverse()` 可能抛 `NoReverseMatch`

权限点里的 `url_name` 是人手写在 `permissions.py` 里的字符串，可能写错，也可能对应的 URL 后来被删了。

```python
try:
    url = reverse(node.url_name) if node.url_name else None
except NoReverseMatch:
    url = None          # 或者记一条日志
```

**不处理的话，一个写错的 url_name 会让整个侧边栏渲染崩溃**——所有页面都打不开。

### 6. 超管的菜单

超管的 `get_user_perm_codes()` 返回 `ALL_PERMS` 哨兵，`code in codes` 恒为 True。所以超管自动看到全部菜单，不需要特殊处理。

**但要测一下**——哨兵对象的行为容易在重构中被破坏。

## 六、卡住了看这里（渐进提示）

<details>
<summary><b>提示 1：核心算法</b></summary>

```python
def get_user_menu_tree(user) -> list[dict]:
    """构建当前用户可见的菜单树。

    算法：自底向上。先标记有权限的 menu 节点，再沿 parent 链向上
    保留全部祖先目录。空目录（无任何有权限的后代）自然不会被保留。

    查询次数固定为 1（不含权限解析），与菜单层级无关（NFR-3）。
    """
    codes = get_user_perm_codes(user)

    nodes = list(
        Permission.objects
        .filter(perm_type__in=[PermType.CATALOG, PermType.MENU],
                is_active=True, is_visible=True, is_deprecated=False)
        .order_by("order_num", "id")
    )
    by_id = {n.id: n for n in nodes}

    # 第一步：标记有权限的 menu
    keep = set()
    for n in nodes:
        if n.perm_type == PermType.MENU and n.code and n.code in codes:
            keep.add(n.id)

    # 第二步：向上保留祖先目录
    for nid in list(keep):
        cur = by_id[nid].parent_id
        while cur is not None and cur not in keep:
            keep.add(cur)
            cur = by_id[cur].parent_id if cur in by_id else None

    # 第三步：组树
    return _assemble(nodes, keep)


def _assemble(nodes, keep):
    dict_map, roots = {}, []
    for n in nodes:
        if n.id not in keep:
            continue
        dict_map[n.id] = {
            "id": n.id, "name": n.name, "icon": n.icon,
            "url": _safe_reverse(n.url_name), "perm_type": n.perm_type,
            "children": [],
        }
    for n in nodes:
        if n.id not in dict_map:
            continue
        item = dict_map[n.id]
        parent = dict_map.get(n.parent_id)
        (parent["children"] if parent else roots).append(item)
    return roots


def _safe_reverse(url_name):
    if not url_name:
        return None
    try:
        return reverse(url_name)
    except NoReverseMatch:
        return None
```

⚠️ 第二步的循环里 `while cur is not None and cur not in keep` —— `not in keep` 这个条件是剪枝：一旦碰到已保留的祖先，说明再往上都保留过了，可以停。
</details>

## 九、延伸思考

1. **菜单树现在每次请求都重新构建。** 它的输入只有「用户的权限码集合」和「权限表的内容」，两者都变化很少。

   想想：这个结果能缓存吗？缓存的 key 该是什么？（提示：`v0.16.0` 会给权限码加缓存，菜单树能不能顺便一起缓存？key 里要不要包含用户 ID？）

   进阶：如果两个用户的权限码集合完全相同，他们的菜单树也完全相同。能不能用**权限码集合的哈希**做 key，让不同用户共享缓存？这个优化在什么规模下才有意义？

2. **到这里，功能权限的三层全齐了**（`v0.10.0` 第九节第 4 条那张表）。

   现在做个实验：找一个只有「部门管理」权限的用户，
   - 侧边栏看不到「角色管理」✅（本 tag）
   - 手工输入 `/rbac/roles/` → 403 ✅（`v0.9.0`）
   - 如果只做了本 tag 而没做 `v0.9.0`，会发生什么？

   **很多真实项目就只做了菜单过滤**，然后以为安全了。

3. **两层菜单够用吗？** 提示 2 的模板只渲染两层。如果业务真的需要三层，你会：
   - 用递归 `{% include %}`（Django 模板支持，但要小心无限递归）
   - 还是重新审视信息架构，把三层压成两层？

   我倾向后者。**菜单深度超过两层，通常是产品设计问题，不是技术问题。**

4. `url` 字段在服务层就 `reverse()` 好了。到了 `v1.2.0` 做 API 时，前端要的是**前端路由**（比如 Vue Router 的 `/system/dept`），不是 Django 的 URL。

   这时 `Permission` 表要不要加一个 `route_path` 字段？还是复用 `url_name` 让前端自己映射？想想两种做法的维护成本。

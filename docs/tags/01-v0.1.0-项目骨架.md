## 三、接口契约（必须与我的实现对齐）

> **为什么要对齐？**
> 你的目标是实现完之后 `git diff` 我的版本，看差异学东西。如果连模块路径和配置项名字都不一样，diff 会全是噪音，看不出真正的设计差异。
>
> **所以：契约部分照抄，实现部分自由发挥。** 这正是真实工作中「接口先行」的意义。

### 模块路径

```
config.settings.base
config.settings.dev
config.settings.prod
```

### `INSTALLED_APPS` 中我们自己的 app（顺序固定，按依赖方向排）

```python
LOCAL_APPS = [
    "apps.common",
    "apps.accounts",
    "apps.rbac",
    "apps.tickets",
    "apps.audit",
]
```

### 必须存在的配置项

| 配置项 | 值 |
| --- | --- |
| `LANGUAGE_CODE` | `"zh-hans"` |
| `TIME_ZONE` | `"Asia/Shanghai"` |
| `USE_TZ` | `True` |
| `STATIC_URL` | `"/static/"` |
| `STATICFILES_DIRS` | `[BASE_DIR / "static"]` |
| `TEMPLATES[0]["DIRS"]` | `[BASE_DIR / "templates"]` |
| `DEFAULT_AUTO_FIELD` | `"django.db.models.BigAutoField"` |

### npm 脚本名（固定）

```json
"build:css"  "watch:css"
```

## 四、实现步骤

**Step 1** — 建虚拟环境，装依赖，写 `requirements.txt`（锁死 `Django==5.2.16`，不要写 `>=`）。

**Step 2** — `django-admin startproject config .`（注意末尾的点，让 `manage.py` 落在仓库根目录）。

**Step 3** — 把生成的 `config/settings.py` 拆成 `config/settings/` 包，分为 `base` / `dev` / `prod`。
- `dev.py` 和 `prod.py` 都以 `from .base import *` 开头。
- 改 `manage.py`、`wsgi.py`、`asgi.py` 里的 `DJANGO_SETTINGS_MODULE`。

**Step 4** — 建 `apps/` 目录和五个 app。
- 用 `apps/` 作为包目录，意味着 app 的 `name` 要写全路径：`apps.accounts`。
- 每个 app 的 `apps.py` 里设 `verbose_name`（中文）。

**Step 5** — 配置 Tailwind。
- `npm init -y`，装 `tailwindcss`。
- `static/src/input.css` 写 Tailwind 的入口指令。
- 跑 `npm run build:css` 产出 `static/css/tailwind.css`。

**Step 6** — 写 `pytest.ini`，指定 `DJANGO_SETTINGS_MODULE = config.settings.dev`。

**Step 7** — 写 `.gitignore`（`.venv/`、`__pycache__/`、`*.sqlite3`、`.env`、`node_modules/`）和 `.gitattributes`。

**Step 8** — 跑 `python manage.py check`。

## 五、⚠️ 容易写错的地方

### 1. 本 tag 最重要的一条：**不要执行 `python manage.py migrate`**

这条看起来很怪——项目建好了不该初始化数据库吗？

**不要。** 原因见 [ADR-002](../02-设计文档.md#adr-002用-abstractuser-自定义用户模型且必须在第一次-migrate-之前)：`AUTH_USER_MODEL` 必须在项目**第一次 migrate 之前**设定。而我们的自定义 `User` 要到 `v0.2.0` 才建。

一旦 `django.contrib.auth` 的迁移跑过，再换用户模型会遇到几乎无解的外键依赖问题——Django 社区的标准建议是「删掉数据库重来」。

这是 Django 最著名的坑之一。本项目用 tag 的先后顺序把它显式化：**`v0.1.0` 建骨架但不建库，`v0.2.0` 先定 `AUTH_USER_MODEL` 再首次 migrate。**

> 所以第一节思考题第 5 问的答案是：`db.sqlite3` 不应该存在。

### 2. `startproject config .` 末尾的点

漏了这个点，你会得到 `config/config/settings.py` 这样的嵌套结构。

### 3. 拆分 settings 后，`BASE_DIR` 会算错

`startproject` 生成的是 `BASE_DIR = Path(__file__).resolve().parent.parent`。当 `settings.py` 变成 `config/settings/base.py` 后，层级深了一层，要多一个 `.parent`。

**这个错误不会立刻报错**，它会让 `STATICFILES_DIRS` 和 `TEMPLATES.DIRS` 静默指向错误的路径，等你 `v0.8.0` 做布局时才发现样式加载不出来。**现在就验证一下 `BASE_DIR` 打印出来对不对。**

### 4. `apps/` 目录下的 app，`name` 要写全路径

```python
class AccountsConfig(AppConfig):
    name = "apps.accounts"          # 不是 "accounts"
    verbose_name = "组织管理"
```

### 5. `.env` 不入库，但 `.env.example` 必须入库

前者含真实密钥，后者是模板——它告诉别人「这个项目需要哪些环境变量」。少了它，新人克隆下来根本不知道要配什么。

## 六、卡住了看这里（渐进提示）

<details>
<summary><b>提示 1：settings 分层的骨架长什么样</b></summary>

```python
# config/settings/base.py
from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent.parent.parent   # ← 注意三层

DJANGO_APPS = ["django.contrib.admin", "django.contrib.auth", ...]
LOCAL_APPS  = ["apps.common", "apps.accounts", "apps.rbac", "apps.tickets", "apps.audit"]
INSTALLED_APPS = DJANGO_APPS + LOCAL_APPS
```

```python
# config/settings/dev.py
from .base import *

DEBUG = True
SECRET_KEY = "django-insecure-dev-only-key"
ALLOWED_HOSTS = ["*"]
DATABASES = {"default": {"ENGINE": "django.db.backends.sqlite3",
                         "NAME": BASE_DIR / "db.sqlite3"}}
```

```python
# config/settings/prod.py
from .base import *
import os

DEBUG = False
SECRET_KEY = os.environ["DJANGO_SECRET_KEY"]        # 缺失就直接崩，这是好事
ALLOWED_HOSTS = os.environ["DJANGO_ALLOWED_HOSTS"].split(",")
SECURE_SSL_REDIRECT = True
SESSION_COOKIE_SECURE = True
CSRF_COOKIE_SECURE = True
```

注意 `prod.py` 里用 `os.environ[...]` 而不是 `os.environ.get(..., default)`——**缺配置就启动失败，好过带着默认密钥跑起来**。
</details>

<details>
<summary><b>提示 2：Tailwind 配置</b></summary>

```css
/* static/src/input.css —— Tailwind v4 语法 */
@import "tailwindcss";
@source "../../templates";
@source "../../apps";
```

```json
{
  "scripts": {
    "build:css": "tailwindcss -i ./static/src/input.css -o ./static/css/tailwind.css --minify",
    "watch:css": "tailwindcss -i ./static/src/input.css -o ./static/css/tailwind.css --watch"
  }
}
```

`@source` 告诉 Tailwind 去哪里扫描用到的 class。漏掉 `apps` 目录的话，将来写在 Python 里的 class 名（比如表单 widget 的 `attrs`）不会被打包。
</details>

<details>
<summary><b>提示 3：pytest.ini</b></summary>

```ini
[pytest]
DJANGO_SETTINGS_MODULE = config.settings.dev
python_files = test_*.py
testpaths = tests
addopts = -ra
```
</details>

## 九、延伸思考

1. **依赖方向靠什么保证？** 第一节的第 3 问。本 tag 只是在文档里写了「禁止反向 import」，这是**靠自觉**。想想有什么机制能让它变成自动检查？（关键词：`import-linter`、自定义 flake8 插件、CI 里跑一个 AST 扫描脚本）

   顺带对照：这和 `v0.9.0` 的「权限装饰器 + 启动自检」是同一个思路——**已知的人为疏漏风险，要用机制变成可见的错误**。

2. **settings 分层还有第三种流派**：`django-configurations` 或 `django-environ` + 单文件。查一下它们，想想为什么本项目选了最朴素的多文件继承。（提示：教学项目的第一优先级是什么？）

3. 如果有一天真的不小心先 `migrate` 了才想起来要换 `AUTH_USER_MODEL`，除了删库还有别的办法吗？搜一下这个问题，你会看到一堆痛苦的经历——**这就是为什么我们要用 tag 顺序把它固化下来。**

## 五、⚠️ 容易写错的地方

### 1. path 的尾斜杠不是装饰——它是正确性的关键

第一节第 5 问的答案：**`path__startswith="/1"` 是错的。**

```python
"/11/".startswith("/1")     # True   ← 部门 11 被误判为部门 1 的后代！
"/11/".startswith("/1/")    # False  ← 正确
```

如果 path 不带尾斜杠，部门 1 的子树查询会把部门 11、部门 12、部门 100 全都捞进来。

**这个 bug 在小数据量下不会暴露**——只有当部门 ID 增长到两位数、且恰好存在 ID 前缀关系时才出现。等你发现的时候，数据权限已经错了很久了。

所以正确的查询是：

```python
Department.objects.filter(path__startswith=self.path)   # self.path 自带尾斜杠
```

**给这个场景写一个专门的测试用例**：造 ID 为 1 和 11 的两个平级部门，断言 `dept_1.get_descendants()` 不包含 `dept_11`。

### 2. 新建时 `self.pk` 还不存在

path 里要包含自己的 ID，但新建时 ID 由数据库生成。解法是**存两次**：先 `super().save()` 拿到 pk，再算 path 并 update。

代价是新建部门有两次写库。**接受它**——部门写操作极低频（一年几次）。

如果你追求「一次写入」，就得先从序列里取下一个 ID，那是数据库特有操作，会破坏 [ADR-014](../02-设计文档.md#adr-014默认-sqlite保持数据库可移植) 的可移植性要求。**这是一个具体可感知的取舍：为可移植性接受一次多余的 UPDATE。**

### 3. 第二次写库不要用 `self.save()`

会无限递归。用 `Department.objects.filter(pk=self.pk).update(...)` 直接打数据库，绕过 `save()`。

### 4. 移动节点时，别用递归逐个 save

```python
# ❌ 慢，且每个子节点都触发一次完整 save
for child in self.children.all():
    child.save()          # 递归下去...

# ✅ 一次查出整棵子树，Python 里做字符串替换，一次 bulk_update
subtree = Department.objects.filter(path__startswith=old_path)
for node in subtree:
    node.path = new_path + node.path[len(old_path):]
    node.depth = node.path.count("/") - 2
Department.objects.bulk_update(subtree, ["path", "depth"])
```

### 5. 用 `on_delete=PROTECT`，不要在 `delete()` 里写检查

```python
parent = models.ForeignKey("self", on_delete=models.PROTECT, ...)
```

为什么？`CLAUDE.md` 里的原话：**用数据库/ORM 约束表达业务规则，比在 `delete()` 里写检查更难被绕过。**

`delete()` 里的检查在 `queryset.delete()` 批量删除时**不会被调用**——Django 的批量删除不走单对象的 `delete()` 方法。而 `PROTECT` 在任何路径下都生效。

视图层要捕获 `ProtectedError` 并翻译成友好提示（FR-1.2 要求「明确提示」）。

### 6. `depth` 的计算

`"/1/3/7/".count("/")` = 4，减 2 得 2。根部门 `"/1/"` 的 count 是 2，减 2 得 0。✅

### 7. ⚠️ `ORDER BY path` **不等于**先序遍历

这是陷阱 1 的同一个根因在另一处的表现，而且更隐蔽。

`path` 是**字符串**，数据库按字典序排：

```
"/2/6/10/"  <  "/2/6/7/"      因为第 6 个字符 '1' < '7'
```

所以只要同级节点的 ID 跨过了个位数，`ORDER BY path` 得到的顺序就乱了——
**而且乱得很微妙**：前 9 个子节点顺序正常，第 10 个开始插到前面去。

更糟的是，它还完全忽略了 `order_num`——管理员精心排的顺序根本没生效。

**正确做法**：`path` 只用于**子树查询**（`startswith` 不受排序影响，是正确的），
树的**显示顺序**在内存里做真正的先序遍历，同级按 `order_num` 排：

```python
children = {}                     # parent_id -> [节点]
for n in nodes:
    children.setdefault(n.parent_id, []).append(n)
for siblings in children.values():
    siblings.sort(key=lambda n: (n.order_num, n.pk))   # ← 显式排序
# 再从 None 开始递归 walk
```

仍然是一次查询、零递归查库，只是排序逻辑挪到了内存里。

> 📌 **坦白一处真实经历**：`v0.3.0` 这个 tag 里的参考实现用的就是错的 `ORDER BY path`。
> 我是在 `v0.4.0` 实现权限树时才发现的——因为权限树的同级子节点有 4~5 个，
> 加上目录层，ID 很快跨过了 10，排序立刻就乱了。
>
> **`v0.3.0` 的测试全绿，因为它只建了 3 个部门。** 这本身就是个教学点：
> **数据规模不足的测试，测不出与规模相关的 bug。**
> 修复在 `v0.4.0` 的 commit 里，配套测试 `tests/common/test_tree_rows.py`
> 特意造了 12 个平级节点，还加了一个「对照组」断言证明 `ORDER BY path` 确实是错的。

## 六、卡住了看这里（渐进提示）

<details>
<summary><b>提示 1：save() 里维护 path 的骨架</b></summary>

```python
def save(self, *args, **kwargs):
    old_path = self.path                    # 移动前的 path（新建时为空）
    super().save(*args, **kwargs)           # 先存，拿到 pk

    parent_path = self.parent.path if self.parent else "/"
    new_path = f"{parent_path}{self.pk}/"
    new_depth = (self.parent.depth + 1) if self.parent else 0

    if new_path != self.path or new_depth != self.depth:
        Department.objects.filter(pk=self.pk).update(path=new_path, depth=new_depth)
        self.path, self.depth = new_path, new_depth
        if old_path and old_path != new_path:
            self._cascade_subtree(old_path, new_path)
```

注意 `old_path` 要在 `super().save()` **之前**取——虽然本例中 save 不会改 path，但养成先快照的习惯。
</details>

<details>
<summary><b>提示 2：子树级联更新</b></summary>

```python
def _cascade_subtree(self, old_path, new_path):
    """自身 path 变化后，同步更新所有后代的 path 和 depth。

    一次查询取出整棵子树，内存里做前缀替换，一次 bulk_update 写回。
    不用递归 save()：写操作次数从 O(n) 降到 O(1)。
    """
    descendants = Department.objects.filter(path__startswith=old_path).exclude(pk=self.pk)
    for node in descendants:
        node.path = new_path + node.path[len(old_path):]
        node.depth = node.path.count("/") - 2
    if descendants:
        Department.objects.bulk_update(descendants, ["path", "depth"])
```
</details>

<details>
<summary><b>提示 3：树形渲染（不用递归模板）</b></summary>

```python
def build_tree_rows(queryset, order_field="order_num"):
    """一次查询取全部节点，内存里做先序遍历。

    ⚠️ 不能靠 ORDER BY path 得到树序，见陷阱 7。
    """
    nodes = list(queryset)
    children = {}
    for node in nodes:
        children.setdefault(node.parent_id, []).append(node)
    for siblings in children.values():
        siblings.sort(key=lambda n: (getattr(n, order_field, 0), n.pk))

    rows = []

    def walk(parent_id, depth):
        for node in children.get(parent_id, []):
            rows.append({"obj": node, "depth": depth, "indent_px": depth * 24})
            walk(node.pk, depth + 1)

    walk(None, 0)
    return rows
```

一次查询，零递归**查库**（内存里的递归不花钱）。
</details>

<details>
<summary><b>提示 4：环检测</b></summary>

把一个部门设为自己后代的子部门，会造出一个游离的环。在 `clean()` 里挡掉：

```python
def clean(self):
    if self.parent_id and self.pk:
        if self.parent.path.startswith(self.path):
            raise ValidationError({"parent": "不能将部门移动到自己的下级部门中"})
```

一行判断解决——**这又是路径枚举方案的红利**。用纯邻接表的话，这里要向上遍历整条链。
</details>

## 九、延伸思考

1. **`path` 是冗余数据，理论上可能和 `parent` 不一致。** 什么情况下会不一致？（提示：有人直接改数据库、`bulk_create` 绕过 `save()`、迁移脚本里改数据）

   这就是为什么要写 `rebuild_dept_path` 命令。想想：这个命令要怎么写才能保证「无论当前 path 多乱，跑完都对」？（提示：只信任 `parent`，从根开始重算）

2. **`bulk_create` 不调用 `save()`。** 这意味着用它批量建部门会导致 path 全空。你打算怎么防？在 `v1.0.0` 写 `seed_demo` 时你会真的遇到这个问题。

3. 现在的实现里，`User.department` 是**单个**外键（PRD 的 FR-1.4 简化）。如果要支持兼岗（一人多部门），要改哪些地方？

   提前剧透一下：`v0.14.0` 里所有需要部门的地方都会走 `services.get_user_dept_ids(user)`，**这个函数返回的是集合而不是单值**——就是为了给这个扩展留位置。留意一下这种「为可能的变化预留形状，但不预先实现」的做法，它和过度设计的界限在哪里？

4. 如果部门数量涨到 10 万（比如做的是政务系统的行政区划），路径枚举还合适吗？`LIKE '/1/3/%'` 的索引效率如何？（关键词：B-tree 索引的前缀匹配、PostgreSQL 的 `text_pattern_ops`）

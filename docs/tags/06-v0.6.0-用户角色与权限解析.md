## 三、接口契约（必须与我的实现对齐）

### ⚠️ `services.py` 的硬约束

> **`apps/rbac/services.py` 不得 import 任何 `django.http` / DRF 的东西，函数不接收 `request` 参数。**

这是 [ADR-013](../02-设计文档.md#adr-013权限内核与表现层解耦让模板和-api-共用同一套判断) 定下的约束，从本 tag 一直保持到 `v1.2.0`。届时的验收条件是：

```bash
git diff v1.1.0 v1.2.0 -- apps/rbac/services.py   # 期望输出为空
```

也就是说：**接入一整套 DRF API 时，这个文件一行都不用改。** 现在多花的这点心思，13 个 tag 之后一次性兑现。

### `UserRole`

```python
class UserRole(models.Model):
    user = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE, related_name="user_roles")
    role = models.ForeignKey(Role, on_delete=models.CASCADE, related_name="user_roles")
    granted_by = models.ForeignKey(settings.AUTH_USER_MODEL, null=True, blank=True,
                                   on_delete=models.SET_NULL, related_name="granted_roles")
    granted_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        unique_together = [("user", "role")]
```

> 用 `settings.AUTH_USER_MODEL` 字符串引用，不要直接 import `User`——这是 Django 的标准做法，避免循环导入。

## 五、⚠️ 容易写错的地方

### 1. 别忘了排除 catalog 节点

`v0.5.0` 的陷阱 4 埋了个雷：如果目录节点也被存进了 `RolePermission`，而目录的 `code` 是 `None`——

```python
codes = Permission.objects.filter(...).values_list("code", flat=True)
# 结果里混进了 None！
```

`frozenset({None, "system:dept:view", ...})` 看起来没问题，直到某天有人写 `if some_var in codes` 而 `some_var` 恰好是 `None`，就通过了。

```python
.exclude(code__isnull=True)     # ← 必须加
```

顺手也加上 `.exclude(code="")`，防御空串。

### 2. 超管不要返回「全部权限码的集合」

```python
# ❌ 看起来很自然，但有两个问题
if user.is_superuser:
    return frozenset(Permission.objects.values_list("code", flat=True))
```

问题一：**多一次数据库查询**，而超管路径本该是零成本的短路。
问题二：**语义错误**。超管的含义是「绕过权限检查」，不是「拥有当前数据库里的所有权限」。如果代码里检查一个尚未同步入库的权限码，超管应该通过——但这个实现会返回 False。

用哨兵对象 `ALL_PERMS`（契约里给了）。

### 3. 匿名用户和禁用用户

```python
if not user or not user.is_authenticated or not user.is_active:
    return frozenset()
```

三个条件缺一不可：
- `AnonymousUser` 没有 `is_active` 属性吗？其实有，恒为 `False`。但 `is_authenticated` 更明确。
- **`is_active` 这一条很关键**：用户被禁用后，他的 session 还在，`request.user` 仍然是那个用户对象。如果不检查 `is_active`，被禁用的账号在 session 过期前还能正常操作。

### 4. 返回 `frozenset` 而不是 `set`

第一节第 2 问。`frozenset` 不可变，意味着：
- 调用方拿到后改不了（防御性）
- 可以安全地放进缓存（`v0.16.0` 会用到）
- 可以作为 dict 的 key

用 `list` 的话，`in` 操作是 O(n)——一个页面判断 50 次权限，权限有 200 个，就是 1 万次比较。用 set 是 O(1)。

### 5. 查询要一次做完，不要循环

```python
# ❌ N+1
for role in user.roles.all():
    for rp in role.role_permissions.all():
        codes.add(rp.permission.code)

# ✅ 一次查询
Permission.objects.filter(
    role_permissions__role__in=role_ids, is_active=True, is_deprecated=False
).exclude(code__isnull=True).values_list("code", flat=True)
```

用 `assertNumQueries` 把次数锁死。

### 6. 别提前加缓存

看到这个函数每次都查库，手会痒。**忍住。**

缓存是 `v0.16.0` 的内容。理由：缓存是优化，优化必须建立在**正确**之上。现在先让逻辑对、看得懂、有测试守住；到了 `v0.16.0`，你会发现缓存可以**包在外面**而几乎不动原逻辑——那时你就理解了「好的抽象让优化可以后加」。

<details>
<summary><b>提示 1：services.py 骨架</b></summary>

```python
"""RBAC 权限内核。

⚠️ 本模块是纯函数模块，严禁 import django.http / DRF，
   严禁接收 request 参数。详见 ADR-013。
   它同时服务于 Web 模板层和（v1.1.0 起的）API 层。
"""
from __future__ import annotations
from typing import Iterable

from apps.rbac.models import Permission, Role


class _AllPerms:
    def __contains__(self, item): return True
    def __iter__(self): return iter(())
    def __repr__(self): return "<AllPerms>"


ALL_PERMS = _AllPerms()


def get_user_perm_codes(user) -> frozenset[str]:
    if not user or not user.is_authenticated or not user.is_active:
        return frozenset()
    if user.is_superuser:
        return ALL_PERMS                       # 短路，不查库

    role_ids = list(
        Role.objects.filter(user_roles__user=user, is_active=True).values_list("id", flat=True)
    )
    if not role_ids:
        return frozenset()

    return frozenset(
        Permission.objects
        .filter(role_permissions__role_id__in=role_ids, is_active=True, is_deprecated=False)
        .exclude(code__isnull=True)
        .exclude(code="")
        .values_list("code", flat=True)
        .distinct()
    )


def user_has_perm(user, code: str) -> bool:
    return code in get_user_perm_codes(user)
```

注意 `get_user_perm_codes` 的返回类型标注是 `frozenset[str]`，但超管路径返回的是 `ALL_PERMS`。这是个善意的谎言——它不是 frozenset，但它支持 `in`。想想有没有更严谨的写法（提示：`Protocol` / `Collection[str]`）。

## 九、延伸思考

1. **第一节第 5 问的完整答案**：为什么 `services.py` 不能 import `django.http`？

   <details>
   <summary>展开</summary>

   因为它要同时服务两种表现层。Web 层不通过时要 `raise PermissionDenied` → 渲染 403 HTML；API 层不通过时要返回 403 JSON。**「不通过之后做什么」是表现层的事，内核只负责回答「通过还是不通过」。**

   一旦内核里出现 `HttpResponseForbidden`，它就绑死在 Web 上了。`v1.1.0` 加 DRF 时，你要么复制一份逻辑（两份逻辑必然漂移，漏洞就诞生了），要么大改内核。

   这个约束的收益延迟 13 个 tag 才兑现——**这也正是它容易在中途被放弃的原因。每次违反，当下都能省几行代码，代价要很久以后才付。**
   </details>

2. **权限取并集，那「负权限」（显式拒绝）怎么办？** 比如「客服主管拥有全部工单权限，但**不能**导出」。

   现在的模型表达不了这个。想想：
   - 加一个 `is_denied` 标记到 `RolePermission` 上？
   - 那么「一个角色允许、另一个角色拒绝」时听谁的？（提示：查一下防火墙规则和 ACL 里的「显式拒绝优先」原则）
   - 引入负权限之后，「这个人为什么没有这个权限」的排查难度会怎样？

   本项目**不做负权限**。想想这个决定和 [ADR-006](../02-设计文档.md#adr-006角色单继承语义固定为子角色--父角色) 选单继承是不是同一类考量。

3. `UserRole` 里有 `granted_by` 和 `granted_at` 两个字段，本 tag 只是存着没用。它们是给谁准备的？（提示：`v0.17.0`）

4. **提前感受一下 `v0.16.0` 的问题**：现在渲染一个有 30 个按钮的页面，`user_has_perm` 会被调用 30 次，每次 2 个查询 = 60 次查询。

   打开 Django Debug Toolbar 或者用 `CaptureQueriesContext` 数一数。**先感受痛，再学解法。**

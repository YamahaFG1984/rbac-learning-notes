## 五、⚠️ 逐个击破

### 🔴 洞 1：表单字段黑名单 → 白名单

```python
# ❌ 黑名单：将来加了新的敏感字段，会自动进入表单
class UserForm(forms.ModelForm):
    class Meta:
        model = User
        exclude = ["password", "is_superuser"]

# ✅ 白名单：新字段默认不在表单里，要显式加
class UserForm(forms.ModelForm):
    class Meta:
        model = User
        fields = ["username", "real_name", "phone", "email", "department", "is_active"]
```

**为什么这是本 tag 最重要的一条？**

> 黑名单是一个**随时间自然劣化**的设计。今天你排除了 `is_superuser`，明天有人加了个 `is_admin` 字段，它会自动出现在表单里，没有任何人会注意到。
>
> 白名单相反：新字段默认**不在**表单里。要加进去必须有人显式写一行代码，那行代码会进 code review。

> **`CLAUDE.md` 安全红线第 3 条。也是本项目「让默认状态是安全的」这一原则的第三次出现**：
> 1. `v0.14.0` 默认拒绝（无角色 → 空集）
> 2. `v0.9.0` `@public_view` 必须显式声明
> 3. 本 tag 的表单白名单

**测试怎么写**：

```python
def test_cannot_escalate_to_superuser(client, normal_user):
    client.force_login(normal_user)
    client.post(reverse("accounts:user_update", args=[normal_user.pk]), {
        "username": normal_user.username, "real_name": "x",
        "is_superuser": "1",              # ← 硬塞
        "is_active": "1",
    })
    normal_user.refresh_from_db()
    assert normal_user.is_superuser is False
```

### 🔴 洞 2：`is_superuser` 只能命令行创建

即使表单排除了它，也要确保**没有任何界面路径**能设置它。

检查：
- 用户新建表单 ✅
- 用户编辑表单 ✅
- 批量导入 ⚠️（如果有的话）
- Django admin ⚠️（`is_staff` 的人能进 admin，admin 的 UserAdmin 默认是能改 `is_superuser` 的！）

**Django admin 是个后门**。要么不给任何人 `is_staff`，要么在自定义的 `UserAdmin` 里也做限制。

> 为什么这么严格？因为「用户管理」页面上一个 `is_superuser` 勾选框，意味着**任何拥有 `system:user:update` 权限的人都能把自己提升为超管**——这是教科书级的垂直越权。

### 🔴 洞 3：权限不可放大

第一节第 4 问。

假设小李有 `system:role:assign_perm` 权限（能给角色配权限），但他自己没有 `ticket:ticket:delete`。

**他能不能给自己的角色加上 `ticket:ticket:delete`？** 在 `v0.5.0` 的实现里——**能**。这就是提权。

```python
def can_grant_role(granter, role) -> bool:
    if granter.is_superuser:
        return True
    granter_codes = get_user_perm_codes(granter)
    role_codes = get_role_effective_codes(role)
    return role_codes <= set(granter_codes)     # 子集判断
```

同理，配置角色权限时也要校验：**不能授出自己没有的权限**。

⚠️ **这个约束在实践中有争议**：
- 优点：杜绝了自我提权。
- 缺点：一个「权限管理员」如果本身权限很少，就配不了别的角色。要让他能配，就得给他所有权限——反而更危险。

**折中方案**：区分「权限管理员」和「业务权限」两套体系，前者只能操作后者。本项目实现简单版（子集校验），并在注释里说明这个争议。

**这是一个没有完美答案的设计问题，值得想清楚再选。**

### 🔴 洞 4：禁用用户的会话

第一节第 5 问。

三道防线（纵深防御）：

1. `ModelBackend.get_user()` 检查 `is_active`（Django 自带，`v0.9.0` 我们继承了它）
2. `get_user_perm_codes()` 检查 `is_active`（`v0.6.0` 加的）
3. `build_scope_q()` 检查 `is_active`（`v0.14.0` 加的）

**验证**：登录后，在另一个会话里把该用户禁用，然后刷新页面——应该立即被踢出。

如果没被踢出，检查你的 `RBACBackend` 是不是重写了 `get_user()` 却漏了 `is_active` 判断。

### 洞 5：CSRF 与写操作

- 所有写操作必须是 POST（`@require_POST`）
- 所有 POST 表单必须有 `{% csrf_token %}`
- 删除操作不能用 GET 链接

**检查方法**：grep 一遍模板里的 `<a href` ，看有没有指向删除/修改类 URL 的。

### 洞 6：越权矩阵里遗漏的组合

把设计文档 6.2 的矩阵拿出来，逐格验证。特别注意「无角色用户」和「匿名用户」这两列——它们最容易被忽略，因为开发时没人用这种账号测试。

<summary><b>提示 2：权限不可放大的校验点</b></summary>

要在**两个**地方校验：

```python
# 1. 分配角色给用户时
if not can_grant_role(request.user, role):
    raise PermissionDenied("不能授予超出自身权限范围的角色")

# 2. 给角色配置权限时
granter_codes = set(get_user_perm_codes(request.user))
new_codes = {p.code for p in selected_perms if p.code}
if not request.user.is_superuser and not new_codes <= granter_codes:
    raise PermissionDenied("不能授出自己不具备的权限")
```

⚠️ 第 2 处还要考虑：这个角色**已有**的权限（可能是别人配的，超出了当前操作者的范围）——不能因为操作者动了别的选项就把它们清掉。想想怎么处理。

## 九、延伸思考

1. **「让默认状态是安全的」这条原则，在本项目出现了三次**（见洞 1 的说明）。

   还能想到第四次吗？（提示：`v0.5.0` 的 `data_scope` 默认值、`v0.4.0` 的权限点只能代码声明。）

   **共同模式**：不是「小心不要出错」，而是「让出错需要额外的动作」。

2. **「权限不可放大」的争议**（洞 3）值得再想想。

   企业里真实的场景是：HR 系统管理员负责给人开账号配角色，但他自己不需要业务权限。按子集校验，他什么都配不了。

   实践中的解法有几种：
   - 引入「授权范围」概念：某个角色可以授予哪些角色，单独配置
   - 双人授权：敏感角色的分配需要两个人确认
   - 事后审计 + 告警：允许操作，但立即通知安全团队

   想想哪种适合什么规模的组织。

3. **本项目现在防住了哪些 OWASP Top 10？**

   对照 OWASP Top 10 2021 逐条看：
   - A01 Broken Access Control ← **本项目的主题**
   - A02 Cryptographic Failures ← 密码哈希 ✅
   - A03 Injection ← Django ORM 天然防 SQL 注入 ✅；XSS 靠模板自动转义 ✅
   - A05 Security Misconfiguration ← 安全响应头 ✅
   - A07 Identification and Authentication Failures ← 登录锁定 ✅、会话管理 ✅

   剩下的呢？哪些是本项目没覆盖的？

4. **渗透测试的思维方式**：第一节让你「假设你是攻击者」。这个视角切换非常重要——

   开发者的思维是「怎么让功能跑通」，攻击者的思维是「哪里没跑通/跑通了不该跑通的」。

   养成习惯：**每写完一个功能，花 2 分钟想「我怎么滥用它」。** 这比事后做安全审计便宜得多。

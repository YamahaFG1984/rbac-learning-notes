## 1. 背景

### 1.1 问题陈述

几乎每个企业内部系统最后都会遇到同一个问题：**谁能做什么，以及能对哪些数据做**。

最开始通常是 `if user.is_admin:`。三个月后变成 `if user.is_admin or user.is_manager or (user.dept == obj.dept and user.level > 3):`。再过半年，权限判断散落在 40 个视图里，没人敢改，产品提一个「财务主管只能看本大区的报销单」的需求要排两周。

RBAC（Role-Based Access Control，基于角色的访问控制）是这个问题的标准答案：**不把权限直接给人，而是给角色；人通过担任角色获得权限。** 这样组织变动时改的是「人-角色」关系，而不是散落各处的判断逻辑。

### 1.2 为什么这个项目值得认真做

RBAC 的核心概念（用户、角色、权限）三句话能讲完，但真正做一套能用的系统，难点全在概念之外：

- 权限点的**粒度**怎么定？定粗了不够用，定细了没人维护得动。
- 菜单和权限是**同一个东西**还是两个东西？
- 角色能不能**继承**？继承的方向是什么？环怎么办？
- 「只能看本部门数据」这种**数据权限**，和「能不能点这个按钮」的**功能权限**，是同一套机制吗？
- 权限判断放在**哪一层**？中间件、装饰器、还是 ORM？
- 每次请求都查一遍权限表，**性能**怎么办？缓存什么时候失效？
- 用户 A 把 URL 里的 `id=1` 改成 `id=2`，你的系统**挡得住吗**？

这些问题没有唯一答案，只有取舍。本项目的价值在于把取舍过程显式地写出来。

### 1.3 教学目标

完成本项目后，学习者应当能够：

| 编号 | 目标 |
| --- | --- |
| G-1 | 准确说出 NIST RBAC 各层级（RBAC0/1/2/3）的区别，以及各自解决什么问题 |
| G-2 | 独立设计一套权限点编码规范，并说明粒度选择的依据 |
| G-3 | 实现角色继承，并处理环检测、继承深度、权限并集计算 |
| G-4 | 实现数据行级权限，理解它与功能权限在实现机制上的根本差异 |
| G-5 | 说清楚 Django 自带 `auth.Permission` 的能力边界，以及何时该弃用它 |
| G-6 | 在视图层、模板层、ORM 层三处正确布设权限检查点，理解各自的职责 |
| G-7 | 设计权限缓存及其失效策略，说明为什么「角色变更后立即生效」是个难题 |
| G-8 | 识别并防御常见越权漏洞（水平越权、垂直越权、IDOR） |
| G-9 | 把同一套权限内核复用到前后端不分离和分离两种架构上 |

### 1.4 非目标（明确不做）

| 编号 | 不做的事 | 原因 |
| --- | --- | --- |
| NG-1 | 多租户 / SaaS 租户隔离 | 会引入一整套正交的复杂度（租户上下文传递、跨租户越权防护、数据库分片），淹没 RBAC 本身 |
| NG-2 | 单点登录（SSO / OAuth2 / CAS） | 属于**认证**（Authentication）范畴，本项目聚焦**授权**（Authorization） |
| NG-3 | 完整的 ABAC 策略引擎 | 见设计文档 ADR-007；本项目在数据权限处会触及 ABAC 思想，但不做通用策略引擎 |
| NG-4 | 工作流 / 审批流 | 独立领域，与权限正交 |
| NG-5 | 生产级部署（K8s、CI/CD、监控） | 与教学目标无关 |
| NG-6 | 前端工程化（Vue/React SPA 脚手架） | 阶段二只提供 API 与 API 层权限校验，不做前端项目 |

## 2. 名词表

统一术语，后续所有文档和代码命名以此为准。

| 术语 | 英文 / 代码标识 | 定义 |
| --- | --- | --- |
| 用户 | User | 系统的操作主体，一个自然人对应一个账号 |
| 部门 | Department | 组织架构节点，树形结构。用户归属于**一个**部门 |
| 角色 | Role | 一组权限的命名集合。角色之间可以有继承关系 |
| 权限点 | Permission | 系统中一个不可再分的受控操作，如「删除工单」。用 `perm_code` 唯一标识 |
| 权限码 | perm_code | 权限点的字符串标识，格式 `模块:资源:动作`，如 `ticket:ticket:delete` |
| 功能权限 | Functional Permission | 回答「能不能执行这个操作」，是布尔判断 |
| 数据权限 | Data Permission / Data Scope | 回答「能对哪些数据行执行这个操作」，是集合过滤 |
| 数据范围 | data_scope | 角色上的一个枚举字段，定义该角色可见的数据行范围 |
| 授权 | Assignment | 用户-角色 或 角色-权限 的绑定关系 |
| 角色继承 | Role Hierarchy | 子角色自动拥有父角色的全部权限（RBAC1 的核心特征） |
| 有效权限 | Effective Permissions | 一个用户经过角色继承展开、多角色合并后，最终拥有的全部权限码集合 |
| 越权 | Privilege Escalation | 用户获得了未被授予的权限。分**水平越权**（访问同级别他人数据）和**垂直越权**（获得更高级别权限） |
| 超级管理员 | Superadmin | 绕过所有权限检查的特殊账号，用于系统初始化和救急 |

## 3. 用户画像

本系统有三类使用者。注意：**「角色」是系统内的数据，「用户画像」是系统外的人**，两者不要混淆。

### P-1 系统管理员（Sysadmin）

- **是谁**：IT 部门的人，负责搭建和维护权限体系。
- **要做什么**：定义部门树、录入权限点、设计角色、给人分配角色。
- **痛点**：需求方说「给张三开个能看报表但不能导出的权限」，他要能在 30 秒内找到对应权限点并完成配置，不需要改代码。
- **对系统的要求**：权限点必须可视化、可搜索、有清晰的层级；角色配置界面要能一眼看出「这个角色到底有哪些权限」，包括从父角色继承来的。

### P-2 部门主管（Manager）

- **是谁**：业务部门的中层，比如客服主管。
- **要做什么**：查看和处理**本部门及下属部门**的工单，给组员派单。
- **痛点**：他不应该看到其他部门的工单，但必须看到自己所有下属的。
- **对系统的要求**：数据权限必须准确。列表页、详情页、导出、统计，**每一处**都不能漏。

### P-3 普通职员（Staff）

- **是谁**：一线操作人员。
- **要做什么**：处理分配给自己的工单。
- **痛点**：菜单里不该出现他点不了的功能——点了报错的体验比看不见更差。
- **对系统的要求**：菜单和按钮必须按权限动态渲染。

## 5. 关键用户故事

### US-1：新人入职开权限

> 作为**系统管理员**，当客服部新入职一名员工时，我希望能在用户管理里创建账号、选择「客服部」、勾选「客服专员」角色并保存，该员工登录后就自动看到客服相关的菜单，且只能看到自己的工单。
>
> **验收**：全程无需改代码；从创建到该员工可用 ≤ 2 分钟。

### US-2：主管的数据范围

> 作为**客服主管**，我希望登录后能看到客服部及其下属所有小组的工单，但看不到技术部的工单。
>
> **验收**：客服部有 3 个子部门共 50 张工单，技术部有 30 张。主管登录后列表总数显示 50，且用技术部工单的 ID 直接访问详情页返回 404。

### US-3：新增权限点

> 作为**系统管理员**，当研发上线了「工单批量关闭」功能后，我希望能在权限管理里看到新增的权限点（由研发在代码中声明并同步入库），把它勾选给「客服主管」角色，主管刷新页面后就能看到这个按钮。
>
> **验收**：权限点同步命令执行后，新权限点出现在权限树中；勾选保存后，主管**无需重新登录**即可看到按钮。

### US-4：角色继承避免重复配置

> 作为**系统管理员**，我已经配置好「客服专员」角色（10 个权限）。现在要配置「客服主管」，它应该拥有客服专员的全部权限，外加派单和导出。我希望把「客服主管」的父角色设为「客服专员」，然后只勾选那 2 个额外权限。
>
> **验收**：客服主管的有效权限数为 12；后续给客服专员加权限时，客服主管自动获得。

### US-5：越权尝试被拦截

> 作为**安全测试者**，我用普通职员账号登录，把工单详情 URL 的 ID 改成一个属于其他部门的工单 ID。
>
> **验收**：返回 404，且审计日志中记录了这次被拒绝的访问。

## 6. 非功能需求

| 编号 | 类别 | 要求 |
| --- | --- | --- |
| NFR-1 | 性能 | 单次请求的权限判断（含数据范围解析）不得引入额外 DB 查询，命中缓存时 < 1ms |
| NFR-2 | 性能 | 列表页的数据权限过滤必须在 SQL 层完成，禁止先查全量再在 Python 里筛 |
| NFR-3 | 性能 | 菜单树渲染的查询次数与菜单层级无关（避免 N+1） |
| NFR-4 | 一致性 | 权限变更后生效延迟 ≤ 一次请求（即变更即失效缓存，而非等 TTL 过期） |
| NFR-5 | 安全 | 所有权限判断在服务端完成；前端隐藏按钮**不构成**安全边界 |
| NFR-6 | 安全 | 密码使用 Django 默认哈希器（PBKDF2-SHA256），不得明文或可逆存储 |
| NFR-7 | 安全 | 所有写操作走 POST 并启用 CSRF 保护 |
| NFR-8 | 可维护性 | 权限内核（`apps/rbac`）不得依赖任何业务模块 |
| NFR-9 | 可测试性 | 核心权限逻辑单元测试覆盖率 ≥ 85%；每个数据范围枚举值至少一个测试用例 |
| NFR-10 | 可移植性 | 默认 SQLite 即可运行，切换 PostgreSQL 只需改环境变量 |
| NFR-11 | 教学性 | 每个 Git tag 都能 `runserver` 起来并完成该阶段声明的功能 |

## 9. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 权限点粒度设计不当，后期大改 | 高 | 在 v0.4.0 就固化编码规范，并在设计文档 ADR-004 中论证 |
| 数据权限与功能权限混为一谈，实现纠缠 | 高 | 两者在代码上完全分离：功能权限在视图层，数据权限在 Manager 层 |
| 缓存失效不彻底导致权限「不生效」 | 中 | 采用版本号失效法而非逐 key 删除，见 ADR-010 |
| 教学项目为了「教学」而过度简化，失去参考价值 | 中 | 所有简化处必须在设计文档中显式标注「生产环境应如何处理」 |
| tag 粒度过粗，diff 看不懂 | 中 | 单个 tag 的代码变更控制在 400 行以内，超出则拆分 |

### 1.1 层数没变，边界数也没变

| 层 | React 版 | Vue 版 | 是不是安全边界 |
| --- | --- | --- | --- |
| 后端 API 鉴权 | `HasPerm` + `.for_user()` | **完全相同** | ✅ **唯一的** |
| 路由守卫 | `<PermissionGate>`（渲染期） | `router.beforeEach`（**导航期**） | ❌ 体验 |
| 菜单渲染 | `menuAdapter` | **同一份逻辑** | ❌ 体验 |
| 按钮 | `<Can>` | `<Can>` | ❌ 体验 |
| 表单字段禁用 | `disabled` | `:disabled` | ❌ 体验 |

> **换了框架，四层体验 + 一层安全的结构没有任何变化。**
>
> 这句话看起来平淡，但它是本阶段最值得记住的结论：
> 权限架构的层次划分**不是框架决定的**，是问题本身决定的。
>
> ⚠️ 但有一处**变化值得警惕**：Vue 的守卫在导航期，写出来是这样——
>
> ```ts
> router.beforeEach((to) => {
>   if (!can(to.meta.perm)) return '/403'    // 看起来太像鉴权了
> })
> ```
>
> 它比 React 的 `<PermissionGate>` **更像真正的鉴权**：拦在导航前，页面组件根本不会被创建，
> 网络请求也不会发出。**正因为它更像，错觉也更强。**
>
> 但它依然挡不住任何攻击者——`can()` 读的是浏览器内存里的 Pinia store，
> Devtools 里改一下就通过了，而且他根本不必用你的前端。

## 2. 架构决策记录（V-ADR）

### V-ADR-001：三套前端并存，Vue 版放独立目录

**问题**：Vue 版是替换 React 版，还是并存？放哪？

**候选**

| 方案 | 说明 |
| --- | --- |
| a. 在 `frontend/` 里加一个 Vue 入口 | 共享 `node_modules`、构建配置 |
| b. **`frontend-vue/` 独立目录** | 完全隔离 |
| c. monorepo（pnpm workspace） | 共享公共包 |

**决定**：方案 b。

**理由**

方案 a 和 c 都会引入**共享代码**，而共享代码正是本阶段要避免的东西：
一旦 `api/client.ts` 被抽成共享包，「两边的拦截器逐字相同」这个**结论**就变成了**前提**，
对比就失去了意义。

> **要证明两边一样，必须让它们真的各写一份，然后 diff。**
> 抽成公共包等于把结论藏进了工程结构里。

方案 b 有重复代码——**这正是我们要的**。`vue-v1.0.0` 会跑一次逐文件 diff，
用行数量化「哪些部分与框架无关」。

**代价**
- `api/`、`e2e/` 有大量重复。**接受**，重复本身是被度量的对象。
- 依赖装两份，磁盘占用翻倍。
- ⚠️ 后端改了 API 契约要同步改两处。→ 靠结构性测试和 `--check` 命令守。

### V-ADR-002：最小差异原则——框架无关的部分，库和版本完全相同

**问题**：Vue 版的技术选型，是「选 Vue 生态最流行的」还是「尽量对齐 React 版」？

**决定**：**凡是与框架无关的，用完全相同的库和版本。** 只替换真正绑定框架的那几个。

| 关注点 | React 版 | Vue 版 | 换了吗 |
| --- | --- | --- | --- |
| 构建 | Vite 8 | Vite 8 | **否** |
| 语言 | TypeScript 6 strict | TypeScript 6 strict | **否** |
| HTTP | axios 1.x | axios 1.x | **否** |
| 服务端状态 | `@tanstack/react-query` 5.101.4 | `@tanstack/vue-query` **5.101.4** | 同库不同适配 |
| 单测 | Vitest 4 | Vitest 4 | **否** |
| 网络 mock | MSW 2 | MSW 2 | **否** |
| E2E | Playwright 1.62 | Playwright 1.62 | **否** |
| —— 以下是真正的替换 —— | | | |
| 框架 | React 19 | **Vue 3.5** | ✅ |
| 路由 | React Router 8 | **Vue Router 5** | ✅ |
| 客户端状态 | Zustand 5 | **Pinia 4** | ✅ |
| UI | Ant Design 6 | **Ant Design Vue 4** | ✅ |
| 组件测试 | `@testing-library/react` | `@testing-library/vue` | ✅ |
| 类型检查 | `tsc` | `vue-tsc` | ✅ |

**理由**

这是**实验设计**问题，不是技术偏好问题。

如果 Vue 版顺手把 axios 换成 `ofetch`、把 Vitest 换成别的、把 TanStack Query 换成
Pinia Colada，那么最后 diff 出来的差异里，**分不清哪些来自 Vue、哪些来自换库**。
控制变量是对照实验的基本要求。

`@tanstack/vue-query` 和 `@tanstack/react-query` 是**同一个 core 的两个适配层**，
版本号都是 `5.101.4`——这是一个近乎理想的对照条件：
同一套缓存语义、同一套失效逻辑，**只有响应式的接入方式不同**。

**代价**
- Ant Design Vue 4 对应的是 antd **5** 的 API 世代，不是 antd 6。
  两边会有几处 API 位置差异（下面第 6 节列出）。→ 这是无法消除的，因为不存在
  「antd 6 的 Vue 版」。**必须诚实记录，不能假装是「Vue 的问题」。**
- 有人会觉得「Vue 生态里 Pinia Colada 更地道」。是的——**但那是另一个实验。**

### V-ADR-003：客户端状态用 Pinia，并显式解决「组件外访问 store」

**问题**：权限快照放哪？怎么在 axios 拦截器里读它？

**背景：React 版没有这个问题**

Zustand 的 store 是**模块级单例**：

```ts
// React 版：任何地方、任何时候都能调
import { useAuthStore } from '@/auth/store'
const perms = useAuthStore.getState().perms      // ✅ 组件外也行
```

Pinia 的 store 绑在 **app 实例**上，`useAuthStore()` 内部要找 `activePinia`：

```ts
// Vue 版：模块加载时就调 → 抛错
import { useAuthStore } from '@/auth/store'
const store = useAuthStore()                     // ❌ 模块顶层执行
// [🍍]: "getActivePinia()" was called but there was no active Pinia. Are you trying to use a store before calling "app.use(pinia)"?
```

而 `api/client.ts` 的拦截器**就是在模块顶层注册的**。这个时序必须处理。

**候选**

| 方案 | 说明 | 问题 |
| --- | --- | --- |
| a. `setActivePinia(pinia)` 全局设一次 | 最省事 | 隐式全局态；SSR 下多实例会串；单测之间互相污染 |
| b. 把 pinia 实例 import 进来，`useAuthStore(pinia)` | 显式 | `api/` 要 import `pinia` 实例，**违反依赖方向** |
| c. **延迟调用：拦截器内部才 `useAuthStore()`** | 拦截器**执行**时 app 已挂载 | 每次调用都走一次 store 解析（可忽略） |
| d. **注入：`App.vue` 启动时把读取函数注入 `api/`** | 与 React 版 `setXxxHandler` 完全同构 | 多一层间接 |

**决定**：**c + d 组合。**

- 纯读取（如「当前 perms」）用 **c**：在拦截器函数体内部调用，而不是模块顶层。
- 需要触发副作用（跳登录页、弹提示、invalidate query）的用 **d**，与 React 版
  `setUnauthorizedHandler()` / `configureVersionWatcher()` **保持完全相同的形状**。

```ts
// ✅ src/api/client.ts —— 注意 useAuthStore() 在函数体内
client.interceptors.request.use((config) => {
  const auth = useAuthStore()          // 此时 app.use(pinia) 早已执行
  ...
})
```

**理由**

方案 d 的形状必须和 React 版一样，否则对比会被工程差异干扰。
而 React 版之所以也用注入（`api/` 不许 import 路由和 QueryClient），理由是**依赖方向**——
Vue 版多了一条理由（**实例化时序**），但结论相同。

> **同一个做法，两边的理由不同。** 这类地方最值得记：
> 它说明「注入」不是某个框架的技巧，而是「模块加载期 ≠ 应用运行期」这个
> 普遍问题的通解。

**代价**
- 单测里每个用例必须 `setActivePinia(createPinia())`，否则 store 在测试间串。
  → 写进 `test/setup.ts` 的全局 `beforeEach`。
  ⚠️ 这与 React 版**恰好相反**：Zustand 的模块级单例需要**手动 reset**，
  Pinia 需要**手动创建**。两种相反的麻烦，**都不能忘**。
- 方案 c 让「拦截器依赖 store」这件事藏在函数体里，读代码时不显眼。
  → 在 `client.ts` 顶部写注释说明为什么不能提到模块顶层。

### V-ADR-004：动态路由用 `router.addRoute()`，并**必须**保存移除函数

**问题**：profile 到手后怎么把有权限的路由装进 router？

**React 版怎么做的**

```tsx
// 用 menus 重新构建整个 router，换掉 RouterProvider 的实例
const router = useMemo(() => createBrowserRouter(buildRoutes(menus)), [menus])
return <RouterProvider router={router} />
```

**「重建」有一个隐含的好处：旧路由自动消失。** 登出时 `menus` 变空，router 重建，
上一个账号的路由不复存在——**不需要写任何清理代码**。

**Vue Router 的 API 是「加」不是「重建」**

```ts
const stop = router.addRoute('layout', record)   // 返回一个移除函数
```

`addRoute` 是**增量**的，没有 `setRoutes()`。这带来两个后果：

| 后果 | 表现 |
| --- | --- |
| 1. 加完之后**当前路由不会重新匹配** | 刷新页面停在 404，见 V-ADR-005 |
| 2. 登出/换账号后**旧路由还在** | `VE-3.8` / `VUS-6` |

**决定**

```ts
// src/router/dynamic.ts
let registered: Array<() => void> = []

export function registerDynamicRoutes(menus: MenuNode[]) {
  clearDynamicRoutes()                         // ⚠️ 先清，再加
  for (const record of buildRoutes(menus)) {
    registered.push(router.addRoute('layout', record))
  }
}

export function clearDynamicRoutes() {
  // 🔴 登出、换账号、权限变更后都必须调。
  //    Vue Router 没有「重建路由表」这回事，只能一条条移除。
  //    React 版靠重建 router 天然获得这个行为，不需要这个函数——
  //    这是「增量 API」相对「重建 API」多出来的一类维护责任。
  registered.forEach((remove) => remove())
  registered = []
}
```

**为什么用 `addRoute` 返回的函数，而不是 `removeRoute(name)`**

`removeRoute(name)` 要求每条路由都有唯一 `name`，而菜单是后端下发的，
`name` 由 `route_path` 派生——**两个菜单指向同一个组件时会撞名**，
而撞名的表现是「移除了不该移除的那条」，非常难查。

`addRoute` 的返回值不依赖 name，是**精确的**。

**代价**
- 多一个模块级数组，是可变全局态。→ 用两个函数封死，禁止外部直接访问。
- 单测里必须验证「登出后路由确实没了」，否则这个 bug 只有 E2E 能发现。
  → `vue-v0.5.0` 的验收清单里有专门一条。

### V-ADR-005：路由守卫放导航期（`beforeEach`），并处理 `addRoute` 后的重新匹配

**问题**：守卫写在哪？刷新页面为什么会 404？

**决定**：一个 `router.beforeEach`，按顺序做四件事。

```ts
router.beforeEach(async (to) => {
  const auth = useAuthStore()

  // 1. 白名单（登录页、403、404）直接放行
  if (PUBLIC_ROUTES.includes(to.path)) return true

  // 2. profile 还没拉过 → 先拉。⚠️ 这一步是 FE-2.3「加载完成前不渲染业务界面」
  //    在 Vue 里的形态：不是「不渲染」，而是「不导航」。
  if (auth.status === 'unknown') {
    try {
      await fetchProfileIntoStore()
    } catch {
      return { path: '/login', query: { redirect: to.fullPath } }
    }
    registerDynamicRoutes(auth.menus)

    // 🔴 3. 关键的一行。
    //
    //    addRoute() 之后，`to` 是**在旧路由表上算出来的**（大概率是 404 兜底路由）。
    //    直接 return true 会渲染 404 —— 这正是 F-ADR-007 描述的
    //    「刷新页面变 404」，在 Vue 里的表现形式。
    //
    //    必须重新发起一次导航，让它在**新**路由表上重新匹配。
    //    replace: true 是为了不在历史记录里留下一条 404。
    return { ...to, replace: true }
  }

  // 4. 权限判断（体验层，不是安全边界）
  if (to.meta.perm && !auth.can(to.meta.perm as PermCode)) return { path: '/403' }
  return true
})
```

**理由：为什么不像 React 那样放在组件树里**

Vue 也能做「渲染期守卫」（在 `<RouterView>` 外面包一层组件），但那是把 React 的
做法硬搬过来。Vue Router 提供了导航守卫，**在导航期拦截有实质好处**：

| | React（渲染期） | Vue（导航期） |
| --- | --- | --- |
| 页面组件何时创建 | **已经创建**，然后被 `<PermissionGate>` 换成 403 | **根本不创建** |
| 页面里的 `useQuery` | ⚠️ 可能已经发出请求 | 不会发出 |
| URL 何时变化 | 先变，再渲染 403 | 可以在变之前就重定向 |

**但这不是「Vue 的守卫更安全」**——页面组件不创建、请求不发出，
省的是**用户这边**的开销。攻击者手动 `fetch` 时，这一层完全不存在。

> ⚠️ 这是本阶段**最容易产生错误认知**的一处。
> 「Vue 的守卫拦在导航前，所以更安全」——**错。**
> 它拦的是「你自己的前端发起的导航」，而攻击者不导航，他直接发请求。
>
> `vue-v0.14.0` 的 E2E 会用与 React 版**完全相同**的断言证明这一点。

**⚠️ 第 3 步的坑：`return { ...to, replace: true }` 的无限循环**

如果 `fetchProfileIntoStore()` 失败但没有把 `status` 从 `'unknown'` 改掉，
守卫会再次进入第 2 步 → 再次 `return {...to}` → **无限重定向**，
Vue Router 会抛 `Maximum recursive navigation guard calls`。

→ `fetchProfileIntoStore()` 必须**无论成功失败都把 `status` 置为终态**
（`'authenticated'` 或 `'anonymous'`）。这条写进 `vue-v0.4.0` 的验收。

**代价**
- 守卫是 `async` 的，profile 慢时用户会看到「点了没反应」。
  → `vue-v0.3.0` 起在 `<RouterView>` 外挂一个全局 loading 条。
- 所有导航都要过这个守卫，逻辑必须极简且无副作用（除了那次 profile 拉取）。
- 🔴📌 **导航期守卫只对「导航」生效，对「状态变化」完全无感。**（`vue-v0.2.0` 实测补记）

  这一条**初稿里漏了**——当时只写了导航期守卫的好处（拦得更早、组件不创建、
  请求不发出），没意识到它的另一面。实测发现的：

  ```
  登出 → session 清了、store 清了、cookie 也没了
       → 但**用户仍然停在原页面上**，界面还是登录态的壳
  ```

  根因：

  | | React | Vue |
  | --- | --- | --- |
  | 守卫是什么 | **组件**（`RequireAuth`），在渲染树里 | **导航流程的一环**（`beforeEach`） |
  | `status` 变成 `anonymous` 时 | 重新渲染 → `<Navigate>` **自动生效** | **没有导航发生，守卫根本不会运行** |
  | 需要写跳转代码吗 | **不需要** | **必须** |

  → 硬规则：**凡是「状态变了所以该换页面」的场景，Vue 版都必须自己发起导航。**
  目前有两处：`useLogout` 的 `onSettled`、`api/client.ts` 的 401 回调。

  ⚠️ 这也顺带解释了 401 为什么必须注入一个跳转回调而不能只清 store——**同一个原因**。

  > 📌 这是本阶段第一个「预判了好处、漏了代价」的决策。
  > `01-PRD.md` 第 1.3 节的 6 条预判里，第 1 条写的是
  > 「Vue 拦得更早，**但错觉也更强**」——**错觉那一半说对了，代价这一半没想到。**

### V-ADR-006：状态三态而非布尔（继承 F-ADR，理由完全相同）

```ts
status: 'unknown' | 'authenticated' | 'anonymous'
```

**继承 React 版的全部理由，一个字不改**：

> 「还没问过后端」≠「确定未登录」。用布尔值的话初始 `false` 会被当成「未登录」，
> 应用启动瞬间闪一下登录页。更危险的是有人写出
> `perms.length === 0 ? 显示全部 : 按权限显示`——那会真的闪现越权内容。

**Vue 版新增一条理由**：`beforeEach` 的第 2 步靠 `status === 'unknown'` 判断
「要不要拉 profile」。用布尔的话，「没登录」和「没拉过」分不开，
每次导航都会重拉一次 profile，直接违反 `VNFR-7`。

> 同一个决策，Vue 版多出一条**独立成立**的理由。
> 这种「不同路径抵达同一结论」的地方，说明这个结论是稳的。

### V-ADR-007：按钮级权限用 `<Can>` + `usePermission()`，**不提供 `v-perm` 指令**

**问题**：Vue 有 React 没有的第三种形态——自定义指令。用不用？

```vue
<!-- 看起来非常优雅 -->
<a-button v-perm="PERM.TICKET_TICKET_DELETE" danger>删除</a-button>
```

**这是「Vue 该怎么做权限」这个问题里最常见的答案，而本项目决定不用它。**

**决定**：只提供两个接口，与 React 版一一对应。

```vue
<!-- 1. 组件式：控制渲染 -->
<Can :perm="PERM.TICKET_TICKET_DELETE">
  <a-button danger @click="onDelete">删除</a-button>
</Can>

<!-- 2. composable：控制数据（表格列、菜单项） -->
<script setup lang="ts">
const { can } = usePermission()
const columns = computed(() => [
  ...baseColumns,
  ...(can(PERM.TICKET_TICKET_UPDATE) ? [editColumn] : []),
])
</script>
```

**理由：指令有三个具体缺陷，且都与权限场景直接相关**

**缺陷 1：先渲染，再删除**

指令的 `mounted` 钩子在元素**已经挂载到 DOM 之后**才执行。
所以 `v-perm` 的实际行为是「渲染出来 → 发现没权限 → 把它删掉」。

对普通元素这只是一帧闪烁；但如果按钮上有 `@vue:mounted`、有自动聚焦、
有埋点上报，**副作用已经发生了**。`v-if`（`<Can>` 内部用的）根本不会创建它。

**缺陷 2：删掉之后回不来**

`vue-v0.11.0` 的权限变更感知会让 `perms` 在运行时变化。
`<Can>` 用 `v-if`，perms 一变自动重新渲染。
指令删掉的元素**已经不在虚拟 DOM 树上了**，`updated` 钩子不会再被调用——
**权限恢复后按钮不会回来**，除非刷新页面。

> 这一条是致命的：它让 `VE-5.2` 在指令方案下**无法实现**。

**缺陷 3：类型收窄失效**

`F-ADR-012` / `V-ADR-008` 的核心收益是「权限码写错编译期报错」。
指令的值是 `DirectiveBinding['value']`，类型是 `any`：

```vue
<a-button v-perm="'ticket:ticket:delet'">删除</a-button>   <!-- ✅ 编译通过，静默失效 -->
```

**这等于把 SPA 相对模板版唯一的权限安全优势原地退回去了。**

而 `<Can :perm="...">` 的 prop 类型是 `PermCode`，写错**编译不过**。

**代价**
- 模板里比指令方案多一层嵌套。**接受**——多一层 `<Can>` 换回三样东西。
- 有人（包括很多团队规范）会觉得指令才是「Vue 的正确写法」。
  → 在 `frontend-vue/CLAUDE.md` 里写明这三条理由，避免后来者「优化」掉。

> 📌 **这是本阶段唯一一个「Vue 有更多选择，但我们选了和 React 一样的那个」的决策。**
> 值得注意的是：结论不是「指令不好」，而是「**在权限这个具体场景下**，
> 指令的三个特性恰好全是负面的」。换个场景（如 `v-focus`、`v-permission-disabled`）
> 指令可能就是最优解。

### V-ADR-008：权限常量仍由后端生成，导出命令增加 `--out`

**继承 F-ADR-012 的全部理由。** 本条只记录实现上的改动。

**问题**：`export_perm_constants` 把路径写死了。

```python
target = Path(settings.BASE_DIR, "frontend/src/constants/permissions.ts")
```

**决定**：加 `--out` 参数，默认值保持不变。

```bash
python manage.py export_perm_constants                                   # React（默认值不变）
python manage.py export_perm_constants --out frontend-vue/src/constants/permissions.ts
python manage.py export_perm_constants --out ... --check                 # CI
```

**为什么默认值必须保持不变**

React 版的 CI 和 `frontend/CLAUDE.md` 都写着无参数调用。改默认值会让
**上一个阶段的 CI 变红**（`VAC-10`）。

> **给一个已有命令加能力时，「不改变现有调用的行为」是最低要求。**
> 这条在后端 `ADR-004` 加 `--check-templates` 时已经用过一次，形状完全一样。

**代价**
- 现在有两个前端要保持常量同步，CI 里要跑两次 `--check`。
- ⚠️ 两个前端的常量文件内容**必须逐字节相同**（同一个数据库同一个生成器）。
  → `vue-v0.13.0` 加一条结构性测试直接 diff 两个文件。这比跑两次 `--check` 更强：
  它能发现「其中一个忘了重新生成」。

### V-ADR-009：`vue-query` 的 `queryKey` 必须是响应式的

**问题**：这是 `@tanstack/vue-query` 最容易踩且**完全不报错**的坑。

```ts
// ❌ 静默失效：改了筛选条件，不会重新请求
const params = reactive({ page: 1, status: '' })
useQuery({
  queryKey: ['tickets', params.page, params.status],   // 求值一次就定死了
  queryFn: () => fetchTickets(params),
})

// ✅
useQuery({
  queryKey: computed(() => ['tickets', params.page, params.status]),
  queryFn: () => fetchTickets(params),
})
```

**决定**：所有带参数的 `useQuery`，`queryKey` **一律**写成 `computed(() => [...])`，
即使当前没有参数会变。

**理由**

React 版没有这个问题——React 每次渲染都重新求值 `queryKey` 数组，
「响应式」由重渲染天然提供。Vue 的 `<script setup>` **只执行一次**，
数组字面量求值一次就固定了。

> 🔴 **这是「不可变 + 重渲染」与「可变代理 + 依赖追踪」两种模型差异的最典型样本。**
>
> React 的模型让你**很难写出不更新的代码**（代价是要用 `useMemo` 手动阻止过度更新）；
> Vue 的模型让你**很难写出过度更新的代码**（代价是要显式声明哪些是响应式的）。
>
> 两边的 bug 方向**恰好相反**：
> - React 版 `fe-v0.7.0` 踩过 `useMemo` 依赖数组写错 → **router 反复重建**
> - Vue 版会踩 `queryKey` 不响应 → **该更新的不更新**
>
> 而且都**不报错**。

**为什么强制「即使没参数也写 computed」**

因为「现在没参数」会变成「以后加了参数」，而加参数的人不会想到还要改 `queryKey` 的形式。
统一写法把这个陷阱从「需要记住」变成「不可能踩到」。

**代价**
- 无参数的查询多写几个字符。→ 换来一类 bug 的彻底消失，划算。
- 靠 lint 规则守不住（`computed` 与数组字面量在 AST 上都合法）。
  → 在 `frontend-vue/CLAUDE.md` 里列为硬规则，code review 时看。

### V-ADR-010：错误边界用 `onErrorCaptured` + `app.config.errorHandler` 双层

**问题**：Vue 没有 `<ErrorBoundary>` 组件。

**React 版**：`AppErrorBoundary` 是一个 class 组件——
**这是 React 里唯一还必须写 class 的地方**（`getDerivedStateFromError` 没有 hook 版）。

**Vue 版**：两个机制，覆盖范围不同。

| 机制 | 覆盖 | 用途 |
| --- | --- | --- |
| `onErrorCaptured(fn)` | 子组件树的**渲染期**错误 | 局部降级：把出错的子树换成错误页 |
| `app.config.errorHandler` | 全应用，包括 watcher / 生命周期 | 兜底上报 |

**决定**：两层都要。

```vue
<!-- components/AppErrorBoundary.vue -->
<script setup lang="ts">
const error = ref<Error | null>(null)
onErrorCaptured((err) => {
  error.value = err as Error
  return false      // ⚠️ 返回 false 阻止继续向上冒泡，否则会同时触发全局 handler
})
</script>
<template>
  <ErrorResult v-if="error" :error="error" @retry="error = null" />
  <slot v-else />
</template>
```

**⚠️ 两边共有的一个限制，必须写清楚**

`onErrorCaptured` 和 React 的 `componentDidCatch` **都不捕获**：
- 事件处理器里的错误（`@click` 里 throw）
- `setTimeout` / Promise 里的错误
- 异步 `queryFn` 的 reject

所以 **5xx 不能靠错误边界兜住**——API 错误走的是 axios 拦截器那条路
（`F-ADR-011` / `VE-7.x`），错误边界管的是**渲染崩溃**。

> 这个限制在 React 版 `fe-v0.14.0` 已经写过。两边**完全一样**——
> 因为它不是框架的选择，是「同步渲染栈之外的错误无法被组件捕获」这个事实。

**代价**
- `return false` 忘了写会导致错误被处理两次（局部降级 + 全局上报同一个错）。
  → 单测里断言全局 handler 没被调用。

### V-ADR-011：单测用 Vitest + `@testing-library/vue`，每个用例重建 Pinia

**继承 F-ADR-013 的三层划分**（单元 / 集成 + MSW / E2E），只记录差异。

| 层 | React 版 | Vue 版 | 差异 |
| --- | --- | --- | --- |
| 单元 | `@testing-library/react` | `@testing-library/vue` | 断言 API 几乎相同 |
| 集成 | + MSW | **+ MSW（handlers 逐字复用）** | **无** |
| E2E | Playwright | **Playwright（spec 几乎逐字复用）** | **无** |

**唯一的实质差异：store 的隔离方式相反**

```ts
// React：Zustand 是模块级单例 → 测试之间会串 → 必须手动 reset
beforeEach(() => useAuthStore.setState(initialState))

// Vue：Pinia 需要 active 实例 → 必须手动创建
beforeEach(() => setActivePinia(createPinia()))
```

**两个都不能忘，但忘了的表现不同**：
- React 忘了 reset → 测试**顺序相关**，单跑绿、全跑红（最难查的一类）
- Vue 忘了 setActivePinia → **立即抛错**，报错信息直接告诉你原因

> Vue 在这里是**失败得更响**的一方。这不是「更好」——
> 它只是把同一个隐患从运行时挪到了更早、更明确的位置。

**⚠️ 关于 `nextTick` 与 `waitFor`**

```ts
// React：状态更新是异步批处理的
await waitFor(() => expect(screen.getByText('删除')).toBeInTheDocument())

// Vue：DOM 更新在 nextTick
store.perms = ['ticket:ticket:delete']
await nextTick()
expect(screen.getByText('删除')).toBeInTheDocument()
```

Vue 的时序是**确定的**（一个 tick），React 的需要轮询等待。
→ Vue 版测试更简洁，但**如果链路里有 `watch` 再触发 `watch`，一个 `nextTick` 不够**，
表现是「断言偶尔失败」。→ 遇到就用 `await flushPromises()`，不要靠加 `nextTick` 凑数。

### V-ADR-013：用 classic router，**不用**文件式路由

**问题**：Vue Router 5 把 `unplugin-vue-router` 收进了主包，支持文件式路由：

```ts
import { createRouter } from 'vue-router/auto'   // 路由由 src/pages/ 的文件结构生成
```

这是 Vue 生态目前**推荐的方向**。要不要用？

**决定**：**不用。** 用 classic `createRouter({ routes })` + `addRoute()`。

**理由：文件式路由与本项目的架构根本冲突**

| | 文件式路由 | 本项目 |
| --- | --- | --- |
| 路由表从哪来 | **文件系统**（构建期确定） | **后端数据库**（运行期下发，F-ADR-008） |
| 谁决定用户能进哪些页面 | 全部页面都注册 | 只注册有权限的（F-ADR-007） |
| 新增页面 | 加个文件 | 后端加权限点 + 加文件 |

这不是「配一下就能兼容」的差异，是**路由表的真相源不同**。
文件式路由的前提是「路由是静态的、构建期可知的」，而本项目的整个 `VE-3.x`
建立在「路由是后端下发的、每个用户不一样」之上。

**更硬的一条证据**：Vue Router 5 的 experimental router 是配合文件式路由设计的，
它的类型定义里写着：

> This router does not have `addRoute()` and `removeRoute()` methods and is meant
> to be used with file-based routing.

**它直接删掉了动态路由 API。** 这不是巧合——**文件式路由和动态注册是互斥的两种世界观。**

**代价**
- 放弃了文件式路由的类型安全（`router.push('/tickets/:id')` 的参数类型推导）。
  → 本项目的路由 path 来自数据库字符串，本来也推导不出来。
- 与 Vue 生态的主流方向不一致，后来者可能会想「升级一下」。
  → 写进 `frontend-vue/CLAUDE.md` 的第 0 节，和这条 ADR 互相引用。

> 📌 **这条 ADR 的价值超出了 Vue 本身。**
>
> 「后端下发路由表」和「文件式路由」都是好设计，但它们**不能共存**。
> 遇到这种情况时，正确的做法是**识别出真相源的冲突**，
> 而不是想办法让两者「都用上一点」——那会得到一个两边都不完整的系统。

## 3. 关键流程

### 3.1 冷启动（刷新页面）—— 与 React 版对照

```
                React 版                          Vue 版
    ──────────────────────────────    ──────────────────────────────
         浏览器加载 SPA                     浏览器加载 SPA
                │                                  │
         <AuthBootstrap>                    router.beforeEach
         挂在 RouterProvider 外              （导航期，组件未创建）
                │                                  │
         useProfileQuery()                  await fetchProfileIntoStore()
                │                                  │
          ┌─────┴─────┐                      ┌─────┴─────┐
        401          200                   401          200
          │            │                     │            │
      跳登录页    写入 Zustand            跳登录页    写入 Pinia
                       │                                  │
              useMemo 重建 router              registerDynamicRoutes()
                       │                                  │
              渲染 <RouterProvider>          🔴 return { ...to, replace: true }
                       │                        （在新路由表上重新匹配）
                  匹配当前 URL                            │
                                                    匹配当前 URL
```

**同一个时序陷阱，两种完全不同的解法**：
- React：**控制渲染时机**——profile 没到就不渲染 `<RouterProvider>`
- Vue：**控制导航时机**——profile 没到就不放行，加完路由后**重新导航一次**

> Vue 的 `return { ...to, replace: true }` 是官方推荐写法，但极不直观：
> 一个守卫返回「导航到我自己刚才要去的地方」看起来像死循环。
> 它之所以不循环，是因为第二次进来时 `status` 已经不是 `'unknown'` 了——
> **这个不循环的保证藏在另一个变量里**，是这段代码最脆弱的地方。

### 3.2 一次受权限保护的操作

**与 React 版完全相同**，只有第一步的按钮由 `<Can>`（Vue SFC）渲染。
axios 拦截器、后端处理、响应分流——**逐字相同**。

→ 详见 [`../frontend/02-设计文档.md`](../frontend/02-设计文档.md) 第 3.2 节，不重复。

### 3.3 权限被撤销（`VUS-1`）

```
后端 bump_version()  →  X-RBAC-Version 变化  →  invalidateQueries(['profile'])
                                                        │
                    ┌───────────────────────────────────┴──────────────────┐
                    ▼                                                      ▼
              React 版                                              Vue 版
        useEffect(() => setProfile(data), [data])          watch(data, (v) => auth.setProfile(v))
                    │                                                      │
        ⚠️ fe-v0.13.0 踩过：                                  ⚠️ 同一个陷阱是否还在？
        await refetchQueries() 之后 store                    → vue-v0.11.0 必须验证
        **还没更新**，因为 useEffect 尚未执行
```

📌 **这是本阶段一个明确的待验证项**，不是已知结论。
`watch` 的默认时机是 `pre`（组件更新前），与 `useEffect`（渲染提交后）不同。
到 `vue-v0.11.0` 会给出实测答案，并回填到本节。

## 4. 安全设计

### 4.1 威胁模型：与 React 版逐行相同

| 威胁 | React 版的防御 | Vue 版 |
| --- | --- | --- |
| 误把路由守卫当安全边界 | 每个守卫有对应后端校验；E2E 绕过前端 | **相同**（且**风险更高**，见 1.1） |
| XSS 偷凭证 | httpOnly Cookie | **相同** |
| CSRF | token + SameSite=Lax | **相同** |
| 前端 store 被篡改 | 无法防，**也不需要防** | **相同**，且 Vue 更容易篡改（`VUS-7`） |
| bundle 泄露系统结构 | 动态注册减少暴露 | **相同** |
| 403 死循环 | 401/403 分流 | **相同** |
| 登出后缓存残留 | `queryClient.clear()` + store reset | 🔴 **多一步**：`clearDynamicRoutes()` |

**全表只有最后一行不同。** 这就是换框架的全部安全影响面。

### 4.2 E2E 越权矩阵

**与 React 版逐格相同**，不重复。见 [`../frontend/02-设计文档.md`](../frontend/02-设计文档.md) 第 4.2 节。

> 矩阵不变**是验收项而不是省事**（`VAC-8`）。

## 5. 已知简化与生产差距

继承 React 版的 8 条（[`../frontend/02-设计文档.md`](../frontend/02-设计文档.md) 第 5 节），
**新增 3 条 Vue 特有的**：

| # | 简化 | 生产环境应该怎么做 |
| --- | --- | --- |
| 9 | 动态路由的清理靠手工调 `clearDynamicRoutes()` | 更稳的做法是把它挂到 store 的 `$reset` 订阅上，让「登出」只有一个入口 |
| 10 | 守卫是单个大 `beforeEach` | 页面多了之后应拆成多个守卫（认证 / 权限 / 埋点）并明确顺序 |
| 11 | 两个前端的常量文件靠 CI diff 保证一致 | 更好的做法是 OpenAPI + 代码生成整条链路（与 React 版第 8 条同源） |

## 6. Ant Design Vue 4 与 Ant Design 6 的差异

> ⚠️ **这一节记录的不是「Vue 和 React 的差异」，而是「两个 UI 库版本世代的差异」。**
> 混淆这两者会得出错误结论（`VNG-7`）。

| 项 | Ant Design 6（React） | Ant Design Vue 4 | 影响 |
| --- | --- | --- | --- |
| 按钮字间距 | `<ConfigProvider button={{ autoInsertSpace: false }}>` | `<a-config-provider :auto-insert-space-in-button="false">` | **同一个坑，配置项位置不同**。不设的话「登录」渲染成「登 录」，所有按文本找按钮的测试全失效 |
| Modal 销毁 | `destroyOnHidden`（`destroyOnClose` 已废弃） | `destroyOnClose`（仍是正确写法） | 直接照抄 React 版会写错 |
| Spin 提示 | `description`（`tip` 已废弃） | `tip` | 同上 |
| Tree 父子联动 | `checkStrictly` | `checkStrictly` | **相同**。权限场景一律开启 |
| message 存活 | 3 秒 | 3 秒 | **相同**。E2E 要先断言它再断言持久状态 |

> 📌 **`autoInsertSpace` 这个坑值得单独说。**
>
> React 版在 `fe-v0.3.0` 踩过一次，`fe-v0.16.0` 又反向踩了一次
> （测试里写了 `确 定`，而全局设置已经关掉了自动空格）。
>
> Vue 版**会再踩一次**，而且是新的形态：照抄 React 版的
> `button={{ autoInsertSpace: false }}` 在 antdv 里是个**无效属性，不报错**。
> 表现是「配了但没生效」，比完全没配更难查。

## 7. 决策速查

| V-ADR | 决策 | 一句话理由 | 与 React 版 |
| --- | --- | --- | --- |
| 001 | 三套前端并存，独立目录 | 抽公共包会把「结论」变成「前提」 | 新增 |
| 002 | 最小差异原则：只换框架绑定的库 | 控制变量，否则分不清差异来自哪 | 新增 |
| 003 | Pinia + 延迟调用 + 注入 | 组件外访问 store 有实例化时序问题 | 🔴 React 无此问题 |
| 004 | `addRoute()` + 保存移除函数 | 增量 API 不会自动清理，登出会残留 | 🔴 React 靠重建天然免疫 |
| 005 | 导航期守卫 + `return {...to, replace}` | 拦得更早，但**不是**更安全 | 🔴 位置完全不同 |
| 006 | 三态而非布尔 | 继承 F-ADR，且 Vue 多一条独立理由 | 继承 |
| 007 | **不**用 `v-perm` 指令 | 先渲染后删、删了回不来、类型失效 | 🔴 Vue 特有的诱惑 |
| 008 | 导出命令加 `--out`，默认值不变 | 不能让上一阶段的 CI 变红 | 微调 |
| 009 | `queryKey` 一律 `computed` | 不响应且**不报错**，是最典型的模型差异 | 🔴 React 无此问题 |
| 010 | `onErrorCaptured` + 全局 handler | Vue 没有 ErrorBoundary 组件 | 🔴 实现不同、**限制相同** |
| 011 | 每个用例 `setActivePinia` | 与 Zustand 的「手动 reset」是相反的麻烦 | 🔴 方向相反 |
| 012 | E2E 逐字复用 | 断言不变**是验收项**，证明它测的是规格 | 继承 |
| 013 | classic router，**不**用文件式路由 | 与「后端下发路由表」的真相源冲突 | 🔴 Vue 特有的岔路 |
| 014 | 产物不入库 | 继承 | 继承 |
| 015 | 不做数据二次过滤 | 继承，与框架完全无关 | 继承 |

**统计**：15 条里 **4 条直接继承**、**2 条微调**、**9 条需要重新决策**。
其中真正「Vue 特有」的只有 6 条（003 / 004 / 007 / 009 / 011 / 013）。

> 这个比例本身就是结论：**权限架构的决策，大部分与前端框架无关。**
> 需要重新想的那 6 条，全部集中在**状态实例化**和**路由注册**这两个点上。

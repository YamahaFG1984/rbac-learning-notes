# `v-perm` 自定义指令方案评估（VE-4.5）

| 项 | 值 |
| --- | --- |
| 结论 | ❌ **不采用**（[V-ADR-007](../02-设计文档.md)） |
| 实测于 | `vue-v0.7.0` |
| 代码 | [`frontend-vue/src/directives/perm.ts`](../../../frontend-vue/src/directives/perm.ts)（保留但**不注册、不使用**） |

---

## 0. 为什么要专门评估它

`<Can>` 组件和 `usePermission()` composable 是 React 版就有的两个接口，
直接同构改写即可。**Vue 比 React 多出第三种形态：自定义指令。**

```vue
<a-button v-perm="PERM.TICKET_TICKET_DELETE" danger>删除</a-button>
```

它比 `<Can>` 少一层嵌套，是绝大多数「Vue 权限管理」教程给出的答案。

`VE-4.5` 要求**把它写出来跑一遍**再决定——只读文档不写代码，
下面第 2 条你不会有实感。

---

## 1. 实验设置

在 `pages/tickets/List.vue` 上并排放三个按钮，用同一个权限码：

```vue
<Button id="dir-del"  v-perm="PERM.TICKET_TICKET_DELETE" @vue:mounted="onDirMounted" />
<Button id="dir-typo" v-perm="'ticket:ticket:delet'" />          <!-- 故意拼错 -->
<Can :perm="PERM.TICKET_TICKET_DELETE">
  <Button id="can-del" @vue:mounted="onCanMounted" />
</Can>
```

`@vue:mounted` 计数器用来回答一个关键问题：**元素到底被创建过没有。**

指令实现是教程里最常见的那种：

```ts
export const vPerm: Directive<HTMLElement, PermCode> = {
  mounted(el, binding) {
    const auth = useAuthStore()
    if (!auth.can(binding.value)) el.parentElement?.removeChild(el)
  },
}
```

---

## 2. 实测结果

### 缺陷 1：先渲染，再删除 —— 副作用**已经发生**

用 `cs_staff`（**没有** `ticket:ticket:delete`）登录：

```
指令删除按钮存在: 0
Can 删除按钮存在 : 0
mounted 副作用   : { dir: 1, can: 0 }     ← 关键
```

两个按钮最终都不可见，**但 `dir: 1`**：
指令版的按钮**被创建、被挂载、`mounted` 钩子跑完了**，然后才被移除。

`<Can>` 版是 `can: 0`——`v-if` 让它**根本没有被创建**。

**为什么这要紧**：按钮上如果有 `autofocus`、有埋点上报、有
`onMounted` 里的副作用，指令版**全都会执行一遍**。
对一个「用户根本无权看到」的按钮来说，这些副作用一次都不该发生。

### 缺陷 2：🔴 删掉之后回不来 —— **致命**

接上一步，在运行时把权限改成 `['*']`（模拟 `vue-v0.11.0` 的权限恢复）：

```
指令删除按钮存在: 0      ← 永远不回来
Can 删除按钮存在 : 1      ← 自动恢复
```

被指令删掉的元素**已经不在虚拟 DOM 树上**，`updated` 钩子不会再被调用。
除非刷新整页，否则它不会回来。

> **这一条让 `VE-5.2`（权限变更后菜单/按钮自动刷新）在指令方案下无法实现。**
> 不是「难实现」，是**做不到**。单这一条就足以否决。

⚠️ 注意这个缺陷的暴露条件：**只有权限在运行时变化时才看得到**。
本项目到 `vue-v0.11.0` 才有那个功能——
**如果先做了指令方案，四个 tag 之后才会发现它是死路。**

### 缺陷 3：类型收窄失效 —— 即使显式声明了类型

用 `cs_manager`（**有** `ticket:ticket:delete`）登录：

```
v-perm="PERM.TICKET_TICKET_DELETE"   → 1 存在
v-perm="'ticket:ticket:delet'"(拼错) → 0 存在   ← 静默消失
<Can :perm="PERM.TICKET_TICKET_DELETE"> → 1 存在
```

而 `npm run typecheck`（`vue-tsc`）**完全通过**。

📌 **这一条比预想的更严重。** 规格书的延伸思考问过：

> 缺陷 3 能不能通过给指令加类型来解决？试着写 `Directive<HTMLElement, PermCode>`。

**实测：写了也没用。** 上面那个指令声明的就是 `Directive<HTMLElement, PermCode>`，
`vue-tsc` 依然放过了拼错的字符串字面量——它不校验模板里指令值的类型。

而 `<Can :perm="...">` 的 prop 类型是 `PermCode`，写错**编译不过**。

`F-ADR-012` 说过：

> TypeScript 在编译期挡住权限码 typo，
> **这是 SPA 相比模板版唯一在权限安全性上更强的地方。**

用了指令，**这个唯一的优势就原地退回去了**——
退回到 Django 模板 `{% if 'ticket:ticket:delet' in perms %}` 的水平。

---

## 3. 汇总

| | `v-perm` 指令 | `<Can>` 组件 |
| --- | --- | --- |
| 模板嵌套 | ✅ 更少一层 | ❌ 多一层 |
| 元素是否被创建 | ❌ **创建后再删**，副作用已发生 | ✅ `v-if`，根本不创建 |
| 权限恢复后 | ❌ **回不来** | ✅ 自动恢复 |
| 权限码写错 | ❌ 编译通过、静默失效（**加了类型也没用**） | ✅ 编译期报错 |
| 能否支持 `VE-5.2` | ❌ **做不到** | ✅ |

**用一层嵌套换三样东西，不划算。**

---

## 4. 结论不是「指令不好」

指令是个好机制。`v-focus`、`v-resize`、`v-click-outside` 用它都很合适——
它们**不参与条件渲染、不需要类型收窄、也不需要在状态变化后恢复**。

**权限场景恰好把这三条全占了。**

> **「Vue 能做而 React 不能做的事」不等于「Vue 应该这么做」。**
>
> 这是本阶段唯一一处「Vue 提供了额外选项，而我们选了和 React 一样的那个」。
> 值得注意的是：结论不是「这个机制差」，而是
> **「在这个具体场景下，它的三个特性恰好全是负面的」**。

---

## 5. 那有没有能用的指令版？

有，但要放弃「删 DOM」这个思路：

```ts
// 用 disabled + tooltip 而不是移除元素
export const vPermDisable: Directive<HTMLElement, PermCode> = { ... }
```

⚠️ 但这解决不了缺陷 3（类型），而且**「禁用」和「隐藏」是不同的产品决策**：
禁用会告诉用户「这里有个功能，但你不能用」，隐藏则不透露它的存在。

本项目选隐藏（与模板版、React 版一致），所以这条路也不通。

📌 真正能同时解决三条的写法是**把指令换成组件**——
而那就是 `<Can>`。**兜了一圈回到原点，这本身就是答案。**

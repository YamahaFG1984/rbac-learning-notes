## 1. 分支与 tag 命名

```
main                    v0.1.0 ... v1.2.0
  └─ feat/react-frontend   fe-v0.0.1-docs ... fe-v1.0.0
        └─ feat/vue-frontend  vue-v0.0.1-docs ... vue-v1.0.0
```

**⚠️ 本分支从 `feat/react-frontend` 切出，不是从 `main`。**

理由：React 阶段做的 7 项后端适配（`BE-1` ~ `BE-7`）Vue 版全部需要——
Session 认证、CSRF、`X-RBAC-Version` 中间件、`Permission` 的路由字段、
`/django/` 前缀迁移。从 `main` 切会把这些重做一遍，
而**重做它们不产生任何新信息**。

从 `fe-v1.0.0` 切出还额外买到一个更强的验收条件：

```bash
git diff fe-v1.0.0 HEAD -- apps/ config/     # 期望：只有两个管理命令
```

不仅内核没改，**整个后端几乎没改**。这是接第三种表现层能给出的最强证据。

**副作用**：工作区里同时存在 `frontend/`（React）和 `frontend-vue/`（Vue）。
这正是 [V-ADR-001](02-设计文档.md) 要的——两份代码并排放着才能 diff。

## 5. 三个刻意留下的中间态

| Tag | 缺什么 | 在哪补上 | 为什么 |
| --- | --- | --- | --- |
| `vue-v0.3.0` | 菜单写死、无守卫 | `vue-v0.5.0` / `vue-v0.6.0` | 与 `v0.8.0`、`fe-v0.4.0` **同一个手法**，第三次用 |
| `vue-v0.7.0` ~ `vue-v0.10.0` | 权限快照不会自动更新 | `vue-v0.11.0` | 亲眼看到「撤权后按钮还在」 |
| **`vue-v0.5.0`** | **登出后动态路由残留** | **`vue-v0.5.0` 内部** | 见下 |

### 第三个中间态是 Vue 独有的，且刻意安排在同一个 tag 内

`vue-v0.5.0` 的规格书要求**先写出有 bug 的版本**，跑一遍 `VUS-6`（换账号登录），
亲眼看到「`cs_staff` 能进 `/system/users`，页面空白，接口 403」，
**然后**再加 `clearDynamicRoutes()`。

理由：这个 bug 在 React 版**根本不会出现**（重建 router 天然清空）。
如果直接写对，学习者永远不会知道**「增量 API」比「重建 API」多欠了一笔债**。

> 前三个阶段的中间态都是跨 tag 的。这一个放在 tag 内部，
> 因为它是**同一个决策的两面**，拆开会让 diff 讲两个故事。

## 6. 贯穿本阶段的原则

### 原则 1：先问「这一层需要重新设计吗」

每写一个文件前，先看 React 版的同名文件，问三个问题：

```
1. 能逐字复制吗？          → 能：复制，并在规格书里记「无差异」
2. 逻辑一样、写法不同？     → 记录「同构改写」，在 04 文档里成对贴出来
3. 需要重新设计？          → 停下来写一条 V-ADR，说清为什么
```

⚠️ **最危险的是第 1 类被误判成第 3 类**——「反正在写 Vue 版，顺手重构一下」。
那会污染对比：分不清差异来自框架还是来自你的重构。

> 这是根目录 `CLAUDE.md` 第 0 节「严禁在后续 tag 里大规模重构前面的代码」
> 在跨框架场景下的延伸。**跨框架时这条更重要**，因为诱惑更大。

### 原则 2：差异必须**成对**记录

04 文档里的每一条差异都必须有**两边的真实代码**，不能只写一边加一句描述。

```
❌ 「Vue 用 computed，比 React 的 useMemo 简洁」
✅ 贴出两段真实代码 + 各自会踩的坑 + 各自的失误表现
```

### 原则 3：前端的一切权限判断仍然只是体验

| 出现位置 | 形态 | 与 React 版 |
| --- | --- | --- |
| `vue-v0.5.0` | 导航守卫拦住无权限页面 | 位置不同，**价值相同：零** |
| `vue-v0.6.0` | 菜单不渲染 | 相同 |
| `vue-v0.7.0` | 按钮不渲染 | 相同 |

`vue-v0.14.0` 的 E2E 用**与 React 版逐字相同的断言**再证一遍。

## 8. 与前三个阶段的关系

```
main ──── v1.0.0（模板）──── v1.2.0（DRF+JWT）──────────────────▶
             │
             └── feat/react-frontend ── fe-v1.0.0（React SPA）
                        │
                        └── feat/vue-frontend ── vue-v1.0.0（Vue SPA）
```

到 `vue-v1.0.0` 为止，**同一个 `apps/rbac/services.py` 服务四种表现层**：

| | 模板 | DRF+JWT | React | Vue |
| --- | --- | --- | --- | --- |
| tag | `v1.0.0` | `v1.2.0` | `fe-v1.0.0` | `vue-v1.0.0` |
| 内核改动 | — | **0** | **0** | **0** |
| 后端适配层新增 | ~200 行 | 117 行 | ~700 行 | **≈20 行** |

最后一行是本阶段最想让人看到的数字。它不是因为 Vue 简单，
而是因为**第三个前端可以直接吃掉第二个前端付出的适配成本**——
前提是第二个前端当初没有把适配层写成「React 专用」。

**如果要合并回主干**：冲突面与 React 版相同，外加两个管理命令。
`apps/rbac/services.py` 仍然不在其中。

## 1. 背景

### 1.1 这不是「再写一个前端」

到 `fe-v1.0.0` 为止，同一个权限内核已经服务了三种表现层：

| | Django 模板 | DRF + JWT | React SPA |
| --- | --- | --- | --- |
| tag | `v1.0.0` | `v1.2.0` | `fe-v1.0.0` |
| 内核改动 | — | **0** | **0** |

`fe-v1.0.0` 的「延伸练习」第 3 条留了一个问题：

> **把前端换成 Vue 再走一遍。哪些 tag 的规格书一个字都不用改？**
> 那些就是与框架无关的部分——也正是这套文档真正的价值所在。

**本阶段就是去回答这个问题。** 所以它的产出有两份：

| 产出 | 说明 |
| --- | --- |
| 一个 Vue 3 前端 | `frontend-vue/`，功能与 React 版对等 |
| **一份逐项对比** | [04-React与Vue3做法对比.md](04-React与Vue3做法对比.md)——**这份才是主要交付物** |

> ⚠️ 如果做完之后只有代码没有对比，这个阶段就白做了。
> React 版已经证明了「SPA 能接上这个内核」，再证一遍毫无意义。
> 有意义的是：**同一份规格书，两个框架，差异出现在哪里、为什么。**

### 1.2 为什么这个对比有价值

大多数「Vue vs React」的文章比的是语法糖和生态热度。那种对比没用，因为它脱离了具体问题。

本项目提供了一个**受控实验环境**：

- 同一个后端，一行不改
- 同一份 PRD、同一批需求编号（`FE-1.1` … `FE-7.5`）
- 同一套 E2E 越权矩阵，同一批断言值（80 / 50 / 5 条）
- 同一批已知陷阱（刷新变 404、403 死循环、权限撤销后按钮还在）

在这种条件下，**凡是两边写法不同的地方，差异必然来自框架本身**，而不是来自需求理解或个人偏好。这是一个可复现的对照实验。

### 1.3 已经预判到的几个差异点

在动手前先记下来，做完再回来对照——**预判错了的地方比预判对了的更值得看**。

| # | 预判 | 涉及 |
| --- | --- | --- |
| 1 | Vue 的路由守卫在**导航期**（`beforeEach`），React 在**渲染期**（组件树）。Vue 拦得更早，**但错觉也更强** | `VE-3.x` |
| 2 | 动态路由：React 是「重建整个 router」，Vue 是「`addRoute` 增量添加」。增量的代价是**登出后要手动清理** | `VE-3.1` |
| 3 | Pinia 的 store 在 `app.use(pinia)` 之前访问会抛错，而 axios 拦截器就在组件外——**React 版不存在这个问题** | `VE-2.x` |
| 4 | Vue 多一种按钮级权限的形态：自定义指令 `v-perm`。它看起来最优雅，**但有三个真实缺陷** | `VE-4.x` |
| 5 | `@tanstack/vue-query` 的 `queryKey` 传普通数组时不会随筛选条件重新请求，且**不报任何错** | `VE-6.1` |
| 6 | E2E 层（Playwright）应该几乎**一个字都不用改** | `VNFR-10` |

### 1.4 教学目标

| 编号 | 目标 |
| --- | --- |
| VG-1 | 用同一份规格书实现两个框架，指出差异**出现在哪一层** |
| VG-2 | 说清「不可变 + 重渲染」与「可变代理 + 依赖追踪」两种响应式模型，在**权限场景**下各自会产生什么 bug |
| VG-3 | 实现 Pinia 版权限 store，解决「组件外访问 store」的实例化时序问题 |
| VG-4 | 用 `router.addRoute()` 实现动态路由，并处理它特有的**清理**问题 |
| VG-5 | 说出导航期守卫相比渲染期守卫的优点，以及它为什么**仍然不是安全边界** |
| VG-6 | 评估「自定义指令做按钮级权限」这个 Vue 特有方案，并给出取舍结论 |
| VG-7 | 验证权限规格书中「与框架无关」的部分究竟占多大比例 |
| VG-8 | 用同一套 E2E 证明：**换了框架，安全边界的数量仍然是 1** |

### 1.5 非目标

| 编号 | 不做 | 原因 |
| --- | --- | --- |
| VNG-1 | 替换 React 版 | 三套并存才有对比价值（[V-ADR-001](02-设计文档.md)） |
| VNG-2 | Nuxt / SSR | 同 `FNG-2`，且会引入与 React 版不对等的变量 |
| VNG-3 | 文件式路由（`vue-router/auto`） | **与「后端下发路由表」根本冲突**，见 [V-ADR-013](02-设计文档.md) |

| VNG-5 | i18n / 移动端 / 微前端 | 同 React 版 |
| VNG-6 | 修改后端权限内核 | **硬约束**，与前三个阶段完全一致 |
| VNG-7 | 「哪个框架更好」的结论 | 本文档只陈述**差异**和**各自的失误模式**，不评优劣 |

## 2. 交付形态

```
浏览器
  │
  ├── :5173  Vite (React)  ──┐
  ├── :5174  Vite (Vue)    ──┤  代理 /api /django /admin /static
  └── 生产：Nginx           ──┘        │
                                       ▼
                                  Django :8000
```

三套前端并存后的入口：

| 路径 | 内容 | 阶段 |
| --- | --- | --- |
| `/` | React SPA | 三 |
| `/vue/` | **Vue SPA** | **四（本阶段）** |
| `/django/` | Django 模板版 | 一 |
| `/api/v1/` | DRF API（三套前端共用） | 二 |
| `/admin/` | Django admin | — |

⚠️ **同域仍然是硬要求**（沿用 [F-ADR-002](../frontend/02-设计文档.md)）。
Vue 版的 Vite proxy 配置与 React 版**逐字相同**——这本身就是一个结论：
同域代理是构建工具的事，与框架无关。

## 3. 功能需求

> 编号规则 `VE-<模块>.<序号>`，与 React 版的 `FE-` **一一对应**。
> 对应关系是刻意的：**编号相同 = 需求相同**，这样对比表才能逐行对齐。

### VE-1 认证（对应 FE-1）

| 编号 | 需求 | 对应 | 优先级 | 与 React 版的差异 |
| --- | --- | --- | --- | --- |
| VE-1.1 | 登录页，凭证写入 httpOnly Cookie | FE-1.1 | P0 | 表单从「受控组件」变成 `v-model` |
| VE-1.2 | 前端不接触 token，`document.cookie` 读不到会话凭证 | FE-1.2 | P0 | **无差异** |
| VE-1.3 | 所有写请求携带 `X-CSRFToken` | FE-1.3 | P0 | **无差异**（axios 拦截器完全复用） |
| VE-1.4 | 登出：清 Cookie + 清空前端状态 | FE-1.4 | P0 | 🔴 **多一步：移除动态注册的路由** |
| VE-1.5 | 未登录访问受保护路由跳登录页，登录后回原地址 | FE-1.5 | P0 | 守卫从渲染期移到导航期 |
| VE-1.6 | 401 静默重定向，不弹一堆提示 | FE-1.6 | P1 | **无差异** |
| VE-1.7 | 登录失败提示与后端一致 | FE-1.7 | P0 | **无差异** |

### VE-2 权限数据获取（对应 FE-2）

| 编号 | 需求 | 对应 | 优先级 | 与 React 版的差异 |
| --- | --- | --- | --- | --- |
| VE-2.1 | 启动时拉 `/api/v1/auth/profile/` | FE-2.1 | P0 | **无差异** |
| VE-2.2 | 权限数据是唯一权限来源，禁止组件自行推断 | FE-2.2 | P0 | **无差异**（这是架构约束，与框架无关） |
| VE-2.3 | profile 未加载完不渲染业务界面 | FE-2.3 | P0 | 实现位置不同：React 在组件树，Vue 在导航守卫 |
| VE-2.4 | profile 失败给可重试错误页 | FE-2.4 | P1 | **无差异** |
| VE-2.5 | 超管 `perms` 为 `["*"]`，正确处理通配 | FE-2.5 | P0 | **无差异** |
| **VE-2.6** | 🔴 **store 必须能在 Vue 组件外被安全访问**（axios 拦截器） | — | P0 | **Vue 独有**，见下 |

> **VE-2.6 是本阶段新增的唯一一条需求**，React 版没有对应项。
>
> Zustand 的 store 是模块级单例，`useAuthStore.getState()` 在任何地方都能调。
> Pinia 的 store 绑在 `app` 实例上，`useAuthStore()` 在 `app.use(pinia)` 执行之前调用会抛：
>
> ```
> [🍍]: "getActivePinia()" was called but there was no active Pinia. Are you trying to use a store before calling "app.use(pinia)"?
> ```
>
> 而 `api/client.ts` 的拦截器是**模块加载时就执行**的。这个时序必须显式处理。

### VE-3 路由与菜单（对应 FE-3）

| 编号 | 需求 | 对应 | 优先级 | 与 React 版的差异 |
| --- | --- | --- | --- | --- |
| VE-3.1 | 根据 profile 的菜单树**动态注册**路由 | FE-3.1 | P0 | 🔴 `addRoute()` 增量 vs 重建 router |
| VE-3.2 | 无权限路由跳 403，不是白屏 | FE-3.2 | P0 | 导航期拦截，页面组件根本不创建 |
| VE-3.3 | 侧边栏由 `menus` 渲染 | FE-3.3 | P0 | **无差异**（同一份 `menuAdapter` 逻辑） |
| VE-3.4 | 空目录不渲染 | FE-3.4 | P0 | **无差异** |
| VE-3.5 | 当前路由高亮、父目录展开 | FE-3.5 | P1 | `route.path` 是响应式的，不需要手动订阅 |
| VE-3.6 | 直接输入 URL 行为与点菜单一致 | FE-3.6 | P0 | **无差异** |
| VE-3.7 | 刷新后路由仍有效 | FE-3.7 | P0 | 🔴 解法完全不同：`next({ ...to, replace: true })` |
| **VE-3.8** | 🔴 **登出后必须移除已注册的动态路由** | — | P0 | **Vue 独有**，见下 |

> **VE-3.8 也是 Vue 独有的。**
>
> React 版登出时把 router 整个重建成「只有登录页」，动态路由自然消失。
> Vue 的 `addRoute()` 是**往现有 router 里加**，登出不会自动清掉——
> 换一个权限更小的账号登录，上一个账号的路由**还在**。
>
> 它不是安全漏洞（后端照样 403），但它是**功能 bug**：
> 用户会看到一个能进去但一片空白的页面。

### VE-4 按钮级权限（对应 FE-4）

| VE-4.1 | 提供 `<Can perm="...">` 组件与 `usePermission()` composable | FE-4.1 | P0 | `children` → `<slot>`；`fallback` → 具名插槽 |
| VE-4.2 | 无权限按钮不渲染 | FE-4.2 | P0 | **无差异** |

| VE-4.4 | 构建期检查：前端权限码必须在后端存在 | FE-4.4 | P1 | **无差异**（`vue-tsc` 替代 `tsc`） |
| **VE-4.5** | 评估 `v-perm` 自定义指令方案并给出结论 | — | P1 | **Vue 独有**，[V-ADR-007](02-设计文档.md) |

## 4. 后端需要配合修改的部分

> ⚠️ 沿用 `FNG-6` / `VNG-6`：**只允许改适配层，不许碰权限内核**。

React 阶段有 7 项后端改动（`BE-1` ~ `BE-7`）。本阶段**只有一项**：

| 编号 | 后端改动 | 涉及文件 | 碰内核 |
| --- | --- | --- | --- |
| VBE-1 | `export_perm_constants` / `export_enforced_perms` 增加 `--out` 参数 | `apps/rbac/management/commands/` | ❌ |

原因很具体：这两个命令把输出路径**写死**成 `frontend/src/...`：

```python
target = Path(settings.BASE_DIR, "frontend/src/constants/permissions.ts")   # 写死
```

接第三个前端时它就不够用了。

> 📌 **这正是 [F-ADR-008](../frontend/02-设计文档.md) 当初预判过的摩擦。**
> 原话是：
>
> > 「如果哪天要支持第三个前端（小程序），这张表会开始打架——那时才是拆表的时机。」
>
> 现在第三个前端来了。实测结果是：**打架的不是那张表，是导出命令的硬编码路径。**
> 表本身（`route_path` / `component`）**一个字都不用改**——因为 Vue 用了
> 与 React 完全相同的组件命名（`tickets/List` → `pages/tickets/List.vue`）。
>
> 预判对了方向，猜错了位置。这个记录比「预判成功」有价值。

### 验收条件

```bash
git diff main HEAD -- apps/rbac/services.py          # 期望：空
git diff fe-v1.0.0 HEAD -- apps/ config/            # 期望：只有两个管理命令
```

**第二条是本阶段新增的、更严格的一条**：不仅内核没改，**整个后端几乎没改**。

## 5. 关键用户故事

与 React 版 `FUS-1` ~ `FUS-5` **完全相同**，编号改为 `VUS-`。

> **它们一个字都不用改，这本身就是结论**：用户故事描述的是**用户的遭遇**，
> 而用户不知道你用的是什么框架。

额外增加两条 Vue 特有的：

### VUS-6：换账号登录后的残留路由

> 作为**测试人员**，我先用 `superadmin` 登录（能看到全部菜单），
> 登出后用 `cs_staff` 登录（只应看到工单）。我在地址栏输入 `/system/users`。
>
> **验收**：跳 403 页面。
> **失败表现**（如果 `VE-3.8` 没做）：页面能进去，但表格空白、接口 403、
> 控制台一片红——用户会以为系统坏了。

### VUS-7：控制台篡改权限（Vue 版更容易）

> 作为**安全测试者**，我打开 Vue Devtools，找到 `auth` store，
> 把 `perms` 直接改成 `["*"]`。
>
> **验收**：所有按钮和菜单立刻出现（响应式自动生效，**不需要刷新**），
> 但点任何一个，后端仍然返回 403。
>
> 📌 React 版为了演示这件事，需要在 e2e 构建里专门挂一个 `window.__AUTH_STORE__`。
> **Vue 版不需要**——Pinia 的 store 本来就是个可写的响应式对象，
> Devtools 里点两下就改了。
>
> **「前端权限可以被篡改」这件事，在 Vue 里演示起来更轻松。**
> 这不是 Vue 的缺点，是它把「前端状态从来就不是秘密」这件事表达得更诚实。

> **VNFR-12 是本阶段最重要的一条非功能需求。**
>
> 「无差异」不是省略，是**结论**。写「无差异」和不写，信息量完全不同：
> 前者说明「这一层与框架无关」，后者说明「作者没想过这个问题」。

## 9. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| **写成「Vue 语法教程」而不是对比** | 高——本阶段唯一的价值就是对比 | `VNFR-12` 强制每个 tag 写差异一节；`VAC-11` 验收 |

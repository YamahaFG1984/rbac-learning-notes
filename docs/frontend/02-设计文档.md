### 1.1 四层体验 + 一层安全

后端文档 `v0.10.0` 那张表在 SPA 下要扩成五行：

| 层 | 作用 | 是不是安全边界 |
| --- | --- | --- |
| **后端 API 鉴权**（`HasPerm` + `.for_user()`） | 拦截请求 | ✅ **唯一的** |
| 前端路由守卫 | 不让进无权限的页面 | ❌ 体验 |
| 菜单渲染 | 不显示进不去的入口 | ❌ 体验 |
| `<Can>` 按钮 | 不显示点不动的按钮 | ❌ 体验 |
| 表单字段禁用 | 不让填改不了的字段 | ❌ 体验 |

> **SPA 比模板版更容易产生「前端做了鉴权」的错觉**，因为路由守卫写起来太像鉴权了：
>
> ```ts
> if (!perms.includes(to.meta.perm)) return '/403'
> ```
>
> 这行代码挡不住任何攻击者——`perms` 就在他的浏览器内存里，改成 `["*"]` 只需要几秒；
> 而且他根本不必用你的前端。
>
> 模板版：「攻击者不点你的按钮，他直接发请求。」
> SPA 版：「**攻击者不用你的路由，甚至不用你的前端。**」

## 2. 架构决策记录（F-ADR）

### F-ADR-001：React 前端与 Django 模板版并存，不替换

**问题**：做了 SPA 之后，模板版还留着吗？

**决定**：并存。模板版整体迁移到 `/django/` 前缀，两套前端共用同一个后端。

**理由**
- 这是**唯一能同时看到「同一内核服务两种表现层」的方式**。删掉模板版，`v1.2.0` 那条
  「`services.py` 一行未改」的验收就失去了对照物。
- 两套 UI 并排跑，能直接对比同一个权限在两种形态下的差异——比如「权限撤销后，
  模板版刷新即生效，SPA 需要重拉 profile」这件事，只有并存时才能亲眼看到。

**代价**
- 仓库里有两套 UI，维护成本翻倍。**本项目接受**，因为对比价值就是产品本身。
- 后端路由要重排（`BE-7`），模板版的 URL 全部变化。
  → 缓解：只改 `config/urls.py` 的 include 前缀，各 app 内部的 `url_name` 不变，
  所以模板里的 `{% url %}` 一处都不用改。这是当初用 URL name 而非硬编码路径的红利。

### F-ADR-002：同域部署 + httpOnly Cookie，而不是 localStorage 存 JWT

**问题**：会话凭证放哪？

**候选**

| 方案 | XSS 下 | 部署要求 | CSRF | 可撤销 |
| --- | --- | --- | --- | --- |
| localStorage 存 JWT | ❌ **直接被偷走** | 可跨域 | 不适用 | ❌ 过期前无法撤销 |
| 内存存 access + httpOnly cookie 存 refresh | ⚠️ 内存里的能偷，但短命 | 同域 | 需要 | 部分 |
| **httpOnly Cookie**（本项目） | ✅ **JS 读不到** | **必须同域** | **必须防** | ✅ 服务端说了算 |

**决定**：httpOnly Cookie + 同域反向代理。

**理由**

localStorage 是教程里最常见的写法，也是最不该抄的一个：

```js
localStorage.setItem('token', res.data.access)   // ← 任何 XSS 都能读走
```

一旦页面上有任何 XSS（第三方脚本、富文本渲染、依赖投毒），token 直接失守，
而且 JWT **在过期前无法撤销**——两个弱点叠加，后果是「攻击者拿到一个你撤不掉的通行证」。

httpOnly Cookie 把凭证从 JS 的可达范围里移出去。代价是必须同域，而同域对企业后台
本来就不是问题（前后端一起部署）。

**代价（必须清楚）**
- **必须同域**。开发期靠 Vite proxy，生产期靠 Nginx。跨域方案（前端 CDN + API 独立域名）
  这条路就走不通了——除非用 `SameSite=None; Secure` + CORS credentials，那又打开了
  另一批问题。
- **CSRF 防护重新变成必需**。Bearer token 时代 CSRF 不适用（攻击者构造不出 Header），
  Cookie 一回来，CSRF 就回来了。见 F-ADR-004。
- 不适合原生 App / 第三方开放平台。→ 所以我们**保留 Bearer JWT 通道**，见 F-ADR-003。

### F-ADR-003：SPA 用 Django Session，JWT 通道保留给第三方

**问题**：既然选了 httpOnly Cookie，那 cookie 里装什么？JWT 还是 Session？

这是本阶段**最值得想清楚**的一个问题。

**候选**

| 方案 | 说明 |
| --- | --- |
| a. JWT 装进 httpOnly Cookie | 保留 JWT 结构，改传输方式 |
| b. **直接用 Django Session** | `sessionid` 本来就是 httpOnly Cookie |
| c. 维持 Bearer JWT，SPA 自己存 | 回到 F-ADR-002 否决的方案 |

**决定**：方案 b。DRF 同时启用两种认证：

```python
"DEFAULT_AUTHENTICATION_CLASSES": [
    # SPA 走这个：同域 + httpOnly Cookie + CSRF
    "rest_framework.authentication.SessionAuthentication",
    # 第三方 / 移动端 / 脚本走这个
    "rest_framework_simplejwt.authentication.JWTAuthentication",
],
```

**理由：同域部署下，JWT 的核心优势不成立**

JWT 卖点是**无状态**——服务端不查库就能验证。但：

1. 我们在 `v1.1.0` 已经实测过：`simplejwt` 每次请求都要查库取 `user`
   （因为 `request.user` 需要真实对象）并检查 `is_active`。
   **所谓无状态早就打了折。**
2. 无状态的代价是**不可撤销**。我们花了 `v0.16.0` 一整个 tag 保证「权限撤销后
   最迟下一次请求生效」，结果认证层却给出一个撤不掉的凭证——这是自相矛盾的。
3. 同域单体应用里，无状态换来的水平扩展能力，用 Redis 存 session 也能拿到。

反过来，Session 白送三样东西：

| 白送的 | 说明 |
| --- | --- |
| **立即可撤销** | `logout()` 或删 session 记录，下一次请求就失效 |
| **CSRF 现成** | Django 的 CSRF 中间件已经在跑，`v0.18.0` 还配了测试 |
| **禁用用户立即失效** | `ModelBackend.get_user()` 的 `is_active` 检查（`v0.18.0` 三道防线之一） |

**保留 JWT 通道**是因为它有真实用途：移动 App、第三方开放平台、CI 脚本
——这些场景没有浏览器，Cookie 不好使。

> **一个应用可以有多种认证方式，但只能有一套授权逻辑。**
> `HasPerm` 不关心你是怎么认证的，它只问 `request.user` 是谁。

**代价**
- 两条认证路径要各自测试（`fe-v0.2.0` 会同时测 Session 和 JWT）。
- SPA 与移动端的会话语义不同（一个可撤销一个不可），运维时要意识到。
- DRF 的 `SessionAuthentication` **强制 CSRF 检查**，前端必须正确带上 token。

### F-ADR-004：`CSRF_COOKIE_HTTPONLY` 必须改回 `False`

**问题**：我在后端 `v0.18.0` 加了这行：

```python
CSRF_COOKIE_HTTPONLY = True   # config/settings/prod.py
```

当时的理由是「减少 XSS 可读的东西」。**但它和 SPA 直接冲突。**

**冲突在哪**

Django 的 CSRF 防护是 double-submit：cookie 里一份，请求头/表单里一份，服务端比对。
模板渲染时，`{% csrf_token %}` 由服务端注入，前端不需要读 cookie。
**SPA 没有服务端渲染的表单，只能自己从 cookie 里读 `csrftoken` 再放进 `X-CSRFToken` 头。**

`CSRF_COOKIE_HTTPONLY = True` 让 JS 读不到，SPA 的所有写请求全部 403。

**决定**：改回 `False`，并在配置里写清楚为什么。

**这不是「为了前端方便而降低安全」**——Django 官方文档明确说明：

> 设置 `CSRF_COOKIE_HTTPONLY` 为 `True` **并不能提供任何实质的防护**。
> CSRF token 本来就不是秘密：它只需要「攻击者站点读不到」，而同源策略已经保证了这一点。
> httpOnly 防的是「XSS 偷走凭证」，而 CSRF token 被 XSS 拿到也没用——
> 因为 XSS 已经在同源里，它可以直接发请求。

**真正的凭证 `sessionid` 仍然是 httpOnly**，那才是要保护的东西。

**代价**
- 需要在文档和配置里解释清楚，否则后来者会以为这是安全倒退，又给它改回 `True`。
  → 在 `prod.py` 里写了长注释 + 一条测试断言它是 `False` 并说明理由。

> **教训**：`v0.18.0` 那行配置是「照着安全清单抄」的产物，没想清楚它防的到底是什么。
> 安全配置也需要 ADR——**抄来的安全措施，和抄来的架构一样危险。**

### F-ADR-005：服务端状态用 TanStack Query，客户端状态用 Zustand，不混用

**问题**：权限数据、用户信息、工单列表——分别放哪？

**决定**：按「数据的真实归属」划分，不按「组件树位置」划分。

| 数据 | 归属 | 工具 | 理由 |
| --- | --- | --- | --- |
| 工单列表、部门树、角色列表 | **服务端** | TanStack Query | 它们的真相在数据库，前端只是缓存 |
| 当前用户、权限码、菜单树 | **服务端**（但特殊） | Query 取 + Zustand 派发 | 见下 |
| 侧边栏折叠状态、表格列宽、主题 | **客户端** | Zustand | 真相就在前端 |

**权限数据的特殊之处**

它来自服务端（所以要 Query 管缓存和失效），但**几乎所有组件都要读它**
（路由守卫、菜单、每个按钮）。如果每个组件都 `useQuery(['profile'])`，
虽然有缓存不会重复请求，但：

- 组件与「权限从哪来」耦合
- 加载态和错误态要在每个组件里重复处理
- 测试时每个组件都要 mock 网络

**做法**：Query 负责拉取和失效，拉到之后写进 Zustand store，组件只读 store。

```
useProfileQuery()  ──拉取/失效──▶  usePermStore.setProfile()
                                         │
                        ┌────────────────┼────────────────┐
                        ▼                ▼                ▼
                    路由守卫          菜单渲染          <Can>
```

**为什么不全用 Redux Toolkit + RTK Query**

RTK Query 是好东西，单一数据层也确实省心。我们选 Query + Zustand 的理由是
**边界更清晰**——Zustand store 里放的一定是客户端状态或已派发的权限快照，
看到 store 里有工单列表就知道写错了。RTK 下两者混在同一个 store，边界靠约定。

这是个**偏好性选择**，不是对错问题。团队熟悉 Redux 的话，方案二同样成立。

**代价**
- 权限数据存在两处（Query 缓存 + Zustand），需要保证单向同步。
  → 硬约束：**只有 `useProfileQuery` 的 `onSuccess` 能写 store**，其他任何地方禁止写。
  这条写进 `frontend/CLAUDE.md` 并用 lint 规则守。

### F-ADR-006：权限的唯一来源是 `/auth/profile`，禁止组件自行推断

**问题**：组件里能不能写这种代码？

```tsx
// ❌ 自行推断
if (user.department.id === ticket.department.id) { showEditButton() }
if (user.is_superuser || user.roles.includes('cs_manager')) { ... }
```

**决定**：禁止。前端只能问「我有没有 `ticket:ticket:update` 这个权限码」，
不能自己推导权限。

**理由**

这是后端 `CLAUDE.md` 安全红线第 5 条「权限规则只能有一处实现」在前端的延伸。
上面那两行代码各自复制了一份权限规则：

- 第一行复制了数据权限规则——而后端的规则是五个枚举值 + 部门子树，
  前端这个 `===` 只覆盖了 `DEPT_ONLY` 一种情形，**主管看子部门时就错了**
- 第二行把角色编码硬编码进了前端——角色改名、新增角色，前端全要跟着改

**代价**
- 有些界面细节确实需要「按角色微调」，比如「主管才显示统计卡片」。
  → 正确做法是**为它定义一个权限码**（`ticket:stats:view`），而不是判断角色。
  这会让权限点数量增加——**接受**，这正是 `ADR-004`「一个可点的东西 = 一个权限点」的延伸。

### F-ADR-007：动态注册路由，而不是静态路由表 + 守卫

**问题**：无权限的路由，是「不注册」还是「注册了但守卫拦住」？

**候选**

| 方案 | 说明 |
| --- | --- |
| a. 静态全量路由 + 守卫拦截 | 所有路由都注册，`beforeEach` 判断权限 |
| b. **动态注册** | profile 到手后，只注册有权限的路由 |
| c. 两者结合 | 动态注册 + 守卫兜底 |

**决定**：方案 c。以动态注册为主，守卫作为兜底。

**理由**

只用方案 a 的问题：所有路由组件都会被打进主 bundle 或至少出现在路由表里，
攻击者读 bundle 就知道系统有哪些页面。这不是严重漏洞（后端才是边界），
但属于不必要的信息暴露。

只用方案 b 的问题：**动态注册有个时序陷阱**——

```
用户刷新页面 → React 挂载 → 路由表是空的 → 匹配不到当前 URL → 404
                    ↑
              profile 还在路上
```

所以必须：**profile 加载完成前不渲染路由**（`FE-2.3`），加载完再注册并重新导航。
这也是 `FE-3.7`「刷新页面后路由仍然有效」被单独列为需求的原因。

守卫兜底的价值：动态注册漏了某个路由、或者某个路由是静态注册的，守卫还能拦一道。

**代价**
- 时序复杂度明显上升，是本阶段最容易出 bug 的地方。
  → `fe-v0.7.0` 的验收清单专门测「刷新页面」「直接输入 URL」「登录后跳回原地址」三种时序。
- 路由懒加载 + 动态注册组合时，`component` 字段要能映射到 `import()`。
  → 用 `import.meta.glob` 建立「组件路径 → 懒加载函数」的映射表。

### F-ADR-008：菜单的前端路由信息放后端，`Permission` 表加两个字段

**问题**：后端的 `Permission` 表现在只有 `url_name`（Django URL name），
SPA 需要的是前端路由 `path` 和组件路径。

**候选**

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| a. **`Permission` 加 `route_path` / `component`** | 一处配置，后端下发完整路由表 | 后端表里塞进更多前端概念 |
| b. 约定 Django URL 与前端路由同构 | 不改表 | 约定是隐性的，破坏了没人知道 |
| c. 前端维护映射表 | 后端最干净 | 新增页面改两处，容易忘 |

**决定**：方案 a。加两个字段：

```python
# --- 展示层关注点（ADR-005）。若将来要拆表，边界在这里 ---
url_name   = models.CharField("Django URL name", ...)   # 模板版用
route_path = models.CharField("前端路由", ...)           # SPA 用，如 /system/user
component  = models.CharField("前端组件", ...)           # 如 system/user/index
icon / is_visible
```

**理由**

方案 c 的「改两处」在实践中必然漂移——后端加了菜单，前端忘了加映射，
菜单点进去白屏，而且**没有任何机制会报错**。

方案 a 承认一个事实：`ADR-005` 决定「菜单和权限点合表」时就已经接受了展示层污染，
现在只是让这个污染再多两个字段。**边界仍然是清晰的**（注释里划出来的那一块）。

**代价**
- 后端表越来越「知道前端的事」。如果哪天要支持第三个前端（小程序），
  这张表会开始打架——那时才是拆表的时机。
- 一份权限点声明要同时写 Django URL name 和前端路由，两边都可能写错。
  → `sync_permissions --check-frontend` 校验 `component` 指向的文件是否存在（`fe-v0.5.0`）。

> 这是 `ADR-005` 那句话的又一次应用：**领域纯洁性和管理便利性冲突时，选后者。**
> 但要记账——这已经是第二次为它让步了。

### F-ADR-009：按钮级权限用 `<Can>` 组件 + `usePermission()` hook 双接口

**问题**：模板版是 `{% if 'x' in perms %}`，React 里对应什么？

**决定**：提供两个接口，用途不同。

```tsx
// 1. 组件式：控制渲染
<Can perm="ticket:ticket:delete">
  <Button danger onClick={handleDelete}>删除</Button>
</Can>

// 2. hook 式：控制逻辑（表格列、菜单项配置这类非 JSX 场景）
const can = usePermission()
const columns = [
  ...baseColumns,
  ...(can('ticket:ticket:update') ? [editColumn] : []),
]
```

**理由**

只有组件式不够——Ant Design 的 `Table columns`、`Menu items`、`Form` 的
`disabled` 属性都是**数据而非 JSX**，包不进组件。
只有 hook 式则会让 JSX 里出现大量 `{can('x') && <Button/>}`，可读性下降。

`<Can>` 额外支持 `fallback`：

```tsx
<Can perm="ticket:ticket:export" fallback={<Tooltip title="无导出权限"><Button disabled/></Tooltip>}>
  <Button>导出</Button>
</Can>
```

**代价**
- 两个接口要保证行为一致（都走同一个 store 的同一个判断函数）。
  → `Can` 内部就是调 `usePermission()`，不重复实现。
- 超管的 `["*"]` 通配要在**唯一那个判断函数**里处理，两个接口自动受益。

### F-ADR-010：用 `X-RBAC-Version` 响应头做权限变更感知

**问题**（🔴 本阶段的核心新问题）

后端 `v0.16.0` 保证了「权限变更最迟下一次请求生效」，但那只保证**服务端**是新的。
SPA 前端手里那份 profile 快照，服务端管不着。

后果：管理员撤销了某人的删除权限，那个人页面上的删除按钮**还在**。
点了 → 后端 403（安全没问题）→ 但用户体验是「系统坏了」。

**候选**

| 方案 | 延迟 | 成本 | 服务端开销 |
| --- | --- | --- | --- |
| 什么都不做 | 直到用户刷新 | 0 | 0 |
| 路由切换时重拉 profile | 一次导航 | 低 | 每次导航一次请求 |
| **响应头带版本号，变了才重拉** | **一次 API 请求** | **低** | **一次 cache 读** |
| 定时轮询 profile | 轮询间隔 | 低 | 持续请求 |
| WebSocket / SSE 推送 | 近实时 | **高** | 长连接 |

**决定**：响应头方案。

后端已经有现成的全局版本号（`v0.16.0` 的 `rbac:version`），加一个中间件即可：

```python
class RbacVersionMiddleware:
    def __call__(self, request):
        response = self.get_response(request)
        if request.path.startswith("/api/"):
            response["X-RBAC-Version"] = str(get_version())
        return response
```

前端在 axios 响应拦截器里比对，不一致就 invalidate profile query：

```ts
const v = response.headers['x-rbac-version']
if (v && v !== lastSeenVersion) {
  lastSeenVersion = v
  queryClient.invalidateQueries({ queryKey: ['profile'] })
}
```

**理由**
- **复用已有机制**，后端只加一个中间件（~10 行），前端加 5 行拦截器逻辑。
- 延迟正好等于「一次 API 请求」，与后端 `FR-4.5` 的承诺对齐——
  **前后端的生效语义一致**，这一点很重要。
- 零额外请求：版本号搭在已有响应上。

**代价**
- **版本号是全局的**（`v0.16.0` 的 ADR-010 已知取舍）：任何人改权限，
  所有在线用户都会重拉一次 profile。
  → 企业后台权限变更低频，可接受。用户量大时需要按角色分级版本号，那是后端的事。
- 用户完全不发请求时（比如停在一个静态页面），感知不到变更。
  → `FE-5.4` 兜底：收到 403 时强制重拉 profile。
- 界面「自己变了」可能让用户困惑。
  → `FE-5.5`：给一条非阻塞提示，不静默改变。

### F-ADR-011：401 / 403 / 404 三分流，403 绝不跳登录页

**问题**：模板版可以含糊（302 跳登录、403 页面），SPA 必须精确。

**决定**

| 状态码 | 含义 | 前端动作 |
| --- | --- | --- |
| **401** | 未认证 / 会话过期 | 清空 store → 跳登录页（记住 `redirect` 参数）→ **不弹错误提示** |
| **403** | 已认证但无权限 | 提示「无权限」+ 重拉 profile（可能刚被撤权）→ **绝不跳登录页** |
| **404** | 不存在 **或** 不在你的数据范围内 | 提示「不存在或无权访问」 |
| 5xx | 服务端错误 | 错误边界页 + 重试按钮 |

**⚠️ 为什么单独强调「403 不跳登录页」**

这是 SPA 里的高频 bug：拦截器写成「4xx 都跳登录」，于是

```
用户点了无权限的按钮 → 403 → 跳登录页 → 重新登录 → 还是 403 → 又跳登录 → ...
```

用户会以为账号坏了。而真实原因只是「他确实没这个权限」。

**关于 404 的说明**

后端 `ADR-009` 决定：数据权限范围外的记录返回 **404 而不是 403**，
避免泄露记录存在性。这条要**明确告诉前端**，否则前端会把 404 当成「接口路径写错了」
而去排查路由。

→ 前端的 404 文案统一为「**不存在或你无权访问**」，两种情况都覆盖，且不泄露哪一种。

**代价**
- 401 的「静默」处理需要小心：多个并发请求同时 401 时，只能跳一次登录页。
  → 用一个 flag 去重。

### F-ADR-012：权限码常量由后端生成，前端禁止手写字符串

**问题**：前端怎么引用 `ticket:ticket:delete`？

**决定**：后端加一个管理命令，生成 TS 常量文件：

```bash
python manage.py export_perm_constants > frontend/src/constants/permissions.ts
```

```ts
// ⚙️ 此文件由 python manage.py export_perm_constants 生成，请勿手工编辑
export const PERM = {
  TICKET_TICKET_VIEW: 'ticket:ticket:view',
  TICKET_TICKET_DELETE: 'ticket:ticket:delete',
  // ...
} as const

export type PermCode = typeof PERM[keyof typeof PERM]
```

`<Can perm={...}>` 的类型约束为 `PermCode`，写错的字符串**编译期就报错**。

**理由**

这是后端 `ADR-004`「权限点在代码里声明」的延续，也补上了模板版的一个已知缺口：
`v0.10.0` 陷阱 3 说过「模板里的权限码 typo 不会报错，只会静默不渲染按钮」——
模板版靠 `sync_permissions --check-templates`（`v1.0.0`）事后扫描，
**TypeScript 可以在编译期就挡住**。

这是 SPA 相比模板版**唯一在权限安全性上更强的地方**，值得利用。

**代价**
- 后端权限点变更后要重新生成，忘了就编译不过（这是好事）。
  → CI 里加一步：重新生成后 `git diff --exit-code`，不一致就失败。

### F-ADR-013：三层测试 —— Vitest + MSW + Playwright

**决定**

| 层 | 工具 | 测什么 | 不测什么 |
| --- | --- | --- | --- |
| 单元 | Vitest + Testing Library | `usePermission` 的判断逻辑、`<Can>` 的渲染、store 的状态转换 | 网络 |
| 集成 | + MSW | 拦截器的 401/403 分流、profile 加载时序、版本号比对 | 真实后端 |
| E2E | Playwright | **越权矩阵**、cookie 的 httpOnly、动态路由刷新 | 单元细节 |

**为什么 E2E 是必需的（不只是加分项）**

前端权限有两个断言只有真浏览器能做：

1. **`document.cookie` 里没有会话凭证**（`FAC-9`）——这是 F-ADR-002 的验收
2. **绕过前端直接调 API 仍然被拒**——证明前端守卫不是安全边界

```ts
// e2e：用 cs_staff 的会话，直接调他没权限的接口
const res = await page.request.delete('/api/v1/tickets/42/')
expect(res.status()).toBe(403)   // 前端没参与，后端照样拦住
```

**这条测试是对整个前端权限体系的「祛魅」**：它证明前端做的一切都只是体验。

**代价**
- E2E 慢、需要真实后端和数据。→ 用 `seed_demo` 造数据，CI 里跑一次。

### F-ADR-014：前端构建产物不入库

**问题**：后端 `ADR-015` 决定 Tailwind 产物入库（为了 `git checkout` 任意 tag 就能看到样式）。
React 也这么办吗？

**决定**：**不入库**。`frontend/dist/` 进 `.gitignore`。

**理由**

`ADR-015` 的理由是「切 tag 不需要 `npm install` 就能看到正确样式」——那是因为
Tailwind 产物是**一个 CSS 文件**，几十 KB。

React 的产物是几百个 chunk、几 MB，且每次构建 hash 都变。入库会：
- 让每个 tag 的 diff 里塞满二进制噪音
- 仓库体积迅速膨胀
- 而且**并不能省掉 `npm install`**——学习者要改代码还是得装依赖

**代价**
- 切到某个 `fe-*` tag 后必须 `cd frontend && npm install && npm run dev` 才能看。
  → 在每份 tag 规格书的开头写明这一步。
- `package-lock.json` 必须入库，保证依赖版本可复现。

> **同一个项目里两个相反的决定，理由都成立** ——因为「产物大小」和「是否省掉安装步骤」
> 这两个前提变了。教条地套用前一个决定就会错。

### F-ADR-015：前端不做数据二次过滤

**问题**：前端拿到列表后，要不要再按权限筛一遍？

**决定**：**绝对不要**。前端展示的条数必须与 API 返回的完全一致（`FNFR-5`）。

**理由**

这看起来是「多一道保险」，实际上是**制造不一致的源头**：

- 分页会错乱：后端说 50 条，前端筛掉 10 条，分页器还显示 50
- 统计会对不上：列表显示 40，导出 50
- 而且它没有任何安全价值——前端能看到的数据早就传到浏览器了，
  **过滤发生在数据到达之后，等于没过滤**

数据权限的唯一执行点是后端的 `.for_user()`（后端 `ADR-009`）。

**代价**
- 无。这条只有好处，写进来是因为它是个**常见的错误直觉**。

## 3. 关键流程

### 3.1 冷启动（刷新页面）

```
浏览器加载 SPA
    │
    ▼
读取 csrftoken cookie ──（没有）──▶ GET /api/v1/auth/csrf/ 种一个
    │
    ▼
GET /api/v1/auth/profile/          Cookie: sessionid (httpOnly)
    │
    ├── 401 ──▶ 跳登录页（带 redirect=当前URL）
    │
    └── 200
         │
         ▼
    写入 Zustand store（user / perms / menus）
         │
         ▼
    根据 menus 动态注册路由  ← ⚠️ 必须在这之后才渲染 <RouterProvider>
         │
         ▼
    导航到当前 URL
         │
         ├── 路由存在 ──▶ 渲染页面
         └── 路由不存在 ──▶ 403 页面（不是 404——用户是没权限而不是路径错）
```

### 3.2 一次受权限保护的操作

```
用户点「删除」
  （按钮之所以可见，是因为 <Can perm="ticket:ticket:delete"> 通过了 —— 仅体验）
    │
    ▼
axios 请求拦截器：注入 X-CSRFToken
    │
    ▼
DELETE /api/v1/tickets/42/
    │
    ▼  【唯一的安全边界】
Django: SessionAuthentication → CSRF 校验
        → HasPerm 查 perm_map["destroy"] → services.user_has_perm()
        → ScopedQuerysetMixin.get_queryset().for_user() → 42 不在范围内？
    │
    ├── 403 ──▶ 拦截器：提示「无权限」+ 重拉 profile（可能刚被撤权）
    ├── 404 ──▶ 拦截器：提示「不存在或你无权访问」
    └── 204 ──▶ invalidate ['tickets'] → 列表自动重拉
    │
    ▼
响应头 X-RBAC-Version 比对 ──（变了）──▶ invalidate ['profile']
```

### 3.3 权限被撤销（`FUS-1`）

```
管理员在后台撤销权限
    │
    ▼
后端 signal / bump_version()          rbac:version 42 → 43
    │
    ▼
该用户的下一次任意 API 请求
    │
    ▼
响应头 X-RBAC-Version: 43   ≠   前端记录的 42
    │
    ▼
queryClient.invalidateQueries(['profile'])
    │
    ▼
重新 GET /profile → store 更新 → 菜单/按钮自动重渲染
    │
    ▼
非阻塞提示：「你的权限已更新」
```

**延迟 = 一次 API 请求**，与后端 `FR-4.5` 的承诺一致。

## 4. 安全设计

### 4.1 前端特有的威胁

| 威胁 | 说明 | 防御 |
| --- | --- | --- |
| **误把路由守卫当安全边界** | 最危险的认知错误 | 每个守卫都有对应的后端校验；E2E 直接绕过前端调 API |
| XSS 偷凭证 | localStorage 存 token 的经典问题 | F-ADR-002：httpOnly Cookie，JS 读不到 |
| CSRF | Cookie 认证的连带风险 | F-ADR-004：CSRF token + `SameSite=Lax` |
| 前端 store 被篡改 | 控制台改 `perms` 为 `["*"]` | 无法防止，**也不需要防**——后端才是边界。E2E 专门验证这一点 |
| bundle 泄露系统结构 | 打包产物里能看到所有页面和权限码 | 动态注册减少暴露；接受剩余风险（不构成越权） |
| 403 死循环 | 拦截器把 403 当 401 处理 | F-ADR-011 |
| 敏感数据留在缓存 | 登出后 Query 缓存仍在内存 | 登出时 `queryClient.clear()` + store reset |

### 4.2 E2E 越权矩阵

复用后端 `tests/test_permission_matrix.py` 的同一套演示数据和期望值，
在真实浏览器里再跑一遍：

```
            │ superadmin │ sysadmin │ cs_manager │ cs_staff │ no_role
────────────┼────────────┼──────────┼────────────┼──────────┼────────
菜单可见项   │    全部     │  系统管理 │  工单管理   │ 工单管理  │  空
/system/users│   200      │   200    │   403      │   403    │  403
工单列表条数 │    80      │    80    │    50      │    5     │  403
删除按钮     │    有       │    无    │    有      │    无     │  —
直调删除 API │   204      │   403    │   204      │   403    │  403
跨部门工单   │   200      │   200    │   404      │   404    │  403
```

**最后两行是关键**：「直调删除 API」绕过前端，验证后端独立成立；
它的期望值必须与「删除按钮」那一行**逻辑一致但独立成立**。

## 5. 已知简化与生产差距

| # | 简化 | 生产环境应该怎么做 |
| --- | --- | --- |
| 1 | 全局版本号感知权限变更 | 用户量大时改按角色分级；或 SSE 精准推送 |
| 2 | 不做 i18n | 企业后台常需中英双语 |

## 6. 决策速查

| F-ADR | 决策 | 一句话理由 |
| --- | --- | --- |
| 001 | 与模板版并存 | 唯一能同时看到「一个内核两种表现层」的方式 |
| 002 | httpOnly Cookie + 同域 | XSS 偷不走凭证；代价是必须同域且要防 CSRF |
| 003 | SPA 用 Session，JWT 留给第三方 | 同域下 JWT 的无状态优势不成立，反而失去可撤销性 |
| 004 | `CSRF_COOKIE_HTTPONLY = False` | 它本来就不提供实质防护；真凭证 sessionid 仍是 httpOnly |
| 005 | Query 管服务端状态，Zustand 管客户端 | 按数据归属划分，边界看得见 |
| 006 | 权限只来自 `/profile` | 组件自行推断 = 复制一份权限规则 |
| 007 | 动态注册 + 守卫兜底 | 减少暴露；但要处理刷新时序 |
| 008 | 路由字段放后端 | 前端维护映射表必然漂移 |
| 009 | `<Can>` + `usePermission()` | JSX 和数据两种场景都要覆盖 |
| 010 | `X-RBAC-Version` 响应头 | 复用已有版本号，零额外请求，延迟与后端承诺一致 |
| 011 | 401/403/404 三分流 | 403 跳登录页会造成死循环 |
| 012 | 权限码常量由后端生成 | TS 把模板版的 typo 问题提前到编译期 |
| 013 | Vitest + MSW + Playwright | E2E 是唯一能验证「前端不是安全边界」的层 |
| 014 | 构建产物**不**入库 | 与后端 ADR-015 相反——前提变了，结论就变 |
| 015 | 前端不做数据二次过滤 | 没有安全价值，只制造分页与统计的不一致 |

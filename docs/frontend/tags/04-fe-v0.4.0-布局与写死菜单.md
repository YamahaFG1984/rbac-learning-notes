## 三、接口契约（必须与我的实现对齐）

### 布局插槽

```tsx
<PageContainer
  title="工单列表"
  extra={<Button type="primary">新建工单</Button>}   // 页头右侧操作区
>
  {children}
</PageContainer>
```

对应后端模板版的 `{% block page_title %}` / `{% block page_actions %}` / `{% block content %}`。

### 路由路径（**固定，后面动态注册时要对得上**）

| 路径 | 页面 | 对应权限码（`fe-v0.7.0` 才用） |
| --- | --- | --- |
| `/tickets` | 工单列表 | `ticket:ticket:view` |
| `/tickets/:id` | 工单详情 | `ticket:ticket:view` |
| `/system/depts` | 部门管理 | `system:dept:view` |
| `/system/users` | 用户管理 | `system:user:view` |
| `/system/roles` | 角色管理 | `system:role:view` |
| `/system/perms` | 权限点 | `system:perm:view` |
| `/monitor/audit` | 审计日志 | `system:audit:view` |
| `/403` `/404` | 结果页 | — |

### uiStore

```ts
interface UiState {
  siderCollapsed: boolean
  toggleSider: () => void
}
```

⚠️ 这是**纯客户端状态**（F-ADR-005）——它的真相就在前端，不来自服务端。
可以 persist 到 localStorage。

## 五、⚠️ 容易写错的地方

### 1. 本 tag 的全部意义在于「先别做动态」

第一节第 1、2 问的答案。

后端 `v0.8.0` 的注释我原样搬过来：

> 把「写死菜单」单独作为一个 tag，是刻意的教学安排。
> 当你在 `fe-v0.8.0` 看 diff 时，会清楚看到「动态菜单」到底只改了什么——
> 而不是混在一堆布局和样式改动里看不清。
>
> **tag 的切分要让 diff 讲故事。**

所以本 tag 的 `Sidebar.tsx` 顶部要写一行注释标明它是临时的：

```tsx
// ⚠️ fe-v0.4.0：菜单硬编码，没有任何权限判断。
//    fe-v0.8.0 会改为由 profile 的 menus 渲染。
//    保持结构简单，让那次改动的 diff 干净。
```

**没有这行注释**，三个月后有人看到会以为是遗漏，或者更糟——以为菜单本来就该写死。

### 2. 现在所有人都能看到所有菜单

本 tag 结束后，`cs_staff` 登录也能看到「系统管理」「审计日志」。
点进去会怎样？

- 页面能打开（本 tag 没有路由守卫）
- 但里面是空占位，还没调 API

到 `fe-v0.10.0` 之后，点进去会看到接口 403。
**这个「菜单能点、进去报错」的难看状态会一直持续到 `fe-v0.7.0` / `fe-v0.8.0`。**

这正是要体验的——它让你直观感受到「为什么要做动态菜单」。

### 3. 布局状态不要放 Query

侧边栏折叠、主题、表格列宽这些**没有服务端对应物**，
放进 TanStack Query 是概念错误（它管的是「服务端状态的缓存」）。

判据（F-ADR-005）：**这份数据的真相在哪？**
在数据库 → Query；在浏览器 → Zustand。

### 4. `PageContainer` 要早点抽

看起来是小事，但业务页面有 8 个，每个都手写一遍页头，
到 `fe-v0.12.0` 想统一改样式时要改 8 处。

后端模板版靠 `{% block %}` 解决了同一个问题——React 里对应的是组合。

### 5. 别急着做面包屑和多页签

这两个功能在企业后台很常见，但**和 RBAC 无关**，而且会显著增加
`fe-v0.7.0` 动态路由的复杂度（页签需要维护一个独立的路由栈）。

留到 `fe-v1.0.0` 之后作为练习。

## 九、延伸思考

1. 后端模板版用 `{% extends %}` + `{% block %}` 实现布局复用，
   React 用**组合**（children / props）。
   两者在「新增一个 block」时的改动量分别是多少？哪个更容易破坏既有页面？

2. 本 tag 的菜单是静态数组，`fe-v0.8.0` 会换成 profile 返回的树。
   **中间那个数据结构转换**（后端的 `{id, name, icon, url, children}`
   → AntD 的 `{key, icon, label, children}`）放在哪合适？
   组件里、store 里、还是一个独立的 selector？

3. AntD 的 `Menu` 用 `key` 做选中判断。我们用路径当 key。
   **详情页 `/tickets/42` 时，`/tickets` 这个菜单项还会高亮吗？**
   这个问题在 `fe-v0.8.0` 要解决，先想想怎么做。

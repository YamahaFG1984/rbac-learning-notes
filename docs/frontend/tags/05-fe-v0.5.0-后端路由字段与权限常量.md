## 五、⚠️ 容易写错的地方

### 🔴 1. 改 `services.py` 会不会破坏 `FAC-4`？

第一节没问这个，但你一定会撞上：`get_user_menu_tree()` 在 `services.py` 里，
而我们要给它加输出字段。**这不是违反了「内核不许改」吗？**

**先看清楚 `FAC-4` 的原话**：

```bash
git diff main feat/react-frontend -- apps/rbac/services.py    # 期望：空
```

那么加字段就会让它变红。有三条路：

| 方案 | 评价 |
| --- | --- |
| a. 改 `get_user_menu_tree`，接受 `FAC-4` 变红 | 承认约束失守 |
| b. 在 API 层做转换，`services` 不动 | 内核纯净，但菜单树要遍历两遍 |
| c. `services` 输出**完整字段**，各表现层各取所需 | 内核多输出两个字段 |

**决定：方案 b。** `services.get_user_menu_tree()` 保持不变，
在 `apps/rbac/api/views.py` 里做一次转换，把 `Permission` 的
`route_path` / `component` 补进去。

```python
# apps/rbac/api/views.py
def _enrich_for_spa(nodes, by_id):
    """给菜单树补上前端路由字段。

    ⚠️ 刻意放在 API 层而不是 services 里：
       route_path / component 是**这一种表现层**特有的东西，
       模板版完全用不上。放进内核就是让内核认识 React（F-ADR-008 / ADR-013）。
    """
```

**为什么不选 c**（看起来更省事）：因为那等于承认「内核可以为某个前端多输出字段」。
今天加 React 的两个字段，明天加小程序的三个，内核就慢慢变成了所有前端的公共字段袋。

> **约束的价值在于它被坚持时才存在。** 破例一次，后面每次都能找到破例的理由。

这条会在 `fe-v1.0.0` 的回顾里再提一次——它是本阶段**最容易失守的地方**。

### 2. `component` 字段是「路径」不是「组件名」

```
✅ "tickets/List"        → src/pages/tickets/List.tsx
❌ "TicketList"          → 前端要维护一张名字到路径的映射，等于回到方案 c
```

用路径的好处：前端可以用 `import.meta.glob` 直接映射，零维护。

### 3. 响应字段命名：统一 camelCase

后端习惯 snake_case，前端习惯 camelCase。混用的后果是
前端代码里一半 `routePath` 一半 `route_path`，谁也记不住哪个是哪个。

**选一个，全局统一。** 我们选 camelCase（因为消费者是前端）。
DRF 可以用 `djangorestframework-camel-case`，也可以在 serializer 里显式命名。

⚠️ 已有的 `/profile` 响应里已经有 `is_superuser`、`real_name` 这类 snake_case，
改动会波及 `fe-v0.3.0`。**要么现在统一，要么一直混用**——现在改成本最低。

### 4. `--check-frontend` 只能检查文件存在，检查不了别的

它能发现「`component` 写成了 `tickets/Lst`」，
发现不了「写成了另一个真实存在但不对的组件」。

**部分解决好过不解决**——和 `v1.0.0` 的 `--check-templates` 是同一个思路。

### 5. 生成的 TS 文件要标明「勿手工编辑」

```ts
// ⚙️ 此文件由 `python manage.py export_perm_constants` 生成，请勿手工编辑。
// 后端权限点变更后重新生成；CI 会校验它与后端一致。
```

并在 CI 里加一步：重新生成后 `git diff --exit-code`，不一致就失败。

### 6. 🔴 权限码常量的类型收窄才是重点

```ts
export const PERM = { TICKET_TICKET_VIEW: 'ticket:ticket:view', ... } as const
export type PermCode = (typeof PERM)[keyof typeof PERM]
```

`as const` 不能少——没有它，类型会被推断成 `string`，收窄就失效了。

有了它，`<Can perm="ticket:ticket:delet">` **编译期就报错**。

> 这是 SPA 相比模板版**唯一在权限安全性上更强的地方**：
> 模板版靠 `sync_permissions --check-templates` 事后扫描（`v1.0.0`），
> TypeScript 可以在编译期就挡住。值得利用。

## 六、卡住了看这里（渐进提示）

<details>
<summary><b>提示 1：API 层的菜单转换</b></summary>

```python
# apps/rbac/api/views.py

def _spa_menu_tree(user):
    """在 API 层给菜单树补上前端路由字段。

    ⚠️ 不改 services.get_user_menu_tree()——route_path / component 是
       SPA 特有的展示层信息，模板版用不上。放进内核就是让内核认识 React。
       这是 ADR-013「内核不认识表现层」在本阶段的具体形态。
    """
    tree = get_user_menu_tree(user)          # ← 内核原样调用，一行不改
    extra = dict(
        Permission.objects.filter(is_active=True).values_list(
            "id", "route_path"
        )
    )
    comp = dict(
        Permission.objects.filter(is_active=True).values_list("id", "component")
    )

    def walk(nodes):
        for n in nodes:
            n["routePath"] = extra.get(n["id"]) or None
            n["component"] = comp.get(n["id"]) or None
            walk(n["children"])
        return nodes

    return walk(tree)
```

⚠️ 这里多了一次查询。可以合并成一次 `values("id", "route_path", "component")`——
留给你优化。
</details>

<details>
<summary><b>提示 2：导出命令</b></summary>

```python
class Command(BaseCommand):
    help = "把权限码导出为前端 TS 常量"

    def handle(self, *args, **options):
        codes = list(
            Permission.objects.exclude(code__isnull=True)
            .exclude(is_deprecated=True)
            .order_by("code")
            .values_list("code", "name")
        )
        lines = [
            "// ⚙️ 此文件由 `python manage.py export_perm_constants` 生成，请勿手工编辑。",
            "// 后端权限点变更后重新生成；CI 会校验它与后端一致。",
            "",
            "export const PERM = {",
        ]
        for code, name in codes:
            const = code.upper().replace(":", "_").replace("-", "_")
            lines.append(f"  /** {name} */")
            lines.append(f"  {const}: '{code}',")
        lines += [
            "} as const",          # ← 少了 as const，类型会退化成 string
            "",
            "export type PermCode = (typeof PERM)[keyof typeof PERM]",
            "",
        ]
        target = Path(settings.BASE_DIR, "frontend/src/constants/permissions.ts")
        target.write_text("\n".join(lines), encoding="utf-8")
        self.stdout.write(self.style.SUCCESS(f"已写入 {target}（{len(codes)} 个权限码）"))
```
</details>

## 八、和我的实现对比什么

```bash
git diff fe-v0.4.0 fe-v0.5.0
```

| 对比点 | 想一想 |
| --- | --- |
| 🔒 **`services.py` 动了吗** | 动了的话，`FAC-4` 已经失守。回去看陷阱 1 的三个方案 |
| **`component` 存的是路径还是名字** | 存名字的话，前端要维护一张映射表——等于把决策推给了前端 |
| **字段命名统一了吗** | 混用 camelCase / snake_case 的话，越往后改成本越高 |
| **`as const` 加了吗** | 跑用例 7。没加的话类型收窄完全失效，而且不报错 |
| **CI 校验加了吗** | 没加的话，后端改了权限点、前端常量没更新，没人会发现 |

## 九、延伸思考

1. **陷阱 1 的方案 c 真的那么糟吗？** 让 `services` 输出完整字段，各表现层各取所需——
   这在很多项目里是常见做法。想想它在什么规模下会开始出问题。

2. `--check-frontend` 检查的是「文件存在」。**能不能检查得更严？**
   （提示：解析 TS 文件确认它 `export default` 了一个 React 组件——
   成本和收益比是多少？）

3. 我们让后端生成前端的 TS 文件。**反过来行不行**——前端定义权限码，后端校验？
   想想「权限点的定义权应该在谁手里」（回看后端 `ADR-004`）。

4. **更彻底的做法是 OpenAPI**：后端生成 schema，前端用 `openapi-typescript`
   生成全部类型（不只是权限码，还有所有请求/响应类型）。
   查一下 `drf-spectacular`，想想它能替代掉本 tag 的多少工作，又会引入什么。

## 三、接口契约

### 🔴 404 的统一文案（**固定**）

```
不存在或你无权访问
```

不是「工单不存在」，也不是「无权访问」——**两种情况都覆盖，且不泄露是哪一种**。

### mutation 后的失效

```ts
onSuccess: () => {
  queryClient.invalidateQueries({ queryKey: ['tickets'] })    // 列表
  queryClient.invalidateQueries({ queryKey: ['ticket', id] }) // 详情
}
```

## 五、⚠️ 容易写错的地方

### 🔴 1. 404 的文案必须模糊

第一节第 1、2 问的答案。

后端 `ADR-009` 决定：数据权限范围外的记录返回 **404 而不是 403**——
403 会泄露「这条记录存在」，攻击者可以遍历 ID 画出数据库的 ID 分布。

**前端如果把文案写成「工单不存在」，等于把后端的努力白费了一半**：
用户（和攻击者）会以为这个 ID 真的没有。更糟的是，真正的管理员看到这个提示
会去数据库里找，发现明明有——然后来报「系统 bug」。

统一文案「**不存在或你无权访问**」：
- 不泄露是哪一种
- 给了用户下一步动作的暗示（去找管理员）

对照后端 `v0.8.0` 的 `404.html`，那里写的是
「如果你认为这是权限问题，请联系系统管理员」——同一个思路。

### 2. `creator` / `department` 不能由前端提交

第一节第 3 问。后端 `TicketSerializer` 把它们设成了 `read_only`（`v1.1.0`），
提交了也会被忽略。

**但前端不该依赖这一点**——表单里就不该有这两个字段。
理由是「不要把安全性寄托在对端的实现细节上」：
后端某天改了 serializer，前端的伪造就会生效。

### 🔴 3. 详情页的 404 要在页面级处理，不是全局 toast

```tsx
// ❌ 全局拦截器弹个 toast，页面还停在那儿显示空白
// ✅ 页面级：整页替换成 ResourceNotFound
const { data, error } = useTicketQuery(id)
if (error?.response?.status === 404) return <ResourceNotFound />
```

全局拦截器负责**通用**处理（`fe-v0.14.0`），
但「详情页拿不到数据」需要**整页替换**，不能只弹提示。

### 4. 删除后用 invalidate，不要本地删行

第一节第 4 问。

```tsx
// ❌ 本地删：分页数字不对了（还显示 50，实际 49），且下一页的数据没补上来
setRows(rows.filter((r) => r.id !== id))

// ✅ invalidate：让后端重新算
queryClient.invalidateQueries({ queryKey: ['tickets'] })
```

这是 F-ADR-015「前端不做数据二次处理」的又一个形态——
**分页和计数的真相在后端**。

### 5. 编辑页也要处理 404

```
cs_staff 直接访问 /tickets/42/edit（42 是技术部的）
```

后端 `v0.15.0` 保证了 GET 和 POST 都返回 404。
前端的编辑页在加载数据时就会拿到 404，此时应该整页替换，
**而不是渲染一个空表单让用户填完再报错**。

### 6. 表单校验不要复制后端规则

```tsx
// ❌ 前端自己判断「标题不能超过 128 字符」
// —— 后端改成 256 时前端不知道
```

基本的必填/类型校验可以做（体验），但**业务规则以后端为准**：
提交失败时把后端返回的字段错误映射到表单上。

```ts
// DRF 的字段错误格式：{ "title": ["该字段不能为空。"] }
form.setFields(Object.entries(err.response.data).map(([name, errors]) => ({ name, errors })))
```

### 🔴 7. 📌 本 tag 挖出了一个真实漏洞：派单的下拉框

派单要选处理人，所以需要一份用户列表。**这份列表该给谁看？**

先看模板版是怎么写的（`v0.15.0`）：

```python
class TicketAssignForm(forms.ModelForm):
    class Meta:
        fields = ["assignee"]     # ← 没有限制 queryset
```

ModelForm 的默认 queryset 是「这个外键指向的**所有**对象」。实际跑一下：

```
候选人数量: 6
['superadmin', 'sysadmin', 'cs_manager', 'cs_staff', 'no_role', 'techie']
```

`cs_manager` **没有** `system:user:view`，却通过派单下拉框
看到了公司完整的用户名册——包括超管和技术部同事。
`TicketForm` 里的 `assignee` 字段有同样的问题，`cs_staff` 新建工单时也能看到。

> **一个「不该看到用户列表」的人，通过另一个功能的下拉框看到了用户列表。**
>
> 这类漏洞不会出现在权限矩阵里——矩阵测的是**接口**，
> 而它藏在一个表单控件的默认行为里。
>
> 可以贴在墙上的规则：**凡是外键下拉框，都要问一句「这个列表该给谁看」。**

修法（`apps/tickets/services.py::get_assignable_users`）：

- 范围规则走 `get_user_dept_ids()`（ADR-016），不另写一套 `path__startswith`
- **两个入口共用同一个函数**——只修 API 那侧的话，模板版的泄露就留在原地
- 忘了传 `actor` 时兜底为**空集**，不是全部用户

最后一条尤其重要。我第一版写的是「不传 actor 就保持默认」，
也就是**悄无声息地退回漏洞本身**。空下拉框会立刻被人报 bug，
全量下拉框不会——没有人会因为「选项太多」去提工单。
这就是「默认值指向出错后果最轻的方向」在表单上的形态。

### 8. 候选人接口不要复用 `/api/v1/users/`

顺着上一条：SPA 需要一个候选人接口。直接用 `/api/v1/users/` 行不行？

**不行。** 那个接口要 `system:user:view`，而 `cs_manager` 只有 `assign`。
复用它就等于「为了让主管能派单，只好给他用户管理权限」——
**权限点被业务需求倒逼着变粗，是权限模型腐化的典型路径。**

所以新增 `/tickets/assignable-users/`，权限点用 `ticket:ticket:assign`：
它不是一个独立的「界面上可点的东西」，只是派单这个动作的一部分（ADR-004）。

⚠️ 返回的字段也要收窄。复用 `UserSerializer` 会把手机号、邮箱一起送出去，
而调用方只需要「显示一个名字、提交一个 id」。
**接口返回的字段量应该由调用方的需要决定，不是由「手边正好有什么」决定。**

⚠️ 提交时后端**必须再校验一次** assignee 在不在范围内。
下拉框只是界面，攻击者直接提交任意 id——
**下拉框不是安全边界**，和「隐藏按钮不是安全边界」是同一句话。

## 七bis、两个测试环境的坑（我自己踩的）

📌 **`确定` vs `确 定`**：`fe-v0.7.0` 我全局关掉了 AntD 的 `autoInsertSpace`，
本 tag 写 E2E 时却顺手写了 `getByRole('button', { name: '确 定' })`，
于是三条用例超时。**同一个坑的反面**——一旦你改了全局渲染行为，
就要记得它对**所有**按文本查找的代码都生效。

📌 **上一个 tag 的测试会因为这个 tag 变红**：`fe-v0.7.0` 的
「详情页刷新不会 404」断言的是占位页标题「工单详情」，
而本 tag 之后详情页的标题变成了工单标题本身。

改测试时又踩了一次：点完链接立刻读 `h4` 拿到的还是「工单列表」，
断言在**刷新之后**才失败，报错指向刷新，真正的原因却是**没等导航完成**。

> **异步 UI 里，断言失败的位置常常不是问题发生的位置。**

📌 **`seed_demo --flush` 本身有个 bug**（顺手修了）：
`Role.inherits_from` 是自引用 `PROTECT`，`Role.objects.all().delete()`
会抛 `ProtectedError`。`v1.0.0` 记得给部门树做「从叶子往根删」，
却漏了角色继承树——同一个形状，只处理了一处。

而且它**只在第二次运行时才会崩**（第一次库是空的），
所以一直没被发现。教训：
**`PROTECT` 是一条只在删除路径上才冒出来的约束，
而删除路径通常是最少被走到的那条。**

## 九、延伸思考

1. **用例 3 和用例 7 分别验证了什么？**
   一个是数据权限（404），一个是功能权限（403）。
   前端对这两者的处理不同——说清楚为什么。

2. 「不存在或你无权访问」这个文案**牺牲了一点用户体验**换取不泄露。
   有没有折中做法？（提示：登录用户 vs 匿名用户能不能区别对待？
   想想这会不会重新打开探测通道。）

3. 后端 `v0.15.0` 用 `ScopedObjectMixin` 让 GET/POST 走同一个 queryset，
   避免「只挡住 GET」的疏漏。**前端有没有对应的疏漏模式？**
   （提示：详情页处理了 404，编辑页呢？删除确认框呢？）

## 五、⚠️ 容易写错的地方

### 1. 测试数据必须与后端演示数据对齐

后端 `apps/common/demo.py` 定义了标准数据集（`v0.19.0`/`v1.0.0`）：
`cs_manager` 看 50 条、`cs_staff` 看 5 条……

前端 fixtures **必须用同一套数字**：

```ts
// src/test/fixtures.ts
export const CS_MANAGER_PROFILE = {
  user: { username: 'cs_manager', ... },
  perms: ['ticket:ticket:view', 'ticket:ticket:create', ...],   // 与后端一致
  menus: [...],
}
```

不一致的话，前端测试全绿但一接真后端就崩——**测的不是同一个系统**。

### 2. MSW 拦的是网络层，不是 axios

```ts
// ❌ mock axios：测不到拦截器
vi.mock('axios')

// ✅ MSW：拦截真实的 fetch/XHR，拦截器照常执行
server.use(http.get('/api/v1/auth/profile/', () => HttpResponse.json(...)))
```

我们的权限逻辑有**一半在拦截器里**（CSRF 注入、401 分流、版本号比对）。
mock 掉 axios 就把它们全跳过了。

### 🔴 3. 前后端权限码对账（第一节第 3 问）

后端 `v0.10.0` 的结构性测试：

```python
def test_every_template_guard_has_a_view_guard(self):
    """模板里有几个 `in perms`，视图层就该有几个对应的 @require_perm。"""
```

前端版要对账两件事：

```ts
// 1. 前端用到的权限码，后端都存在
//    （TS 类型已经保证了——但常量文件可能过期，所以还要跑一次）
// 2. 前端用到的权限码，后端 perm_map 里有对应声明
//    （即「隐藏了按钮但后端没拦」）
```

实现：扫描 `src/**/*.tsx` 里的 `PERM.XXX` 引用，
与 `src/constants/permissions.ts` 和后端导出的清单比对。

⚠️ **第 2 条前端做不完整**——它需要知道后端的 `perm_map`，
那要么后端再导出一份，要么留给 E2E。**本 tag 先做第 1 条，第 2 条记在 TODO。**

诚实地承认这个缺口，比假装覆盖了要好。

📌 **写到这里我把第 2 条也做了**，因为它正是延伸思考第 2 题问的那件事。

后端加了 `export_enforced_perms` 命令：扫描全部路由，
收集**服务端实际用于判断**的权限码（模板视图的 `@require_perm`
+ ViewSet 的 `perm_map`），导出成 `frontend/src/test/enforced-perms.json`。

⚠️ 复用 `checks.py` 的 `_iter_views` / `_unwrap`，不另写一套遍历——
另写一套的话，`rbac.W001` 能看到的视图和这里能看到的视图会不一致，
**而不一致的那部分正好是最容易出漏洞的地方**。

前端的结构性测试拿它对账，抓的是最危险的一类漏：

```
<Can perm={PERM.TICKET_TICKET_DELETE}>   ← 前端藏了按钮
# 后端 destroy 忘了写进 perm_map        ← 服务端根本没拦
```

权限码存在、TypeScript 编译通过、界面看起来完全正确，而那个接口是裸奔的。
**前端的隐藏给了所有人一种安全的错觉。**

这就是安全红线 2「成对出现，缺一不可」变成一条会跑的断言。

⚠️ 但它仍然**不完整**，而且必须说清楚不完整在哪：

| | |
| --- | --- |
| ✅ 抓得住 | 前端管了、后端**完全没管**这个码 |
| ❌ 抓不住 | 后端管了，但管在了**另一个接口**上 |

要抓住后者，导出的清单得带上路由，前端还得声明「这个按钮会调哪个接口」——
那是另一个量级的工作。真正兜住这一层的是 `fe-v0.16.0` 的越权矩阵 E2E：
**它不看代码，直接拿每个角色去打每个接口。**

⚠️ 还有一条容易忽略的：这份导出文件**过期的话，对账就是假的**——
前端那条测试仍然会绿。所以后端有一条 `--check` 测试守着它。
**用一份陈旧的清单对账，比不对账更危险**，因为它给人一种已经检查过的错觉。

### 4. `staleTime: Infinity` 让测试之间串数据

QueryClient 是模块级单例的话，测试 A 拉的 profile 会被测试 B 读到。

```ts
// 每个测试新建一个 QueryClient
function renderWithProviders(ui: ReactElement) {
  const client = new QueryClient({ defaultOptions: { queries: { retry: false } } })
  return render(<QueryClientProvider client={client}>{ui}</QueryClientProvider>)
}
```

对照后端 `v0.16.0` 加的 `tests/conftest.py` 全局清缓存 fixture——
**同一个问题的两种语言版本**：有缓存就必须管测试隔离。

### 5. 权限相关的模块要求 90% 覆盖率

```
src/auth/**          ≥ 90%
src/components/Can   ≥ 90%
src/router/**        ≥ 90%
整体                 ≥ 80%
```

和后端 `apps/rbac ≥ 90%` 是同一个标准。

📌 **实现时发现上面这张表自相矛盾**，值得单独说明。

`src/router/** ≥ 90%` 和本节陷阱 6「路由行为留给 E2E」是冲突的：
`AppRouter` 的价值**全在时序上**（刷新、动态注册、403 vs 404），
而 jsdom 的 history 行为和真实浏览器有差异——在 jsdom 里测它，
写出来的正是陷阱 6 说的那种「测了但没测到」的假测试。

最后的取舍：

| 范围 | 阈值 | 理由 |
| --- | --- | --- |
| `src/auth/**` | 90% | 权限判断的逻辑，纯函数居多 |
| `Can.tsx` / `PermissionGate.tsx` | 90% | 同上 |
| `errorHandlers.ts` / `versionWatcher.ts` | 90% | 同上 |
| `AppRouter.tsx` / 各页面 | **不设阈值** | 交给 e2e/（真浏览器 + 真后端） |
| 整体 | **不设 80%** | 见下 |

全局覆盖率因此只有约 **22%**。这个数字不好看，但它是诚实的：
把 CRUD 页面用 jsdom 测一遍能把它推到 80%，
但那些断言 `e2e/admin-pages.spec.ts` 已经用**真后端**做过了，
重复一遍只增加维护成本，不增加任何保证。

> **覆盖率是下限不是目标。90% 的覆盖率不代表那 90% 测对了。**
> 一个能靠「多写几个 render() 测试」刷上去的指标，
> 一旦变成目标就立刻失去意义。

如果你更倾向于凑满 80%，那也是一个合理的选择——
但请先想清楚新增的那些测试**能发现什么现在发现不了的问题**。

### 6. 有些东西单测测不了，别硬测

第一节第 4 问：

| 测不了的 | 为什么 | 留给谁 |
| --- | --- | --- |
| `document.cookie` 里没有 sessionid | jsdom 不实现 httpOnly | E2E |
| 绕过前端直接调 API 被拒 | 需要真后端 | E2E |
| 真实的 CSRF 校验 | 同上 | E2E |
| 动态路由在真实浏览器刷新后的行为 | jsdom 的 history 行为有差异 | E2E |

**硬用 jsdom 测这些，会写出「测了但没测到」的假测试**——比不测更糟。

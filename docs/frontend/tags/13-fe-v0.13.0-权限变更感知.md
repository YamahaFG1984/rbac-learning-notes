## 五、⚠️ 容易写错的地方

### 🔴 1. 先想清楚「后端的承诺」到底承诺了什么

第二节第 1 问的答案。

后端 `FR-4.5`：「授权变更后，受影响用户的权限**最迟在下一次请求时**生效」。

这句话**只管服务端**。它保证的是：`cs_manager` 下一次调删除接口时会被拒。
**它从来没承诺过「前端的按钮会消失」**——那是另一层的事。

理解这一点很重要：**这不是后端的 bug，是 SPA 引入的新问题。**
模板版之所以没有，是因为它的「界面」和「判断」是同一次请求产生的。

### 2. 为什么选响应头方案

第二节第 2、3 问。四种办法的对比：

| 方案 | 延迟 | 前端成本 | 服务端成本 |
| --- | --- | --- | --- |
| 什么都不做 | 直到用户 F5 | 0 | 0 |
| 路由切换时重拉 profile | 一次导航 | 低 | **每次导航一次请求** |
| **响应头带版本号** | **一次 API 请求** | **低** | **一次 cache 读** |
| 定时轮询 | 轮询间隔 | 低 | 持续请求 |
| WebSocket / SSE | 近实时 | **高** | 长连接 |

响应头方案的优势是**零额外请求**——版本号搭在已有的响应上。

而且它的延迟**正好等于后端的承诺**（一次 API 请求）：
前后端的生效语义对齐了，这一点比省几个请求更重要。

### 3. 中间件只给 `/api/` 加头

```python
if not request.path.startswith("/api/"):
    return response
```

给模板版的 HTML 响应加这个头没有意义（它每次都重算），
反而增加响应体积。

### 4. `get_version()` 是一次 cache 读，不是 DB 查询

`v0.16.0` 的版本号存在 cache 里。中间件里调它成本极低。

⚠️ 但**每个 API 响应都调一次**。如果用的是 LocMemCache 没问题；
Redis 的话就是一次网络往返——在高 QPS 下值得测一下。

可以用请求级缓存优化（一次请求内只读一次），但**先别提前优化**。

### 🔴 5. 前端只在版本**真的变了**时才 invalidate

```ts
// ❌ 每次响应都 invalidate → 每个请求都触发重拉 profile → 无限循环
queryClient.invalidateQueries({ queryKey: ['profile'] })

// ✅ 只在变化时
if (v && lastSeen !== null && v !== lastSeen) { invalidate() }
lastSeen = v
```

⚠️ 注意 `lastSeen !== null` 这个条件——**第一次收到版本号时不该 invalidate**
（那时 profile 刚拉完，再拉一次是浪费，而且会形成循环：
profile 请求本身也会带回版本号）。

### 6. 兜底：403 时强制重拉

第二节第 4 问。用户停在静态页面不发请求时，版本号方案感知不到。

但只要他**点了任何一个按钮**，就会收到 403 —— 这正是兜底时机：

```ts
if (status === 403) {
  queryClient.invalidateQueries({ queryKey: ['profile'] })
  message.warning('权限不足，正在刷新你的权限信息')
}
```

这样即使版本号漏了，用户点一次也能恢复到正确状态。

### 7. 给用户一个提示，不要静默改变界面

第二节第 5 问。

界面上的按钮突然消失、菜单少了一项——用户会以为自己看错了或者系统抽风。

```tsx
message.info('你的权限已更新')
```

**非阻塞**（不是 Modal），因为这不是需要用户确认的事。

### 8. 版本号变化不等于「我的权限变了」

全局版本号是粗粒度的（后端 `ADR-010` 的已知取舍）：
**任何人**改权限，所有在线用户都会重拉一次 profile。

所以「你的权限已更新」这句提示**有可能是误报**（重拉后发现权限没变）。

更精确的做法：重拉后比对新旧 `perms`，真的变了才提示。

```ts
const before = useAuthStore.getState().perms
await refetchProfile()
const after = useAuthStore.getState().perms
if (!sameSet(before, after)) message.info('你的权限已更新')
```

## 六、卡住了看这里（渐进提示）

<details>
<summary><b>提示 1：后端中间件</b></summary>

```python
class RbacVersionMiddleware:
    """在 API 响应头里带上当前的 RBAC 版本号。

    SPA 靠它感知「我手里的权限快照过期了」——这个问题在模板版不存在，
    因为模板版的界面和权限判断是同一次请求产生的（F-ADR-010）。

    复用 v0.16.0 已有的全局版本号，零额外存储。
    """

    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        response = self.get_response(request)
        if request.path.startswith("/api/"):
            from apps.rbac.cache import get_version
            response["X-RBAC-Version"] = str(get_version())
        return response
```
</details>

<details>
<summary><b>提示 2：前端 watcher</b></summary>

```ts
let lastSeen: string | null = null

export function watchRbacVersion(response: AxiosResponse) {
  const v = response.headers['x-rbac-version']
  if (!v) return

  // ⚠️ 第一次不 invalidate —— 那时 profile 刚拉完，再拉一次会形成循环
  if (lastSeen !== null && v !== lastSeen) {
    const before = useAuthStore.getState().perms
    queryClient.invalidateQueries({ queryKey: ['profile'] }).then(() => {
      const after = useAuthStore.getState().perms
      // 全局版本号是粗粒度的：别人改权限也会 bump。
      // 真的变了才提示，避免误报（ADR-010 的已知取舍）
      if (!sameSet(before, after)) message.info('你的权限已更新')
    })
  }
  lastSeen = v
}

export function resetVersionWatcher() {
  lastSeen = null      // 登出时调用
}
```
</details>

## 九、延伸思考

1. **回到第一节的实验**：现在再做一遍，对比模板版和 SPA 的行为。
   两者的延迟分别是多少？谁的实现更复杂？**这个复杂度是 SPA 的固有成本还是我们的选择？**

2. 全局版本号意味着「任何人改权限，所有在线用户都重拉 profile」。
   1000 个在线用户 + 一天 20 次权限变更 = 多少次额外的 profile 请求？
   **什么规模下这个方案会撑不住？** 那时该换成什么？
   （提示：后端 `ADR-010` 的进阶思考题——按角色分级版本号。）

3. **SSE 方案**长什么样？后端在 `bump_version()` 时向订阅者推送。
   它的延迟更低，但引入了什么新问题？（提示：长连接的数量、
   Nginx 的超时配置、多进程部署时的消息分发。）

4. 我们的提示是「你的权限已更新」。**如果用户正在填一个长表单**，
   界面突然变了会不会丢失输入？想想有没有需要「延迟应用」的场景。

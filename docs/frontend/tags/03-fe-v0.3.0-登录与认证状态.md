## 三、接口契约（必须与我的实现对齐）

### store 形状（本 tag 版本）

```ts
interface AuthState {
  user: User | null
  status: 'unknown' | 'authenticated' | 'anonymous'
  setUser: (u: User | null) => void
  reset: () => void
}
```

⚠️ `status` 三态而不是布尔——`unknown` 表示「还没问过后端」，
不能和「确定未登录」混为一谈（见陷阱 1）。

### CSRF 注入

```ts
client.interceptors.request.use((config) => {
  if (!['get', 'head', 'options'].includes(config.method ?? '')) {
    config.headers['X-CSRFToken'] = getCookie('csrftoken') ?? ''
  }
  return config
})
```

### 登录后的跳转

```
/login?redirect=%2Ftickets%2F42   →  登录成功后回到 /tickets/42
```

## 四、实现步骤

**Step 1** — `getCookie()` + CSRF 请求拦截器。

**Step 2** — 应用启动时 `GET /auth/csrf/` 种 cookie。

**Step 3** — 登录页（AntD `Form`），调 `POST /auth/login/`。

**Step 4** — 401 响应拦截：清 store → 跳 `/login?redirect=当前路径`。

**Step 5** — `RequireAuth` 包住受保护路由。

**Step 6** — 登出：调接口 + `queryClient.clear()` + `store.reset()`。

## 五、⚠️ 容易写错的地方

### 1. 认证状态是三态，不是布尔

第一节第 1 问的答案：**前端不保存 token，它靠「调一次接口试试」来判断自己登没登录。**

这就带来一个中间态：应用刚启动，还没问过后端，此时既不是「已登录」也不是「未登录」。

```ts
// ❌ 布尔值：初始 false = 未登录 → 应用启动瞬间闪一下登录页，然后又跳回来
const [isAuth, setIsAuth] = useState(false)

// ✅ 三态
status: 'unknown' | 'authenticated' | 'anonymous'
```

`unknown` 时渲染全屏 loading，**不渲染登录页也不渲染业务界面**。

这条在 `fe-v0.6.0` 会变得更重要（`FE-2.3`：profile 未加载完不渲染业务界面）。

### 2. CSRF token 要在**登录之前**就拿到

第一节第 2 问。DRF 的 `SessionAuthentication` 强制 CSRF 检查，
而登录本身是 POST——**它也需要 token**。

正确顺序：

```
应用启动 → GET /auth/csrf/（种 cookie）→ 用户填表 → POST /auth/login/（带 X-CSRFToken）
```

反过来的话，登录直接 403，而且报错信息完全指不到 CSRF。

⚠️ 登录成功后后端会 `rotate_token`，**cookie 里的值变了**。
所以拦截器必须**每次请求都重新读 cookie**，不能在启动时读一次存起来。

### 3. 🔴 400 和 401 要区别处理

第一节第 4 问。

| 场景 | 状态码 | 前端动作 |
| --- | --- | --- |
| 登录页填错密码 | **400** | 在表单上显示错误，**留在登录页** |
| 会话过期 | **401** | 清 store → 跳登录页 |

如果拦截器把 400 也当 401 处理，用户填错密码后页面会「刷新一下」跳回登录页，
**错误提示根本来不及看**。

这是 `fe-v0.2.0` 让登录失败返回 400 的原因。

### 4. 401 并发去重

一个页面可能同时发 5 个请求，会话过期时会同时收到 5 个 401，
于是 `navigate('/login')` 被调 5 次。

表现：地址栏出现 `/login?redirect=/login?redirect=/login...`

```ts
let redirecting = false
if (status === 401 && !redirecting) {
  redirecting = true
  // 跳转后重置
}
```

### 5. 登出必须清三样东西

第一节第 5 问：

| 要清的 | 漏了会怎样 |
| --- | --- |
| 后端 session（调接口） | 服务端还认这个会话 |
| Zustand store | 界面还显示上一个用户的名字 |
| **TanStack Query 缓存** | **下一个用户登录后会看到上一个用户的数据**（缓存里还留着） |

第三条最容易漏，也最严重——这是**跨用户数据泄露**。

```ts
await logoutApi()
queryClient.clear()      // ← 别忘
useAuthStore.getState().reset()
```

### 6. `redirect` 参数要校验

```ts
// ❌ 开放重定向
navigate(searchParams.get('redirect') ?? '/')

// ✅ 只接受站内路径
const raw = searchParams.get('redirect') ?? '/'
const safe = raw.startsWith('/') && !raw.startsWith('//') ? raw : '/'
```

`//evil.com` 会被浏览器当成协议相对 URL 跳到外站——这和后端 `v0.7.0`
的 `url_has_allowed_host_and_scheme` 是同一个问题的前端版本。

## 六、卡住了看这里（渐进提示）

<details>
<summary><b>提示 1：CSRF 工具与拦截器</b></summary>

```ts
// src/api/csrf.ts
export function getCookie(name: string): string | null {
  const match = document.cookie.match(new RegExp(`(^|;\\s*)${name}=([^;]*)`))
  return match ? decodeURIComponent(match[2]) : null
}

// ⚠️ 每次请求都重新读 —— 登录后后端会 rotate_token，缓存住旧值会 403
client.interceptors.request.use((config) => {
  const method = (config.method ?? 'get').toLowerCase()
  if (!['get', 'head', 'options'].includes(method)) {
    config.headers.set('X-CSRFToken', getCookie('csrftoken') ?? '')
  }
  return config
})
```
</details>

<details>
<summary><b>提示 2：401 拦截（含并发去重）</b></summary>

```ts
let redirectingToLogin = false

client.interceptors.response.use(
  (r) => r,
  (error) => {
    const status = error.response?.status
    // ⚠️ 只处理 401。400（登录失败）和 403（无权限）由调用方自己处理，
    //    详见 F-ADR-011 —— 403 跳登录页会造成死循环。
    if (status === 401 && !redirectingToLogin) {
      redirectingToLogin = true
      useAuthStore.getState().reset()
      queryClient.clear()
      const here = window.location.pathname + window.location.search
      window.location.href = `/login?redirect=${encodeURIComponent(here)}`
    }
    return Promise.reject(error)
  },
)
```
</details>

<details>
<summary><b>提示 3：RequireAuth</b></summary>

```tsx
// 只管「登没登录」，不管「有没有权限」——权限守卫是 fe-v0.7.0 的事，
// 两者职责分开，否则以后改一个会影响另一个。
export function RequireAuth({ children }: { children: ReactNode }) {
  const status = useAuthStore((s) => s.status)
  const location = useLocation()

  if (status === 'unknown') return <FullPageSpin />
  if (status === 'anonymous') {
    const redirect = encodeURIComponent(location.pathname + location.search)
    return <Navigate to={`/login?redirect=${redirect}`} replace />
  }
  return <>{children}</>
}
```
</details>

## 九、延伸思考

1. **前端怎么知道「我登录了」？** 我们的答案是「调 `/profile` 试试，401 就是没登录」。
   另一种做法是登录后在 `localStorage` 存一个 `isLoggedIn: true` 标记。
   后者有什么问题？（提示：这个标记和服务端的真实状态会不会不一致？不一致时听谁的？）

2. **「记住我」功能**怎么做？它和 `SESSION_COOKIE_AGE` 的关系是什么？
   查一下 `request.session.set_expiry()`。

3. 用例 11 的并发去重用了一个模块级变量。
   **如果用户在跳转过程中又触发了请求**，这个 flag 什么时候该重置？
   想想有没有更干净的做法（提示：跳转本身会卸载整个应用）。

4. 我们让 `login` 接口直接返回 profile 结构，省掉一次往返。
   这是个好设计吗？想想它的代价：登录接口和 profile 接口的响应结构耦合了，
   将来 profile 加字段时会怎样？

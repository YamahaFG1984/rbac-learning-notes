## 三、接口契约（**固定**）

| 状态码 | 含义 | 前端动作 |
| --- | --- | --- |
| **401** | 未认证 / 会话过期 | 清 store + 清缓存 → 跳登录（带 redirect）→ **不弹提示** |
| **403** | 已认证但无权限 | 提示「权限不足」+ 重拉 profile → **绝不跳登录页** |
| **404** | 不存在 **或** 不在数据范围内 | 由调用方决定（详情页整页替换 / 列表页提示） |
| **400** | 业务校验失败 | 由调用方处理（映射到表单） |
| **429** | 被限流/锁定 | 显示后端的 `detail` |
| **5xx** | 服务端错误 | 错误边界 + 重试按钮，**不弹 toast** |
| 网络错误 | 无响应 | 「网络连接失败」+ 重试 |

## 五、⚠️ 容易写错的地方

### 🔴 1. 403 绝不跳登录页

第一节第 1、2 问的答案。这是 SPA 里的高频 bug：

```ts
// ❌ 一个字之差，用户体验天差地别
if (status === 401 || status === 403) redirectToLogin()
```

后果：

```
用户点了无权限的按钮 → 403 → 跳登录页 → 重新登录 → 还是 403 → 又跳登录 → ...
```

用户会以为账号坏了、密码错了、系统崩了——**而真实原因只是「他确实没这个权限」**。

401 = **「我不知道你是谁」** → 需要重新认证
403 = **「我知道你是谁，但你不能做这个」** → 认证没问题，重新登录毫无意义

### 2. 401 要静默，403 要出声

| | 提示 | 理由 |
| --- | --- | --- |
| 401 | **不提示** | 用户马上会看到登录页，再弹一个「请求失败」是噪音 |
| 403 | **提示** | 页面不会变，不提示的话用户不知道发生了什么 |

尤其是会话过期时，页面上可能有多个请求同时 401，
每个都弹一个红色 toast——用户看到一片红色然后被跳走。

### 3. 401 并发去重

第一节第 4 问。5 个请求同时 401 → `navigate()` 被调 5 次 →
URL 变成 `/login?redirect=/login?redirect=/login...`

```ts
let redirecting = false
if (status === 401 && !redirecting) {
  redirecting = true
  ...
}
```

`fe-v0.3.0` 已经做了，本 tag 把它整理进统一的 `errorHandlers`。

### 4. 404 交给调用方，不要全局统一处理

第一节第 3 问。404 的正确处理**取决于场景**：

| 场景 | 处理 |
| --- | --- |
| 详情页加载失败 | **整页替换**成 `ResourceNotFound` |
| 列表页某个操作 404 | 提示 + 刷新列表（那条可能刚被删） |
| 后台静默请求 404 | 可能什么都不用做 |

全局拦截器统一弹 toast 的话，详情页会停在空白上还弹个提示。

**做法**：拦截器**不处理** 404，原样抛出，由 `useQuery` 的调用方判断
（`fe-v0.11.0` 已经这么做了）。

### 5. 5xx 用错误边界，不用 toast

第一节第 5 问。500 意味着「服务端炸了」，页面上的数据可能是半截的。
弹个 toast 然后让用户继续在坏掉的界面上操作，比整页替换更糟。

```tsx
<AppErrorBoundary fallback={<ErrorResult onRetry={...} />}>
```

⚠️ React 的 Error Boundary **只捕获渲染期错误**，
捕获不了 `async` 回调里的异常。所以还需要
`QueryClient` 的全局 `onError` 配合。

### 6. 网络错误和业务错误要分开

```ts
if (!error.response) {
  // 没有 response = 请求根本没到服务器
  message.error('网络连接失败，请检查网络后重试')
  return
}
```

把网络错误显示成「服务器错误」会误导用户去联系 IT，
而真实原因可能只是他的 WiFi 断了。

### 7. 后端的 `detail` 字段要用起来

DRF 的错误响应是 `{"detail": "..."}`。后端已经写了人话文案
（「用户名或密码错误」「登录失败次数过多，请 15 分钟后再试」），
前端硬编码一套自己的文案是浪费，而且两边会漂移。

```ts
const detail = error.response?.data?.detail
message.error(detail ?? '操作失败')     // 优先用后端的
```

### 8. 📌 拦截器里一定要继续 `reject`

```ts
// ❌ 处理完就吞掉
handleApiError(error)
return Promise.resolve({ data: undefined })
```

调用方拿到的是「成功但 data 是 undefined」——错误被吞掉，页面显示空白，
而且 Query 认为请求成功了，**不会进 error 分支**，
`fe-v0.11.0` 那套「404 整页替换」全部失效。

拦截器的职责是**加处理**，不是**替调用方决定**。

### 9. 📌 兜底组件的依赖必须比它兜的东西更少

`AppErrorBoundary` 的 fallback 一开始我想直接复用 `ErrorResult`——
但那个组件用了 `useNavigate`，而错误边界挂在 `BrowserRouter` **外面**
（错误可能就发生在路由初始化时）。

在路由上下文之外调 `useNavigate` 会**再抛一个错误**，
于是错误边界的 fallback 自己也炸了，用户看到彻底的白屏。

所以单独写了一个 `BootErrorFallback`，只用 `window.location`。

> **兜底组件的依赖必须比它兜的东西更少**，否则它兜不住自己。

### 10. 📌 重试策略：读可以重试，写绝对不行

`TanStack Query` 默认 `retry: 3`。在权限系统里这有两个问题：

- **4xx 重试毫无意义**：403 重试三次仍然是 403，只是让用户多等两秒；
  而且会把「一次越权尝试」放大成审计日志里的**四条** `perm_denied`。
- **写请求重试有副作用**：网络超时不代表服务端没收到，
  重试可能创建出两张工单。

```ts
queries:   { retry: (n, err) => (is4xx(err) ? false : n < 1) }
mutations: { retry: false }        // 🔴 写请求绝不自动重试
```

## 六、卡住了看这里（渐进提示）

<details>
<summary><b>提示：统一拦截器</b></summary>

```ts
client.interceptors.response.use(
  (response) => {
    watchRbacVersion(response)          // fe-v0.13.0
    return response
  },
  (error: AxiosError<{ detail?: string }>) => {
    // 网络错误：没有 response
    if (!error.response) {
      message.error('网络连接失败，请检查网络后重试')
      return Promise.reject(error)
    }

    const { status, data } = error.response
    const detail = data?.detail

    switch (status) {
      case 401:
        // ⚠️ 静默 —— 用户马上会看到登录页，再弹提示是噪音
        redirectToLoginOnce()
        break

      case 403:
        // 🔴 绝不跳登录页！重新登录解决不了「没权限」
        message.warning(detail ?? '权限不足')
        // 兜底：可能是权限刚被撤销（fe-v0.13.0）
        queryClient.invalidateQueries({ queryKey: ['profile'] })
        break

      case 404:
        // 不处理 —— 交给调用方，因为处理方式取决于场景
        break

      case 429:
        message.warning(detail ?? '操作过于频繁，请稍后再试')
        break

      default:
        if (status >= 500) message.error('服务器开小差了，请稍后重试')
        // 4xx 其余（如 400）交给调用方映射到表单
    }

    return Promise.reject(error)
  },
)
```
</details>

## 七、自测清单

| # | 用例 | 期望 |
| --- | --- | --- |
| 1 | 手工删掉 `sessionid` cookie 后操作 | 跳登录页，**没有红色报错** |
| 2 | 🔴 `cs_staff` 用控制台调删除接口 | 提示「权限不足」，**留在当前页** |
| 3 | 承上，会跳登录页吗 | **绝对不会** |
| 4 | 5 个并发请求同时 401 | 只跳一次，URL 不嵌套 |
| 5 | 访问不存在的工单详情 | 整页「不存在或你无权访问」，**不弹 toast** |
| 6 | 登录时密码错（400） | 表单上显示错误，不弹全局 toast |
| 7 | 连错 5 次（429） | 显示后端的「请 15 分钟后再试」 |
| 8 | 模拟 500 | 错误边界页 + 重试 |
| 9 | 断网后操作 | 「网络连接失败」，不是「服务器错误」 |
| 10 | 收到 403 后 | profile 被重拉（Network 面板确认） |
| 11 | 后端全量测试 | 全绿 |

**用例 2 + 3 是本 tag 的核心。**

📌 **写这些 E2E 时踩的两个坑**（都不是产品代码的问题）：

1. **同文件内的状态污染**。第一条用例撤销了 `cs_manager` 的查看权限，
   同文件后面的用例就拿不到列表数据，分页按钮根本不渲染——
   报错是「点不到元素」，指不到真正原因。
   `fe-v0.12.0` 遇到的是**跨文件**的同一个问题。
   > **共享可变状态的污染范围，取决于你在哪一层重置，不取决于你的意图。**

2. **清 cookie 的时机**。模拟会话过期要先等页面渲染完再清，
   清早了首屏请求就 401，页面直接跳走，后续操作全部找不到元素。

## 九、延伸思考

1. **401 vs 403 的语义**：HTTP 规范里 401 叫 "Unauthorized"，403 叫 "Forbidden"。
   **401 的名字其实是错的**——它表达的是「未认证」（Unauthenticated）。
   这个历史遗留的命名让多少人写错过拦截器？

2. 我们让 404 由调用方处理。**这算不算「把复杂度推给了调用方」？**
   有没有办法既统一又灵活？（提示：拦截器可以给 error 打个标记，
   由调用方决定用不用。）

3. **重试策略**：网络错误时要不要自动重试？
   TanStack Query 默认重试 3 次——这对**写请求**是危险的
   （可能重复创建工单）。检查一下你的 mutation 配置。

4. 后端返回 404 是为了不泄露记录存在性（`ADR-009`）。
   但**前端的 Network 面板里能看到状态码**。
   这算不算泄露？（提示：攻击者本来就能看到——关键在于 404 和 403
   的差异不能用来区分「存在但无权」和「不存在」。）

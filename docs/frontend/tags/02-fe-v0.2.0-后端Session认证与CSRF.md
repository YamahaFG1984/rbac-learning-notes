## 三、接口契约（必须与我的实现对齐）

### settings

```python
REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": [
        # SPA 走这个：同域 + httpOnly Cookie + CSRF（F-ADR-003）
        "rest_framework.authentication.SessionAuthentication",
        # 移动端 / 第三方 / 脚本走这个
        "rest_framework_simplejwt.authentication.JWTAuthentication",
    ],
    ...
}
```

### 三个接口

```
GET  /api/v1/auth/csrf/      种下 csrftoken cookie，返回 {"detail": "ok"}
POST /api/v1/auth/login/     {username, password} → 200 + 种 sessionid
POST /api/v1/auth/logout/    → 204，清除 session
```

`login` 的响应体直接复用 profile 的结构（省掉一次往返）：

```json
{ "user": {...}, "perms": [...], "menus": [...] }
```

### 失败响应

| 情形 | 状态码 | body |
| --- | --- | --- |
| 用户名或密码错 | 400 | `{"detail": "用户名或密码错误"}` |
| 账号被锁定 | 429 | `{"detail": "登录失败次数过多，请 15 分钟后再试"}` |
| 未认证访问受保护接口 | 401 | `{"detail": "..."}` |
| CSRF 校验失败 | 403 | Django 默认 |

⚠️ 登录失败用 **400** 而不是 401——401 的语义是「需要认证」，
会触发前端拦截器的「跳登录页」逻辑，而用户**已经在登录页了**（F-ADR-011）。

## 五、⚠️ 容易写错的地方

### 🔴 1. 为什么是 Session 而不是「JWT 装进 Cookie」

第一节第 1~3 问的答案。

JWT 的卖点是无状态。但我们在 `v1.1.0` 已经实测并写成了测试：

```python
def test_disabled_user_token_is_rejected(...):
    """simplejwt 每次请求都会查库取 user 并检查 is_active，
    所以禁用用户其实会被挡住——代价是牺牲了「无状态」。"""
```

**无状态早就打了折**，而它的代价（不可撤销）却是实打实的。

更要命的是第 3 问：`v0.16.0` 花了一整个 tag 保证「权限撤销后最迟下一次请求生效」，
如果认证层却给出一个撤不掉的凭证，**整个系统的安全承诺是自相矛盾的**。

Session 白送三样东西：

| | 说明 |
| --- | --- |
| 立即可撤销 | 删 session 记录，下一次请求就失效 |
| CSRF 现成 | Django 中间件已经在跑，`v0.18.0` 还配了测试 |
| 禁用用户立即失效 | `ModelBackend.get_user()` 的 `is_active` 检查 |

> **一个应用可以有多种认证方式，但只能有一套授权逻辑。**
> `HasPerm` 不关心你怎么认证的，它只问 `request.user` 是谁——
> 所以两条通道可以并存，而 `services.py` 一行都不用改。

### 🔴 2. `CSRF_COOKIE_HTTPONLY = True` 必须改回 `False`

第一节第 5 问。这是我在 `v0.18.0` 埋的一个雷。

Django 的 CSRF 是 double-submit：cookie 一份，请求头一份，服务端比对。
模板渲染时 `{% csrf_token %}` 由服务端注入，前端不用读 cookie。
**SPA 没有服务端渲染的表单，只能自己从 cookie 里读 `csrftoken`。**

`httpOnly` 让 JS 读不到 → SPA 的所有写请求全部 403。

**改回 `False` 不是降低安全**——Django 官方文档明确说明它**不提供任何实质防护**：

- CSRF token 本来就不是秘密，它只需要「攻击者的站点读不到」，
  而**同源策略已经保证了这一点**
- httpOnly 防的是「XSS 偷走凭证」；但 CSRF token 被 XSS 拿到也没用——
  XSS 已经在同源里，它可以直接发请求

**真正需要保护的 `sessionid` 仍然是 httpOnly。**

在 `prod.py` 里写长注释，并加一条测试断言它是 `False` 且说明理由——
否则后来者会以为这是安全倒退，又给改回去。

> **教训**：`v0.18.0` 那行是「照着安全清单抄」的产物，我没想清楚它防的到底是什么。
> **抄来的安全措施，和抄来的架构一样危险。**

### 3. DRF 的 `SessionAuthentication` 会强制 CSRF 检查

这是 DRF 的刻意设计（`SessionAuthentication.enforce_csrf`）。

所以前端**必须**先 `GET /auth/csrf/` 拿到 cookie，之后每个写请求带 `X-CSRFToken` 头。

⚠️ 一个容易混淆的点：**登录接口本身也需要 CSRF token**。
所以顺序是 `GET /csrf/` → `POST /login/`，不能反过来。

### 4. 登录失败返回 400 不是 401

见契约表。401 会触发前端的「跳登录页」，而用户已经在登录页——
表现是页面莫名其妙刷新一下，错误提示都看不见。

### 5. 复用已有的失败锁定与审计，不要重写

`v0.7.0` 已经有 `record_login_failure` / `is_locked_out` / 审计日志。
API 版登录必须复用它们，否则出现「Web 登录被锁了，API 登录还能试」的漏洞。

**测试要专门验证这一点**：Web 侧失败 5 次后，API 登录也被锁。

### 6. `login()` 之后要 `rotate_csrf_token()`

Django 的 `login()` 会 cycle session key（防会话固定），
但 CSRF token 需要单独轮换：

```python
from django.middleware.csrf import rotate_token
login(request, user)
rotate_token(request)      # 登录后换一个新的 CSRF token
```

不换的话，登录前拿到的 token 在登录后仍然有效——这是一个（较弱的）会话固定变体。

<summary><b>提示 1：三个接口</b></summary>

```python
"""API 认证（F-ADR-003）。

SPA 走 Session（httpOnly Cookie + CSRF），第三方走 Bearer JWT。
登录的业务规则（失败锁定、审计）全部复用 v0.7.0 的实现，不重写。
"""

from django.contrib.auth import authenticate, login, logout
from django.middleware.csrf import get_token, rotate_token
from django.views.decorators.csrf import ensure_csrf_cookie
from rest_framework import status
from rest_framework.decorators import (
    api_view, authentication_classes, permission_classes,
)
from rest_framework.permissions import AllowAny, IsAuthenticated
from rest_framework.response import Response

from apps.accounts.auth_views import (
    LOGIN_FAILED_MESSAGE, LOGIN_LOCKED_MESSAGE,
    clear_login_failure, get_client_ip, is_locked_out, record_login_failure,
)


@api_view(["GET"])
@permission_classes([AllowAny])
@ensure_csrf_cookie
def csrf(request):
    """种下 csrftoken cookie。SPA 启动时先调它。"""
    return Response({"detail": "ok", "csrfToken": get_token(request)})


@api_view(["POST"])
@permission_classes([AllowAny])
def login_view(request):
    username = request.data.get("username", "")
    password = request.data.get("password", "")

    if is_locked_out(username):
        return Response(
            {"detail": LOGIN_LOCKED_MESSAGE.format(minutes=15)},
            status=status.HTTP_429_TOO_MANY_REQUESTS,
        )

    user = authenticate(request, username=username, password=password)
    if user is None:
        record_login_failure(username)
        audit_log(...)                      # 复用 v0.17.0
        # ⚠️ 400 而不是 401：401 会触发前端跳登录页，而用户已经在登录页
        return Response({"detail": LOGIN_FAILED_MESSAGE},
                        status=status.HTTP_400_BAD_REQUEST)

    clear_login_failure(username)
    login(request, user)        # 内部 cycle_key，防会话固定
    rotate_token(request)       # CSRF token 也要换
    audit_log(...)
    return Response(build_profile(user))    # 复用 profile 的结构，省一次往返


@api_view(["POST"])
@permission_classes([IsAuthenticated])
def logout_view(request):
    audit_log(...)
    logout(request)
    return Response(status=status.HTTP_204_NO_CONTENT)
```

## 九、延伸思考

1. **DRF 的 `SessionAuthentication` 为什么强制 CSRF 检查，而 `JWTAuthentication` 不用？**
   （提示：CSRF 攻击的前提是「浏览器会自动带上凭证」。哪种凭证会被自动带上？）

2. **多标签页登出**：用户在标签页 A 登出，标签页 B 还停在业务页面。
   B 的下一次请求会 401——但 B 的界面在此之前一直显示着数据。
   查一下 `BroadcastChannel` API，想想怎么做跨标签页同步。

3. **Session 存哪**：默认存数据库，且我们 `v0.7.0` 开了 `SESSION_SAVE_EVERY_REQUEST`
   （滑动过期），意味着每个请求一次 UPDATE。
   我们在 `v0.9.0` 的查询数测试里实测到了这 3 次额外查询。
   换成 Redis 会怎样？改一行配置试试，再跑一遍那个测试。

4. **如果既要 Session 又要支持移动 App**，两种会话的语义不同
   （一个可撤销一个不可）。运维上会带来什么问题？
   （提示：「强制下线某个用户」这个功能，对两种通道分别要怎么做？）

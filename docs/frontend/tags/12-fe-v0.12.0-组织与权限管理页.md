## 五、⚠️ 容易写错的地方

### 🔴 1. 继承权限的只读态，和后端 `v0.12.0` 是同一个坑

第一节第 1、2 问。

后端的处理（`v0.12.0` 陷阱）：

> `disabled` 的 checkbox **不会被提交**。如果一个权限既是直接授予又是继承来的，
> 一律禁用会导致保存时把**直接授权静默删掉**。
> 所以只对「纯继承、非直接授予」的项禁用。

AntD 的 `Tree` 有完全一样的问题——`disabled` 节点不进 `checkedKeys` 的提交值。

```tsx
// 后端返回的每个节点带两个标记
interface PermNode {
  checked: boolean      // 直接授予
  inherited: boolean    // 纯继承（后端已经算好「非直接授予」）
}

// 只禁用纯继承的
disabled: node.inherited
// 勾选状态 = 直接授予 或 继承
checked: node.checked || node.inherited
```

⚠️ **`inherited` 的语义必须和后端一致**——后端算的是「继承来的**且不是**直接授予的」。
前端如果自己算 `inherited = 在父角色权限里`，就会踩回那个坑。

**这是 F-ADR-006「组件禁止自行推断权限」的又一个实例。**

### 2. 父子联动会把 disabled 节点也带上

AntD `Tree` 的 `checkStrictly={false}`（默认）会做父子联动，
勾父节点时**子节点即使 disabled 也可能被计入**（版本行为有差异）。

保险做法：`checkStrictly={true}` 自己控制联动，或者提交前显式过滤掉 disabled 的 key。

**建议**：`checkStrictly={true}` + 手写联动。看起来麻烦，
但你能完全掌控「哪些 key 会被提交」——这在权限场景值得。

### 3. 数据范围的部门勾选：只提交勾选的，不提交子树

后端 `get_role_custom_dept_ids()` 会自动展开子树（`v0.15.0`）。
前端**只提交用户勾了哪几个部门**，不要自己展开。

```tsx
// ❌ 前端展开子树后提交 —— 后端会再展开一次，且新增子部门后不会自动包含
// ✅ 只提交勾选的节点
```

界面上要写明「勾选的部门**包含其所有下级**」，否则管理员会困惑。

### 4. 树形组件的性能

部门/权限树节点不多（几十个），不需要虚拟滚动。
**别提前优化**——先把逻辑做对。

### 5. 审计日志的 `detail` 展示

后端记录了 `{before, after, added, removed}`（`v0.17.0`）。
直接 `JSON.stringify` 出来没人看得懂。

```tsx
// 至少要把 added / removed 高亮出来
<Tag color="green">+ ticket:ticket:delete</Tag>
<Tag color="red">- ticket:ticket:export</Tag>
```

**审计日志要能回答「当时到底发生了什么」**（后端 `v0.17.0` 的原话），
展示层不做处理的话，这个价值就打折了。

### 6. 用户管理页不要出现 `is_superuser`

后端 `v0.18.0` 的表单白名单已经挡住了提交，
但前端表单里**根本就不该有这个字段**——同 `fe-v0.11.0` 陷阱 2 的道理。

## 五bis、实现时才撞上的四件事

### 🔴 A. `inherited` 必须由后端算，而且要两个前端共用

第五节第 1 条说了「前端不能自己算」，但还差一步：
**模板版和 SPA 也不能各算一遍**。

所以本 tag 把 `checked` / `inherited` 的计算抽到了
`apps/rbac/perm_tree.py::annotate_role_perm_rows()`，两边共用。

⚠️ 它刻意**不放进** `services.py` ——那里是权限内核（ADR-013），
算「一棵给人勾选的树长什么样」是表现层的关注点，
只是恰好被两个表现层共用。验收条件仍然是
`git diff main HEAD -- apps/rbac/services.py` 为空。

### 🔴 B. 树形接口不能分页（我踩了）

前端一开始写的是 `?page_size=500`。但 DRF **没有配** `page_size_query_param`，
这个参数被**静默忽略**——权限点页只显示了 26 个里的 20 个，不报错、不警告。

> 「传了一个不被识别的参数」是最难发现的一类错误：**它长得像生效了。**

正确的做法不是去配 `page_size_query_param`，而是**这两个接口根本不该分页**：

> 客户端拿第 1 页的 20 个节点去建树，第 21 个节点的父节点如果在第 2 页，
> 整条分支就悄无声息地消失了。
>
> 分页解决的是「数据太多」，树形结构的正确性要求「一次拿全」。
> 两者冲突时先保证正确。

`DepartmentViewSet` / `PermissionViewSet` 都设了 `pagination_class = None`，
并有一条测试造 30 个部门（超过 `PAGE_SIZE=20`）来守它。

### 🔴 C. 数据范围变更之前**完全没有审计**

`AuditAction.ROLE_SCOPE_SET` 这个枚举值定义了，却**没有任何地方发出它**。
也就是说「把一个角色从『仅本人』改成『全部数据』」不留任何痕迹——
而这是影响最大的权限变更之一，FR-9.2 是 P0。

> **「需求写了但没落地」最难发现的形态就是这种**：
> 不报错、不缺功能，只是那条日志永远不会出现。

补法：`apps/rbac/scope_config.py::save_role_scope()` 负责保存 **并发出信号**，
两个前端共用它。各写一遍的话很可能只有一边记了日志，
而缺失的那一边正好是会被利用的那一边。

📌 顺手加的结构性测试
（`tests/audit/test_audit.py::test_every_audit_action_has_an_emitter`）
扫出**还有 6 个**同样的缺口：
`ROLE_CREATE / ROLE_UPDATE / ROLE_DELETE / USER_CREATE / USER_UPDATE / USER_DELETE`。

它们被记在一个 `KNOWN_GAPS` 清单里——**这个清单只能变短不能变长**，
新增枚举值忘了发出点，测试会立刻红。
把已知缺口写成会跑的断言，比写在 TODO 里靠谱得多。

### 🔴 D. E2E 突然「不稳定」——三个原因叠在一起

全量跑 48 条 E2E 时开始随机红，每次红的还不一样。
很容易归因成「E2E 就是不稳定」然后加 retry 盖掉——
**那等于把三个真实问题变成噪音**。逐一拆开是：

| # | 症状 | 真正的原因 |
| --- | --- | --- |
| 1 | 断言 `共 80 条` 偶尔失败 | `ticket-crud.spec.ts` 会新建/删除工单，按文件名它跑在 `ticket-list` **前面**，把基线改了 |
| 2 | 随机超时、耗时 9.6 分钟 | 机器只有 2 核 1.9G，Vite **dev server** 每个请求现场转译模块，内存被吃光后开始换页 |
| 3 | `cs_manager` 登录后菜单全空、页面 403 | `seed_demo` 和 `runserver` 是**两个进程**，各有一份 LocMemCache——管理命令里的 `bump_version()` 服务端根本看不到 |

三个修法：

1. 给需要确定基线的用例显式重置数据（`e2e/reseed.ts`）。
   ⚠️ **不要**为了让测试变绿而把断言改成相对的——
   「前端条数 == 后端数据权限矩阵」正是那条用例存在的理由。
2. E2E 跑 `vite preview`（生产构建）而不是 dev server。
   顺带的好处：测的就是用户实际拿到的那份代码。
   ⚠️ `preview.proxy` 是**独立的一份配置**，不继承 `server.proxy`。
3. 开发环境改用 `FileBasedCache`（跨进程共享），和生产的 Redis 行为一致。
   **一个只在开发环境出现的诡异行为，会把人引向完全错误的排查方向**——
   第 3 条的症状看起来完全像「权限逻辑坏了」。

改完：48/48 全绿，1.7 分钟。

## 九、延伸思考

1. 用例 5 这个坑在后端和前端各出现了一次，**根因是同一个**：
   「disabled 的表单控件不会被提交」。
   还有哪些 HTML 控件有类似的「看起来在那儿但不提交」的行为？

2. 权限树的父子联动我们建议 `checkStrictly={true}` 自己控制。
   **这和后端模板版用原生 JS 手写联动是同一个选择**（`v0.5.0`）。
   为什么在权限场景值得多写这些代码？

3. 这四个页面的 CRUD 模式高度重复。**要不要抽一个通用的 CRUD 组件？**
   想想什么时候该抽（提示：现在是第 4 个，YAGNI 的边界在哪？
   回看后端 `ADR-016` 的「抽象的成本是即时的，收益是推测的」）。

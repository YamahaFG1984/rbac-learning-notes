## 五、⚠️ 容易写错的地方

### 🎯 1. 本 tag 最重要的一条测试

第一节第 1、2 问的答案：**安全价值为零**，用这条证明：

```ts
test('前端权限判断全部可绕过，但后端拦得住', async ({ page }) => {
  await loginAs(page, 'cs_staff')          // 只有 5 条工单、无删除权限

  // 1. 前端确实隐藏了
  await page.goto('/tickets')
  await expect(page.getByRole('button', { name: '删除' })).toHaveCount(0)

  // 2. 把前端的权限判断整个改掉
  await page.evaluate(() => {
    // @ts-expect-error 直接篡改 store
    window.__ZUSTAND_AUTH__.setState({ perms: ['*'] })
  })
  await expect(page.getByRole('button', { name: '删除' })).toBeVisible()   // 按钮出现了

  // 3. 但真的点下去 —— 后端拒绝
  const [res] = await Promise.all([
    page.waitForResponse((r) => r.request().method() === 'DELETE'),
    page.getByRole('button', { name: '删除' }).first().click(),
  ])
  expect(res.status()).toBe(403)

  // 4. 甚至不用前端：直接发请求
  const direct = await page.request.delete('/api/v1/tickets/1/')
  expect(direct.status()).toBe(403)
})
```

四步依次证明：**隐藏了 → 可以改回来 → 改回来也没用 → 连前端都不用**。

⚠️ 为了让测试能篡改 store，需要在**开发/测试构建**里把 store 挂到 window 上。
生产构建不要挂——虽然挂了也不构成漏洞（攻击者有 devtools），但没必要。

### 🔴 2. 「直调 API」这一行必须独立成立

矩阵最后两行**不能**依赖前端的任何状态：

```ts
// ✅ 用 Playwright 的 request context，完全绕过页面
const res = await page.request.delete('/api/v1/tickets/42/')

// ❌ 通过点击按钮触发 —— 那还是在测前端
```

这两行的期望值和「删除按钮」那一行**逻辑一致但独立成立**——
如果哪天前端改错了，这两行仍然是绿的；
如果后端改错了，它们会立刻变红。

### 3. `document.cookie` 只能在真浏览器里测

第一节第 3 问。jsdom 不实现 httpOnly 语义，
在单测里 `document.cookie` 的断言是**假绿**。

```ts
test('会话凭证对 JS 不可见（F-ADR-002 的验收）', async ({ page }) => {
  await loginAs(page, 'cs_manager')

  const jsVisible = await page.evaluate(() => document.cookie)
  expect(jsVisible).not.toContain('sessionid')
  expect(jsVisible).toContain('csrftoken')       // 这个必须可读，见 F-ADR-004

  // 但浏览器确实持有它
  const cookies = await page.context().cookies()
  const session = cookies.find((c) => c.name === 'sessionid')
  expect(session?.httpOnly).toBe(true)
})
```

### 4. E2E 不是重复劳动

第一节第 4 问。后端矩阵测的是「API 的行为」，
E2E 测的是**「用户实际看到什么」**——两者可能不一致：

| 后端对 | 前端错 | 表现 |
| --- | --- | --- |
| API 返回 50 条 | 前端多过滤一次 | 用户看到 40 条 |
| API 403 | 前端跳登录页 | 死循环 |
| 菜单接口正确 | 前端渲染逻辑错 | 菜单少一项 |

**E2E 测的是这个「之间」。**

### 5. 登录态复用，不要每个测试都走一遍登录

```ts
// 一次登录，存 storageState，后续测试直接复用
setup('authenticate as cs_manager', async ({ page }) => {
  await login(page, 'cs_manager', 'demo1234')
  await page.context().storageState({ path: '.auth/cs_manager.json' })
})
```

5 个角色 × 20 个测试 = 100 次登录，每次几百毫秒——省下来的时间很可观。

### 6. 数据要可重复

E2E 会删工单。跑第二遍时数字就对不上了。

```bash
python manage.py seed_demo --flush --noinput      # 每次 E2E 前重置
```

**注意**：`--flush` 不清审计日志（后端 `v1.0.0` 的刻意设计），
所以审计日志的断言要用「至少有」而不是「恰好有」。

### 7. 别在 E2E 里测细节

E2E 慢且脆。表单校验文案、按钮颜色、loading 态这些交给单测。

E2E 只测**跨层的、单测测不了的**：越权、cookie、路由时序。

### 🔴 8. 📌 我在这个 tag 里又踩了一次「403 来自错误的原因」

`page.request.delete()` **不带 CSRF token**，Django 一律返回 403。
于是矩阵里的直调那一段出现了两种问题：

| 行 | 期望 | 实际 | 后果 |
| --- | --- | --- | --- |
| `sysadmin` / `cs_staff` | 403 | 403 | **通过了，但是因为 CSRF 而不是权限** |
| `superadmin` / `cs_manager` | 204 | 403 | 失败，报错指向权限，真实原因是 CSRF |

前两行才是真正危险的：它们**绿着**，而且什么都没证明。

这条规则我自己在 `fe-v0.9.0` 写过：

> 一个鉴权测试如果因为请求根本没到达权限判断那一步而通过，
> 它是**假绿**——比没有测试更糟，因为它给人安全感。

写下来和不再犯是两件事。修法是给直调请求补上 `X-CSRFToken`，
让它真的走到权限判断那一步；
「无 CSRF 的写请求被拒」是**另一件事**，单独一条测试。

> **一条测试只测一件事**，否则你分不清它到底在测什么。

### 9. 📌 把 store 挂到 window 上，算不算为了测试降低安全

第九节第 3 题的答案：**不算。**

攻击者本来就能做到同样的事，而且不需要这个变量——
React DevTools 能直接改组件状态，devtools 里能改任何 JS 内存，
最省事的是他连前端都不用，直接 curl 你的 API。
挂上去只是让**测试**能表达这件事，没有创造任何新的攻击面。

生产构建仍然不挂，理由不是安全，是**没必要**：
一个只有测试用的全局变量留在生产包里，下一个人看到会去猜它是干什么的。

实现上用 `--mode e2e` + `.env.e2e`：

```
生产构建   __AUTH_STORE__ 出现 0 次
e2e 构建   __AUTH_STORE__ 出现 1 次
```

### 10. 📌 一次没能复现的 403

第一次跑 `bypass.spec.ts` 时，`cs_manager` 的一个 GET 拿到了 403，
之后连跑四遍都是绿的。

最可能的解释：`reseedDatabase`（独立进程）和 Django 服务进程
在 `FileBasedCache` 上竞争——**`cache.incr` 在文件缓存后端上不是原子的**，
两个进程同时改版本号可能丢更新，服务端于是短暂地用了一份陈旧的权限缓存。
生产用 Redis，`INCR` 在那里是原子的。

我没有把它坐实，**所以这里如实记下来而不是当作偶然**。
如果它再次出现，第一个要查的就是这一点。

## 七、自测清单

| # | 用例 | 期望 |
| --- | --- | --- |
| 1 | 功能权限矩阵 5 角色 × 若干页面 | 全绿 |
| 2 | 数据范围矩阵 4 角色 | 数字与后端一致（80/80/50/5） |
| 3 | 跨部门工单 | 404 页面 |
| 4 | 🎯 **篡改 store 后按钮出现** | 出现（前端确实挡不住） |
| 5 | 🎯 **承上点击** | **403** |
| 6 | 🎯 **直接 `page.request.delete`** | **403** |
| 7 | `document.cookie` | 无 `sessionid`，有 `csrftoken` |
| 8 | `sessionid` 的 `httpOnly` 标志 | `true` |
| 9 | 在 `/tickets/42` 刷新 | 正常渲染，不 404 |
| 10 | 未登录访问 `/tickets/42` | 登录后回到该页 |
| 11 | 权限变更感知 | 撤权后翻页，按钮消失 |
| 12 | 无 CSRF token 的写请求 | 403 |
| 13 | 后端全量测试 | 全绿 |

用例 4~6 是本 tag 存在的理由。

📌 **第九节第 1 题的答案**（如果新同事问「那我们为什么还要做前端权限」）：

> 前端权限的价值是**体验**，不是安全。它让用户不去点一个必然失败的东西，
> 让界面只呈现他用得上的部分。
>
> 这份价值是真实的——一个满屏都是点了就报错的按钮的系统很难用。
> 但它**一分钱的安全价值都没有**，
> 而把它误当成安全边界的那一刻，就是漏洞诞生的时刻。
>
> 用一句话说：**前端权限是给用户的，后端权限是给攻击者的。**

## 八、和我的实现对比什么

| 对比点 | 想一想 |
| --- | --- |
| 🎯 **有没有「绕过前端」的测试** | 没有的话，前面三层体验的安全价值就只是口头声明 |
| **直调 API 是用 request context 还是点按钮** | 点按钮的话，测的还是前端 |

| **登录态复用了吗** | 没复用的话，E2E 要跑多久？ |
| **每次跑前重置数据了吗** | 没重置的话，第二遍就红 |
| **在 E2E 里测表单校验了吗** | 测了的话，那些应该在 `fe-v0.15.0` |

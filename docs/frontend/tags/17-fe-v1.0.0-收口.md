## 三、⚠️ 收口时最该检查的一件事

**`FAC-4` 有没有真的守住？**

`fe-v0.5.0` 是最容易失守的地方——当时要给菜单加 `route_path` / `component`，
最省事的做法是直接改 `get_user_menu_tree()`。我们选了在 API 层转换。

现在回头看：

```bash
git diff main HEAD --stat -- apps/
```

改动应该只落在：`config/`、`apps/rbac/api/`、`apps/rbac/models.py`（两个字段）、
`apps/common/middleware.py`。

**如果 `apps/rbac/services.py` 出现在列表里，本阶段的架构承诺就没兑现。**
那不是小瑕疵——它意味着「内核不认识表现层」这条约束，
在遇到第三种表现层时就破了。

## 四、阶段回顾

### 做完之后，重新评估几条 F-ADR

📌 **下面是我实现完之后的回答。**你自己实现过一遍再来对照，
分歧的地方比一致的地方有价值。

| F-ADR | 事后评价 |
| --- | --- |
| **002** httpOnly Cookie | ✅ 站得住。同域限制**没有**带来麻烦，因为一开始就把 Vite proxy 和 Nginx 配成同一件事。唯一的代价是 `changeOrigin` 那个坑——踩了一次，且报错完全指不到原因 |
| **003** Session 而非 JWT | ✅ 收益比预想的大。前端状态机只有三态（`unknown`/`authenticated`/`anonymous`），没有「token 快过期了」「正在刷新」「刷新失败要重登」这一整套。**省下的不是代码量，是状态组合数** |
| **004** `CSRF_COOKIE_HTTPONLY=False` | ✅ 认同。SPA 必须从 cookie 里读 token，设成 `True` 会让**所有写请求 403**。而 CSRF token 本来就不是秘密——`fe-v0.16.0` 那条「XSS 偷不到会话但仍能发请求」的测试正好说明：httpOnly 防的是凭证异地复用，不防同源内的操作 |
| **005** Query + Zustand | ⚠️ 边界基本清晰，但有过一次真实的混淆：`fe-v0.13.0` 里我以为 `await refetchQueries()` 之后 store 就更新了——**没有**，store 的写入走 `useEffect`。两套状态之间存在一个「异步已完成但派生状态未更新」的窗口，这是双状态方案的固有成本 |
| **007** 动态路由 | 时序 bug 踩了 **3 个**：刷新变 404（`AuthBootstrap` 层级）、`useMemo` 依赖导致 router 反复重建、403 与 404 分不清。全都不是权限逻辑的问题，全都是时序 |
| **008** 路由字段放后端 | ⚠️ **开始难受了。** `Permission` 表现在有 `icon` / `url_name` / `route_path` / `component` 四个展示层字段，而 `icon` 的大小写混乱已经暴露了「一份后端喂两套前端」的摩擦。再加第三个前端就该重构了 |
| **010** 版本号感知 | ✅ 延迟（一次 API 请求）完全可接受。误报靠「重拉后比对新旧 perms」解决了——**不比对的话，任何人改权限所有在线用户都会收到提示** |
| **014** 产物不入库 | ✅ 站得住。它和后端 ADR-015（Tailwind 产物入库）相反，理由也不同：后端产物是**一个 CSS 文件**，前端产物是**几十个带 hash 的 chunk**，入库会让每次 diff 里塞满二进制噪音，直接摧毁「跨 tag 读 diff」这个学习方式 |

### 三个交付形态的对比

到这里，同一个权限内核已经服务了三种表现层：

| | Django 模板 | DRF + JWT | React SPA |
| --- | --- | --- | --- |
| tag | `v1.0.0` | `v1.2.0` | `fe-v1.0.0` |
| 适配层代码量 | ~200 行 | **117 行** | ~700 行后端适配 + ~4000 行前端 |
| 内核改动 | — | **0** | **0** |
| 权限变更生效 | 刷新即生效 | 每次请求 | 一次请求 + 感知机制 |
| 鉴权层数 | 3 | 1（API） | **4**（+ 路由守卫） |
| 安全边界数 | **1** | **1** | **1** |

**最后一行才是重点**：无论前端做几层，安全边界永远只有一个。

📌 **实测数据**（`fe-v1.0.0` 收口时）：

| 项 | 数值 |
| --- | --- |
| 后端测试 | **417** 全绿（阶段开始时 365） |
| 前端单测 | **98**（12 个文件，含集成与结构性） |
| E2E | **92** 全绿（3.9 分钟） |
| 🔒 `git diff main HEAD -- apps/rbac/services.py` | **0 行** |
| 后端改动面 | `config/`、`apps/*/api/`、`apps/rbac/models.py`（2 个字段）、`apps/common/middleware.py`、几个共用模块 |

### 📌 这个阶段挖出的 4 个真实问题（都不在计划里）

它们的共同点是：**都不是「React 怎么写」的问题，而是接第二个前端时才暴露出来的。**

| # | 问题 | 为什么之前没发现 |
| --- | --- | --- |
| 1 | 派单下拉框列出**全部用户** | 权限矩阵测的是接口，而它藏在一个表单控件的默认行为里 |
| 2 | 改数据范围**完全没有审计** | 枚举值定义了却没人发出——不报错、不缺功能，只是那条日志永远不会出现 |
| 3 | `seed_demo --flush` 崩溃 | `Role.inherits_from` 是自引用 `PROTECT`，而删除路径是最少被走到的那条 |
| 4 | 树形接口分页导致**丢分支** | `?page_size=500` 被静默忽略——传了一个不被识别的参数，长得像生效了 |

> 接第二个前端的价值，一半在前端，另一半在**它逼着你重新看一遍后端**。

## 三、⚠️ 收口时最该检查的一件事

**`FAC-4` 有没有真的守住？**

`fe-v0.5.0` 是最容易失守的地方——当时要给菜单加 `route_path` / `component`，
最省事的做法是直接改 `get_user_menu_tree()`。我们选了在 API 层转换。

现在回头看：

```bash
git diff main HEAD --stat -- apps/
```

改动应该只落在：`config/`、`apps/rbac/api/`、`apps/rbac/models.py`（两个字段）、
`apps/common/middleware.py`。

**如果 `apps/rbac/services.py` 出现在列表里，本阶段的架构承诺就没兑现。**
那不是小瑕疵——它意味着「内核不认识表现层」这条约束，
在遇到第三种表现层时就破了。

## 四、阶段回顾

### 做完之后，重新评估几条 F-ADR

| F-ADR | 决策 | 实现完之后怎么看 |
| --- | --- | --- |
| 002 httpOnly Cookie | | 同域限制有没有真的带来麻烦？ |
| 003 Session 而非 JWT | | 少了「token 刷新态」，前端状态机简单了多少？ |
| 004 `CSRF_COOKIE_HTTPONLY=False` | | 这条「更正后端 v0.18.0」的决定，你认同吗？ |
| 005 Query + Zustand | | 边界真的清晰吗？有没有过混淆的时刻？ |
| 007 动态路由 | | 时序 bug 你踩了几个？ |
| 008 路由字段放后端 | | `Permission` 表现在有几个展示层字段？开始难受了吗？ |
| 010 版本号感知 | | 延迟可接受吗？误报多吗？ |
| 014 产物不入库 | | 和后端 ADR-015 相反的决定，理由站得住吗？ |

### 三个交付形态的对比

到这里，同一个权限内核已经服务了三种表现层：

| | Django 模板 | DRF + JWT | React SPA |
| --- | --- | --- | --- |
| tag | `v1.0.0` | `v1.2.0` | `fe-v1.0.0` |
| 适配层代码量 | ~200 行 | **117 行** | ~400 行（含前端） |
| 内核改动 | — | **0** | **0** |
| 权限变更生效 | 刷新即生效 | 每次请求 | 一次请求 + 感知机制 |
| 鉴权层数 | 3 | 1（API） | **4**（+ 路由守卫） |
| 安全边界数 | **1** | **1** | **1** |

**最后一行才是重点**：无论前端做几层，安全边界永远只有一个。

## 五、⚠️ 容易写错的地方

### 🔴 1. 绝不要在前端二次过滤

第一节第 2 问的答案：**绝对不要**（F-ADR-015）。

```tsx
// ❌ 看起来像「多一道保险」，实际是制造不一致的源头
const visible = data.results.filter((t) => canSee(t))
```

三个后果：

| 后果 | 说明 |
| --- | --- |
| 分页错乱 | 后端说 50 条，前端筛掉 10 条，分页器还显示 50 |
| 统计对不上 | 列表显示 40，导出 50 |
| **零安全价值** | 数据早就传到浏览器了，过滤发生在数据到达之后 = 没过滤 |

数据权限的唯一执行点是后端的 `.for_user()`（后端 `ADR-009`）。

**第一节第 3 问的答案**：前端**什么都不用做**。
`cs_staff` 看到 5 条、`cs_manager` 看到 50 条，是后端 `build_scope_q` 的结果，
前端只是把 `results` 渲染出来。

### 2. `queryKey` 必须包含全部查询参数

```ts
// ❌ 换页时 key 不变 → Query 认为是同一份数据 → 页面不刷新
useQuery({ queryKey: ['tickets'], queryFn: () => fetchTickets(params) })

// ✅
useQuery({ queryKey: ['tickets', params], queryFn: () => fetchTickets(params) })
```

漏了的表现很迷惑：**第一次换页有效（因为缓存空），之后就不动了。**

### 3. 分页参数属于哪种状态？

第一节第 1 问：

| 数据 | 归属 | 放哪 |
| --- | --- | --- |
| 工单列表本身 | 服务端 | TanStack Query |
| 当前页码、筛选条件 | **客户端**，但… | **URL search params** |

放 URL 而不是 `useState` 的理由：**刷新页面后筛选条件还在，链接可以分享**。
这是企业后台的基本预期。

### 4. `keepPreviousData` 让翻页不闪

不加的话，每次翻页表格会先变空再填充，视觉上很跳。

```ts
useQuery({ ..., placeholderData: keepPreviousData })
```

### 5. 列表的操作列要走 `<Can>`，但不要在 `columns` 里调 hook

```tsx
// ❌ hook 不能在数组里条件调用
const columns = [{ render: () => { const can = usePermission(); ... } }]

// ✅ 在组件顶层拿到 can，闭包捕获
const can = usePermission()
const columns = useMemo(() => [...], [can])
```

### 6. 导出走后端，不要前端拼 CSV

后端 `v0.15.0` 的导出**走同一个 `.for_user()`**。
前端自己拼 CSV 的话，导出的就是「当前页」而不是「全部有权限的数据」，
而且绕过了后端的 `EXPORT` 权限校验。

```tsx
// ✅ 直接开新窗口让浏览器下载（Cookie 会自动带上）
window.open('/api/v1/tickets/export/')
```

📌 **但这个接口本来不存在。** 模板版的导出在 `/django/tickets/export/`，
API 版没有。所以本 tag 有一块**后端工作**（仅适配层）：

| 新增 | 作用 |
| --- | --- |
| `apps/tickets/filters.py` | `apply_ticket_filters(qs, params)`，两个前端共用 |
| `apps/tickets/export.py` | `tickets_csv_response(qs)`，两个前端共用 |
| `TicketViewSet.filter_queryset` / `@action export` | API 侧接上去 |

**为什么一定要抽出来共用**：两个入口各写一份 CSV/筛选，
就有两个可能漂移的地方。表现会是「同一个用户在两个前端看到的条数不同，
而两边的数据权限其实都是对的」——这种 bug 极难定位。

守这条的测试直接断言两边**逐字节相同**：

```python
def test_two_frontends_export_identically(...):
    web = client.get(reverse("tickets:export")).content
    api = api_as("cs_manager").get("/api/v1/tickets/export/").content
    assert web == api
```

⚠️ `filter_queryset()` 里**只放业务筛选，不放权限过滤**。
权限过滤在 `get_queryset()`（`ScopedQuerysetMixin`），
DRF 的调用顺序保证了进到 `filter_queryset` 的东西已经 `.for_user()` 过。
两者混进同一个函数之后，任何人加一个业务筛选都可能顺手改坏权限过滤。

### 7. 📌 URL 参数的类型标注是一厢情愿的

`useTableQuery` 会把 URL 里的字符串按默认值的类型还原，标注成
`status: TicketStatus | ''`。但用户可以直接输 `?status=xyz`——
**TypeScript 管不到运行时的 URL**。

要不要在前端加一层校验？**不要。** 理由是：

> 无效的筛选值只会让后端筛出 0 条，**不可能筛出更多**。
> 筛选永远是收窄，不可能放宽。

后端有一条测试专门钉这个：

```python
def test_filter_cannot_widen_scope(self, world):
    for qs in ["", "?status=open", "?priority=1", "?kw=单"]:
        assert client.get(f"/api/v1/tickets/{qs}").json()["count"] <= 5
```

前端再加一层校验，就又多了一份会漂移的重复逻辑，
换来的安全收益是零。

### 9. 📌 「派单」按钮的位置在 fe-v0.9.0 放错了

写这一页时才发现：`fe-v0.9.0` 我把「派单」放进了页面工具栏。
但派单是针对**某一条**工单的操作（后端路由是 `/tickets/<pk>/assign/`），
放在工具栏等于问「派哪一单」。

权限点本身画得对（`ticket:ticket:assign` 确实是一个可点的东西），
**位置画错了**。本 tag 把它移进行操作列。

> 顺带一个教训：`fe-v0.9.0` 的 E2E 因此变红了。
> 这是**好事**——它说明那条测试真的在测东西，而不是恰好通过。
> 一个 tag 的实现改动让上一个 tag 的测试变红，
> 应该先问「哪一边是错的」，而不是直接把测试改绿。

### 8. 📌 `type` 和 `interface` 在这里不等价

```ts
// ❌ interface 没有隐式索引签名，不满足
//    useTableQuery 的 T extends Record<string, string | number>
interface TicketQuery { page: number; kw: string }

// ✅ 类型别名有
type TicketQuery = { page: number; kw: string }
```

报错信息是「'TicketQuery' is not assignable to
'Record<string, string | number>'」——**看起来像某个字段类型不对，
其实和字段毫无关系**。这类报错值得单独记一笔，因为按字面意思去查会绕很久。

## 六、卡住了看这里（渐进提示）

<details>
<summary><b>提示：URL 同步的分页参数</b></summary>

```ts
export function useTableQuery<T extends Record<string, unknown>>(defaults: T) {
  const [searchParams, setSearchParams] = useSearchParams()

  const params = useMemo(() => {
    const merged = { ...defaults } as T
    for (const key of Object.keys(defaults)) {
      const raw = searchParams.get(key)
      if (raw !== null) (merged as Record<string, unknown>)[key] = raw
    }
    return merged
  }, [searchParams, defaults])

  const setParams = useCallback((patch: Partial<T>) => {
    const next = new URLSearchParams(searchParams)
    for (const [k, v] of Object.entries(patch)) {
      if (v === undefined || v === '') next.delete(k)
      else next.set(k, String(v))
    }
    setSearchParams(next, { replace: true })
  }, [searchParams, setSearchParams])

  return [params, setParams] as const
}
```
</details>

## 七、自测清单

| # | 用例 | 期望 |
| --- | --- | --- |
| 1 | `superadmin` | 80 条 |
| 2 | `sysadmin` | 80 条 |
| 3 | `cs_manager` | **50 条** |
| 4 | `cs_staff` | **5 条** |
| 5 | 前端有没有过滤代码 | grep `filter`，业务过滤应该一个都没有 |
| 6 | 翻页 | URL 变化，刷新后保持 |
| 7 | 筛选后分享链接给同事 | 同事打开看到同样的筛选（但数据按他的权限） |
| 8 | 翻页时 | 表格不闪空 |
| 9 | `cs_staff` | 无「导出」按钮 |
| 10 | 导出（有权限时） | 行数 == 列表 count |
| 11 | 后端全量测试 | 全绿 |

用例 1~4 的数字必须与后端 `tests/test_permission_matrix.py` 的 `SCOPE_MATRIX` 完全一致。

📌 **用例 5 可以做成自动化的。** 「grep 一下有没有过滤」是人工检查，
迟早会漏；写成一条结构性测试就永远不会漏：

```ts
// tests/unit/no-client-side-filtering.test.ts
const FORBIDDEN = [/\bresults\s*\.\s*filter\s*\(/, ...]
// 扫 src/ 下全部 .ts/.tsx，断言 offenders 为空
```

⚠️ 一条「什么都没找到」的测试**必须自证有效**——正则写错的话它会永远绿。
所以要配一条反例：

```ts
it('正则本身有效 —— 用一段反例证明它抓得住', () => {
  const bad = 'const visible = data.results.filter((t) => canSee(t))'
  expect(FORBIDDEN.some((p) => p.test(bad))).toBe(true)
})
```

这和 `fe-v0.9.0` 的对照组是同一条原则：
**断言「不存在」时，必须证明你的检测手段真的能发现「存在」。**

📌 **一个我自己踩到的运行环境坑**：Django 开发服务器是用
`runserver --noreload` 起的，加了新的 `export` action 之后没重启，
E2E 拿到 **404**——看起来像「路由没配对」，其实是**服务器在跑旧代码**。

和 `fe-v0.9.0` 那条「403 可能来自 CSRF 而不是权限」是同一类错误：
**状态码不会告诉你它的原因，只会告诉你结果。**
排查越权问题时，先确认请求到底打到了哪一份代码。

## 九、延伸思考

1. 我们让「前端展示条数 == 后端返回条数」成为硬要求（FNFR-5）。
   **有没有反例场景**——前端确实需要再过滤一次？
   （提示：纯 UI 层面的「只看未读」算不算？它和权限过滤的区别是什么？）

2. TanStack Query 的缓存是按 `queryKey` 的。
   **用户 A 登出、用户 B 登录后，`['tickets', {page:1}]` 的缓存还在。**
   `fe-v0.3.0` 我们在登出时 `queryClient.clear()` 了——验证一下它真的生效。

3. 后端列表页做了 `select_related` 避免 N+1（`v0.13.0`）。
   **前端有没有对应的问题？** 想想「列表里每行都发一个请求查详情」这种写法。

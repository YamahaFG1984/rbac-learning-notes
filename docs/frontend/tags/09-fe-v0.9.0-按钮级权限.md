## 五、⚠️ 容易写错的地方

### 🔴 1. 本 tag 存在的真正理由

第一节第 3 问的答案：**还能删除。**

> 隐藏按钮是**体验优化**——让用户不去点一个必然失败的东西。
> 真正的安全边界只有一个：**后端的 `HasPerm` + `ScopedQuerysetMixin`**。
>
> 攻击者不点你的按钮，他直接发请求。
> 在 SPA 里更进一步：**他连你的前端都不用。**

必须写一条测试把这个钉死（对照后端 `v0.10.0` 的
`test_hidden_delete_button_still_rejects_direct_post`）：

```ts
// 按钮确实不渲染
expect(screen.queryByText('删除')).toBeNull()
// 但直接调 API 仍然被后端拦住
const res = await client.delete('/tickets/1/')
expect(res.status).toBe(403)
```

前半句在单测里做，后半句必须在 `fe-v0.16.0` 的 E2E 里做（需要真后端）。

### 2. 两个接口，不是两套逻辑

第一节第 2 问：只有组件式**不够**。

AntD 的这些场景是**数据**，包不进 JSX：

```tsx
<Table columns={...} />        // columns 是数组
<Menu items={...} />           // items 是数组
<Form.Item {...} disabled />   // disabled 是布尔
```

所以两个接口都要。但**内部必须是同一个判断函数**：

```tsx
export function Can({ perm, anyOf, allOf, fallback = null, children }: CanProps) {
  const can = usePermission()        // ← 复用，不重新实现
  ...
}
```

写两遍的话，将来加「否定权限」语法要改两处，而且很可能只改一处。

### 🔴 3. `perm` 的类型必须是 `PermCode` 不是 `string`

第一节第 4 问的答案。这是 SPA **唯一比模板版在权限安全性上更强的地方**。

```tsx
perm?: string      // ❌ 写错不报错，静默不渲染（和模板版一样糟）
perm?: PermCode    // ✅ 编译期报错
```

模板版的这个问题我们靠 `sync_permissions --check-templates` 事后扫描解决（`v1.0.0`），
**TypeScript 可以在编译期就挡住**——别浪费这个优势。

配合 `fe-v0.5.0` 生成的常量：

```tsx
<Can perm={PERM.TICKET_TICKET_DELETE}>   // ✅ 自动补全 + 拼写检查
<Can perm="ticket:ticket:delet">          // ✅ 编译报错
```

### 4. 数一数：模板里有几个判断，后端就该有几个装饰器

后端 `v0.10.0` 有一条结构性测试：

```python
def test_every_template_guard_has_a_view_guard(self):
    """模板里有几个 `in perms`，视图层就该有几个对应的 @require_perm。"""
```

前端应该有对应物：扫描 `<Can perm={PERM.X}>` 用到的权限码，
与后端 `perm_map` 里声明的求差集。

⚠️ 这条在 `fe-v0.15.0` 实现（需要能解析 TSX）。本 tag 先记着。

### 5. `<Can>` 的默认行为是**不渲染**

```tsx
// 没传 perm 时怎么办？
<Can>{children}</Can>
```

两种选择：默认渲染（宽松）或默认不渲染（严格）。

**选严格**——「让默认状态是安全的」在前端的形态。
不传 `perm` 大概率是写漏了，不渲染会立刻被发现；默认渲染则会静默放行。

### 6. `fallback` 不要滥用

```tsx
// 大多数情况：直接不渲染
<Can perm={...}><Button>删除</Button></Can>

// 少数情况：显示禁用态 + 原因，让用户知道「有这个功能但我没权限」
<Can perm={...} fallback={<Tooltip title="需要导出权限"><Button disabled>导出</Button></Tooltip>}>
```

**默认应该是「不渲染」**。显示禁用按钮等于告诉用户「系统有这个功能」——
在多数场景无所谓，但在敏感功能上是不必要的信息暴露。

### 🔴 7. 📌 用例 7 + 8 没法在同一层测，要拆开

实现时才想清楚的事。用例 7「改 perms 按钮就出现」和用例 8「点了仍然 403」
是一句话的两半，但它们**属于两个测试层**：

| 半句 | 在哪测 | 为什么只能在那测 |
| --- | --- | --- |
| 改 `perms` → 按钮出现 | **单测** `Can.test.tsx` | 要直接改 store，E2E 里改不到（除非把 store 挂到 window，那是给测试开后门） |
| 绕开前端发请求 → 403 | **E2E** `button-perm.spec.ts` | 要真后端，单测里 mock 出来的 403 什么也证明不了 |

单测那条我写成了一个「**通过才是对的**」的测试：
把 `perms` 改成 `['*']`，断言按钮**确实出现了**。

```
// ⚠️ 这条测试通过 = 前端权限确实可以被绕过。
//    它不是在测功能，是在把「前端不是安全边界」钉成一条会跑的断言。
```

E2E 那条直接在浏览器里 `fetch('/api/v1/tickets/1/', {method:'DELETE'})`——
连 React 都不经过。

### 🔴 8. 📌 一条「403」测试很容易因为**错误的原因**通过

上面那条 E2E 我第一版写完就意识到一个问题：

> 断言 `status === 403`。但如果 CSRF token 没带对，后端**也**返回 403。
> 这条测试会绿，而它其实什么都没证明。

一个鉴权测试如果因为请求根本没到达视图而通过，它是**假绿**——
比没有测试更糟，因为它给人安全感。

解法是加**对照组**：同一个请求，换一个**有**权限的用户发，
用一个不存在的 id，断言拿到的是 **404 而不是 403**。

```
cs_staff  → DELETE /tickets/1/       → 403   （被权限挡住）
cs_manager→ DELETE /tickets/999999/  → 404   （权限通过了，只是数据不存在）
```

对照组返回 404 证明了：**请求确实穿过了 CSRF 和认证，到了权限判断那一步**。
于是上一条的 403 才真的是「没权限」的意思。

> 可以贴在墙上的规则：
> **断言「被拒绝」时，必须再证明「换个身份就不会被拒绝」。**
> 否则你测的可能是管道堵了，不是门锁上了。

## 六、卡住了看这里（渐进提示）

<details>
<summary><b>提示：Can 组件</b></summary>

```tsx
/**
 * 按钮级权限。
 *
 * ⚠️ 这是**体验优化**，不是安全边界。
 *    隐藏按钮的用户照样能删除——攻击者不点按钮，他直接发请求，
 *    在 SPA 里甚至不用这个前端。
 *
 *    唯一的安全边界是后端的 HasPerm + ScopedQuerysetMixin。
 *    每一个受控按钮都必须有对应的后端校验，成对出现，缺一不可。
 */
export function Can({ perm, anyOf, allOf, fallback = null, children }: CanProps) {
  const can = usePermission()          // 复用唯一的判断函数，不重新实现

  const ok = perm ? can(perm)
    : anyOf ? anyOf.some(can)
    : allOf ? allOf.every(can)
    : false                            // ⚠️ 什么都没传 = 不渲染（默认安全）

  return <>{ok ? children : fallback}</>
}
```

## 九、延伸思考

1. **四层体验现在全齐了**（路由守卫、菜单、按钮，加上后面的表单字段禁用）。
   用 `cs_staff` 登录，界面非常干净——**这份干净有多少安全价值？**
   答案是零。`fe-v0.16.0` 会证明。

2. 后端 `v0.10.0` 有条结构性测试，扫描模板里的权限码与视图装饰器求差集。
   **前端版怎么写？** 需要解析 TSX（提示：`@babel/parser` 或简单正则），
   在 `fe-v0.15.0` 实现。先想想正则的边界在哪。

3. **表单字段级权限**：某些字段只有特定角色能改。
   我们的权限点粒度是「界面上一个可点的东西」（`ADR-004`），
   字段级是明确的非目标（PRD `NG` 清单）。
   如果非做不可，你会加权限点还是在序列化层做白名单？

4. `<Can>` 现在只判断功能权限。**数据权限呢？**
   比如「这条工单我能不能编辑」——它取决于行数据，不是全局权限码。
   前端应该判断吗？（提示：回看 F-ADR-006 和 F-ADR-015。
   正确答案是：让后端在每行数据里返回它，或者干脆不判断，点了再说。）

## 五、⚠️ 容易写错的地方

### 1. 权限数据「既是服务端状态，又要全局可读」

第一节第 1、2 问的答案。

它来自服务端（要 Query 管缓存和失效），但**几乎所有组件都要读**
（路由守卫、菜单、每个按钮）。全用 Query 的问题不是性能，是：

- 每个组件都和「权限从哪来」耦合
- 加载态、错误态要在每个组件重复处理
- 测试时每个组件都要 mock 网络

**做法**：Query 拉取和失效，拉到后写进 Zustand，组件只读 store。

```
useProfileQuery()  ──拉取/失效──▶  setProfile()
                                       │
                    ┌──────────────────┼──────────────────┐
                    ▼                  ▼                  ▼
                路由守卫            菜单渲染             <Can>
```

### 🔴 2. 只有一个地方能写 store

这是 F-ADR-005 的硬约束：

```ts
// ✅ 唯一入口
useProfileQuery({ onSuccess: (data) => setProfile(data) })

// ❌ 任何其他地方写 store 都是错的
setPerms([...perms, 'ticket:ticket:delete'])     // 从哪来的？
```

两处写入 = 两个真相源，很快就会不一致。

在 `frontend/CLAUDE.md` 里写明这条，并考虑用 ESLint 规则守
（限制 `setProfile` 的调用位置）。

### 🔴 3. profile 加载完成前不渲染业务界面

第一节第 3 问。

```tsx
// ❌ 会闪一下「无权限」的界面
{menus.map(...)}          // menus 初始是 []，先渲染空菜单，然后突然冒出来

// ❌ 更糟：先渲染出用户不该看到的按钮，200ms 后消失
<Can perm="...">          // perms 初始是 []，判断为 false —— 这次侥幸对了
```

第二种「侥幸对了」才是最危险的：**初始空数组恰好等价于「无权限」**，
所以看起来没问题。但如果有任何地方写成 `perms.length === 0 ? 显示全部 : 按权限`
（有人会这么写，理由是「还没加载完就先都显示吧」），就会真的闪现越权内容。

**正确做法**：`status === 'unknown'` 时整个业务区不挂载。

这是「让默认状态是安全的」在前端的形态：**未知 ≠ 允许**。

### 4. `['*']` 通配只在一个地方处理

第一节第 4 问。

```ts
// ✅ 处理一次
export function usePermission() {
  const perms = useAuthStore((s) => s.perms)
  return useCallback(
    (code: PermCode) => perms.includes('*') || perms.includes(code),
    [perms],
  )
}
```

`<Can>` 内部调它，路由守卫调它，菜单调它——**通配逻辑只写一遍**。

写三遍的话，将来改成 `["*", "-ticket:ticket:delete"]` 这种否定语法时要改三处。

### 🔴 5. 组件禁止自行推断权限

第一节第 5 问的答案：**不能**。

```tsx
// ❌ 复制了一份数据权限规则
if (user.department.id === row.department.id) showEdit()
```

后端的数据权限规则是**五个枚举值 + 部门子树**（`ADR-007`）。
上面这行只覆盖了 `DEPT_ONLY` 一种——**主管看子部门数据时就错了**：
主管有权编辑客服一组的工单，但 `user.department.id`（客服部）
≠ `row.department.id`（客服一组），按钮不显示。

```tsx
// ❌ 把角色编码硬编码进前端
if (user.roles.includes('cs_manager')) showStats()
```

角色改名、新增角色，前端全要跟着改。

**正确做法**：需要「主管才显示统计卡片」时，**为它定义一个权限码**
（`ticket:stats:view`），前端只问权限码。

这会让权限点数量增加——**接受**，正是后端 `ADR-004`
「一个可点的东西 = 一个权限点」的延伸。

### 🔴 5b. 两个实现时才撞上的坑

**(1) TanStack Query v5 移除了 `useQuery` 的 `onSuccess`**

本文档提示 1 里写的 `useProfileQuery({ onSuccess })` 是 **v4 的写法**。
v5 只有 `useMutation` 还保留 `onSuccess`——`useQuery` 上的那个**静默失效**，
不报错、不警告，store 永远是空的。

改用 `useEffect` 写入，「唯一写入口」的约束不变：

```ts
useEffect(() => {
  if (query.data) setProfile(query.data)
  else if (query.isError) reset()
}, [query.data, query.isError, setProfile, reset])
```

**(2) `AuthBootstrap` 必须在 `RequireAuth` 的外面，否则死锁**

第一版我把它放进了受保护区内部：

```tsx
<RequireAuth>        {/* status === 'unknown' → 只渲染 spinner */}
  <AuthBootstrap>    {/* ← 永远不挂载 */}
```

结果：`RequireAuth` 等 `status` 变化，而改变 `status` 的请求在
`AuthBootstrap` 里发——它永远不挂载。**转圈转到天荒地老。**

> **谁负责确定某个状态，就必须在依赖这个状态的东西之上。**

正确层次：

```
AuthBootstrap          ← 触发 profile 请求，确定认证状态
  └── Routes
        ├── /login          （公开）
        └── RequireAuth     ← 依赖认证状态
              └── AdminLayout
```

**(3) 401 不是错误**

未登录用户拉 profile 拿到 401 是**正常流程**，
此时应该正常渲染 children 让路由把他送去登录页，而不是显示错误页。

只有网络错误 / 5xx 才该显示「无法加载权限信息」。

### 6. `staleTime: Infinity` 是刻意的

profile 不该被 Query 的自动重取机制随意刷新（窗口聚焦、网络重连都会触发）。
它只应该由两件事触发重拉：**版本号变化**（`fe-v0.13.0`）和**收到 403**。

```ts
useQuery({
  queryKey: ['profile'],
  queryFn: fetchProfile,
  staleTime: Infinity,
  refetchOnWindowFocus: false,
  retry: false,          // 401 不该重试
})
```

`retry: false` 也重要：401 重试三次会让用户等更久才跳登录页。

```ts
export const useAuthStore = create<AuthState>((set) => ({
  user: null,
  perms: [],
  menus: [],

  // ⚠️ F-ADR-005：这是权限数据的**唯一**写入口。

  setProfile: (p) =>

// 唯一的权限判断。通配 '*' 只在这里处理一次。
export function usePermission() {
  const perms = useAuthStore((s) => s.perms)

    (code: PermCode) => perms.includes('*') || perms.includes(code),
    [perms],
  )
}
```

```tsx
export function AuthBootstrap({ children }: { children: ReactNode }) {
  const status = useAuthStore((s) => s.status)
  const { isError, refetch } = useProfileQuery()

  // ⚠️ 未知 ≠ 允许。加载完成前不挂载任何业务界面（FE-2.3）

  if (isError) return <ErrorResult onRetry={() => refetch()} />
  return <>{children}</>
```

## 九、延伸思考

1. `perms` 是 `string[]`，判断用 `includes()` 是 O(n)。
   200 个权限码、一个页面 50 次判断 = 1 万次比较。
   **要不要换成 `Set`？** 什么规模下值得？
   （对比后端 `v0.6.0` 用 `frozenset` 的理由。）

2. 我们用 `['*']` 表示超管。**另一种做法是返回数据库里的全部权限码。**
   两者对前端的影响分别是什么？（提示：想想 `fe-v0.13.0` 的版本号比对，
   以及「超管在权限点新增后是否需要重拉 profile」。）

3. `status` 现在是三态。**如果加上「token 过期正在静默刷新」这个状态**，
   会变成几态？状态机画出来会不会太复杂？
   （这也是我们选 Session 而非 JWT 的一个隐性收益——没有刷新态。）

4. 如果某个页面需要「实时」的权限（比如权限管理页自己），
   `staleTime: Infinity` 会不会让它看到过期数据？想想怎么处理这个特例。

## 五、⚠️ 容易写错的地方

### 1. 不要在前端再过滤一次权限

第一节第 1 问的答案：**不需要**。

后端 `get_user_menu_tree()` 已经做完了全部过滤（`v0.11.0`）：
自底向上标记有权限的菜单、向上保留祖先目录、空目录自动消失。

```tsx
// ❌ 重复实现了后端的过滤逻辑
{menus.filter((m) => can(m.permCode)).map(...)}
```

这是 F-ADR-015「前端不做数据二次过滤」在菜单上的形态。
前端再过滤一遍的后果：**两套逻辑必然漂移**——后端改了「空目录不显示」的判定，
前端不知道。

### 2. 结构转换放在纯函数里，不放在组件里

第一节第 2 问。

```tsx
// ❌ 组件里内联转换：没法单测，改一次要跑整个应用
<Menu items={menus.map((m) => ({ key: m.routePath, label: m.name, ... }))} />

// ✅ 抽成纯函数
<Menu items={toAntdMenuItems(menus)} />
```

`toAntdMenuItems` 是纯函数 → `fe-v0.15.0` 可以直接单测，
输入一棵树，断言输出结构，零 mock。

### 3. 图标映射要有兜底

后端存的是字符串，可能写错，也可能前端没引入那个图标。

```tsx
// ❌ undefined 组件会让整个菜单崩溃
const Icon = ICONS[name]
return <Icon />

// ✅
const Icon = ICONS[name] ?? AppstoreOutlined
```

同后端 `v0.11.0` 对 `NoReverseMatch` 的处理：
**一个配错的图标名不能让整个侧边栏崩掉**。

### 4. 详情页的菜单高亮

第一节第 4 问：**应该高亮**。用户在 `/tickets/42` 时，
侧边栏「工单列表」应该是选中态，否则会觉得自己「不在任何菜单里」。

AntD 的 `selectedKeys` 需要精确匹配，所以要自己算：

```ts
// 找出所有「是当前路径前缀」的菜单项，取最长的那个
const matched = allPaths
  .filter((p) => pathname === p || pathname.startsWith(p + '/'))
  .sort((a, b) => b.length - a.length)[0]
```

⚠️ 注意 `startsWith(p + '/')` 的斜杠——不加的话 `/tickets-archive`
会被误判为 `/tickets` 的子路径。

> **这和后端部门树 `path` 尾斜杠是同一类陷阱**（`v0.3.0` 陷阱 1、
> `v0.4.0` 发现的排序 bug）：**字符串前缀匹配必须带分隔符。**
> 同一个坑，第三次出现了。

### 5. `openKeys` 要受控但允许用户手动折叠

自动展开当前项的父目录，但用户手动折叠后不该被强制展开回去。

```tsx
const [openKeys, setOpenKeys] = useState<string[]>([])
useEffect(() => { setOpenKeys(computeOpenKeys(pathname)) }, [pathname])
<Menu openKeys={openKeys} onOpenChange={setOpenKeys} />
```

只在**路径变化**时重算，用户操作时不干预。

## 六、卡住了看这里（渐进提示）

<details>
<summary><b>提示：适配器</b></summary>

```tsx
export function toAntdMenuItems(menus: MenuNode[]): MenuProps['items'] {
  return menus.map((node) => {
    const Icon = ICONS[node.icon] ?? AppstoreOutlined     // 兜底，见陷阱 3
    const base = { key: node.routePath ?? `cat-${node.id}`, icon: <Icon />, label: node.name }
    // 后端已保证空目录不会返回（v0.11.0 自底向上算法），这里不再判断
    return node.children.length
      ? { ...base, children: toAntdMenuItems(node.children) }
      : base
  })
}

export function findActiveKeys(menus: MenuNode[], pathname: string) {
  const flat = flatten(menus).filter((m) => m.routePath)
  // ⚠️ 加 '/' —— 否则 /tickets-archive 会被误判为 /tickets 的子路径
  const matched = flat
    .filter((m) => pathname === m.routePath || pathname.startsWith(m.routePath + '/'))
    .sort((a, b) => b.routePath!.length - a.routePath!.length)[0]
  return {
    selectedKeys: matched ? [matched.routePath!] : [],
    openKeys: matched ? ancestorKeys(menus, matched.id) : [],
  }
}
```

## 九、延伸思考

1. **陷阱 4 是同一个坑的第三次出现**（部门树 path 尾斜杠、`ORDER BY path` 排序、菜单高亮）。
   三次的共同点是什么？**你能总结出一条可以贴在墙上的规则吗？**

2. 后端 `v0.11.0` 延伸思考问过「菜单树能不能缓存」，当时留白了。
   前端这里同样可以问：`toAntdMenuItems` 每次渲染都跑一遍，要不要 `useMemo`？
   **先想清楚它的成本**（菜单几十个节点）再决定——不要凭直觉优化。

3. 至此**四层体验已经完成三层**（路由守卫、菜单、还差按钮）。
   用 `cs_staff` 登录，现在的界面已经很干净了。
   **但它安全吗？** 用控制台改 `perms` 试试，再想想 `fe-v0.16.0` 要证明什么。

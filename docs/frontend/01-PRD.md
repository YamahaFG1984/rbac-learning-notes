## 1. 背景

### 1.1 我们已经有什么

主干分支到 `v1.2.0` 为止已经完成：

- 一套 RBAC 权限内核（`apps/rbac/services.py`），**不认识 HTTP**
- Django 模板前端（`v1.0.0`），服务端渲染
- DRF API + Bearer JWT（`v1.2.0`），复用同一内核

`v1.2.0` 的验收结果是：接入 DRF 时 `services.py` **一行未改**，适配层 117 行。

### 1.2 为什么还要做 React 版

`v1.2.0` 只证明了「同一个内核能服务两种表现层」，但它的 API 消费者是 `curl` 和测试代码。
**真正的 SPA 会暴露一批模板渲染下根本不存在的问题**：

| 问题 | 模板版 | SPA |
| --- | --- | --- |
| 权限数据存在哪 | 不存，每次请求重算 | 前端内存，会过期 |
| 管理员改了权限 | 刷新即生效 | 用户不重拉就一直是旧的 |
| 菜单的路由信息 | Django URL name 就够 | 需要前端路由 path + 组件名 |
| 未认证 vs 无权限 | 302 / 403 页面，用户看得懂 | 必须精确区分，前端做不同动作 |
| 凭证放哪 | Session cookie，不用想 | localStorage？内存？cookie？ |
| 鉴权层数 | 3 层（视图 / 模板 / 菜单） | **4 层**（多一层路由守卫） |

这批问题在上一轮问答里已经列过，本阶段把它们**逐个实现出来**。

### 1.3 教学目标

| 编号 | 目标 |
| --- | --- |
| FG-1 | 说清同域部署下「为什么还要 JWT」这个问题，并做出有依据的选择 |
| FG-2 | 实现 httpOnly Cookie 认证，并处理它带回来的 CSRF 问题 |
| FG-3 | 区分「服务端状态」与「客户端状态」，知道权限数据属于哪一类 |
| FG-4 | 实现动态路由注册，并说明它与静态路由 + 守卫的取舍 |
| FG-5 | 设计权限变更的前端感知机制，量化其延迟与成本 |
| FG-6 | 说出前端路由守卫为什么**不是**安全边界，且比隐藏按钮更容易造成错觉 |
| FG-7 | 设计 401 / 403 / 404 的前端分流，避免「403 误跳登录页」的死循环 |
| FG-8 | 用 E2E 测试把越权矩阵在真实浏览器里再验证一遍 |

### 1.4 非目标

| 编号 | 不做 | 原因 |
| --- | --- | --- |
| FNG-1 | 替换 Django 模板版 | 并存才有对比价值（[F-ADR-001](02-设计文档.md)） |
| FNG-2 | SSR / RSC | 权限判断会横跨服务端组件和客户端组件两处，复杂度显著上升且带偏主题 |
| FNG-3 | 微前端 / 模块联邦 | 与 RBAC 正交 |
| FNG-4 | 移动端适配 | 企业后台以桌面为主，响应式做到「不崩」即可 |
| FNG-5 | 国际化（i18n） | 与 RBAC 正交，且会让每个页面的 diff 变大 |
| FNG-6 | 修改后端的权限内核 | **硬约束**。若需要改，说明设计有问题 |

## 2. 交付形态

```
浏览器
  │
  ▼
Vite Dev Server (5173)              生产：Nginx
  ├── /            → React SPA        ├── /        → 静态资源
  └── /api、/admin → 代理到 :8000     └── /api     → Django
                                      └── /django  → Django 模板版（并存）
```

**同域是硬要求**（[F-ADR-002](02-设计文档.md)）：httpOnly Cookie 方案不允许跨域。
开发期用 Vite 的 `server.proxy`，生产期用反向代理。

两套前端并存后的入口：

| 路径 | 内容 |
| --- | --- |
| `/` | React SPA |
| `/api/v1/` | DRF API（两套前端共用） |
| `/django/` | Django 模板版（原 `/accounts/`、`/rbac/`、`/tickets/` 前缀迁移到此下） |
| `/admin/` | Django admin |

## 3. 功能需求

编号规则 `FE-<模块>.<序号>`。

### FE-1 认证

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FE-1.1 | 登录页：用户名 + 密码，登录成功后凭证写入 **httpOnly Cookie** | P0 |
| FE-1.2 | 前端**不接触** access token，`document.cookie` 里读不到会话凭证 | P0 |
| FE-1.3 | 所有写请求携带 `X-CSRFToken` 头 | P0 |
| FE-1.4 | 登出：调用后端接口清除 Cookie，并清空前端所有缓存状态 | P0 |
| FE-1.5 | 未登录访问受保护路由时跳转登录页，登录后回到原地址 | P0 |
| FE-1.6 | 会话过期（401）时静默重定向登录页，且**不弹一堆错误提示** | P1 |
| FE-1.7 | 登录失败提示与后端一致（不区分用户不存在/密码错误） | P0 |

### FE-2 权限数据获取

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FE-2.1 | 应用启动时调用 `/api/v1/auth/profile/` 获取用户信息、权限码、菜单树 | P0 |
| FE-2.2 | 权限数据是应用的**唯一权限来源**，禁止任何组件自行推断权限 | P0 |
| FE-2.3 | profile 未加载完成前，不渲染任何业务界面（避免闪现无权限内容） | P0 |
| FE-2.4 | profile 请求失败时给出可重试的错误页，而不是白屏 | P1 |
| FE-2.5 | 超管的 `perms` 为 `["*"]`，前端需正确处理这个通配 | P0 |

### FE-3 路由与菜单

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FE-3.1 | 根据 profile 返回的菜单树**动态注册**路由 | P0 |
| FE-3.2 | 路由守卫：访问无权限路由时跳 403 页面，不是白屏 | P0 |
| FE-3.3 | 侧边栏菜单由 profile 的 `menus` 渲染，无权限的不出现 | P0 |
| FE-3.4 | 空目录（无任何有权限子菜单）不渲染 | P0 |
| FE-3.5 | 当前路由对应的菜单项高亮，父目录自动展开 | P1 |
| FE-3.6 | 直接输入 URL 访问无权限页面，行为与点击菜单一致（403） | P0 |
| FE-3.7 | 刷新页面后路由仍然有效（动态路由需在 profile 加载后重新注册） | P0 |

### FE-4 按钮级权限

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FE-4.1 | 提供 `<Can perm="...">` 组件与 `usePermission()` hook | P0 |
| FE-4.2 | 无权限的操作按钮不渲染 | P0 |
| FE-4.3 | **每个受控按钮必须有对应的后端权限校验**，前端隐藏不构成安全边界 | P0 |
| FE-4.4 | 提供构建期检查：前端用到的权限码必须在后端权限点中存在 | P1 |

### FE-5 权限变更感知（🔴 本阶段的核心新问题）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FE-5.1 | 后端在响应头返回 `X-RBAC-Version`，前端比对本地版本 | P0 |
| FE-5.2 | 版本号变化时自动重新拉取 profile 并刷新菜单/按钮 | P0 |
| FE-5.3 | 权限变更后的界面生效延迟 ≤ 一次 API 请求 | P0 |
| FE-5.4 | 收到 403 时强制重拉 profile（兜底：可能是权限刚被撤销） | P1 |
| FE-5.5 | 权限刷新时给用户一个非阻塞提示，不静默改变界面 | P2 |

### FE-6 业务页面

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FE-6.1 | 工单：列表（分页/筛选）、详情、新建、编辑、删除、派单、导出 | P0 |
| FE-6.2 | 部门管理：树形展示 + 增删改 | P0 |
| FE-6.3 | 用户管理：列表（筛选/分页）+ 增删改 + 分配角色 | P0 |
| FE-6.4 | 角色管理：增删改 + 权限树勾选（含继承只读态）+ 数据范围配置 | P0 |
| FE-6.5 | 权限点：只读树形展示 | P1 |
| FE-6.6 | 审计日志：列表 + 筛选 | P1 |

### FE-7 错误处理

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FE-7.1 | 全局响应拦截：401 → 跳登录；403 → 提示无权限；404 → 提示不存在 | P0 |
| FE-7.2 | **403 绝不能跳登录页**（会造成登录→403→登录的死循环） | P0 |
| FE-7.3 | 数据权限范围外的记录返回 404，前端展示「不存在或无权访问」 | P0 |
| FE-7.4 | 5xx 展示错误边界页面，可重试 | P1 |
| FE-7.5 | 网络错误与业务错误区分展示 | P2 |

## 4. 后端需要配合修改的部分

> ⚠️ **原则：只允许改「适配层」，不允许改权限内核**（FNG-6）。

| 编号 | 后端改动 | 涉及文件 | 是否碰内核 |
| --- | --- | --- | --- |
| BE-1 | DRF 支持 SessionAuthentication（与 JWT 并存） | `settings/base.py` | ❌ |
| BE-2 | `CSRF_COOKIE_HTTPONLY` 改回 `False` | `settings/prod.py` | ❌ |
| BE-3 | 新增 `/auth/login/`、`/auth/logout/`、`/auth/csrf/` 接口 | `apps/rbac/api/` | ❌ |
| BE-4 | 响应头注入 `X-RBAC-Version` | 新中间件 | ❌ |
| BE-5 | `Permission` 增加前端路由字段（`route_path` / `component`） | `apps/rbac/models.py` | ❌（展示层字段） |

## 5. 关键用户故事

### FUS-1：权限被撤销的那一刻

> 作为**客服主管**，我正在工单列表页。管理员在后台撤销了我的删除权限。
> 我在页面上点了「刷新」按钮（不是浏览器刷新）。
>
> **验收**：下一次 API 请求的响应头带回新的 `X-RBAC-Version`，前端自动重拉 profile，
> 「删除」按钮消失，并出现一条非阻塞提示「你的权限已更新」。全程不需要刷新页面或重新登录。

### FUS-2：直接输入 URL

> 作为**客服专员**（无用户管理权限），我在地址栏直接输入 `/system/users`。
>
> **验收**：跳转到 403 页面，**不是**白屏、不是跳登录页、不是渲染出用户列表再报错。

### FUS-3：跨部门工单

> 作为**客服专员**，我拿到一个技术部工单的 ID，直接访问 `/tickets/42`。
>
> **验收**：后端返回 404，前端展示「工单不存在或你无权访问」。
> 页面不崩，可以返回列表。

### FUS-4：会话过期

> 作为**任何用户**，我离开电脑两小时后回来点了一个按钮。
>
> **验收**：收到 401 → 静默跳登录页并记住原地址 → 登录后回到原页面。
> **不能**弹出一串「请求失败」的红色提示。

### FUS-5：凭证拿不到

> 作为**安全测试者**，我在浏览器控制台执行 `document.cookie`。
>
> **验收**：看不到会话凭证（httpOnly），只能看到 `csrftoken`（这是设计如此）。

## 6. 非功能需求

| 编号 | 类别 | 要求 |
| --- | --- | --- |
| FNFR-1 | 安全 | 会话凭证 `httpOnly` + `SameSite=Lax`，JS 不可读 |
| FNFR-2 | 安全 | 所有写请求带 CSRF token |
| FNFR-3 | 安全 | 前端权限判断**仅用于体验**；每一处都有对应的后端校验 |
| FNFR-4 | 安全 | 前端 bundle 中不出现任何密钥、不内嵌权限判断规则 |
| FNFR-5 | 一致性 | 前端展示的数据条数必须与后端 API 返回一致，不做二次过滤 |
| FNFR-6 | 性能 | 首屏（登录后到菜单可见）≤ 2 次 API 请求 |
| FNFR-7 | 性能 | 列表页切换分页/筛选不重复请求 profile |
| FNFR-8 | 可维护性 | 前端不得硬编码权限码字符串，统一从生成的常量文件引用 |
| FNFR-9 | 可测试性 | 单元测试用 MSW 拦截网络，不依赖真实后端 |
| FNFR-10 | 可测试性 | E2E 覆盖越权矩阵的全部角色 × 关键页面组合 |
| FNFR-11 | 教学性 | 每个 tag 都能 `npm run dev` 起来并完成该阶段声明的功能 |

## 9. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 为了前端方便而修改权限内核 | 高——推翻 ADR-013 的全部成果 | FAC-4 用测试守住 |
| 前端路由守卫被误当成安全边界 | 高 | 每个守卫旁必须有对应后端校验的测试；E2E 直接绕过前端调 API |
| 权限码在前端硬编码，与后端漂移 | 中 | FNFR-8：从后端生成常量文件；构建期校验 |
| 动态路由与刷新页面的时序问题 | 中 | FE-3.7 专门列为需求；`fe-v0.7.0` 的核心验收点 |
| httpOnly Cookie 导致的 CSRF 回归 | 中 | `fe-v0.2.0` 必须带 CSRF 测试；后端 347 个测试不能红 |
| 两套前端并存导致后端路由冲突 | 低 | BE-7：模板版整体迁到 `/django/` 前缀 |
